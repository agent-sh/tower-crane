- A rung can name a provider credential kept in the OS secret store: `ladder set RUNG --credential NAME`, owner-required like `env_file`. The value never goes in an env file, argv, `project.json`, events or logs, and no harness gets it in its environment. claude on Bedrock reaches Bedrock through a loopback broker the supervisor runs for the spawn, which adds the bearer token under a random path nonce; claude starts with the broker's URL and `CLAUDE_CODE_SKIP_BEDROCK_AUTH=1`, and its commands get neither. claude on the Anthropic API gets the token through `apiKeyHelper`, and codex through its provider's `auth` command, in `config.toml` and each profile file that defines the provider.
- New commands `credentials set NAME` (the value from stdin, never argv), `credentials import --env-file PATH --var VAR --name NAME`, `credentials check [NAME]...` and `credentials rm NAME`. On Linux a credential lives in the Secret Service (`secret-tool`, `service=tower-crane name=NAME`), else in a `systemd-creds --user` file beside the user file. The macOS Keychain and Windows Credential Manager stores are written from their documented behaviour, untested, and off unless the user file names them. `"store": "env"` in the user file reads the value from an env file the owner keeps, and `ladder show` names that fallback, and every rung with an `env_file`, on every show.
- Spawn reads a route's credential before it starts anything and refuses, naming the stores it tried and the fix, when the store cannot give it; a fallback route that fails the check is skipped. A credential helper that fails while the harness runs is a harness login failure, not a task attempt.
- With `sandbox.session_bus`, a credential is read from systemd-creds alone, and spawn refuses one kept in the Secret Service, which the bus puts in reach of the agent's commands.
- codex agent homes no longer link the user's `~/.codex/.env`. A codex route on Bedrock names a credential instead; until it does, codex there has no bearer token from that file.
