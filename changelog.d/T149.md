- `submit --pr` checks the PR's CI and revuto at the submitted head before it records the head. Pending checks refuse with the job names and `wait for CI`; a failing job refuses with its name and the first failing lines of its log (the first three failing jobs print their logs; each other one names the `gh run view` command that reads its log); revuto's open inline findings print with file, line and body. Capped reviews do not block. Before, a worker could submit a head whose Windows jobs were already red on its PR, and the gate and rework round ran after.
- A PR that GitHub reports CONFLICTING or DIRTY refuses the submit with the conflict diagnostic `check ci` gives: GitHub does not start `pull_request` workflows for it, so the submit names the conflict instead of waiting for checks that will not start. A mergeability GitHub has not computed yet counts as pending.
- A revuto inline comment stays open until the latest reply from anyone else starts with `[resolved]` on its own line. `submit --json` carries the same report as `ci_report`.
- `submit --force-ci-pending` submits past pending checks only when the brief has the line `force-ci-pending: allowed` outside its fenced code blocks, and the brief is read again under the state lock before the head is recorded. Failing checks always refuse.
- A shimmed agent whose gh policy refuses `gh api` cannot read the checks at submit. Its submit prints that the head was not checked and goes ahead; the orchestrator's `check ci` still judges the head before merge.
- The worker role says to push, wait for CI, fix and then submit.
