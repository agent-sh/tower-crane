- The worktree lock moved from the repository's git directory to `worktree/lock` in the state directory. A sandboxed worker writes the git directory, so it could hold the old lock to stall gates, dispatch and prune for a minute, or delete a held one. No sandboxed agent writes the state directory. Gates no longer create the worktrees root.
- The lock holds its holder's marker, as the state lock does. A lock whose holder was killed is cleared by the next process that wants it. A live holder on the same host and pid namespace keeps it whatever its age; a holder elsewhere counts as gone 60 s after its marker last changed, and gates under automation refresh theirs every 10 s. The lock is per state directory, so two projects on one repository do not exclude each other.
- Spawn refuses a `sandbox.write` path inside the state directory, or one that holds the state directory or the worktrees root.
- Upgrading: a holder of the new lock also takes the old path while it is free, so an older Tower Crane process still running waits for it. A lock already at the old path is not waited for; each process that finds it prints a notice naming it. Stop older processes after upgrading, then remove it.
- Removing a task worktree (cancel, retirement, `worktree prune`) and each prune now run under the worktree lock, so a relink no longer writes into an admin directory git is emptying. Preparing a worktree that a retirement is removing is refused at once instead of waiting for that lock.
- An agent file with `sandbox: true` and `writeOutside: worktrees` is refused.
