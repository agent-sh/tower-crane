- A failed `tests`, `clean` or `ci` gate at a submitted head no longer waits for an operator. Infrastructure failures run the gate once more at the same head: a timeout, a runner killed by a signal, a CI run that timed out, was cancelled or never started, a cleanup scan with checks that did not run, and a test that also fails on the base branch. Any other failure, or a retry that fails too, sends the task to rework with the gate's summary: the failing test names and the output tail. A test that also fails on the base branch is named in the rework, so the worker can link the existing failure instead of fixing unrelated code. The base is the newer of the local and `origin` branch. A confirmed quality failure on a task with a tier range keeps its escalation climb; a failure that also fails on the base does not climb.
- A `tests`, `clean` or `ci` check run by hand while the watcher runs is settled the same way, so its failure is not left submitted.
- A change with no test, or with no changes against the base, reworks with the gate's reason. A missing or uninstalled pinned command, including `gates.tests_proof_cmd` for `tests.expensive`, is project configuration: its gate waits for a pin, and the inbox shows a `gate_config` item addressed to the orchestrator that names the setting. Later software gates still collect missing evidence and settle independent failures. `gates retry` reruns the configuration gate once the command is pinned.
- A test or cleanup command killed by a signal is recorded as `runner_crash`, not as a confirmed quality failure, so a crash no longer climbs a rung. A shell reports the signal as exit 128 plus its number, and that exit counts the same. A proof run killed after the change is reverted is a crash too: it is not passing proof, and it retries once like any other crash.
- The ranged main-failure integration test waits for worker refill and verifies the rework event, both main-failure receipts and the unchanged tier after the task is claimed again.
- Integration fixtures read complete audit lines, verify one base fetch independently of process startup time, and recover an incomplete native directory copy through JavaScript traversal before running the tests gate.
- Gate-failure tests verify the rework event and worker note after refill, so a new worker claiming the task cannot invalidate the settlement check.
- A separately run host-only test keeps its command and opt-in environment when probing the base for a matching failure. Node spec-reporter durations are removed from failure names so timing differences cannot hide a base failure.
- A missing or unavailable separate host-test command records `gates.tests_proof_cmd` as its configuration remedy. Reporter and inbox fixtures check stable names and failures confined to the submitted head.
- Windows command-not-found classification is preserved before combining host-test diagnostics with the ordinary suite's output.
- The executor queue fixture checks initial task starts separately from later successful check reactions, retaining its three-suite-run and two-executor bounds.
- Host-only command expansion and evidence acceptance stay aligned with the pinned proof template. Event fixtures retain the final-newline boundary for concurrent audit writes.
- GitHub observation errors retry once at the submitted head: transport and API failures, unreadable output and unknown mergeability. A recovered read uses the new verdict instead of reworking from a stale transport failure; a repeated error reworks with its diagnostic.
- The worktree fixture retains main's preparation-time bound and its start timestamp alongside the single-fetch guards.
