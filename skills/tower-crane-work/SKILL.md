# Tower Crane: work one task

You build one task. The brief is your context; the acceptance is your definition of done. Someone else reviews it, so make it easy to check.

Arguments: `$ARGUMENTS`. Use `TOWER_CRANE_TASK` and `TOWER_CRANE_AGENT` when set; otherwise use the task id and agent name passed by the orchestrator. Pass `--agent <name>` on every tower-crane call. If `TOWER_CRANE_STATE` is absent, also pass `--state <dir>` with the supplied state directory.

1. `tower-crane task show <id> --agent <name>`, `tower-crane brief get <id> --agent <name>` and `tower-crane project show --agent <name>`. If not claimed by you, `tower-crane claim <id> --agent <name> --lease MIN`, sized for expected work and waits using `limits.lease_minutes` as the default; if refused, stop and report why. If work needs longer, renew before expiry with `tower-crane renew <id> --agent <name> --lease MIN` when reporting progress.
   Your first message restates the project goal and this task's target in one or two sentences. Read the rule files the prompt's `## House rules` marks "read it" (the user's and the repository's AGENTS.md and CLAUDE.md files) before changing anything.
2. Work in the task's worktree (`tower-crane worktree <id> --agent <name>` prints it). Native workers use absolute paths under that worktree for every edit and command. Read only what the brief points to, plus what you discover you need.
3. Build the smallest change that meets every acceptance item. Follow the repository's `AGENTS.md` and the standards the brief names.
   When the brief has prior blocking review findings, follow **Rework** below before patching.
   Report progress through `tower-crane task note` or `tower-crane msg --to orchestrator --task <id> "<update>"`. Renew your lease with `tower-crane renew <id>` when the work needs longer.
4. For code changes, add or change a test that fails without the change and passes with it. Run only the test files the change touches, at the repository's capped concurrency; never the whole suite. The tests gate runs the full suite once at your submitted head, and CI runs it on every platform. Your sandbox has no root mapping: root-owned host files appear there as uid/gid 65534, so a test that asserts root ownership or needs other host state fails there. Gate commands run on the host, outside the sandbox. The tests named under `## Host-only tests` in your brief cannot run locally: skip them, and the tests gate runs them on the host. When that list is set, name the test files you run one by one: a runner refuses a directory or a glob, since it could reach a host-only file. For a research task on any tier, use the network to search for evidence and fetch at least `research.min_sources` distinct pages (default 10). Commit `research/<id>.json` with `sources: [{id, url}]` and `claims: [{claim, quote, source}]`. Every claim cites a source and quotes text found on its page; every source must be cited. The sources gate fetches them again at check time. For other work, verify the acceptance as the brief specifies.
   Waits: do not wait for or poll CI, and do not run `gh pr checks --watch` or `gh run watch`. Every poll turn re-reads your whole context, and submit does not need finished checks: it refuses only a check that already failed, and the ci gate waits for running checks on the host (step 8). Wait for tests in the foreground with a bounded wait, `tower-crane wait --task <id> --agent <name> --timeout SEC` (exits 2 at the deadline). Do not start a background job to wait on: a headless run is not guaranteed to resume for its notification, and the Stop hook holds you once if a background job is still running.
   A CI job that already failed: do not wait for the whole run to finish. `tower-crane ci log JOB_ID --failed-tests` writes the job's log under your task scratch and names each failing test with its first error line. Before asking the orchestrator about a non-green check or a code-scanning alert, run `tower-crane ci checks <id>`: it reads every non-green check's title, summary and annotations, marks configured capped reviews, ignored apps and superseded runs as nonblocking, and lists current open alerts with rule, file:line and message. It resolves your PR from the recorded branch before your first submit, including CodeQL alerts on its verified current merge commit. Alert fetch errors are explicit; retry them before treating the alert list as clear. These commands read your own PR through the state broker without `gh api`. `ci alerts` also lists alerts at the recorded PR's head ref.
5. Before submitting, run the pinned `gates.clean_cmd` from the task worktree with the worktree path, `--base=<merge-base with the configured base>` and `--json`, as the host clean gate does. Report its exit status, findings by severity, each HIGH finding with file and line, and any `errors`, `detectorErrors` or `failedChecks`. A failed command, invalid JSON, missing `items` list or incomplete scan blocks submission. Judge a `scope: "diff"` report whole; for other reports judge only findings in changed files and added or rewritten lines, and treat a report capped below `total` as incomplete. Fix confirmed HIGH findings and rerun cleanup. External tool files and directories are read-only sandbox paths; wrapper dependencies must be declared by the orchestrator or owner in `gates.clean_paths`. Record the cleanup command and result under the pre-submit checklist; update docs and examples your change made untrue, and update the changelog the repository's way as its house rules specify.
6. Before publishing, use the `base` shown by `tower-crane project show` in step 1, or the `base` under `stack` in `tower-crane task show` when the task is stacked. Replace `BASE` in these commands with that literal branch name:

   ```sh
   git fetch origin +refs/heads/BASE:refs/remotes/origin/BASE
   git merge --no-ff origin/BASE
   ```

   In a sandbox, `git fetch origin` goes through your state broker, as `git push` does: the sandbox has no credential and often no working ssh (no SSH agent, and ssh refuses its own config files when root-owned files show as owned by nobody), so the broker fetches with the user's login on the host and your git shim indexes its pack and updates `origin/<branch>` and `FETCH_HEAD`. It fetches only the base, the stacked base and your task branch, by name or with the form above, plus `-q`, `-v`, `-p` and `--no-tags`; it refuses other branches, tags and other options. `git pull`, `git ls-remote origin` and `git remote update` cannot reach origin: fetch, then merge `origin/BASE`. Only an origin that is the project's recorded repository goes through the broker; git fetches any other origin, such as a local path, in the sandbox as usual.

   Resolve conflicts and rerun affected tests. The PR's squash merge makes this merge commit harmless. Push with a plain `git push`: the task branch already tracks origin, and the sandbox keeps the repository config read-only, so `git push -u` cannot record an upstream. If git reports no upstream, `git push origin HEAD`. If a rebase would require a force push, leave that history rewrite to the orchestrator. Create or update the PR (`gh pr create` or `gh pr edit`) with what changed, why, how it was verified and the limits. When task show has `stack`, use its `base` as the PR base. Stack refresh runs through the orchestrator's `tower-crane stack sync` while the chain is idle; report a stale dependency instead of rebasing another task's branch.
7. Pre-submit review. Run the reviewer's checklist, the points below, against your own diff at the head you will submit. Do it after the PR exists, so CI, and revuto where the repository uses it, run at that head. Check each point:
   - Acceptance: for each item, name the file, line or command that shows it holds. An item with no probe is not met.
   - Claims: probe each claim in the PR body, docs and changelog by running the command or reading the code it describes. A stale claim is a finding.
   - Copies and contracts: docs, callers and other copies the change touched still agree with it.
   - Edge cases and scope: error paths, wrong conditions, unused additions, and files outside the task's named paths, each with a reason.
   - Revuto at the head: revuto is an optional review bot. When the PR has no revuto comments and no `revuto-review` check, write `not used` and go on. When its check is still running, write `pending` and go on; do not wait for it. Otherwise read the PR's comments and checks there (`gh pr view <n> --comments`, `gh pr checks <n>`). Fix each valid finding, or record why it is not valid. Then close each one you fixed or found invalid with `tower-crane ci resolve <comment id> --agent <name> --reason "<the fix and where, or why it does not apply>"`. This includes findings named in your brief's rework notes. A reviewer's ok is refused while a `[P1]`/`[P2]` finding has no code change at its own path and no `[resolved]` reply, so a fix in another file needs that reply.
   - CI at the head: read the PR's checks once with `gh pr checks <n>`, without `--watch`. Fix a check that already failed, or name it. Checks still running are not a finding: write `pending` and go on, since submit records the head and the ci gate waits for them.
   - Fresh context: if your tools include a subagent and your dispatch allows starting one, give it only the task acceptance, the diff and the PR body, and have it run the checklist. Otherwise run it in this context and record `Fresh context: no`.

   Sort each finding as the reviewer does. These block: an unmet acceptance line; a defect on a line or path the diff adds or changes, shown by a reproduction: a test, probe or concrete input; a false claim in the PR body, docs or changelog; a contract or copy the change broke; any security or data-loss defect the change introduces. Everything else is a follow-up. Fix the blocking ones, push, and run the checklist again on the new head until nothing blocks. Follow-ups stay out of this PR. Then add a `## Pre-submit review` section to the PR body. Read the body with `gh pr view <n> --json body`, then write the whole body back with `gh pr edit <n> --body-file <file>`:

   ```md
   ## Pre-submit review
   - Head: <full sha>
   - Fresh context: yes | no
   - Acceptance: <one line per item: probe and result>
   - Rework coverage: <each prior blocker: sibling cases, table-driven test and result; or none>
   - Revuto at head: <clean, not used, or each finding and its fix>
   - CI at head: <green, or the failing check and why>
   - Left open: <each blocking finding you did not fix, and why; or none>
   - Result: pass | fail | skipped
   ```

   `pass` means nothing blocking is left at the head. `fail` means something blocks and is listed under Left open. `skipped` means the checklist could not run, with the reason under Left open. This is worker behavior, not a gate: it does not replace the review that follows submission, reviewers work from the diff and the task, and you do not post a review or comment yourself; `ci resolve` is the one reply you post.
8. Submit without waiting for CI or revuto to finish: `tower-crane submit <id> --agent <name> --sha <head> --branch <branch> --pr <number> --summary "<one line>" --precheck pass|fail|skipped`. Submit reads the PR's checks and revuto at that sha once before it records the head. Checks still running do not refuse: the head is recorded, the output names them, and your work on this attempt is done. The ci gate waits for them on the host; a failure comes back to you as rework with the failing jobs and the first failing lines of their logs. When a job already failed, submit refuses with the failing job names and the first failing lines of their logs (the first three failing jobs; for any other, read its log with the `gh run view --job ID --log-failed -R REPO` command the refusal prints): fix them, push, and submit the new head. If those fixes change the head, run step 7 again on it before submitting, so the PR body's `Head` is the submitted sha. Revuto's open inline findings print with file, line and body. A `[P1]`/`[P2]` finding already posted refuses the submit while its path has no change since the comment and it has no `[resolved]` reply: fix it at its path, or close it with `tower-crane ci resolve` as in step 7. Fix other findings in this head, or say in `--summary` why one stays. Then `tower-crane spend <id> --agent <name> --minutes N` if you know them. Spawned CLI usage is recorded automatically on exit. For a native dispatch, the orchestrator records tokens once with `tower-crane spend <id> --tokens N [--input I] [--cached C] [--output O] --rung R --harness H --model M --agent <name>`.

## Rework

Read every prior blocking finding copied into the brief's rework notes, including the linked review when the notes only contain its summary. For each blocker, name the failure class and list its sibling cases before changing code: other callers, equivalent inputs, platforms, lifecycle states and error paths that use the same mechanism. Fix the class across that list within the task's acceptance. Ask the orchestrator when a sibling requires a scope change.

Add a table-driven regression test for each blocker, covering the reported case and its siblings. For pure logic, run the variant table in process with one CLI integration test for its wiring; use an integration table when the cases depend on state transitions. Prove the reported defect fails without the fix, and run every row with the fix. Host-only rows stay with the host tests gate and must be named as pending in the summary.

Record each blocker, its sibling list, the table-driven test path and the verification result under `Rework coverage` in the pre-submit summary. A fix to the reported line alone is not coverage of the failure class.

Two failed reviews with blocking findings at the same normalized file path hold worker dispatch and claim across rework revisions. Failures at the same SHA and revision count once per area, whichever reviewers recorded them. The inbox reports `review_redesign`. The orchestrator must narrow acceptance to a closed list with `task update --acceptance ... --closed-acceptance`, or record a design change with `task note --kind scope-ruling`, before another worker can start. A routine note or acceptance edit does not clear this gate.

Ask the orchestrator for scope and technical guidance with `tower-crane msg --to orchestrator --task <id> --agent <name> "<question>"`. When the answer blocks your task, `tower-crane ask --agent <name> --kind <kind> --question "<question>" --option "<A>" --option "<B>" --blocks <id>` opens a decision. Pick the kind honestly: `technical` is the orchestrator's to answer; `spend` (money), `credential` (a grant of a secret or access, or a looser sandbox, named with `--setting env`, `env_file`, `sandbox`, `scope` or `ladder.reach`) and `setting` (an owner-required change) go to the owner, as does a question you mark with `--owner-required "<reason>"` because only the owner can decide it. A host or harness that fails, or a test that also fails on main, is technical: such a question goes to the orchestrator whatever kind you give it. Name an owner-required setting with `--setting KEY` (a setting in lib/authority.js). The reviewer checks the kind, so do not call a spend or credential question technical. Then `tower-crane task note <id> "<what you tried>" --agent <name>` and `tower-crane release <id> --agent <name> --reason "waiting on D<n>"`. If you already opened a PR for the branch, add `--pr <n>` to the release so the task keeps the link and the next worker continues that PR. If the question becomes moot before anyone answers it, `tower-crane decision withdraw <decision-id> --reason "<why>" --agent <name>` closes it. Note a wrong or incomplete brief, or a task harder than its tier (`tower-crane task show` prints it) so the orchestrator can re-tier it; do not guess at product decisions.

Do not review your own work, do not merge, and do not touch other tasks' branches. Your last message is a short report: PR link, what the test proves, anything the orchestrator should carry to dependent tasks.
