# Tower Crane: review one task

You did not write this change and have not seen it being written. Keep it that way: work only from the task, the diff and the reports.

Arguments: `$ARGUMENTS`. Use `TOWER_CRANE_TASK` and `TOWER_CRANE_AGENT` when set; otherwise use the task id and agent name passed by the orchestrator. Pass `--agent <name>` on every tower-crane call. If `TOWER_CRANE_STATE` is absent, also pass `--state <dir>` with the supplied state directory.

1. Use the supplied task, acceptance, submitted sha, PR and software gate results. Read the named review context file when the prompt references one. If dispatched without that packet, `tower-crane task show <id> --agent <name>` gets the task and evidence. Code requires tests and clean gates; every task with a PR needs CI before review dispatch (`docs/state.md`). The tests gate usually runs after your review passes, and then the packet says so: judge the tests in the diff and do not fail the review for missing tests evidence. CI is the orchestrator's gate; reviewers judge the code and acceptance. Missing or unfinished CI evidence belongs in a message to the orchestrator, not a failed code review.
2. Read the packet's `## Review scope`, supplied diff, the brief's `## Reviewer` section and the PR body. Follow **Re-review** below when the packet carries an earlier failed review. Without a supplied packet, get the review instructions with `tower-crane brief get <id> --agent <name>` and use `git diff $(git merge-base <base> <sha>) <sha>`; an earlier failed review at this revision can narrow that diff under **Re-review**. A review from an older revision needs the dispatch's rework link before it can narrow the scope. Read surrounding code where the diff depends on it; if worktree HEAD differs from the submitted sha, use `git show <sha>:<path>`. Use the recorded tests, clean and CI gate results. Do not re-run the full suite unless you change something in a scratch checkout to probe a specific concern; run only the affected tests for that probe. Keep the submitted worktree read-only.
   A packet headed `## Light claim check` replaces the full checklist in step 3: verify every listed claim in the current PR body or named changelog fragment against its code or probe, report whether each correction is true, and record the result through steps 4 and 5. Do not repeat the full review of unchanged code. Unresolved claims and introduced security or data-loss defects still block.
3. Check, in this order, within the review scope. Classify each finding by **What blocks** and **Re-review** below:
   - each acceptance item is met; code changes have a test shown failing before and passing after, and other work has the verification its brief requires;
   - for a research task on any tier, read `research/<id>.json` at the submitted sha and the sources receipt. Check each claim maps to a cited source, its quote supports the claim, and no factual claim in the deliverable lacks a citation. Successful fetching and quote matching do not establish that a source is credible or that the claim follows from the quote;
   - claims in the PR body, docs, comments and changelog are true of the code (current models most often leave stale or overstated text, not broken syntax);
   - copies and contracts the change touched elsewhere still agree (docs, configs, other callers, other locales);
   - edge cases, error paths that fail silently, wrong conditions, races, and security boundaries the change crosses;
   - anything added that nothing uses, and anything the standards rule out;
   - files the packet's `## Scope` lists outside the paths the task names: each needs a reason in the task, or it is a finding.
4. Post one review on the PR as a comment, first line `Review (Tower Crane, clean context)`, followed by `SHA: <full submitted sha>` before the findings. Use separate `## Blocking findings` and `## Follow-ups` headings, writing `None` when a list is empty. Write findings as `file:line - what is wrong - why it matters`, most severe first. Include the reproduction for each blocking defect. State the blocking count explicitly. On a repository the project does not own, do not post; put the review in the evidence summary only, with the same headings.
5. Record it: `tower-crane evidence <id> --agent <name> --type review --ok|--fail --sha <sha> --revision <revision> --summary "<blocking count and the top blocking finding>"`, adding `--ref <comment URL>` when posted. `<revision>` is the task revision you reviewed: the `revision` in `tower-crane task show` when you started, not when you finish. A reviewer that `tower-crane spawn` did not start cannot record review evidence without it. Choose `--ok` when the blocking list is empty and `--fail` when it is not. Follow-ups do not affect that verdict. revuto is an optional review bot; a PR without its comments has no revuto findings to check. When `--ok` is refused for a revuto finding the diff already fixes, do not record `--fail` for it: name the refusal and the fix in your final report and stop. The worker or the orchestrator closes the finding with a `[resolved]` reply (`tower-crane ci resolve`), and automation dispatches no other reviewer at that head until then.
   On failure, also pass `--findings '<JSON array>'` listing every blocker as `{ "kind": "...", "path": "...", "claim": "..." }`. Use `kind: "false-claim"` only when correcting prose resolves the finding without changing behavior or a contract. Use `path: "PR body"` for the PR description, or the actual file path for other findings. Use another kind, such as `defect`, `acceptance`, `contract`, `security` or `data-loss`, for those blockers. A diagnostic defect described at a code location remains a defect unless the implementation meets acceptance and correcting the PR claim alone resolves it. Never omit a blocker to qualify for the light path. Missing metadata keeps the full review path.

## What blocks

Subject to the re-review rule below, these findings block:

- an unmet acceptance line;
- a defect on a line or path the diff adds or changes, shown by a reproduction: a test, probe or concrete input;
- a false claim in the PR body, docs or changelog;
- a contract or copy the change broke;
- any security or data-loss defect the change introduces.

Defects in code the diff did not touch, requirements beyond the acceptance, hardening ideas, style and P3s are follow-ups. List them under **Follow-ups** in the review. The orchestrator files them as separate tasks after a passing or failing review; the worker does not add them to this PR.

When every blocker is only a false claim in the PR body, `CHANGELOG.md` or `changelog.d/*.md` prose, label them all `false-claim`. For PR-body claims, automation dispatches a body-only worker, then automatically requests a light reviewer check after the body is edited and the worker exits without changing commits or checkout files. The task stays submitted at the same head and revision. The orchestrator leaves the body alone while automatic repair is pending or running; status shows `fixing PR body`. After two consecutive failed light re-checks, automation stops with `review_body_stuck` in inbox; the initial full review failure does not count. The orchestrator must correct the PR body before running `accept ID` for another check, or use `rework ID --reason R` for code changes. Without a recorded PR or branch, the orchestrator uses this manual correction and accept path. Changelog claims go back through rework, and the next revision gets a light check when only the named fragments change. The claim still blocks until verified. Claims in `docs/cli.md` and `docs/state.md` are contract text and stay on the full blocking path. Any implementation change during correction also restores the full review.

## Re-review

The dispatch narrows a review when an eligible independent review failed at the current revision, or when rework links the current revision to a failed review of the rejected head at its previous revision. The reviewed SHA must still exist, be an ancestor of the submitted head and contain its current merge base with the project base. A missing reviewed SHA, rewritten history or base update gets a full review from the project base's merge base so upstream changes stay out of the diff. That full review still lists the failed review's blockers: report whether each one is fixed, and an unresolved one still blocks. Narrowed or full, a re-review runs at or above the failed review's rung, unless the project's `min_rung` is `review`, which starts it on the `review` rung. The rework revision bump invalidates gate evidence but does not by itself restart the review scope. A changed brief, acceptance, dependencies, needs or kind starts a full review; a rework without a matching failed review also stays full.

For a narrowed review, read the prior blocking findings and recorded sha from the packet, using its linked comment or evidence summary and rework request. First check each earlier blocking finding at the submitted sha and report whether it is fixed. An unresolved earlier blocker still blocks. Then review only the supplied diff since that review's sha with `git diff <earlier-review-sha> <submitted-sha>`, using the checklist above within that scope.

A defect the new diff causes blocks wherever it shows, including in unchanged code, such as an unchanged caller broken by a changed function. Any other new finding on code the earlier reviewed diff already contained blocks only if it is a security or data-loss defect introduced by the change. Otherwise list it as a follow-up, even if it would have blocked the first review. This applies to newly noticed acceptance, claim and contract findings on unchanged work too. Changes in the new diff get the full checklist. An older review without the dispatch's rework link does not narrow the current review.

Run any probe, test run or PR check in the foreground with a bounded wait, `tower-crane wait --task <id> --agent <name> --timeout SEC` (exits 2 at the deadline), not in a background job: a headless run is not guaranteed to resume for a background job's notification.

Do not fix the code, push, or merge. Your last message is the review text.
