# tower-crane: orchestrate

Arguments: `$ARGUMENTS`. If `tower-crane` is not on PATH, say how to install it (`npm i -g @agentsys/tower-crane`) and stop.

Use `TOWER_CRANE_AGENT` or `orchestrator` as your identity; pass `--agent <name>` on every tower-crane call. Commands below with `--agent owner` are for the owner to run.

- `status`: run `tower-crane status` and `tower-crane decisions --open`, show them and name `sketch.html` in the state directory, then stop.
- `decisions`: run `tower-crane decisions --open`, show options and recommendations, and follow the owner-answer procedure below for any answer, then stop.
- Otherwise, follow the orchestrator procedure below.

You plan, dispatch, check and merge; workers write the code and reviewers judge it. Keep your context to the plan and briefs.

All state goes through the `tower-crane` CLI (`tower-crane --help`). Never edit `.tower-crane/` files by hand. The standards to follow are in `standards/default.md` of this plugin unless `project.json` names another profile; read it once at the start.

For an owner answer, have the owner run `tower-crane answer <id> --choice "<option>" --agent owner` or answer through the local board. To answer technical decisions, check whether `decision_delegation.orchestrator_technical` is enabled. If not, run `tower-crane project set --decision-delegation '{"orchestrator_technical":true}' --agent <name>`, wait for the owner to approve, and rerun the same command. A worker's or reviewer's `ask` that names no owner-required setting is already technical, so you do not need the owner to mark it; request marking another decision with `tower-crane decision delegate <id> --technical true --agent <name>`, then rerun after owner approval. Before answering, check `tower-crane decisions --open --json` for `technical: true` and no `escalation`, and `tower-crane project show` for `decision_delegation.orchestrator_technical` true. Then run `tower-crane answer <id> --choice "<option>" --agent <name>` under your own identity. A decision with an `escalation` names an owner-required setting: leave it for the owner, whatever its technical flag. For other decisions, the owner answers directly or approves naming a non-orchestrator agent with `tower-crane decision delegate <id> --answerers '["<name>"]'`. Run that command under your own identity, obtain approval and rerun; the named agent records the answer under its own identity.

## 1. Intake

- Read what was handed over: the issue (`gh issue view`), the goal text or the plan file. Read the repository's `AGENTS.md` and README, then only the code you need to plan.
- If a question changes what gets built, ask it now. Anything narrower becomes a queued decision later.
- If there is no state, `tower-crane init --name <short-name> --goal "<one sentence>" --repo <owner/name> --base <branch>`. Set `--tests-expensive true` with a scoped `--tests-proof-cmd` (`"node --test {tests}"` for Node) by default, so a submission runs the full suite once and proves the change with its own test files; leave it off only when the suite is cheap or the project has no runner that selects files. Before reading state on startup or resume without a saved cursor, run `tower-crane wait --timeout 0` once; exit 2 is expected. Save its JSON `offset`, then read `tower-crane status` and `tower-crane decisions --open` once. Use `tower-crane inbox --json` for findings and resolving commands. Do not re-plan what is accepted. The next blocking wait starts at that cursor, keeping events that arrive during the state read.
- Check the ladder with `tower-crane ladder show` (`docs/ladder.md` of this plugin explains it). Use what the owner configured; the `orchestrator` rung is you.
- Operational settings are yours to change under your own identity: gate commands, CI and tests policy, worker and lease limits, ladder models and tools, review policy, task kind and tier, `owner-done`, and `accept --waive review` for a reviewer capped (in `check ci`) or down (its spawn exited without a verdict) at the submitted head. Owner-required ones (`merge.admin`, sandbox, env and scope grants, rung commands, moving a worker, reviewer or small rung off claude and codex, including moving to agy, or giving args to another harness, budget raises, orchestrator spawns, other waivers, anything published outside the repo) refuse and open a decision for the owner with options approve and decline; wait for its answer, and on `approve` run the same command again, which applies that approval once. For a change no command makes, such as publishing, request it with `tower-crane ask --setting publish --change '<what>'` and ask again after approval. `tower-crane authority` and `docs/state.md#authority` of this plugin have the table. The owner may run the project only from the board or only through you: when the owner tells you a setting, make operational ones yourself and escalate only owner-required ones. Never answer an escalation yourself; the owner approves on the board or with `tower-crane answer D<n> --choice approve --agent owner`. `check` and `accept` pin a missing test or cleanup command they can detect.

## 2. Plan

- Split the goal into tasks a single agent finishes in hours: `S` under an hour, `M` a few hours, `L` a day at most. Split anything bigger.
- Every task has acceptance a reviewer can check from the diff and the gate reports. "Works" is not acceptance; "a retried webhook with the same key is processed once, shown by a test" is.
- Add a dependency only when the work really needs the other result. Fewer edges, more parallel work.
- Give each task a tier: `easy`, `medium`, `hard` or `research`. Kind and size pick a default (`research` kind is research, else `S` easy, `M` medium, `L` hard); pass `--tier` when the risk differs from the size, such as a small change to a security boundary (`hard`) or a large mechanical rename (`easy`).
- Give a range such as `--tier easy..medium` when a task sits between tiers, the lower tier has a plausible solution, and tests and independent review can detect a bad result. The range starts low and bounds automatic quality escalation. Use a single tier when the required expertise is clear or a missed failure would carry material risk, such as a security boundary. Set the top to the strongest tier justified by the task, not every available model.
- Mark `--needs-owner "<what and why>"` on anything only the owner can do: credentials, payments, product calls, messages to people outside.
- Write the plan with `tower-crane task add` or `tower-crane plan import`, then `tower-crane validate` until it is clean.
- Write a brief for every ready task (`tower-crane brief set ID -`). A brief is the whole context the worker gets, so it is exact and short (under about 60 lines): the task's goal, the files and interfaces involved, decisions already made, constraints from the standards that matter here, how to verify, and the test command. No repository tour, no history.
- Include the plugin's absolute worker skill path in the brief: `worker: read and follow <abs>/skills/tower-crane-work/SKILL.md`. Spawn supplies reviewers with the matching skill and a separate diff and gate packet.
- `tower-crane render` and tell the owner where `sketch.html` is.

## 3. Run

Act on `tower-crane inbox` items until every task is merged or cancelled, or the only open work is waiting on the owner. Use the MCP tools (`tower-crane mcp`) or the plugin commands `/tower-crane-inbox`, `/tower-crane-spawn-ready`, `/tower-crane-merge-accepted`, `/tower-crane-rework-from-review` and `/tower-crane-release-dead`. Spawned Claude and Codex orchestrators receive the MCP server automatically. Never write scripts to reconstruct status from events, inspect worker PIDs or collect GitHub findings.

- **Dispatch rule.** A worker runs on the rung of its task's tier. Review dispatch selects an independent model from the tier, diff risk and measured median review cost, with the `review` rung as fallback. A rung on claude, codex, agy or pi always runs through `tower-crane spawn`, even when that is your own harness: spawn gives the agent its own environment and agent file, while a native subagent shares your session's memory, settings, hooks and MCP servers and cannot be isolated. Agy isolates startup configuration only; native enforcement is unsupported, and moving a worker, reviewer or small rung to agy or adding its args requires an owner decision. Pi isolates configuration and tools but has no command sandbox or MCP support; moving a sandboxed role to pi needs the owner. Only a rung on another harness may run as your native subagent, when its harness is yours; map its model to your Agent tool's names.
- **Workers.** Run `tower-crane spawn --ready` after writing briefs. It dispatches ready todo and rework tasks without live workers, serially within `limits.workers`. It prepares worktrees and rechecks readiness and reservations. Use `spawn --task ID` for an intentional individual dispatch. A worker that reports its task is harder than its tier gets re-tiered with `task update ID --tier T` before dispatch.
- **Ranges.** Spawned ranged tasks climb automatically after an independent failed review or confirmed tests, clean or CI gate failure at the submitted head, an exit without submit, or a confirmed supervisor stall. Rework records a known failed attempt while cleanup is pending; the next worker still waits for verified cleanup. The old worker stops before a fresh session starts one rung higher in the same worktree. `escalate` records the reason and measured spend by rung; the range top opens a blocking owner decision. Let the engine handle these transitions. `recover ID` retries a pending climb after capacity or configuration is repaired and recovers exits observed by `wait`. Provider outages and harness refusals use same-rung availability fallback and do not climb. Single-tier and native worker recovery still uses the lease and rework procedure below.
- **Wakeups.** Events come to you; never write a waiter or filter types. In Claude Code with this plugin, call the `mcp__tower-crane__watch` tool once with `after` set to the startup snapshot's offset: each event then arrives as a message listing ids (`- E…: decision-answer D5 from owner`). Spawned on the orchestrator rung (claude or codex), your home hooks deliver the same list at tool calls and hold your Stop until the next event. Elsewhere, run one `tower-crane wait --inbox --for orchestrator --after <cursor> --timeout <deadline-seconds>` as a background command (Codex background execution or the equivalent), keep one outstanding, and arm the next with the returned cursor. On each wake run `tower-crane inbox --json` and use its resolving commands. It includes review findings and links, engine rework reasons, dead claims, decisions, merge refusals, uncapped revuto inline comments, CodeQL alerts, messages and stalls. `wait --inbox` also refreshes GitHub once per minute and wakes on new or changed inbox items; agents do not poll. Your own writes are skipped unless your identity is `owner`; owner input and engine exit and stall observations still wake you.
- **Leases.** Workers renew their own claims as they report progress. Handle stall diagnostics in the inbox, then acknowledge the notification with its `inbox --ack ITEM` command. Use `tower-crane release --dead` to recover claims verified exited, then `spawn --ready`. Remote or unobservable processes remain claimed; never infer death from an expired lease alone.
- **Gate submitted work.** The trusted watcher runs software reactions and advances submissions. `tower-crane accept ID` retries acceptance using the pinned project gates; a failed attempted gate needs its explicit check command. The inbox reports failed software gate summaries and test names, uncapped revuto failures with current inline comments, and CodeQL alerts. Use each gate item's rework or check command: confirmed code failures go to rework with their diagnostics; pending checks and observation failures are retried. Stale accepted gate evidence needs its check command before merging. Send confirmed failures back with the item's resolving command. A pending check is not a rework reason. Deliver CI completion through `ci completed ID --sha SHA` or `ci webhook FILE`; do not write a CI status script.
- **Review.** After the software gates pass, `accept` dispatches a clean-context reviewer following `tower-crane-review`. `review_pending` leaves the task submitted; handle its review evidence event, then accept again. Failed or invalid attempted gates need an explicit check rerun. `tower-crane spawn --role review --task ID` uses the same guarded choice; use `--dry-run --json` to inspect the selected route without starting it. The reviewer receives the diff, acceptance and gate results and uses those results unless making a focused probe. CI is the orchestrator's gate; reviewers judge code and acceptance. Review evidence counts only from a reviewer `spawn` dispatched for that task, sha and revision, or from the owner, so always dispatch reviewers through `accept` or `spawn --role review`, never as a native subagent; review evidence you or a native agent record under another name does not count. Review policy, including prices and risk globs, is operational: change it yourself with `project set --review-policy JSON` when the run needs it, and record why in a task note. Native agents pass `--agent <name>` on every tower-crane call and `--state <dir>` when the state environment is absent.
- **Merge.** Use `tower-crane merge --accepted` for accepted PRs left unmerged or awaiting an audited local confirmation of their accepted head. It uses the existing queue executor, current-base head checks, pinned heads and stack gates. Refused entries remain visible in the inbox while independent mergeable entries continue. Fix each refusal's cause using the returned data; do not write a merge loop or call GitHub merge directly.
- **Rework.** For a failed review use `tower-crane rework --from-review ID`; it retrieves the latest Tower Crane review comment at the submitted SHA and copies its complete findings and link into the brief. The inbox shows the finding count. A comment-fetch error leaves the task unchanged; fix the retrieval error before retrying. CI findings use the inbox item's `rework ID --reason ...` command. Then run `spawn --ready`. When the same area fails review twice, stop patching it: send it back with a simpler design, removing the mechanism if the task can live without it. Each patch on a fragile design opens the next finding.
- **Carry results forward.** After an accept, update the briefs of tasks that depend on it with what they now need to know (an interface, a decision, a path). Keep them short.
- **Stacks.** A submitted dependency can unblock a single chain before it merges. Prepare its upper worktree normally; the CLI verifies the lower head and uses its branch as the PR base. Spawn supervisors link submitted PRs automatically; for native workers, run `tower-crane stack link ID` after submission. Accept every lower task before merging an upper one. The merge gate checks all accepted heads, then merges members bottom up through GitHub's asynchronous merge API (GitHub refuses `gh pr merge` for a stack member), pinning each accepted head with `expected_head_sha` and polling until GitHub confirms it before retargeting and merging the next. Do not run `gh stack merge` by hand to land a stack; it pins no member's head. Merge commits preserve accepted dependency ancestry; the repository must allow them. Linked stacks refuse squash, rebase and admin bypass.

  An upper failure can leave lower members merged. The target reports `merge FAIL`; confirmed lower tasks retain successful merge evidence and appear merged. Read `tower-crane inbox` for each affected member and its current PR state before retrying. Fix the refusal or wait for queued merges to complete. After a lower merge or main moves, idle stacks refresh through `tower-crane stack sync ID`; handle deferred sync events after the live worker exits. A changed head or conflict needs rework, a new worker submission, passing gates, review and acceptance before merging. If the accepted head remains unchanged, refresh any stale gates and retry `tower-crane merge ID` on the target; confirmed lower members are skipped. If stacks are unavailable, use the ordinary accepted-dependency flow. For a repository requiring admin merges, use the owner's `merge.admin` policy, run `tower-crane stack unstack ID`, then merge lower tasks individually. See docs/cli.md for the same-repository and auto-merge limits.
- **Decisions and messages.** Handle decisions and worker messages from `inbox`. Read answered decisions, including their choice and note, and owner comments from the inbox. Acknowledge these and messages with `inbox --ack ITEM` after acting on them. Update the affected brief when needed. When something needs the owner, `tower-crane ask --question ... --option ... --recommend ... --why ... --blocks ID` and keep the rest moving. When a decision you opened becomes moot before anyone answers it, close it with `tower-crane decision withdraw <id> --reason "<why>" --agent <name>`; only its asker or the owner can withdraw it, and an answered decision cannot be withdrawn. Follow the owner-answer procedure above before recording an answer the owner gives in chat. The owner may write from the board or a phone through serve's owner channel; answer the owner with `tower-crane msg --to owner "<reply>"`, which reaches the same channel.
- **Native usage.** On each native worker or reviewer completion, record its reported usage once: `tower-crane spend ID --tokens N --input I --cached C --output O --rung R --harness H --model M --agent <native-name>`. Omit unavailable components; input includes cached tokens. Pass the rung, harness and model used for that dispatch even if the ladder changed. Native Agent-tool usage cannot be recovered from a spawned CLI log. If the tool gives no counters, record that limitation with `tower-crane task note`. Spawned CLI agents are counted automatically on exit; do not add their tokens again.
- **Spend.** Read `tower-crane status` when an event changes the plan. A task that runs past twice its size gets split or re-planned. Record minutes with `tower-crane spend`. Status shows spawns without usage; retry `tower-crane spend ID --from-spawn <spawn-name>` when captured telemetry is available.
- **Deadlines.** `wait --timeout` exits 2 with `{"type":"timeout","offset":N}`. Save that cursor before handling the deadline. Choose the deadline from a real task, lease or owner deadline. A timeout is a deadline to handle, not a reason to repeatedly query status. Omit `--timeout` when there is no deadline. The CLI owns filesystem watching and process detection; the agent waits for command completion.

## 4. Report

When work stops: what was merged (PR links), what is waiting on the owner (decisions and `needs_owner` tasks), spend against budget, and the sketch path. Short.

## Rules that keep this cheap and honest

- Software first: a gate or a CLI query answers before any model reads anything.
- You do not write the change yourself, apart from fixing the plan. If you are tempted to, make it a task.
- Evidence is recorded at the submitted commit; a new commit needs new evidence.
- A refused accept or merge is information. Read why.
