# Testing

The suite proves behavior through the real CLI on temporary git repositories. It stays small enough to run often without loading the machine. This page is how to run it, how to write for it, what it costs and how its accuracy is measured.

## Running

- `npm test` runs every file in `test/` and `test/gates/` with 4 file workers. Every concurrency option, including repeated and space-separated values, is consumed before emitting one value. `test/run.js` caps any request at one below the machine's core count, since each file also starts CLI, git and stub processes. A caller on a large host, such as the tests gate, asks for more: see [Suite time](#suite-time). `test/run.js` runs each file in a `node --test` runner of its own, longest measured file first, prints each file's output whole when it ends, and ends with the run's totals and every failing file's `✖ failing tests:` details. Inside Tower Crane (a gate command or a spawned agent) the worker count is a request: the host governor grants up to it and the pool follows the grant as it changes ([state.md](state.md#test-threads)); plain `npm test` and CI keep the request.
- `npm test -- test/claim.test.js test/gates/tests.test.js` runs only those files. Pass node:test flags the same way: `npm test -- test/events.test.js --test-name-pattern="decision answer"`.
- Run only the files a change touches. With `tests.crucial` and a coverage-built `tests.map` pinned (crucial mode, [state.md](state.md#projectjson)), the tests gate runs the crucial files, the task's changed tests and the suites the map links to its changed files at the submitted head on Linux Node 26, and no task runs the full suite; without them it runs the full suite once. A same-repository PR and a push to `main` run one hosted job, `checks (shared files)`, which runs `npm run check:shared` on the PR's or the push's range. A fork PR runs the full matrix below, with `npm run check:shared` in each shard. The gate scratch cleanup and model swap proofs and the Windows repeat job below run on fork PRs, release tags, daily and manual runs, not on same-repository PRs or main pushes. Same-repository PRs therefore get no hosted Windows run before merge; a Windows regression first shows on the next daily run.
- Fork PRs, the daily schedule at 03:17 UTC, `workflow_dispatch` without `profile` and `v*` release tags run all ten test shards: Linux Node 26 and Linux Node 24 in three shards each, and Windows Node 26 in four. Node 24 compatibility and hosted Linux shard coverage are checked after merge on daily runs, or in a manual full run. These runs also keep the proofs and shared check. A release reads the newest of these on `main`: it must be green and at or after the head it ships ([state.md](state.md#projectjson) has the rule), so a release runs one manually when `main` moved after the daily run. One matrix serves every event that runs the test job, with job names `test (<os>, node <n>, shard <i>/<shards>)`, where `<shards>` is 3 on Linux and 4 on Windows, so the `ci.required` prefix `test (` matches fork PR jobs.
- PR runs share a workflow concurrency group keyed by PR number. A new push to the same PR cancels its superseded CI run. Main pushes share one group, `ci-main-push`, without cancel-in-progress; tag pushes do not join it. GitHub keeps one running and one pending run per group, so a running main run always finishes and a newer push replaces the pending one. The newest main head covers every earlier commit, so a skipped intermediate head loses no coverage, and main runs no longer queue one behind another on saturated hosted runners. Scheduled and manual runs have unique groups keyed by run ID, so no later event replaces or cancels them.
- A shard run also prints `file started:` and `file ended:` lines as `test/run.js` starts and ends each file, so a log that stops shows which files were running. A shard still running 36 minutes in prints its live process tree (on Windows also the processes started during the run whose parent is gone), stops them and fails, since GitHub keeps no log for a job its limit cancels; a healthy Windows shard runs its tests in about 28 minutes. The deadline runs in `test/shard-watchdog.js`, a detached process `test/run.js` starts, so it still fires when the runner's own event loop is blocked; it exits when the runner does. `TC_TEST_SHARD_DEADLINE_MIN` overrides the deadline, and `test/ci-required.test.js` holds the default under the test step's 40-minute `timeout-minutes` and that under the job's 45.
- With `TC_TEST_SHARD_LOG_DIR`, the shard also writes the file lines to `progress.log` and the watchdog writes `watchdog.log` there: its start, a line a minute with free memory and load, and at the deadline the process dump and the stop. On Windows it takes a second snapshot after `taskkill`, retries any process that survived with `Stop-Process -Force` and logs what is still running. CI sets it and uploads the directory as the `shard-progress-<os>-node-<n>-<job index>` artifact on every outcome, so a shard that hangs or times out still leaves its progress and process tree. A manual run with the `hang` input sets `TC_TEST_SHARD_HANG=1`, which blocks every shard runner's event loop, and a 2-minute deadline: each Linux shard then fails through its watchdog, each Windows shard through the guard below (node's watchdog waits 10 minutes there, as if node itself were stuck), and each uploads the dump. Those failed jobs are check runs on the commit the run tests, and same-repository PR runs skip the test shards, so a hang run on such a PR's head leaves that head with only failed `test (` checks and the CI gate refuses it. Run it on an earlier commit of the branch and submit a later one.
- Windows shards run through `scripts/shard-guard.ps1`, a PowerShell process outside node, because a runner that froze in CI run 39552229082 stopped the node watchdog, the step and job limits and the upload together, and left no log. The guard starts `npm test` inside a Windows job object, which holds every process the tests start, orphans included, and caps them at `TC_SHARD_GUARD_MAX_PROCESSES` active processes and `TC_SHARD_GUARD_MAX_MEMORY_MB` of committed memory; past either limit a new process or allocation fails in its test instead of freezing the VM. CI sets 1000 processes and 12288 MiB: in run 39561962547 the four healthy Windows shards peaked at 28 to 69 active processes (sampled each second from the next run on, every five seconds there), 0.9 to 1.8 GiB committed and 3,900 to 8,700 handles, and started 90,000 to 116,000 processes each. The VM has 16 GiB with about 3 GiB in use before the tests, so a job at its memory limit still leaves the runner room. Every minute it logs the files still running, the job's processes, handles and committed memory with their peaks, and the machine's free memory, commit, process and handle counts and free disk, to the step log and to `guard.log` beside `progress.log`. It also posts that report through the GitHub API as the check run `shard progress (<os>, node <n>, shard <i>/<shards>)` on the tested commit. The check is created completed and neutral, so a runner that freezes cannot leave a pending check, and its title (`running at 12.3 min: 20/32 files ended; running: test/claim.test.js`) and its summary are readable on the commit's checks page or through the checks API while the shard runs: `gh api repos/OWNER/REPO/commits/SHA/check-runs --jq '.check_runs[] | select(.name | startswith("shard progress")) | [.name, .output.title] | @tsv'`. `gh pr checks` lists the check but not its title. A fork PR's token cannot write checks, so there the guard keeps only its logs. At `TC_SHARD_GUARD_DEADLINE_MIN` (38, after node's 36 and before the step's 40) it names the files still running, dumps the job's processes with handle, thread and memory counts and command lines and the system's ten largest by handles and by memory, stops the tree with `taskkill /T /F` and then the whole job, and exits 1, so the step ends and the upload runs. `test/shard.test.js` runs it on Windows against a blocked runner with an orphan, a process limit and a memory limit, and `test/ci-required.test.js` holds its deadline between node's and the step limit.
- `TC_TEST_SHARD=INDEX/TOTAL` selects one shard of the file list. Shards split by measured time: `test/durations.json` holds each file's summed test durations from CI logs, per platform, and `test/run.js` gives the longest remaining file to the shard with the least time so far. A file the table does not list counts as its median file. Every run, sharded or not, starts its longest files first by the same table, so a long file does not start late and hold the run open alone: `node --test` sorts the paths it gets as text, but each spelling of a path sorts in a band of its own: more `../` steps up from the working directory first, then absolute paths, then plain relative ones. The runner gives the longest files the earliest bands, one worker's worth to each, so they start in about longest-first order; the shortest keep their plain paths. Reports name a file the same however it is spelled. A run of no more than two files per worker keeps the order given, and a checkout without the table the sorted order. Refresh the table after a change that moves a lot of test time, such as splitting a slow file: `node scripts/test-durations.js RUN_ID...` reads the `npm test` step of each successful test job in those runs and maps each test title to the file in this checkout that declares it. A file those runs did not measure, such as one in a failed shard, keeps its old time; a file no longer in the checkout leaves the table. The script prints which files kept their old time, which are new and which are gone. `test/shard.test.js` checks that the shards cover every file once and that the checked-in table splits each platform evenly, and `test/ci-required.test.js` checks the workflow matrix for PR, push, schedule and manual events.
- Scratch uses `TOWER_CRANE_TEST_TMP`, then `TOWER_CRANE_TMP`, then `~/.cache/tower-crane/test-tmp` (`XDG_CACHE_HOME/tower-crane/test-tmp` when set). Windows uses `LOCALAPPDATA/tower-crane/test-tmp`, falling back to `~/AppData/Local/tower-crane/test-tmp`. Repository seeds, gate fixtures and secret fixtures share this root; Chrome first tries it before the socket-path fallback below.
- Live probes whose agent hides the user's own home (`test/live-sandbox.test.js`) keep their fixtures in `tower-crane-live` in the same cache directory instead. Every test process adds and removes fixtures and a harness guard in the shared root. A claude reviewer or small agent once hid each entry beside the path from the home to its worktree, as the entry was at spawn, and an entry that went while a command started failed that command's sandbox. It hides the home whole now, so nothing there is listed entry by entry; the separate root stays as isolation, and the home probe still runs while 3,000 stand-ins in the shared root come and go, so a layout that lists them again fails it. A fixture pinned with `pinLiveRung` also drops the harness guard from its PATH, since it runs a real harness on purpose.
- CI test jobs have a 45-minute per-shard limit and their test step a 40-minute one, a guard against a hung job and not the suite deadline; three Windows shards took 28 to 36 minutes, so Windows runs four, and Linux shards take 9 to 13. Each test still has its own 300-second deadline. No test file should take more than about 15 minutes of Windows test time: the files of one shard run in parallel, but the tests of a file run in turn, so one long file sets its shard's floor. `test/automation.test.js` was split into three files for this reason.

On POSIX, Chrome profiles whose paths exceed its socket limits use a private directory under `XDG_CACHE_HOME/tct` (`~/.cache/tct` when unset), then the account's `~/.cache/tct` if the configured cache is also too deep. If fitting caches deny allocation, the requested test root is used so Chrome reports its own startup error. Chrome's temporary files stay inside its profile, which teardown removes after completion or a failed start. Windows profiles keep the shared test temp root.

Unix socket fixtures use `test/socket-dir.js`: a fresh directory under the worker's `TOWER_CRANE_SOCKET_DIR`, then the broker's socket roots (`XDG_RUNTIME_DIR`, then `~/.cache/tc` in the account's home), never `TMPDIR`, which a gate or test root nests too deep. The helper checks the resolved path before allocation. Fixtures do not use the repository fixture path or assume `/tmp` exists. `lib/socket-path.js` checks UTF-8 byte length against 103 bytes, leaving the terminating NUL within macOS's 104-byte limit and Linux's 108-byte limit. Broker tests cover the boundary, multibyte names, long fixture paths and directory cleanup. Windows brokers use named pipes.

Outside PRs, the `repeat (windows-latest, node 26)` job runs the Windows flake repeats in its own runner, so they do not unbalance the test shards. It runs the Claude interrupted native worker case ten consecutive times, stopping on the first failure. The case waits for final usage through `wait --types spend --observe` and checks the supervisor's stopped phase and exit receipt before redispatch. Its parent clock models startup consuming the session deadline, so shutdown completion must be independent of that deadline.

The repeat job runs the lock-free reader and torn recovery tests of `state-durability.test.js` thirty consecutive times. Windows file ids run past 2^53, so these tests catch an identity that a Number rounds, and they run there with real ids.

The repeat job also runs the owner-authority and board-approval files ten consecutive times: `authority.test.js`, `approval-context.test.js`, `board-controls.test.js` and `windows-ancestry.test.js`. The Windows ancestry regression releases a held CIM snapshot through a native event and waits for the CLI's close signal. It verifies one provider query, transient-shell skipping and bounded ancestry output even with a large unrelated command line. Repetitions run the submitted code without loading ancestry code from the PR base.

The repeat job's last step runs `mutants.test.js` ten consecutive times. Every fixture process records its pid and the time it saw it. After each contained run the test asserts that none of them still runs, reading Windows creation times in one PowerShell query so a reused pid does not count.

The same file also runs a CLI authority regression on either platform with a provider fixture that refuses individual parent lookups. It reproduces the `ETIMEDOUT` refusal with the old discovery code and reaches the owner-required decision with snapshot discovery, so the Linux tests gate can prove the change too.

The repeat job's first step runs the Claude Code mod wakeup case twenty consecutive times, stopping on the first failure. The first pass is the job's first orchestrator command, so its follower's lease discovery is the runner's first PowerShell CIM snapshot, which can take longer than the push deadline. The case waits for the follower's ready line or exit before any delivery deadline starts. It then waits on prompt and append signals, then checks the steer's event id rather than the total prompt count. An ordinary worker message during the turn forces an independent wake to overlap with the steer, as delayed inbox reconciliation can do after the initial decision answer and worker message.

For projects Tower Crane manages, expensive proof is the default: the orchestrator pins `--tests-cmd "npm test" --tests-expensive true --tests-proof-cmd "node --test {tests}"`. A submission then runs the full suite once and proves the change with its own test files. Once a full run has built a coverage map, the default is crucial mode: `--tests-crucial JSON` and `tests map refresh --from-run RUN_ID`, and a submission runs the crucial files and the suites covering its change instead of the full suite.

Release tags, daily and manual CI runs also run `node scripts/probe-gate-scratch.js` at the pushed head on an unsandboxed Linux runner. It initializes separate state through the CLI and runs a complete `check tests` in run-only mode with fresh on-disk outer and gate directories. The `gate-scratch-proof` artifact records both directories' before/after contents, the actual gate parents from command receipts and their removal. The check fails if the tests fail, the outer directory gains contents or a gate parent survives. A failing head reruns the suite on the base for the failing names, so the probe and its job wait out two gate runs and keep the gate's report of the failures. This full proof refuses a worker sandbox. `node scripts/probe-socket-scratch.js` runs the same proof on the broker, sandbox extension and spawn test files only, so a host probe (`submit --host-probe`) finishes within its deadline. `test/gate-scratch-proof.test.js` verifies the recorder with small real-CLI fixtures. The default representative proof uses isolated governor readings, like its test fixtures: it checks cleanup, and an enclosing host gate already reserves its resources. This avoids a second reservation deferring the nested proof inside the enclosing gate's memory cap. The probe preserves a supplied `TOWER_CRANE_HOST_ROOT` so fixture gates use their configured machine readings; custom commands outside tests retain real host admission. A governor deferral or other check outcome without a receipt fails with a descriptive error containing the exit status and diagnostic, and removes the probe directory; no execution supplies no cleanup proof.

Both proofs run `node test/run.js --test-concurrency=3 test/ladder.test.js test/broker.test.js test/spawn.test.js test/gates/tests.test.js`. `PROOF_FILES` in `scripts/suite-time.js` fixes the selection. Ladder covers model changes and the documented-defaults assertion; broker and spawn start real brokers and fixture workers; gates/tests creates nested gate worktrees, scratch and base reruns. The scratch proof runs this command through a complete tests gate. The model swap proof replaces the built-in defaults before running the selected files and still requires exactly the documented-defaults assertion to fail. These proofs check gate lifecycle and independence from built-in model choices. Daily, release and manual CI runs cover the full suite; configured task gates run crucial and relevant files.

`PROOF_DEADLINE_MIN` in `scripts/suite-time.js` bounds each proof run at 10 minutes, independently of the project's full-suite timeout. Each proof prints its wall time and its share of that deadline, adds the line to the job summary and emits a GitHub warning annotation past 75% of it. The gate scratch artifact keeps the same figures as `suite_time`, and the `model-swap-tap` artifact keeps the swap run's TAP with every test's duration. `npm run check:shared` rejects drift in the proof jobs' deadlines: model swap gets 15 minutes including setup; gate scratch gets 30 minutes for two bounded runs plus setup and failure reporting. A clone's full-suite gate timeout remains its own setting.

The 2026-10-21 local Node 26/Linux sizing run took 133.5 seconds at three file workers: 194 tests passed; two gate assertions met worker-shim restrictions on git config and hooks. The 10-minute deadline is 4.5 times that measured wall time, leaving 466.5 seconds for slower process startup and nested gates. Complete clean-proof times and planted-failure results require a host run and are recorded by the task's host probes.

On a host, `node test/proof-breaks.js scratch` plants a surviving gate parent and requires the scratch proof to reject it after a passing gate. `node test/proof-breaks.js model-swap` plants a worker test that depends on the original built-in harness and requires the swap proof to reject that extra failure. Both use temporary processes or copies and remove their scratch. These commands complement `test/gate-scratch-proof.test.js` and `test/model-config.test.js`, whose regression checks pin the representative command and preserve the leak and unexpected-failure assertions.

`test/proof-breaks.test.js` executes the planted-proof CLI and its generated hooks with fixture proof responses. Its variant table covers detected and absent properties, a failed gate, wrong exit status or diagnostics, child-process errors, invalid modes and cleanup after each outcome. These runs give task gates measured coverage of the helper.

Proof scratch may be deep: socket paths use the runner's private runtime directory and the broker's short socket roots, independently of `TMPDIR`. Both proofs preserve a supplied `TOWER_CRANE_SOCKET_DIR`, so a sandbox's granted short leaf remains available when the runtime root is missing or overlong. The scratch regression table starts real brokers through the CLI gate with deep scratch and account caches, covering short, missing and overlong runtime roots and cleanup after each run.

## Writing tests

- One integration test per piece of functionality and one end-to-end test per full feature. A unit test is only for pure logic nothing else reaches.
- A table of variants over pure logic runs in process against the module, with one CLI test for the wiring: address ranges and markup in `test/sources.test.js`, build-file and policy tables in `test/gates/tests.test.js`, outage classification in `test/supervision.test.js`, broker authorization in `test/broker.test.js`.
- A fixture several tests share is built once per file with `cachedFixture(t, key, build)` from `test/helpers.js`. Each test gets a copy, with paths that name the template rewritten in its files, env and git config.
- `test/global-setup.js` names one Node compile cache for the run (`TC_TEST_COMPILE_CACHE`, beside the run's git seed), and every test file and fixture CLI uses it: each of them compiles the same lib modules. A test file run without the runner gets `NODE_DISABLE_COMPILE_CACHE`, so no child writes a cache into its fixture after teardown.
- Fixture state skips the flush to disk. `test/fixtures/no-fsync.js`, which `test/run.js` preloads into every test file and the account home hook into every CLI, turns `fs.fsyncSync` into a descriptor check: no test powers a fixture off, and on a busy host each flush made a state write wait on the disk. `test/fixtures/hooks.js` wraps the call after it, so a test that traces, fails or delays a sync still sees every one.
- Cases that wait on their own child processes and share no state run side by side in a `describe` with `concurrency`: two at a time in the reviewer, supervision, fallback and spawn-resume groups, and all three merge races. A case that mocks timers or sets `process.env` stays outside such a group.
- File teardown cleans every remaining fixture, including templates and repositories created without a test context, using the same detached-process shutdown as per-test cleanup. A stopping monitor can record a new monitor or worker, so teardown rereads the records and kills new ones until none appear, then removes the directory. Plain scripts clean their remaining fixtures before a normal exit. After `process.exit()` or an uncaught exception, an exit listener kills their detached processes and removes their directories synchronously.
- A CLI the test signals or reads while it runs starts with `h.spawnCli(args, { pre })`, which preloads the test hooks before `pre`. Detached processes it starts, such as the worker an idle `wait` host dispatches, are then recorded and stopped by cleanup. `assertNoProcessesIn(t, base)` fails when a process still has its working directory in the fixture after cleanup. `processesIn(base)` finds them through `/proc` on Linux and `lsof` on macOS and other POSIX systems. Windows has no such probe, and neither does a system where `lsof` does not run: there the check prints a `process leak check skipped` diagnostic instead of passing silently.
- Each test repository has its own `HOME`; `spawn` receipts stay under its `~/.cache/tower-crane`. Chrome uses the private profile location described above.
- No test reads the developer's user ladder file. `baseEnv` names a `TOWER_CRANE_CONFIG` in the fixture for every CLI; lib code a test calls in its own process reads `process.env`, so such a test calls `useFixtureUserFile(t, h)` (`isolateUserFile(dir)` in the gate tests). `test/fixtures/user-config-guard.js` fails any process that resolves the user file outside the test temp roots, which it fixes when it loads and passes to every child, comparing real paths only, so a root given as a link (the model swap probe's) holds its fixtures and a link in a root that leads outside it does not: `test/run.js` preloads it into every test file, and the account home hook brings it into every CLI. It replaces `userFile` in this checkout's `lib/ladder.js` as the module compiles, so `resolve`, `readUser` and `check` reach it too; a change to that declaration fails every test until the guard follows it. Each process writes its hits to a file of its own in its test process's hits directory: fixture cleanup fails the test whose fixture made it, even when the CLI was expected to exit nonzero or ran detached, and the file fails at exit on any hit left, even one lib code caught. `test/user-config-guard.test.js` covers it.
- No test starts a real harness CLI without its live opt-in. `test/helpers.js` puts a guard `claude`, `codex`, `opencode`, `pi` and `agy` first on `PATH` in every test process. A call to one fails at once and records itself; the test that owns the fixture then fails at cleanup, the file fails when no fixture owns the call, and a plain script that loads `test/helpers.js` exits 1. `TOWER_CRANE_LIVE_CLAUDE=1`, `TOWER_CRANE_LIVE_CODEX=1`, `TOWER_CRANE_LIVE_REVIEW_CACHE=1` (claude) and `TOWER_CRANE_LIVE_BROWSER=1` lift the guard for the harness they run. A fixture whose automation dispatches workers or reviewers the test never inspects calls `stubRungs(h)` before `h.init()`.
- Readiness waits use `test/signals.js`: `fileWritten(file)` watches the parent directory so empty writes and atomic replacements count; `eventAppended(file, predicate)` reads only complete JSONL records; `childExit(child)` observes the child exit; `childClosed(child)` also waits for output pipes to drain; `portListening(port)` observes a successful connection. Every helper cleans up its watchers, listeners and timers, and accepts an AbortSignal. File probes recover from missed notifications and restricted recursive watchers; supply `check` when readiness requires particular contents, such as a nonempty PID. `waitOnRepo(h, check)` watches fixture changes, with probes for detached processes and other predicates without portable notifications. Browser predicates use `waitUntil(check)`. `runAsync` accepts `onSpawn` to expose the child when a test needs its exit before retained output closes. When the test holds the process that makes the condition true, pass it as `alive` (a child, a detached pid or a function): the wait fails as soon as that process is gone and one last check of the condition is still false. A check runs again no sooner than it took the last time: a check that starts a CLI, such as `h.json(['task', 'show', 'T1'])`, wakes on that CLI's own lock files, and without the pause one wait kept a core busy (a lock held for 63 s cost 64 CPU seconds).
- Timer-driven code takes its intervals from settings or `TOWER_CRANE_INTERVALS` ([state.md: Lock](state.md#lock)), and tests use short values or a fake clock. Supervision has rung settings (`stall_ms`, `backoff_ms`, `max_backoff_ms`); gates have `--tests-timeout-min`, `--rework-hold-min` and similar; leases move with the `test/fixtures/clock.js` and `shifted-clock.js` clocks; supervisor sampling and outage budgets with `monitor-clock.js` and `supervision-backoff-clock.js`. `TOWER_CRANE_INTERVALS` covers the state lock wait and marker refresh, the supervisor startup windows and the governor's registry waits; set it in the fixture's `h.env` so every CLI, supervisor and hook it starts inherits it, or pass it in the env an in-process call takes. One test per mechanism keeps the production interval on the real clock: `test/spawn-startup.test.js` the 10 s startup window, `test/lock.test.js` the 60 s lock wait, with writes that wait out 11 s and 16 s holds, and a held lock's 10 s marker refresh, and `test/governor.test.js` the 5 s registry lock wait and the 10 s bind wait. The dispatch's marker refresh (`test/automation-dispatch.test.js`) and a bind that reports it did not land run at 1000 ms and 600 ms. `scripts/mutants.js --deadline-floor MS` lowers the 30 s mutant deadline floor for the timeout-catch test, and a unit test checks the default.
- The runner's 300 s hung-test timeout is the only readiness backstop. Synchronous fixture interceptors use the same backstop because they cannot run watch callbacks while holding a caller. An explicit zero subprocess timeout delegates to the runner; positive watchdogs retain the hung-test minimum.
- `npm run check:shared` runs `scripts/test-waits.js` over all test JavaScript, including fixture scripts generated in strings and templates. It rejects a readiness budget below the hung-test timeout in: clock deadlines and elapsed checks (`Date.now()`, `performance.now()`, `process.hrtime`, `new Date()` arithmetic); timer sleeps (`setTimeout`, `timers/promises`, `promisify(setTimeout)`, `scheduler.wait`); wait-helper, `AbortSignal.timeout`, subprocess and test watchdog budgets; and CLI `--timeout` flags. A synchronous sleep (`Atomics.wait` with a timeout, a `sleep` command, also one run through `sh -c`) is allowed only as the probe cadence of a loop whose condition is the signal. A loop that a counter bounds around a sleep is rejected, whether the counter is in its header or in an `if` that breaks, returns or throws, and so is a call in such a loop to a named function that sleeps outside a loop of its own; a `wait-allow` on that function's sleep does not cover the loop. The same holds in shell scripts a test writes, over real newlines, escaped ones, `+` chains (an operand the check cannot read is a word break) and arrays of lines that a `.join` puts together; a loop whose `done` the check cannot read runs to the end of the script, and any `sleep` word in the body counts, `/bin/sleep` and `command sleep` included, but not an option such as `--sleep`, an `echo` or `printf` text, or a comment. A sleep word in quoted text or a heredoc in the body counts too, since the check cannot tell which text a shell runs. A loop word inside a loop header is text, and one in quoted text (`$'...'` with its escapes included), a comment or a heredoc body neither opens nor closes a loop around it, while a `#` glued to `$(...)` is part of a word and `<<` in arithmetic is a shift; a quoted string or heredoc that holds a whole loop, as `sh -c '...'` or `sh <<EOF` does, is read as a script of its own. A `sh -c` helper sleeps only when its command literal holds a bare sleep; a command built with `+` or passed in a variable counts as no sleep, since the check cannot read it: a `while` or `until` loop comparing a variable its body counts, in its condition or in a test before a `break`, or a `for` loop over `seq`, a brace range such as `{1..50}`, a fixed list of numbers or a C-style `for ((...))` header. Budgets are folded from literals and from constants and default parameters bound to them, in the scope of the wait. Computed budgets need a recognizable hung-guard minimum, such as `Math.max(HUNG_TEST_MS, budget)`. A wait whose duration is the contract under test, a fixture delay that is the fixture's behaviour, or a bound that turns an outcome that never comes into a prompt failure keeps it with `// wait-allow: reason` on that line; empty reasons and strings posing as comments do not count.
- Assert the reason a command refuses, not only its exit code. A refusal for the wrong reason passes an exit-code check while the guarded code is gone.
- A fixture or stub that writes a file a test may poll writes it with `writeAtomic` from `test/atomic-file.js`: the content goes to a hidden file beside the target, which a rename then puts in place. `fs.writeFileSync` truncates before it writes, so under load a poller finds the file empty or half written. An empty marker that signals by existing may use `fs.writeFileSync`. A content write that no test polls keeps it with a `// write-atomic: reason` comment on its line or the line before. `test/atomic-file.test.js` fails on any other `writeFileSync` with content in `test/fixtures/`.
- A fixture that changes a file other fixture processes also change, such as a gh stub's state or a harness stub's attempt list, does it with `updateJson` from `test/atomic-file.js`. It holds a lock file across the read and the write, so a call never writes back a copy that misses another call's change. `test/atomic-file.test.js` fails on a fixture that reads a file and later writes the same path with `writeFileSync` or `writeAtomic`; a write that no other process races keeps it with a `// update-json: reason` comment on its line or the line before.
- Readers wait through a file that is not written yet. `fileWritten(file, { json: true })` in `test/signals.js`, and `waitFor` in `test/canary.js` with the same option, returns the parsed value and keeps waiting while the file is missing, empty or not yet valid JSON; `check` then receives the parsed value.
- A test signals a pid it did not get from its own `spawn` through `killPid(pid, signal)` or `killGroup(pid, signal)` from `test/signals.js`. Both throw unless the pid is a whole number above 0, and above 1 for a group. A pid read from a file that is not written yet is `Number('')`, which is 0, and `process.kill(0)` signals the test's own process group: the whole suite dies with no teardown. `npm run check:shared` rejects any `process.kill` in test JavaScript, generated fixture scripts and template interpolations included, whose pid is not `process.pid`, optional-chaining calls such as `process?.kill(0)` and `process.kill?.(0)` included. It also rejects an alias of `process.kill`, since the alias takes pids the check cannot see: `const kill = process.kill`, `process['kill']`, `process[name]`, `process.kill.call`, `const { kill } = globalThis.process`, `const k = global.process.kill`, or `p.kill` after `const p = process`. Only the fixtures that replace `process.kill` to fake a pid probe and forward other calls to the original may hold one; `KILL_INTERPOSERS` in `scripts/test-waits.js` names them. Even there, the one exempt line is `const kill = process.kill;` directly followed by `process.kill = function (pid, signal) {`, and the held alias may only appear as `kill.call(this, pid, signal)` inside that function, with `pid` and `signal` never reassigned. Any other use of the alias in its scope, or `process['kill']`, is rejected in those files too; a parameter or a nested declaration with the same name is another value. A comparison such as `process.kill === original`, or an argument of a comparing assertion (`assert.equal`, `assert.deepStrictEqual` and the like) or `Object.is`, is not an alias. Prose is not a call: a comment, text after `//` on a code line, or a quoted sentence where a word that is not a keyword comes right before the name, such as `'do not call process.kill(0)'`. `child.process.kill(pid)` is another object's member. In an interposer, a parameter changed by assignment, destructuring, `for (pid of ...)`, `arguments[0] = ...`, `arguments[0]++` or `Object.assign(arguments, ...)`, or a forward from an inner function with its own `pid`, is not a forward; a write keyed by the pid, such as `calls[pid] = signal`, leaves it unchanged. The alias is checked in its whole block, above its declaration too. The check reads patterns, not a parsed program, so some spellings still pass: passing `process` itself to a function (tests do it often, as in `kill.call(process, pid, signal)`, and the check does not follow it into the callee), `(process).kill(0)`, `require('node:process').kill(0)`, `const { kill } = p` after `const p = process`, `p = process` without a declaration, and `process['ki' + 'll']`. A fixture that writes a pid a test signals publishes it with `writeAtomic`, and the reader waits with `nonempty: true`.

[testing-signal-waits.json](testing-signal-waits.json) summarizes the loaded runs and mutation catches behind the signal-wait conversion, per measured test file.

## Tools

- `node scripts/suite-profile.js [--test-concurrency=N] [--top 30] [--json FILE] [--runs N] [--baseline REF | --baseline-dir DIR] [files...]` runs the suite through `test/run.js` and prints, per file and per test, wall seconds, CPU seconds of the process tree and the share spent waiting. Then come its wall time, the longest file, the host's 1-minute load at start, peak and end, and from its own cgroup: CPU seconds (`cpu.stat`, which counts detached processes too), CPU pressure (`cpu.pressure`: seconds some or all of its tasks waited for a CPU, and the peak 10-second averages) and peak memory above the start. It sets no wall limit. The summary comes last, so a log tail such as a host probe's receipt keeps it with the top tests; names over 100 characters are cut. `--baseline REF` checks `REF` out in a detached worktree under the temp root (`TOWER_CRANE_TEST_TMP`, else `TMPDIR`) and runs it and this checkout in turn, baseline first, `--runs` times each, so both see the same load; `--baseline-dir DIR` uses a checkout already there. It ends with a table of every run and the medians, and exits 1 unless this checkout's median CPU seconds (the cgroup's, or the file processes' sum where there is no cgroup) and median longest-file wall time are both lower, or when a run of this checkout failed. It preloads itself into every test process and reads the start and end of each test from node:test's tracing channels; CPU per test is the process's own plus its reaped children's, so a detached process that init reaps counts as waiting there. Tests that run beside each other in one process share their CPU and show as overlapped. Linux only.
- `node scripts/test-cost.js [--before DIR] [files...]` measures CPU and wall seconds per file, median of three runs, four files at a time. With `--before`, it measures another checkout interleaved with this one.
- `node scripts/mutants.js` copies git-listed repository inputs, including workflow files, hooks and rules. It requires the named tests to pass without mutations. Before a full-suite fallback, it restores the original source and requires that same copy to pass the full suite too. A broken baseline aborts the run. `--root DIR` selects another checkout; `--only ID,ID --no-full` confines a rerun to selected bugs and their named files.
- `node scripts/test-coverage.js` uses node:test coverage, which follows the CLI processes a test starts. For each file it lists the lib lines it runs and how many no other file runs. A file with no unique lines is a candidate to merge or delete.
- `node scripts/tests-coverage-map.js run --dir DIR -- CMD` builds `tests-coverage-map.json`, the map crucial mode selects suites from; `merge --expect N --out FILE MAP...` joins the maps of a run's shards. See the coverage map below.

## Coverage map

The suites a change needs come from measured coverage, not imports. The import seed (`tools/tests-map.js`) misses code a test reaches only through the CLI it spawns or loads by name: T427's reviewer planted a bug in `lib/gates/merge.js` that every import-mapped suite passed.

The tool is V8's own coverage. `NODE_V8_COVERAGE=DIR` makes every Node process write a profile of the scripts it ran when it exits, and child processes inherit the variable, so the CLI processes a test starts are counted. With `TC_TEST_COVERAGE_DIR` set, `test/run.js` preloads `lib/tests-coverage-scope.js` into every test file process; it points that file's children at a directory of their own and names the file, so each profile belongs to the test file that caused it. When a test file exits, its profiles are folded into the set of repository files it ran and deleted; the runner folds the rest when the run ends and writes `DIR/tests-coverage-map.json`: `{sha, tests, map}`, each repository file to the test files that ran any of its code. A script counts as run when any of its functions ran once, so a module that loaded counts.

The daily and manual CI runs set it on the three Linux Node 26 shards, which together run every file, and upload each shard's map. The `coverage map` job joins them with `node scripts/tests-coverage-map.js merge --expect 3` into the `tests-coverage-map` artifact. After each daily run the orchestrator pins it with `tower-crane tests map refresh --from-run RUN_ID`, which keeps the declared entries: globs such as `changelog.d/**` and paths V8 never runs, such as `docs/cli.md` mapped to the tests that read it.

## Suite time

The tests gate runs the whole suite once per submission. On 2026-10-19 that took about 28 minutes at its 3 file workers on the 24-core host and was the fleet's bottleneck. In a worker sandbox the suite does about 2800 CPU seconds of real CLI, git and stub work; on the loaded host, which also runs the tests that fail fast in a sandbox, about 4700. 3 workers cannot finish either in 10 minutes even with no timer waits. The worker count the tests gate's command (`gates.tests_cmd`) passes is a request: the host governor grants up to it from the host's free cores ([state.md](state.md#test-threads)). The governor reserves 2560 MiB for each tests gate and merge-queue suite.

The suite is measured on GitHub-hosted runners, not on the host: Tower Crane is not to be the heaviest load there. A `workflow_dispatch` of `.github/workflows/ci.yml` with `profile` set runs two jobs and nothing else. `suite profile against the baseline` runs `scripts/suite-profile.js --baseline <profile_baseline> --runs 3`: the suite at that commit and at the dispatched one, in turn on one runner, three runs each at the runner's three file workers. It fails unless the dispatched commit's median CPU seconds and median longest-file wall time are both lower, and keeps the JSON and the log as the `suite-profile` artifact. `mutation sample` runs `scripts/mutants.js --no-full` and keeps its log as `mutation-sample`. CPU seconds do not depend on the load, and the two commits share a runner, so the comparison holds wherever the runner is. The orchestrator dispatches it on a task's branch:

```sh
gh workflow run ci.yml --ref BRANCH -f profile=true -f profile_baseline=COMMIT
```

## Accuracy: the mutation sample

`scripts/mutants.js` holds 125 planted bugs across the areas where a silent regression costs the most. Each changes a check, bound or guard. The original 31-bug sample below records the historical test cleanup.

After the suite-time work the sample caught 125/125 with `--no-full`. In a worker sandbox at 4ec133e and f8d4eaf, with `--skip` naming the tests that fail only there, 109 were caught (105 by tests, 4 by timeout); the 16 it missed are named for files whose catching tests fail only in a sandbox (the first 9 miss at 425eea2 under the same skips too), and the orchestrator's host run at 8b76e68 caught all 16 by tests.

`npm run check:shared` checks that every mutant's target text occurs exactly once in its file. Missing and duplicate targets fail before tests run, including drift in a mutant outside a scoped selection. `node scripts/mutants.js --check` runs only that validation; `--root DIR` checks another checkout and `--only ID,ID` selects targets. Both the check and mutation runner normalize CRLF source to LF before matching multiline anchors.

The npm command opts into anchor validation with `check-shared-files.js --mutants`. Ordinary shared-check fixtures run without that flag, and mutation full-suite fallback excludes `test/mutants.test.js`: checking pristine anchors after planting a bug would score a survivor as caught without testing its behavior.

Every baseline, mutant and fallback run has a process watchdog. On Linux with a working user systemd manager, it also runs in a separate `systemd-run --user --scope --quiet -p TasksMax=512 -p MemoryMax=4G` scope. Each mutant scope joins the caller's slice, outside any outer capped scope, so nested runs retain the shared slice's resource fence. In a scope the watchdog reads `cgroup.procs`, `pids.current` and cap events; it reads process identities only for those members and previously observed children. A memory catch requires `memory.events`'s `oom_kill`, since `max` also counts reclaim without a kill. Without a scope it tracks process groups, detached descendants and inherited Linux markers through `/proc` (or the platform's process inspector). It stops the run at the process bound and removes remaining children when the runner exits. A cap reached under a planted bug counts as caught with the cap reason; a capped baseline aborts the catalog. `--process-limit N` lowers the process bound for containment probes (2 to 512). An unavailable process inspector or scope launch aborts instead of scoring a kill.

On Windows a snapshot cannot follow the tree: Windows does not reparent an orphan and has no process groups, and a failed CIM query lost the run. Each run there starts suspended in its own job object, created by a PowerShell helper that compiles a small C# class. The job sets `KILL_ON_JOB_CLOSE` and an active process limit at the process bound, and no breakaway flag, so every descendant stays in it, detached ones included. The helper reads the job's active process count every 25 ms and its completion port's limit message, and stops the job when the command exits, the cap is reached or the caller asks. It reports once the job is empty; a member still running after 30 seconds fails the run with `mutant descendants survived containment cleanup`. The helper holds the job's only handle, so the job dies with it if the caller kills it. The helper prints a start line while the command is still suspended, and the run's timeout starts there, so the helper's startup and compile do not count against a baseline-derived timeout.

The runner measures each named file's unmutated wall time in its own capped run, using at most `--jobs` file workers (1 to 4). A mutant's deadline is five times the sum of its files' baseline times, with a 30-second floor for startup on a loaded host. A timeout-only catch retries once at the same deadline. A passing retry clears that catch; two timeouts report `caught-by-timeout`. The summary counts test catches, timeout catches and cap catches separately. Before full-suite fallback, remaining files get their own unmutated baseline and the same deadline calculation, including the timeout retry. A failing baseline never contributes a kill.

Removing a scope can make an already-open cgroup file return `ENODEV`. The watchdog treats this like a missing cgroup, continues cleanup of observed processes, and still aborts on permission or I/O inspection errors.

The scoped watchdog removes a tracked descendant PID when its stat read reports `ENOENT` or `ESRCH`. It retains the runner's own PID and start identity after exit to reject reuse, and signals only process groups whose observed leader still matches. Later ticks inspect current members and still-observed processes, so exited children do not add repeated failed reads to the rest of the run.

Test controller CLIs preload `test/fixtures/account-home.js` to bind owner authority to the fixture home. Spawn drops inherited Node injection before starting an agent, whose sandbox hides the test checkout. Explicit project/rung Node options still apply. The model-config tests run bounded Claude and Codex stand-ins whose command sees a missing preload path, so a leaked fixture preload fails without a live model call.
