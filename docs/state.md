# State

Tasks may carry `stack: { parent, base, parent_sha, repo, linked, synced_base }`. `parent` is the lower task id, `base` is the PR's current target branch, `parent_sha` is the dependency head used for dispatch or the last synchronization, `repo` is the same GitHub repository as the project, and `synced_base` is the last observed main commit. `linked` records successful `gh stack link`. One unmerged dependency chain forms one stack; outstanding sibling branches are not appended to that chain.

`stack_disabled: true` records an unavailable stacks capability or explicit `stack unstack`. It selects ordinary merges, which wait for lower merge evidence before retargeting an existing upper PR. An accepted dependency can still use the ordinary main-based dispatch flow when the repository cannot stack; a submitted dependency requires an available chain.

A successful `stack link` clears fallback markers for its linked members and restores the stack merge gate, including its refusal of admin merges.

When claim or worker spawn readiness depends on an existing stack PR, Tower Crane queries `gh api repos/OWNER/REPO/stacks` outside the state lock and applies linked-state changes only if the affected task snapshot is unchanged. The query runs only when a chain holds two or more unmerged PRs, so a merged dependency needs no check. A spawned worker's gh is limited by its agent file and cannot call that endpoint: spawn runs the query for its task before dispatch, and that worker's claim reads the recorded result. Any other claim queries it itself. A confirmed remote chain clears stale disabled markers; a missing remote link is recorded as unlinked for that member's own chain only. An outage marks only members that have a stack record and a PR, so a dependent without a stack record carries no flag; one left by an earlier outage is cleared once its submitted dependency's chain is confirmed. Transient GitHub errors refuse the readiness check without disabling stacks.

For an unlinked dependent whose lower members all have merge evidence, linking retargets its PR to the project base, removes `stack` and `stack_disabled`, and emits `stack complete` with the former parent, new base and PR number. Its sha is unchanged. Rework notes append only to an existing brief; a brief removed during the append is treated as absent.

The shared generated-conflict preflight runs before automatic refresh from
merge, worktree preparation and spawn. It can also retire a linked dependent
whose lower members all have confirmed merge evidence. It uses the same
snapshot and PR validation as ordinary completed-chain retirement, emitting
`stack complete` before generated repair. This prevents synchronization from
requesting worker rework first. Generated-only conflicts receive a new
submitted head; mixed conflicts retain a prepared merge; unconfirmed remote
conflicts wait. Other stacks keep their existing automatic sync behavior.

`github_stack` holds the unmodified `pull_request.stack` object (or the payload's top-level `stack`) from a trusted payload passed to `stack webhook`, or null when the payload has no stack. The repository and PR number must match a known task. Task show and board sheets expose this metadata separately from Tower Crane's local dependency chain. Webhook metadata does not satisfy a gate, change a submitted head, accept a task or prove a merge.

Stack merges record ordinary `merge` evidence and matching gate audit events for each confirmed task at its own submitted sha and revision. Their command receipts include the remote membership query, every PR head check, bottom-up asynchronous merge requests (`gh api repos/{owner}/{repo}/pulls/{n}/merge-async --method POST` with `merge_method=merge` and `expected_head_sha`) and their status polls, upper PR retargeting and the confirmations. Merge commits keep every accepted head as an ancestor of the project base; the submitted shas remain unchanged. A refused or queued member stops later merges; confirmed accepted lower members retain successful evidence even when the target fails. Terminal POST or job failures retain their reason across status and PR read errors. Unless the PR is confirmed merged at its accepted head, the failure is reported when the PR is read open or when the confirmation deadline expires. Branches are retained while merging a linked chain. Sync emits `stack sync` events for the affected tasks with `ok`, `head`, the parsed abort `reason`, and `failure` (`conflict`, `tool`, or null on success). A moved branch or an explicit conflict report emits rework and appends its reason to the task's brief. A tooling or transport failure preserves unchanged submissions, claims, briefs, gate evidence and stack metadata; the next refresh retries it. A branch moved before a failed push still requires rework. Refresh deferred for a live worker or dirty worktree emits `stack sync deferred`; it does not change the claim. PR linking uses `stack dispatch`, `stack link`, `stack readiness`, `stack unavailable` and `stack link failed` events. An open PR whose head GitHub moved after a lower stack merge, the requested task or a dependent above it, records a `stack head` event with its old and new sha and returns to submitted.

Sync holds the state lock only for its initial read and final compare-and-apply. Its gh commands and branch reads, fetches and pushes run unlocked. Application compares project configuration, stack membership, complete member task records and member events against the snapshot, leaving out hook, startup and spawn session receipts, automation reservation receipts and the orchestrator notice a hook stop writes. A difference refuses application without writing sync events, briefs or task records. Writes to unrelated tasks are preserved by applying to freshly read state.

Linking, completed-chain retirement and unstacking use the same snapshot, unlocked commands and compare-and-apply rule. Automatic linking runs after exit collection commits, outside that mutation. A stale link or unstack result cannot clear a new claim or replace member metadata. Remote PR changes may already have completed when application is refused; inspect them before retrying.

The shared command runner rejects Git and gh calls inside state mutation transactions. Spawn prepares repository directories and credentials before its write; acceptance and review dispatch prepare local CI inputs and snapshots before their writes and reject changed inputs. View rendering starts after the mutation releases its lock and reads current state.

Tests, cleanup, review diffs and local CI use the dependency branch as the base for stacked tasks. A successful sync changes that base to main when the lower task has merge evidence. Old head evidence cannot count after the worker resubmits a refreshed head. Stack merge checks all lower heads first, then pins each member's accepted full head with an ordinary PR merge because GitHub's stack merge command has no head-match option; see cli.md for partial completion and the ordinary admin fallback.

Tower Crane keeps a project's plan and progress in plain files. People and dashboards read them; the `tower-crane` CLI and serve's owner forms write through the same locked, validated functions. An agent that needs to change state runs a command.

## Where

The state directory is the first of:

1. `--state DIR` on the command line
2. `TOWER_CRANE_STATE` in the environment (`tower-crane spawn` sets it for every agent it starts)
3. `.tower-crane/` at the root of the main checkout, found through `git rev-parse --git-common-dir`, so every worktree of the repo shares one state

`tower-crane init` adds `.tower-crane/` to `.git/info/exclude`. State is not committed unless the project chooses to. In a bare repository, `.tower-crane/` sits inside the common git directory.

Commands that need the repository (`worktree`, `spawn`, the gates) use the one Tower Crane runs in; outside a repository, the one that holds the state directory.

## Agent identity

The identity recorded in state and events comes from `--agent NAME`, then `TOWER_CRANE_AGENT`. With neither, the CLI uses `owner` only when stdin and stdout are both TTYs and `TOWER_CRANE_TASK` is unset. In every other case it exits 2 with `no agent: pass --agent NAME or set TOWER_CRANE_AGENT`, before reading or writing state. An empty or whitespace-only identity exits 2 with the same message. Help needs no identity.

Resolving either identity source to `owner` (the terminal fallback included) is refused unless the owner runs the process, and the refusal starts with `owner identity needs a process the owner runs (docs/state.md#agent-identity)` and names the rule that failed:

- `TOWER_CRANE_TASK` is set: a task process never acts as owner.
- `TOWER_CRANE_AGENT` names any identity other than `owner`: a process started as another identity, such as `orchestrator` or a spawned `worker-T1-1`, never acts as owner, whatever `--agent` it passes.
- stdin or stdout is not a terminal, and `TOWER_CRANE_OWNER_KEY` does not hold the owner key. The key is the owner's own credential for scripts and other non-interactive owner commands: `tower-crane owner-key --agent owner`, run at a terminal, creates it (mode 600, in a mode 700 directory) as `owner/key` under the canonical `owner_config_dir` recorded in `project.json` (`~/.config/tower-crane/owner/key` by default) and prints its path, never the key. Every spawn creates that directory and hides it from claude's and codex's sandboxes, and from claude's Read, Grep and Glob tools, so no sandboxed agent reads the key. The CLI captures `TOWER_CRANE_OWNER_KEY` privately and removes it from its environment at command entry, before state discovery or authentication can start a child. Nothing it starts, including Git used to discover the state directory, agents or gates, inherits the key. Terminal checks leave piped stdin unchanged for hooks and command input. An unsandboxed process running as the same user can read the user's files, the key included; the key keeps owner identity out of reach of `--agent owner` alone, not of a process that deliberately reads the owner's secrets.

`spawn` passes the name `<job>-<task>-<n>` (`worker-T1-1`, `reviewer-T1-1`) in `TOWER_CRANE_AGENT`. A sandboxed claude or codex agent cannot write the state files (a codex agent's commands write only its own `HOME`, sessions and broker directory there); its state changes go through its spawn's [state broker](ladder.md#state-broker), which records them under the spawned name whatever the agent passes, allows only its role's commands on its own task, and refuses another identity. Its credential is the token in its private broker directory, made for that spawn and invalid once the agent exits. Its prompt says `you are not the owner; never pass --agent owner` and closes with `run tower-crane with --agent <name> if TOWER_CRANE_AGENT is missing`, so a shell that loses the environment can still record the correct identity.

The credential location for an initialized project comes only from `project.json`, never from the command's `TOWER_CRANE_CONFIG`, `HOME` or `USERPROFILE`. Changing those variables does not redirect authentication or a pinned sandbox denial. An absent, invalid or missing recorded credential refuses headless owner access. For a project without `owner_config_dir`, only an explicit owner at a terminal can record it with `owner-key`; an existing binding is never replaced. Until it is recorded, spawning still works and hides `owner/` under the spawning environment's resolved Tower Crane config directory, where a terminal `owner-key` would create the key. This denial does not establish a binding or allow owner authentication.

## Authority

The owner hands the run to an orchestrator and is asked only when the owner is required. `lib/authority.js` holds the one table that classifies every guarded setting and command, and one check that every command uses:

- **operational**: the orchestrator or the owner. The orchestrator acts under its own identity; the event records that agent, and `project set`, `ladder set`, `ladder harness` and `ladder save-user` events add `"authority": "orchestrator"`.
- **owner-required**: the owner only. When the orchestrator tries one, the command writes nothing it asked for, opens a decision for the owner and refuses with its id. The decision and its `ask` event carry `escalation: { settings, change }` naming the settings and the requested owner-required values, with options `approve` and `decline`. The same open request reuses that decision. Only the owner answers an escalation, from the CLI or the board. After `approve`, the orchestrator runs the same command again: a request whose owner-required settings and values equal an approved, unapplied escalation is allowed once, and the decision records `applied: { at, by }`. Operational parts of the same command are the orchestrator's either way. `decline`, or the owner making the change, leaves the orchestrator's next attempt to open a new decision. A waiver the orchestrator records under an approval carries `approved_by` with the decision id, and counts only while the log holds that escalation's `ask` and the owner's `approve` answer.
- **refused**: no identity makes the change while the task stands as it is. The command writes nothing and names the step that comes first (`rework`); no decision opens.

The owner can run a project by telling the orchestrator, and every row below has a CLI path: the orchestrator makes operational changes itself and asks only for owner-required ones; the owner approves with `tower-crane answer D<n> --choice approve --agent owner`. A row no command changes, `publish`, is requested with `ask --setting publish`; `ask` without `--question` refuses a row a command changes, since that command applies the approval. From the board (`serve --agent owner`) the owner answers decisions, which approves or declines escalations, and changes the ladder (`/api/ladder`) and tier rungs (`/api/tiers`); those writes go through the same check and audit event with `mode: board`. Board controls for the remaining rows are not built yet (T89 part 2).

Every allowed change of a guarded setting appends one `setting` event in the same write as the command's own event, just before it: `detail: { command, actor, mode, settings, approved_by? }`. `actor` is `owner` or `orchestrator`, `mode` is `board` for a write through `serve` and `cli` otherwise, and `settings` maps each guarded setting the command changed to its class. A refused or escalated request records none, and neither does a command that fails after its check: `accept --waive` and `spawn --role orchestrator` apply the owner's approval and audit it only in the write that records the acceptance or the started spawn; unguarded fields such as `name` and `goal` record none.

When the owner's successful write satisfies a request's fields, matching open or approved requests record `applied: { at, by: "owner" }` in that same write. The owner may write additional settings or fields at once; every satisfied request is retired. An open request also becomes answered `approve`, with an owner `answer` event. Failed commands leave these requests untouched, including acceptance that fails a gate and a spawn that never starts. The owner's setting audit uses their own authority, without `approved_by`. A later orchestrator retry needs a new decision, even if the owner has since changed the value again.

Matching preserves the request's target, such as a rung, user file or decision. Ladder/rung objects group fields, so an owner can satisfy an environment request while also writing scope or another rung. Replacement values must match whole: adding keys inside an environment map or routes inside a fallback list does not satisfy a request for a different value. JSON formatting and object key order do not change the value. Orchestrator approval consumption still requires the exact request; only owner-write retirement accepts additional fields.

Budget requests match the owner's written amounts independently of whether those amounts currently raise, lower or repeat the budget. For example, after approving a request to raise hours from 5 to 10, owner writes of 20, 10 and 5 retire that approval at the write of 10. The subsequent orchestrator retry needs another decision. The audit still classifies the owner's decrease or unchanged amount as operational `budget.lower`; operational orchestrator writes do not retire an unused raise approval.

`project set --budget-hours null` and `--budget-tokens null` remove their limits; `task update` accepts the same flags for a task's limits. Removing a finite limit is `budget.raise`, so the owner may do it directly and the orchestrator needs a one-use approval. Task-budget approvals name the task, and a task-budget write cannot retire a project-budget request. Live-budget alerts are owner questions, not setting approvals. `init` accepts the same nullable flags. Other numeric flags retain their numeric-only parsing.

The same rule applies to primary ladder reach grants and task kinds: an owner writing the requested tools, harness, arguments or kind retires the matching request even when the current edit is operational or unchanged. Primary reach requests describe grants, so additional tool or unconfined-route grants in the same owner write are allowed. Only written fields and routes affected by a written harness count; an unrelated model edit does not settle a reach request. Task cancellation and review waivers also retire matching owner requests after their owner-only condition has cleared. Authorization and audits still use the current classes.

Waiver requests include `{ accept, sha, revision, waive, reason }`. Their approval and the recorded waiver must name the same task, SHA and positive revision. Changing acceptance, dependencies or capabilities requires a new approval even when the commit is unchanged. A waiver approval without a revision cannot authorize a new accept or back an orchestrator's waiver evidence; request fresh approval for the current revision.

Release requests include `{ release, holder, claim_since }`, binding the task, holder and claim start time. Renewing that claim keeps the approval usable, but a replacement claim needs a new decision even when the holder has the same name. Browser-kit requests include `{ user_file, servers }`, using the same resolved absolute path the command writes. Changing `TOWER_CRANE_CONFIG` to another target needs another approval, and owner writes retire requests only for their own target file. Legacy approvals without these bindings cannot authorize the corresponding command; request fresh approval.

An interruption audits `task.interrupt` in the write that releases the claim. `task update --interrupt` combines that row with its other guarded changes in one setting event. A mixed waiver request attaches `approved_by` only to owner-required waivers; an operational review waiver retains its own eligibility.

Workers, reviewers and every other identity are refused both. For an operational change they ask the orchestrator (`tower-crane msg --to orchestrator` or a task note), not the owner. An owner-required change they request with `tower-crane ask --question Q --kind setting --setting KEY`, which keeps the decision with the owner. A worker's or reviewer's `ask --kind technical` that names no owner-required setting opens a technical decision the orchestrator can answer; a `spend`, `credential` or `setting` kind stays with the owner (see `decisions.json`).

Tools and MCP servers are operational because choosing what a rung works with is running the project, and the owner's autonomy rule hands that to the orchestrator; the two conditions keep it from widening what an agent reaches. An MCP server runs outside the rung's sandbox, so the orchestrator may opt in only a server already defined in the owner's own harness config (claude `mcp.json` or `.claude.json`, codex `config.toml`, agy `~/.gemini/config/mcp_config.json`); naming another is refused, and the owner adds it. A tool the agent files name (claude tool names, codex features, agy native tool names, pi built-ins) or codex `web_search` re-enables a harness built-in inside the same sandbox; any other tool opens a `ladder.reach` decision. Only opt-ins new to a rung and harness are checked, including rungs a `ladder harness` change moves to another harness. The owner can overrule either condition by making the change. The conditions hold because the rung keeps its sandbox: claude and codex enforce one, so a sandboxed role's rung that a change moves to agy, opencode, pi or command (with the personal fallback routes that follow its harness), or args on those harnesses (agy also checks its args against a safe list), open a `ladder.reach` decision too. A route the owner already put there is the orchestrator's to tune with the same args; the orchestrator rung runs unsandboxed, so only args open a decision there. The sandbox, env, env_file and scope grants, `merge.admin`, `decision_delegation`, budget raises, delegation and publishing stay owner-required.

The research agent ships with network and web tools enabled in code; initializing or tuning its model does not ask for a new grant. Changing its explicit `web_mcp` command or tools is owner-required, including clearing it to return to native web tools. The orchestrator's attempt opens a decision without changing the rung. A setting that widens network access is owner-required under `ladder.reach`; operational built-in opt-ins must keep the existing sandbox network confinement.

`init` checks the same table; with no state to hold a decision, an orchestrator's owner-required `init` setting is refused and it inits without it.

The owner is the resolved name `owner`, supplied explicitly by `--agent owner` or `TOWER_CRANE_AGENT=owner`, from a process that passes the [owner identity rule](#agent-identity): no task variable, no other `TOWER_CRANE_AGENT`, and a terminal or the owner key from the project's recorded `owner_config_dir`; the terminal fallback grants no authority. The orchestrator is an explicit identity that some spawn recorded with role `orchestrator`, or, never spawned, the name `orchestrator` (the owner's interactive session). A name any spawn started as a worker, reviewer or small agent is never the orchestrator, nor is a command the state broker runs, nor a `--agent` that differs from a `TOWER_CRANE_AGENT` naming such an agent. A waived gate counts when the owner recorded it, or the orchestrator for an operational waiver. Any agent may recover a spawned claim when the shared process detector verifies its exit under the state lock. Set `TOWER_CRANE_AGENT=owner` per command, never in a shell profile, where it could override a spawned agent's identity.

## Files

| File | Holds |
|---|---|
| `project.json` | name, goal, repo, base branch, default harness and model ladder, limits, budgets, standards profile, owner policies |
| `tasks.json` | every task and its status, evidence and spend |
| `decisions.json` | questions for the owner and their answers |
| `briefs/<task>.md` | shared task context and optional worker or reviewer sections, kept current by the orchestrator |
| `reviews/<task>-<sha>.md` | the brief's reviewer sections, diff and software gate results prepared by review dispatch; large packets are read from this file to keep argv within Windows limits |
| `events.jsonl` | append-only log of every change, with time and agent |
| `progress/<agent>.jsonl` | the agent's tool activity, `hook progress` rows appended without the state lock; the supervisor watches the file for activity, and no state decision reads it |
| `evidence/<task>/<sha256>.json` | one settled evidence field over 1 KiB, as compact JSON named by its SHA-256; never changes once written ([tasks.json](#tasksjson)) |
| `sketch.md`, `sketch.html` | rendered views; regenerated by `tower-crane render` and after every write |
| `lock` | the write lock, a directory; never edit |
| `logs/<task>-<agent>.log` | output of agents started by `tower-crane spawn` |
| `homes/<agent>/` | the home `tower-crane spawn` builds fresh for each claude, codex and agy agent: its harness config directory with generated settings, instructions and permission profile, `git` and `gh` shims, links to the user's credentials, and `home/`, the agent's `HOME`; plus what the harness writes there (transcripts). Private to the user; `homes/.gitignore` ignores everything. A spawn removes the homes of agents whose process has exited. `homes/.codex/<agent>/sessions/` keeps that agent's codex sessions for usage after its home is gone ([Agent files and homes](ladder.md#agent-files-and-homes)) |
| `brokers/<agent>/` | `broker.json`, the [state broker](ladder.md#state-broker)'s address and token for a sandboxed agent (and its `broker.sock` for claude), while the agent runs; only that agent's sandbox can read it. `brokers/.gitignore` ignores everything |

Each spawn pins its tool runtime in `homes/<agent>/tool/`. `homes/<agent>/tool.json` and the `spawn` event's `detail.tool` record `{sha, version, path}`. `sha` is the tool checkout's HEAD, or null for an installed package without Git metadata; `version` is the package version. The snapshot copies `bin/`, `lib/`, `agents/`, `skills/`, `standards/` and `package.json`, without links back to the checkout. The generated Git and gh shims, harness hooks, notify command and supervisor resolve this snapshot. Its policy is generated by the same tool version. Retries and route fallbacks keep it until the supervisor exits; a later spawn prunes it with the home. A new dispatch, including a rework resume after exit, gets the tool version then installed.

Pinning keeps upgrades independent of live dispatches. On 2026-10-08, moving the orchestrator checkout to T112 (`33d7eb5`) made existing shims read new requirements against policies without `branch` or `repo`. Pushes from T30 and T79 had to be completed by hand. Copying the runtime at dispatch prevents a checkout move from changing a live agent's policy reader or hook protocol. Upgrades take effect on the next dispatch, with no feature flag.

The shim defaults missing `gitPush` to `none`, `gh` to `[]` and `hook` to null. Missing branch and repository default to null and deny remote pushes. Before checking permissions, a pre-T112 branch policy with absent `branch` or `repo` migrates those fields in memory from its recorded task and project; a field state does not record migrates to null, which refuses remote pushes (no branch or no repository to bind them to) and leaves every other command allowed. Migration requires its protected `hook.json` in the same home and matching dispatch agent, task and state environment; it never infers authority from the current Git branch or remote. Missing recorded values or a mismatched binding refuse the call. The policy file stays read-only, and all calls use the same migrated shape and push checks. The historical policy fixture is generated from `lib/agents.js` and the worker frontmatter at `e034a4325677ada9d0752a1acee60483acfd8849`, T112's parent.

Codex homes rebuild `config.toml` and every `<profile>.config.toml` with explicit allowlists for provider, MCP server and per-tool fields. Provider sub-tables keep only named fields: `aws.region` and `aws.profile`, and `query_params.api-version`; a credential-shaped name (containing key, bearer, token, secret or password) never crosses from a sub-table, and `aws.credential_export` and `aws.auth_refresh` stay outside. Unknown fields, credential fields, literal env and headers, and fields with unexpected types are omitted. Named environment-variable references remain for explicit MCP opt-ins; the browser kit also removes `env_vars` and `env_http_headers`. Auth files remain linked to the user's originals.

Codex model and auth-store fields also require their expected scalar types in base configs, profile files and legacy `[profiles.NAME]` tables; arrays and tables are omitted. Claude's `mcp.json` keeps only string `type`, `command` and `url` fields and `args` arrays containing only strings. A nested credential table cannot cross through these settings.

A brief without role headings is shared by worker dispatch and role-filtered brief readers. A brief can add level-two headings `## Shared`, `## Worker` and `## Reviewer`; matching is case-insensitive and headings inside fenced code blocks are ignored. Text before the first role heading is shared; each section ends at the next role heading. The `## Rework notes` heading is also a shared section boundary, so corrections appended by `rework` stay visible to each role. Worker dispatch and `brief get` send shared text followed by the matching role section, and omit the other role's section. Review dispatch sends only reviewer sections alongside the diff, acceptance and gate results. `brief get` infers the role from a `worker-` or `reviewer-` agent name, or accepts an explicit `--role`; owner and orchestrator identities see the full brief by default. `brief set` warns on stderr when it finds a reviewer section without a worker section.

All JSON files carry `"version": 1`. Writes go to a temp file in the same directory and are renamed into place. A refused state mutation writes nothing. `accept` can record software gate results before refusing acceptance.

### Schema compatibility

`project.json.schema_version` is the project-wide compatibility version, currently `1`. `init` records it; an absent field in an older project means `1`. File `version` fields describe the individual envelopes. A malformed known field still fails validation.

Additive fields, decision and task enum members, evidence types, and event commands do not require a schema bump. Readers retain unknown fields and non-empty enum strings when writing unrelated records. Unknown evidence types remain opaque and cannot satisfy known gates. Readiness, dispatch and gate acceptance refuse task values that this tool cannot interpret, including unknown kinds, tiers, sizes, statuses and capabilities. They also refuse an unknown decision status when that decision lists the task in `blocks`; unrelated tasks remain usable. Command arguments still accept only supported values. A new status whose semantics cannot be handled by these rules needs a breaking bump.

Live-spend readers also retain future non-empty state and error-class strings. They still require a positive integer sampling interval. An incompatible supervisor skips its final live sample after worker closure, leaving reconciliation to a compatible collector.

An unfamiliar task status retains its unexpired claim in both resource-lock and worker-capacity accounting. The recorded lease deadline still applies; a status change alone never frees a live lease. Automatic recovery keeps failed review evidence but reports `waiting` for an upgrade when task routing values are unsupported. It leaves the tier, range, status, claim and escalation history unchanged. Manual rework refuses before changing state or the brief.

A breaking change raises `schema_version` before publishing incompatible payloads. The migration writer must hold the state lock and atomically publish the project marker before changing other files; readers check it before validation and again before returning a snapshot or reporting a payload error. A tool refuses reads, mutations and new spawns when the version exceeds its supported schema, with an upgrade message. There is no automatic downgrade or generic migration command.

A running supervisor that encounters the marker, or an unsupported value affecting its own task, stops lease renewal, state writes, retries and automation. This includes an unfamiliar decision status that lists the task in `blocks`. It reports the incompatibility and keeps output capture and the broker alive until the current worker exits, without signaling that worker. The broker refuses incompatible state commands. The supervisor then exits `1`; an upgraded tool must recover the lease and collect usage. Supervision stays stopped even if the marker is subsequently reverted. Tools pinned before this compatibility contract cannot gain it at runtime; drain those supervisors before the first breaking migration.

### Lock

Every command that writes in the state directory holds the lock while it reads and writes, `render` included. Reads take no lock.

A writer prepares a private `lock.<pid>.<random nonce>.new` directory for each attempt and takes the lock with one atomic rename to `lock`. That directory holds one file named after the writer's random nonce, with its pid, host, pid namespace (`pidns`, the target of `/proc/self/ns/pid`, or null where there is none), process identity and time. Linux markers record `start_ticks` from `/proc/<pid>/stat` and `boot_id` from `/proc/sys/kernel/random/boot_id`; unreadable start ticks are omitted, and an unreadable boot id is null. The rename fails while `lock` holds such a file, so one writer holds it at a time. CLI commands, harness hooks and brokered writes use the same acquisition bound of 60 s, matching the stale-marker window and allowing startup bursts to drain. Retry sleeps start at 10-19 ms, double to 100-199 ms, and include random jitter; each sleep is capped by the remaining time. The deadline uses a monotonic clock, so wall-clock changes do not shorten or extend it. A holder still alive at the deadline causes exit 3. An `ENOENT` or `EEXIST` from concurrent cleanup retries within the same deadline with a fresh private directory. A missing state directory is still refused with the initialization instructions.

After acquisition, a writer sweeps abandoned staging directories older than 60 s. A staging name whose pid is visible and alive is left alone, even if its marker is not written yet or its timestamps look old. Cleanup only unlinks that directory's marker and removes the directory if empty. A writer whose staging is removed by a sweeper in another pid namespace retries; a rename that arrives without its marker does not grant the lock.

A marker's holder and modification time are read through one opened file descriptor, so they refer to the same file even if its path is replaced. The holder is checked by pid and start ticks only when it ran on the same host in the same pid namespace: a command sandbox gives each command a namespace of its own, where a live holder in another one looks gone, and breaking its lock would let two writers save over each other. Matching start ticks identify a live holder, which keeps its lock regardless of marker age. A missing process, a zombie or mismatched start ticks identifies a dead holder and permits immediate reclaim. A mismatched readable boot id on the same host also permits immediate reclaim, even if the pid namespace changed after reboot. An unverifiable holder becomes stale after 60 s: this includes older markers without start ticks and platforms without a readable process identity. A marker without `pidns`, from an older writer, counts only by age on hosts that have pid namespaces. The next writer breaks it by deleting that file by its name, then the directory if it is empty. A name is never reused, so breaking a stale lock cannot remove a newer holder's, however the writers interleave. Successful cleanup retries consume the same deadline and jittered backoff as contention retries. Reclaiming a dead holder or removing an empty lock at the deadline permits at most one final acquisition attempt; another failed attempt exits 3. If a stale lock cannot be removed, or staging cleanup prevents acquisition throughout the bound, writers exit 3 after 60 s and say so.

`tower-crane init` writes the default harness and ladder (see below), `limits` as shown, and `budget` values of `null` (no budget) until `tower-crane project set` gives them. `limits.workers` caps worker slots held by live leases, unclaimed worker spawns and interrupted supervisors still stopping; `lease_minutes` is the default lease. `repo` defaults to the GitHub slug of the `origin` remote, `base` to the branch checked out in the main checkout.

`owner_config_dir` implements the credential trust rule for T101 F3 ([review #92](https://github.com/agent-sh/tower-crane/pull/92)). The first `init` may read the owner key from the environment's config directory exactly once, only while creating new state, and pins that directory's absolute, canonical path into `project.json`. Once bound, owner authentication and sandbox denials use only this recorded directory; the caller's environment is never consulted for the credential location. No `project set` flag changes the binding. When `project.json` already exists, even `init` authenticates against its recorded directory and refuses to replace the project. A project without a binding requires an owner-authorized repair: an explicit terminal owner runs `owner-key`, which records the directory under the state lock and logs an `owner-key` event. Owner authentication has no automatic fallback to the environment. Unbound projects can spawn sandboxed agents: their denial hides the owner directory under the spawning environment's resolved config directory without recording a binding. Invalid bindings still refuse validation and sandboxed spawning.

Worker dispatch, claim and expired-lease renewal use the same slot count under the state lock. A successful worker `spawn` event without a claim of its own records `reserved: true` and reserves one slot until that task's generated agent claims, a matching exit receipt is recorded, the monitor records the attempt with `active: false`, or `lease_minutes` pass with no claim since the attempt's latest `spawn`, `spawn retry`, `spawn fallback` or `spawn phase` event, counted from the scheduled relaunch when a `retrying` phase records `backoff_ms`. `spawn session` receipts replay an earlier attempt's detail and neither move the reservation's pid nor extend it. A lapsed reservation stays lapsed: later monitor records do not revive it, because another holder may have taken the slot. The claim consumes its own reservation and then holds the slot by lease, without counting twice. Reservations persist through supervised retries, route fallbacks and backoff. Launch failure commits no spawn event and holds no reservation. A full limit refuses dispatch before launching a process, writing a home or recording spend, and names the task and agent holding each slot. Reviewer and other non-worker jobs do not reserve worker slots.

The holders are a function of the event log, the task leases and the clock, identical for every observer. Slot counting never probes processes: a sandboxed worker cannot see peer pids, and a probe that freed slots only for the orchestrator would let dispatch pass and the claim fail. Hidden or unknown pids therefore never release a reservation, and spawns without the `reserved` marker, recorded before reservations existed, hold none.

If an expired pre-claim already belongs to the generated worker, dispatch renews it under the spawn lock to the default lease duration, preserving its agent, `since` and `from`. The live lease holds the slot before supervision begins. Launch failure commits neither the lease renewal nor its receipt.

`base` names the branch used to create new task branches. `worktree` and `spawn` fetch it from origin into `origin/<base>` before creating a branch, then use the fetched commit if the local base is missing or is its ancestor. A local base that is ahead or has diverged is kept, with both commit SHAs reported on stderr, and the local branch is never moved. Task branches start from the selected commit SHA with no upstream branch. When origin has no such branch, the local base is used with a stderr note; if neither has it, the command refuses. Repositories without origin use the available local base or `origin/<base>`. For a dispatch, the caller runs `worktree ID [ID ...]` once before starting workers. It validates every task id, fetches the base once if any task needs a new branch, and creates all worktrees serially from that SHA. Callers serialize preparation within the repository across worktrees and state directories; parallel workers then reuse the prepared trees without fetching. A later dispatch fetches again even if the tracking ref did not move. A `cannot lock ref` or `incorrect old value` failure retries once after 100 ms before reading the tracking ref. Each fetch and missing-branch verification has a 60 s timeout. An unpack failure is usable only if a fresh origin read proves another caller already imported that exact tip. Other fetch failures, including a second ref-race failure, create no task branch and record no branch or event in state.

`ci.local`, when present, selects local CI instead of hosted checks: `{ "command": ["python3", "tools/check.py"], "timeout": 120 }`. The CLI writes it through `project set --ci-local JSON` or `init --ci-local JSON`; `null` clears it. The command is a nonempty string argv with a nonblank executable and no NUL bytes. Arguments are preserved, including empty strings. The timeout is required in positive seconds and must fit Node's 2147483647-millisecond timer range. No timeout is chosen implicitly. Other fields under `ci` are preserved.

`gates` is an optional object with `tests_cmd` (the full test shell command), `clean_cmd` (the cleanup shell command prefix) and `tests_proof_cmd` (the expensive-mode scoped shell template with `{tests}`). Commands must be non-blank strings without NUL bytes; absent or null means unpinned. They are operational ([Authority](#authority)): the orchestrator or the owner sets or clears them through `init` or `project set --tests-cmd CMD --clean-cmd CMD --tests-proof-cmd CMD`. Prove and run-only require `tests_cmd`; clean requires `clean_cmd`. An unpinned project does not block: when the orchestrator or the owner runs `check tests`, `check clean` or `accept` and a needed pin is missing, the engine pins the detected command under that identity first. `tests_cmd` becomes `npm test` when the repository's `package.json` has a test script other than npm's placeholder; `clean_cmd` becomes the configured cleanup tool: `TOWER_CRANE_CLEAN_CMD`, else `deslop` on PATH, else the deslop plugin's `~/.agentsys/plugins/deslop/scripts/detect.js`. Each pin logs a `gates pin` event with `key`, `value`, `from` and `authority`, and `status` lists pins that still stand. Workers and reviewers pin nothing, and a gate with nothing detected refuses as before. Tests mode none needs no command. Gate flags `--cmd`, `--proof-cmd` and a non-blank `TOWER_CRANE_CLEAN_CMD` can only repeat the corresponding pinned value after whitespace trimming. They refuse a different value before any process runs. Clean appends the checkout directory, `--base=SHA` and `--json` to its prefix.

`gates.executors` is a positive integer, default 2, that caps automation executors running at once on this host ([events.jsonl](#eventsjsonl)). The default fits one full suite at tests concurrency 3, about 6 processes, so two keep tests under half the cores of a 24-core box. The orchestrator or the owner raises it with `project set --executors N` on a larger machine.

`gates.tests_timeout_min` and `gates.clean_timeout_min` set positive minutes per test or cleanup shell invocation. Fractions are allowed; the rounded duration must be at least 1 ms and the duration cannot exceed Node's 2147483647 ms timer range. Each defaults to 20 minutes when absent or null, preserving the original gate budget for existing projects. Set a budget that fits the project's measured suite under local load. `init` and `project set` accept `--tests-timeout-min MIN` and `--clean-timeout-min MIN`; `null` clears either setting. Both are operational, and `project show` prints their effective values. Tests uses its budget separately for the full suite, scoped head proof and reverted proof. Automation uses these same settings for gate executors and the merged-head suite. A budget change applies to the next invocation and does not invalidate successful command evidence.

`merge` is an optional object with boolean `keep_branch` and `admin` fields, both defaulting to false. `keep_branch: true` omits `gh pr merge --delete-branch` so retained worktrees can keep their task branches; it also keeps branches without a worktree. After a merge is recorded, and after a task is cancelled, Tower Crane removes that task's worktree and then runs `git worktree prune`. It only removes the worktree of an accepted or cancelled task, and only one whose real location, with links resolved, is under the worktrees root. A worktree with uncommitted changes stays, and so does every worktree while `keep_branch` is true; the event names the reason. Each outcome is a `worktree removed` or `worktree kept` event for the task, naming the path. Task branches are not deleted locally. Only owner-set `admin: true` (owner-required) adds `--admin` for repositories solely owned by the project owner, as allowed by SHARED.md. A command argument cannot enable admin merging; `merge --admin` is refused. Neither option skips Tower Crane's acceptance gates or its accepted-head check.

Set these fields through `project set --merge-keep-branch true --merge-admin true`, or the same flags on `init`. They accept JSON true, false or null. Null clears that field, preserving other merge settings and removing an empty merge object. Changes to `merge.admin`, including clearing or setting an unchanged value, are owner-required; `keep_branch` is operational ([Authority](#authority)). Refused changes write no settings. `project show` prints both resolved defaults.

`decision_delegation` is an optional owner-required policy. Its `orchestrator_technical` boolean defaults to true when the policy or the key is absent, so the orchestrator answers technical decisions by default. The owner sets it to false with `project set --decision-delegation '{"orchestrator_technical":false}'` (or the same flag on `init`) to keep technical decisions with the owner; `null` clears it back to the default. Setting, repeating or clearing it is owner-required and uses the shared approval and audit path. While it is not false, the orchestrator may answer a decision that is technical: an `ask` with `--kind technical` starts technical unless it names an owner-required setting or carries `--owner-required`, and the owner marks or unmarks one decision with `decision delegate DID --technical true|false`; `--technical true` also lifts a spend, credential, setting or `--owner-required` reason, never an escalation.

For technical delegation, `lib/authority.js` must resolve the explicit caller as the orchestrator. A generated name such as `orchestrator-T1-1` is recognized through its recorded spawn role; an unsandboxed worker cannot claim the literal `orchestrator` identity by passing `--agent orchestrator`. Answers keep the caller's identity in `answered_by` and the event's actor fields.

Every use of `init --ci-local` or `project set --ci-local`, including setting the current value or clearing it with `null`, is operational: the orchestrator or the owner. Refused calls write no settings or events.

`ci.local.by_kind` is an optional object mapping known task kinds (`code`, `docs`, `research`, `design`, `ops`) to overrides, for example `{ "code": { "args": ["--native-extended"] }, "ops": { "args": ["--lab"], "timeout": 300 } }`. An override has exactly one of `command` (a replacement argv with the same validation as the default) or `args` (a string argv appended to the default, allowing an empty array). Optional `timeout` replaces the project timeout and uses the same range. Unknown fields and invalid mappings are refused. Missing kinds inherit the default. A task's `ci_local` override takes precedence and resolves directly against the project default, without combining with its kind mapping. These overrides apply only when `ci.local` is present.

`review`, set through `project set --review-policy JSON` or `init --review-policy JSON` by the orchestrator or the owner, holds optional `small_lines`, `small_files`, `risk_paths` and `prices`. The line and file limits are non-negative safe integers, defaulting to 100 changed lines and 5 files: a short patch across a handful of files fits a focused review. They raise an easy task to medium when exceeded; they never lower the task's tier. `risk_paths` is an array of repository-path globs with the tests gate's glob syntax, defaulting to empty. A matching old or new path, or a binary diff, raises review to at least hard. `prices` maps configured model IDs to non-negative dollar rates per million tokens: `{ "input", "cache_write", "cache_read", "output" }`. All four rates are required for each model. IDs compare with whitespace trimmed and case folded; provider prefixes remain distinct. `null` clears the policy and restores diff defaults without cost promotion.

Review selection starts at the task's tier, raised by the diff or failed reviews at the current head and revision. Each failed independent review climbs one tier, capped at research. It takes the first runnable tier at that level or above, then promotes to a stronger tier when its measured median review cost is no higher. The `review` rung is the fallback when no tier rung can run. The reviewer may use the builder's model because it receives a clean context. Builder identity comes from the submitter's worker spawn route, not its reported spend; without a recorded route it uses the current task tier. Explicit model names take precedence over profiles; readable Codex profiles resolve to their model. Profiles resolve from the user's origin configuration, matching dispatch even when the caller's home is isolated: `<profile>.config.toml` or `[profiles.<profile>]` in `config.toml`. A readable standalone profile or a named profile table can inherit the base config's top-level model. Unknown profiles retain their profile identity, rather than inheriting the caller's default model. Spend entries and rung models use the same case-folded price identity before cost comparisons. A running reviewer's live entry is not a cost sample until exit collection finalizes it. `validate` warns per open task only when no reviewer rung can run.

Review dispatch computes the submitted diff before taking the spawn state lock. Under the lock it rechecks software gates and refuses if the submitted SHA or configured base changed. It chooses the reviewer from the current tier, policy, history and ladder. A refusal starts no reviewer and writes no review packet; retry to prepare the current diff.

Cost samples use T31's `spend.entries` across all tasks, restricted to native `rung: review` or spawned reviewer entries. Worker usage, including usage by the submitter, is excluded. Inclusive input, cached input and output must all be known. Recorded `cache_write`, when available, is subtracted from fresh input and priced separately; older records price non-cached input at the higher of input and cache-write rates. Unknown components cannot justify promotion. Model IDs compare with whitespace trimmed and case folded before spend is matched to prices; every Claude rung expands `BUILTIN.claude_aliases` to the release ID its spend records, and native Claude review-spend aliases use the same table when matching samples to prices. Explicit Claude reviewer candidates use the same plain Anthropic or global Bedrock model identity as spend; price a Bedrock Opus route under `global.anthropic.claude-opus-5-5`. Use rates for the provider, cache lifetime and context size being measured. Aggregate T31 records cannot reconstruct per-request long-context surcharges or unlogged thinking tokens; missing output remains a measurement limit.

Worktree creation has no added timeout and uses Git's native initialization lock. The CLI unlocks only after checkout and its hooks finish. It refuses to reuse an unfinished locked registration, including one whose CLI died while a Git child survived or before HEAD was written. An unfinished registration for any task refuses the whole batch call; worktrees prepared earlier in the call can remain. There is no automatic recovery by pid or age. After Git and its children finish, inspect the worktree, then run `git worktree unlock <path>` for a complete checkout or `git worktree remove --force <path>` for an incomplete one. Existing branches and completed worktrees are reused offline. If an add later in a batch fails, earlier tasks can remain prepared.

Task preparation, temporary gate preparation and stack sync run `git worktree prune` before using worktree registrations. Gate cleanup prunes after every removal attempt, including successful removals. This clears orphan admin directories, including empty read-only `commondir` and `config.worktree` mount points recreated by a sandbox after removal. Git owns admin-file writes and initialization ordering; Tower Crane does not synthesize or repair those files. Prune preserves locked registrations while another checkout or its hooks are running.

A merge or cancel retires the task's worktree after its state change is recorded, and only for accepted or cancelled tasks. A `worktree removed` event records each removal. The worktree stays, with a `worktree kept` event whose `reason` says why, when `merge.keep_branch` is set, when git still has it locked, when a link in its path leads outside the worktrees root, when a worker or reviewer recorded for the task has a process or supervising monitor that has not exited, when it has uncommitted changes, or when the task was sent back or claimed after the check and before the delete. The task is read again under the state lock right before the delete, and its `retiring` marker is written then; git itself runs outside the lock. Claim, rework and spawn refuse a task whose marker is live, so nothing takes the worktree while git removes it. The outcome event clears the marker. Each retirement ends with `git worktree prune`.

### Ladder

The ladder says which harness, model and effort runs each kind of work. It has seven rungs:

Pi uses a generated config home and tool allowlist, with credential files linked to the original user. Pi has no command sandbox or native MCP; a rung with `mcp` on pi is refused. Its `args` accept only `--no-session` and `--verbose`. Moving a sandboxed role to pi remains owner-required. Dry-run reports `home.mcp_supported: false` and `home.sandbox: false`; its startup receipt names the generated instruction file and marks every house rule as `read`, since context discovery is disabled, and records `sandbox: false` with `confinement: "unconfined"`.

| Rung | Runs |
|---|---|
| `orchestrator` | planning, briefs, dispatch, gates and merges |
| `easy`, `medium`, `hard`, `research` | a task at that tier (see `tier` under tasks.json) |
| `review` | clean-context reviews |
| `small` | small mechanical checks |

`harness` is the default for every rung that does not name its own, so moving everything to pi or opencode is one field (`tower-crane ladder harness pi`), and a rung with its own `harness` keeps it (a split setup). `harness` is one of `claude`, `codex`, `opencode`, `agy`, `pi`, or `command`. A rung's fields:

| Field | Applies to | Meaning |
|---|---|---|
| `harness` | all | overrides the default harness for this rung |
| `model` | all but `command` | model id; pi also takes `provider/id`, opencode takes `provider/model` |
| `profile` | `codex` | codex config profile |
| `provider` | `pi`, `claude` | pi provider name; claude takes `anthropic` or `bedrock` |

| `tools` | `claude`, `codex`, `agy`, `pi` | tools the role's agent file leaves out that this rung opts back in to: claude tool names (`WebFetch`), codex feature names (`multi_agent`) or `web_search`; agy native tool names such as `search_web`; pi built-ins (`read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`) |

| `scope` | all | owner-required: systemd user scope properties as an object of non-blank string values, e.g. `{"CPUQuota":"200%","MemoryMax":"8G"}`; `{}` disables |

`sandbox`, `env`, `env_file` and `scope` also apply at project level. They are owner-required ([Authority](#authority)): the owner may set, clear or repeat them through `init`, `project set` or `ladder set`; once state exists, an orchestrator may apply the identical request after owner approval. Rung environment variables override project variables with the same name; both override the environment file, which overrides the inherited process environment. A rung's `env_file` replaces the project file. Each specified rung sandbox field replaces that project field: `write: []` removes the project extra paths for that rung. A rung `scope` replaces the whole project scope, so `{}` disables it for that rung. Clearing the rung field restores the project default. Extra writes are added to the role's normal writable paths. Harnesses without a sandbox renderer receive environment settings but do not enforce `sandbox`.

Paths in `sandbox.write` and `env_file` accept `~` for the original user's home, even when spawn runs from an isolated orchestrator home. Relative paths resolve from the repository root. Sandbox grants use real paths, including symlink targets. Environment values are literal strings and do not expand `~`, `$VARIABLE` or commands. Variable names use letters, digits and underscores and cannot begin with a digit. `HOME`, `USERPROFILE`, `PATH`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR` and `TOWER_CRANE_*` are reserved so environment settings cannot replace the isolated home, command shims or task identity. NUL bytes are refused.

Agent launches discard `NODE_TEST_*` values from all environment sources after merging them, including on retries and fallback routes. The supervisor also drops inherited test-runner variables. A parent `node --test` runner's context must not make an agent's own test run skip every file.

The env file supports blank lines, `#` and `;` comment lines, `NAME=value`, unquoted backslash escapes and line continuations, single-quoted multiline values, and double-quoted multiline values with systemd's escapes for `"`, `\`, `$` and backticks. There is no shell evaluation, variable substitution or `export` prefix. An initial quote delimits the whole value; quotes inside unquoted text remain literal. Duplicate assignments use the last value. Invalid assignments, reserved names, unfinished quotes and unreadable files fail the spawn with a path and line or error code, without printing contents. The CLI supervisor reads the file once for each route and keeps those values for same-route retries; a route switch reads the target route's file and a fresh dispatch rereads it. Dry-run never reads the file. Only the path is saved in project, rung and dispatch configuration. File variable names and values are absent from generated settings, events, job files and CLI output. The monitor's state-writing subprocesses do not inherit them. `env` values from the project or a rung are stored only in `project.json`, and those of a personal fallback route only in the user file: events (including `ladder set`, `project set` and every spawn, retry, fallback and exit event), the spawn receipt, the spawn job file in `~/.cache/tower-crane` and spawn output name each variable with the value `[redacted]`. The dispatching CLI hands the values to the spawn monitor once each, however many job fields name them, in its `TOWER_CRANE_SPAWN_SECRETS` environment variable, which the monitor removes before it starts any process. Values too large for one environment entry (Linux caps one at 128 KiB, Windows at 32767 characters) go instead to a 0600 `secrets.json` beside the job file, named by `TOWER_CRANE_SPAWN_SECRETS_FILE`, which the monitor deletes when it reads it; a monitor that never starts leaves that file until the dispatch removes its spawn directory. No value travels in argv. A process listing (`ps -eww`, `/proc/<pid>/cmdline`) shows no value; a claude sandbox's own PID namespace hides other agents' `/proc/<pid>/environ`. Session resume compares routes by variable names, so a changed value alone does not prevent a resume. `test/secret-canary.test.js` places a unique canary in rung and project env, an env_file and the harness credentials, then scans every file, event, output and process listing a run leaves, on success, a harness crash, a fallback switch and a supervisor stop; its opt-in live tests (`TOWER_CRANE_LIVE_CLAUDE=1`, `TOWER_CRANE_LIVE_CODEX=1`) also probe another agent's view of a running agent's `/proc` entries and home and scan the real harness transcripts and sessions. Harness output and transcripts are persisted as usual, so agents must not print secrets or put them in prompts.

`scope` wraps the agent process itself on the host with `systemd-run --user --scope --quiet --expand-environment=no -p PROPERTY=VALUE ... -- COMMAND`, so its descendants inherit the limits. It applies to every harness and every retry, and the agent environment gets `TOWER_CRANE_SCOPED=1`. Property names contain ASCII letters and digits and begin with a letter; values are non-blank strings without NUL bytes or newlines. Systemd validates property support and values. Real spawn refuses configured scopes without Linux or an executable `systemd-run` on PATH; failed access to the user manager or invalid properties fails the launch. Unconfigured scopes keep portable spawning, including Windows. Dry-run renders the wrapper without invoking systemd. Environment expansion of command arguments is disabled so literal `$VAR` and `${VAR}` in briefs and diffs cannot expose agent environment values in prompts. Systemd versions that lack `--expand-environment=no` reject the scoped launch; there is no fallback with expansion enabled. The host CLI needs a working user systemd session, but the command sandbox does not need its bus socket. `sandbox.user_bus` is unsupported: Codex blocks AF_UNIX connections to that bus even when its directory and environment are exposed. Granting the bus would also expose other user services and processes launched by the user manager outside the command sandbox.

Both rendered sandboxes enable network access, including TCP loopback binds and connections. The opt-in real Codex worker test in `test/sandbox-extensions.test.js` checks a loopback server and client along with the toolchain-cache lock and environment-file delivery.

Inside a worker sandbox there is no root mapping: the harnesses launch bwrap with `--unshare-user` and no `--uid`, so a root-owned host file appears as uid/gid 65534, and a test that asserts root ownership fails there. Gate commands run on the host, outside the sandbox, so the tests gate sees the real ownership of the submitted commit. Tests that need the host are listed in `tests.host_only` (see below).

Spawn replaces the inherited `TOWER_CRANE_SANDBOX` value with `1` for sandboxed claude and codex roles and `0` for unsandboxed roles and other harnesses. The board browser test helper uses it to disable Chrome's nested sandbox under the outer command sandbox. Only sandboxed launches redirect browser HOME, crashpad, cache and shared-memory temp files into a per-browser temporary directory; no extra writable paths are granted. Host launches retain the original environment, ignored stderr and flags, including the existing root `--no-sandbox` exception. See [ladder.md](ladder.md#agent-files-and-homes) for the opt-in live worker probe.

Supervision defaults are `retries: 5`, `backoff_ms: 30000`, `max_backoff_ms: 600000`, `stall_ms: 300000`, `usage_ms: 30000`, and `progress_paths: []`. `usage_ms` is how often the supervisor reads live usage (see `spend.entries`). Values below `1000` are clamped to `1000` ms when the rung runs. A monotonic deadline bounds periodic reads even when state-file notifications wake the supervisor; unchanged readings write nothing. Each launch resets the deadline, and every completed attempt gets a final reading before any retry or fallback. The 2026-10-07 Bedrock/Luna incident lasted more than ten minutes and ended worker-T8-1 attempts 2 and 3 with a rate-limit and temporary-unavailability error ([incident receipt](https://github.com/agent-sh/tower-crane/pull/21#issuecomment-6027888067), [recorded harness fixture](../test/fixtures/bedrock-outage.json)). Five additional reruns wait 30, 60, 120, 240 and 480 seconds, totaling 930 seconds (15 minutes 30 seconds). This extends recovery past that observed window while bounding the paid loop at six attempts. Harness-internal reconnect time adds to the scheduled waits. Each delay remains below the ten-minute cap; rungs with larger budgets reach that cap. The supervisor keeps the lease throughout the waits. A five-minute quiet interval avoids flagging brief pauses between tool calls. A stall requires both stale progress and unchanged CPU ticks, so a busy build remains running.

`progress_paths` adds relative files or directories inside the worktree to the durable log and claimant events that always count as progress. Directory checks skip symlinks, `.git`, `.tower-crane` and `node_modules`. Absolute paths and `..` components are refused. Linux samples the harness and descendant CPU ticks. Without CPU metadata, the supervisor keeps the lease but does not infer a stall from quiet output alone.

`fallbacks` lives only in the user file `~/.config/tower-crane/config.json` (or `TOWER_CRANE_CONFIG`), under `ladder.RUNG.fallbacks`. For example, `{ "ladder": { "hard": { "fallbacks": [{ "harness": "codex", "profile": "astra", "effort": "high" }, { "harness": "claude", "model": "fable", "effort": "high" }] } } }` applies the same personal routes to every project's hard rung, even when the project defines its own primary. A user rung containing only fallbacks does not replace the primary defaults. Remove the field or set `[]` to disable it. `ladder set RUNG --fallbacks JSON` replaces that personal list; `--clear fallbacks` removes the override and `--fallbacks '[]'` empties it. These edits cannot be combined with primary-field edits. They preserve other personal settings and project primaries; clearing a fallback-only rung removes the empty rung so defaults still resolve. Project fallbacks remain refused. Each changed route field uses the primary field's authority class, including clearing owner-required fields. Tools, MCP opt-ins and newly unconfined routes use the same checks as primary routes. A one-use approval binds the user file path, rung and complete replacement list; invalid lists and refused requests write neither the user file nor a setting audit.

An owner fallback write replaces the whole list and retires matching requests independently of which route fields currently differ. This includes writes that only tune a model or repeat the existing list. Authorization and audit still classify the actual changed fields, so operational orchestrator tuning leaves an unused owner approval pending.

Personal fallback authorization compares the old and proposed personal routes for that rung. A grant on a project's primary cannot authorize a grant in this shared file. Inherited and explicit harness selections are distinct: an inherited route does not authorize forcing that harness in another project. A route without a harness is checked across every harness compatible with its fields, since other projects may resolve it differently. New privileged tools, unconfined routes and argument grants require the owner under the existing authority rules; existing personal grants still permit operational model tuning. Specifying a sandboxed harness keeps the route's interpretation fixed.

Claude primaries and personal routes may name `provider: "anthropic"` or `"bedrock"`. For an Anthropic hard primary on Opus, `{ "ladder": { "hard": { "fallbacks": [{ "provider": "bedrock", "model": "opus" }] } } }` tries the same model on Bedrock first after the primary exhausts its outage retries. Reverse the provider names for a Bedrock primary. No provider switch is enabled by default. Without `provider`, Claude keeps the user's harness provider settings.

An explicit Claude provider overrides inherited Bedrock, Vertex and Foundry selectors and model settings. The aliases in `BUILTIN.claude_aliases` (`lib/ladder.js`, snapshot in `docs/builtin-ladder.json`) resolve to full ids: `opus`, `fable` and `sonnet` to `claude-opus-5-5`, `claude-fable-5-1` and `claude-sonnet-5-5`. Bedrock uses `global.anthropic.` model ids; Anthropic uses plain ids. Regional Bedrock ids supplied on an explicit route are converted to the global inference profile. Provider routing settings come from the original user's Claude config and environment, even through isolated homes. Bedrock receives absolute paths to that user's AWS config and credentials files, never copies of their contents.

`ladder show` reports missing configuration for explicit Claude providers. Anthropic needs the presence of `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `CLAUDE_CODE_OAUTH_TOKEN` in the inherited or configured launch environment, a linked `.credentials.json` login file, or the user's `apiKeyHelper`. Bedrock needs an AWS region from environment, Claude settings or the selected AWS config profile, plus local authentication configuration: AWS credential variable names, web identity or container credential variable names, an AWS credentials file, SSO/role/process configuration for the selected profile, or a Claude AWS helper. Checks include project and rung `env` using variable names and safe routing fields; they do not inspect credential values, execute helpers, validate logins or query provider access. A configured `env_file` defers readiness to the real launcher, which reads the file and fails on read or parse errors. Preview and `ladder show` never read that file. Generated Claude settings leave AWS routing in the launch environment so file and literal overrides take effect. Credentials stored only in Claude settings env must already be inherited by the spawning process. Missing primary configuration refuses dispatch; unavailable fallback providers are skipped by the existing supervisor.

Every spawned harness receives `TOWER_CRANE_CONFIG` with the absolute path resolved in the spawning environment. This preserves the original user file through isolated orchestrator homes, nested worker dispatches and fallback switches, including when the caller uses the default location or a relative override.

A fallback without `harness` uses the primary route's resolved harness. It inherits the primary `supervision` unless it names its own. Research Claude fallbacks also inherit the primary `web_mcp` unless they supply their own. Other harnesses do not inherit it. An inherited or explicit web MCP cannot combine with `mcp`. Other route fields are independent, so model, profile, provider, args, tools and environment settings from one route cannot bleed into another. Project environment, sandbox and scope defaults still apply to each route. Nested fallback lists and malformed route shapes are refused. `ladder show` prints the list and its user-file source; JSON rungs carry `fallbacks` and `fallbacks_from: "user"` when configured. Its `problems` reports routes with incompatible harness fields, missing models, missing executables or unavailable Codex profiles. Profiles may come from `[profiles.NAME]` in `config.toml` or `NAME.config.toml`; a profile needs a model there, in the base config, or in the route. These local checks do not query providers for model access. Unavailable routes do not invalidate the primary rung: the supervisor skips them and routes that fail preparation, then tries the next personal route. If none remain, it records the primary or last running route's blocked exit. The list is captured under the spawn lock with the primary route; later user-file edits apply to new dispatches.

A command fallback may use placeholders in its executable, such as `["{cwd}/scripts/fallback", "{prompt}"]`. `ladder show` defers executable lookup for templates that need task context. During fallback preparation, the supervisor expands the command and checks the resulting executable before launch; a missing expanded executable is skipped.

Every rung must be able to run on the harness it resolves to: a `codex` rung needs a `model` or a `profile`, `claude`, `opencode`, `agy` and `pi` rungs need a `model`, and a `command` rung needs a `command`. A field the resolved harness does not use (a `profile` on pi, say) is refused, not ignored, so a switch of harness never quietly runs a model nobody chose. A ladder write is refused when it leaves a rung unable to run that could run before; `spawn` refuses a rung that cannot run, and `validate` reports every such rung. Loading checks only the shape (known rungs, harnesses and field types): a rung that falls back to the user file can break when that file changes, and the project must still load so `tower-crane ladder set` can repair it, one rung at a time.

Defaults come from the user file `~/.config/tower-crane/config.json` (or the path in `TOWER_CRANE_CONFIG`), which holds `{ "harness", "ladder" }`, else from the built-in ladder shown above. `tower-crane init` copies primary settings into the project, excluding personal fallbacks. The default harness and each primary rung come whole from the first layer that has them: project, user file, built-in. Personal fallbacks always come from the user file, which is read even when the project supplies every rung. A project that leaves a primary rung out follows the user file for it; `tower-crane ladder show` prints each source. `tower-crane ladder save-user` writes the default harness and each primary rung the project defines to the user file, preserving its personal fallbacks and any other keys. It never writes a value the project did not set: a default harness or rung the project leaves out keeps whatever the user file has, or stays unset so the built-in applies.

The user file also accepts `"browser_kit": ["playwright"]`, a deduplicated list of MCP server names. The omitted default is `["playwright"]`; `[]` disables automatic server attachment. `browser-kit set --servers JSON` writes this setting as the explicit owner or through a one-use owner approval bound to the resolved user file and server list. It is not copied into projects and `ladder save-user` preserves it. Every dispatch of a `design` task or a task with `needs: ["browser"]` resolves the kit from the original user's file, even inside an isolated orchestrator home, and merges its servers with explicit rung `mcp`. Claude/Codex/agy spawns attach those named user server definitions and pre-approve their tools; kit server env and headers are excluded. Missing definitions and unsupported harnesses omit those kit servers and continue with a warning. Only a task explicitly declaring `needs: ["browser"]` is refused when no primary or fallback route can attach a configured kit server. Each browser-task `spawn` and `spawn fallback` event carries `browser_kit: { requested, attached, omitted, warning }`, also shown in spawn output. Other tasks receive no automatic kit, and no task gets wider filesystem grants: installed Chrome is read-only and its test profiles use existing temp writes.

`project.json` files from before the ladder carry `roles`; loading one is refused with a pointer here. Remove `roles` and set the ladder.

docs/cli.md lists the command each harness gets.

`standards` is `default` (the profile shipped with Tower Crane) or a path to a Markdown file. A path is checked for readability and recorded relative to the repository root; only the default gates apply for now.

`ci` is optional. `ci.ignore_apps` is an array of GitHub app slugs, for example `{ "ci": { "ignore_apps": ["claude", "cursor"] } }`, whose check suites and check runs `tower-crane check ci` skips. It is for apps that open a check suite on every push and never report on it, such as review bots; their suites stay queued and would otherwise hold the gate forever. It defaults to empty, and Tower Crane never infers which apps to skip. Set it with `tower-crane project set --ci-ignore-apps '["claude","cursor"]'`. Entries must be non-blank strings; the CLI trims leading and trailing whitespace before storing them. `--ci-ignore-apps '[]'` stores an empty list; `--ci-ignore-apps null` removes `ci.ignore_apps`, so no apps are skipped.

`ci.required` is an optional array of non-blank strings naming hosted check runs or literal, case-sensitive prefixes. Each entry must match at least one non-ignored run at the submitted sha. Every matching run must have status `completed` and conclusion `success`; skipped, neutral, unfinished and capped runs do not satisfy it. A prefix requires all matching runs that exist, so enumerate full matrix job names to detect a missing member. Only the latest run of each check name and app counts, ordered by `started_at` and then `id`; a run that has not started has no `started_at` and is current when its `id` is above the latest started run's. A rerun or a reopened PR supersedes the older runs of that name, so a failed run that a later run replaced does not block. A completed, failed suite does not block either when every run it reports was read and superseded by a newer run; a suite still running, or one whose reported runs were not all read, still blocks. For Tower Crane, the project lists `["test (ubuntu-latest, node 26)","test (ubuntu-latest, node 24)","test (windows-latest, node 26, shard 1/3)","test (windows-latest, node 26, shard 2/3)","test (windows-latest, node 26, shard 3/3)"]`. Configure it with `project set --ci-required JSON` or `init --ci-required JSON`; entries are trimmed. An empty list, `null` or an absent field imposes no named-run requirements. The CLI preserves other `ci` fields; `--ci-required null` removes only `required`. Malformed lists fail the hosted CI gate.

`ci.capped_review` optionally lists `{ "app", "pattern" }` rules. The app slug must be exact without surrounding whitespace, and the pattern is a nonempty case-insensitive regular expression matched against a completed failed run's output title and summary. A matched cap is nonblocking only outside required jobs. Its failed suite also needs its complete set of runs to be green or capped. Other failures and unfinished checks still block; a capped review alone cannot prove CI ran. Absent or null rules default to `[]`; malformed rules fail closed.

Hosted CI first verifies the PR's head and reads `mergeable` and `mergeStateStatus`. `CONFLICTING` or `DIRTY` fails because GitHub does not run `pull_request` workflows on conflicting PRs. Unknown or missing mergeability requires a later retry. `MERGEABLE` with a known state such as `BLOCKED` permits checking CI, leaving reviews and merge protection to their own gates. Tasks without a PR still enforce required runs at their submitted sha. With `ci.local` configured, the local merged-tree check applies instead.

`ci.capped_review` is an array of `{ "app": "<GitHub app slug>", "pattern": "<regular expression>" }`, for example `{ "ci": { "capped_review": [{ "app": "revuto-review", "pattern": "reached the \\d+-round review limit" }] } }`. The app slug must be exact and have no surrounding whitespace. A completed check run with conclusion `failure` from that app is nonblocking when its output title or summary matches the case-insensitive regular expression. Output text is not searched because review findings can quote a cap message. The gate summary names every matched run and app, including when another check still blocks. At least one run outside ignored apps and matched caps must exist; a capped review alone does not prove CI ran. The linked completed, failed suite is nonblocking only when all its reported runs were read and each is green or a matching capped review. Other suites from that app, other failures, cancellations and unfinished checks still block. This defaults to empty; malformed rules or invalid regular expressions fail the gate. It implements the project's policy that a capped review bot can be replaced by the independent review, whose separate acceptance gate still applies.

`tower-crane project set --ci-capped-review '<json array>'` sets it (`null` clears it). The ci evidence keeps the matched runs as `capped_review`, which lets the orchestrator waive review for that head ([Authority](#authority)).

`tests` is optional too. `tests.mode` selects how `tower-crane check tests` verifies the submitted commit:

| Mode | Behavior |
|---|---|
| `prove` (default) | The command must pass at the submitted sha. Code tasks must add or change a test file. Keep changed tests and build files, revert other changed files to the merge base, and require the command to fail. If only tests and kept build files changed, or a non-code task changed no tests, pass after the head run. |
| `run-only` | The command must pass once at the submitted sha. No changed test path or merge base is required, and no file is reverted. This handles Rust inline `#[cfg(test)]` modules in source files that also contain production code. |
| `none` | Skip the suite; any supplied `--cmd` must still match the pin. Verify that the submitted sha resolves to a commit, then record ok evidence naming the policy. No test command or temporary worktree is needed. |

`tests.by_kind` overrides the project mode for a task kind (`code`, `docs`, `research`, `design`, `ops`). Missing kinds inherit `tests.mode`, which defaults to `prove`. For example, `{ "tests": { "mode": "prove", "by_kind": { "code": "run-only" } } }` lets a Rust project's code tasks use its inline test suite without a revert proof. Only code tasks require tests evidence for acceptance, so kind overrides affect required tests gating only for code. Docs, research, design and ops already need independent review without a tests gate; their overrides apply only when someone explicitly runs `check tests`. These are owner-controlled project settings, not per-invocation bypass flags.

`tests.expensive: true` keeps an effective `prove` mode and runs the head suite once at the submitted sha, using mapped suites when configured below. When there are files to revert, `check tests` requires pinned `gates.tests_proof_cmd` containing `{tests}`. The gate substitutes the shell-quoted paths of the added or changed test files. The scoped command must pass at head and fail after non-test files are reverted, with the same build-file keep rules. This preserves failing-before proof without running the full suite twice, and a broken scoped command cannot count as proof. This is the documented default for projects: the orchestrator sets it at `init`, for a Node project with `--tests-cmd "npm test" --tests-expensive true --tests-proof-cmd "node --test {tests}"`, then uses `check tests ID`. Leave it off only for a suite cheap enough to run twice. The project must have a runner that can select its changed test files; there is no inferred runner across languages. Reviewers check that the scoped command actually runs those tests. `run-only` and `none` keep their respective behavior. False, null or an absent field leaves the normal full-suite proof.


`tests.map` is an optional pinned object from repository source paths or globs to arrays of literal test paths, for example `{ "lib/gates/tests.js": ["test/gates/tests.test.js"], "**/*.md": [] }`. Set or replace it with `project set --tests-map JSON`; `null` clears it. Matching globs use the `tests.paths` syntax and union their suites. Empty arrays explicitly cover paths needing no additional suites. Source and test paths must be relative without parent components, backslashes or NUL bytes; tests cannot be globs. Invalid maps refuse before execution. It is operational at `init` and `project set`, including unchanged values and clearing.

With effective `prove` mode, `tests.expensive: true`, a map, a scoped `{tests}` template and a nonempty `ci.required` naming the full-suite job, the head run uses the changed test files plus mapped suites. A task without a PR retains the full head command because hosted CI is not required. A configured `ci.local` retains the full head command because hosted required jobs no longer run. Helpers and fixtures need source mappings even under broad test globs. The orchestrator pins the job that actually runs the full suite; job contents cannot be inferred from its name. Every changed non-test path needs a map entry, including deleted paths, test support and kept build files. Unmapped paths, missing or non-test mapped paths at head, or an empty selection fall back to `gates.tests_cmd`; missing prerequisites retain that full run too. Deleted tests are excluded. The scoped head and failing-before proof still run only the added or changed tests, with the same reversion and build-file keeps. `run-only` and `none` are unchanged.

Tests evidence carries `receipt.head_mode` (`mapped` or `full`), `head_reason`, and `head_tests` for mapped runs. Its summary names the same selection and fallback reason. While a map is pinned, `gate_policy` also snapshots `tests_map`, `ci_required` and `ci_local`; changing any makes old receipts stale. Head command receipts must match the pinned template expanded with `head_tests`, and proof receipts still match `proof_tests`. The committed repository seed is `tools/tests-map.json`, generated from imports with `node tools/tests-map.js` (or `node tools/tests-map.js SHA` for a submitted head); shared CLI infrastructure keeps all suites, and uncovered executable paths stay unmapped. The orchestrator pins the seed through the CLI after checking coverage.

Set these fields with `tower-crane project set --tests-mode prove --tests-by-kind '{"code":"run-only"}'` for inline tests, or `project set --tests-expensive true` for a full suite with scoped proof. `--tests-mode null` restores the project default; `--tests-by-kind '{}'` or `--tests-by-kind null` clears kind overrides; `--tests-expensive false` or `--tests-expensive null` restores full-suite reversion. A kind map replaces the whole map and accepts only known kinds with one of the three modes. The expensive flag accepts JSON true, false or null. Malformed mode settings fail the gate before a suite runs.

On both `init` and `project set`, `--tests-mode`, `--tests-by-kind`, `--tests-expensive`, `--tests-paths`, `--tests-keep`, `--tests-host-only` and `--tests-map` are operational ([Authority](#authority)): the orchestrator or the owner, with explicit identity from `--agent` or `TOWER_CRANE_AGENT`. Terminal fallback to owner is insufficient. Setting, clearing and unchanged values all require that identity. Refused calls write no state or events, including other settings supplied in the same call; a refused init creates no state directory. Workers request policy changes from the orchestrator with `tower-crane msg --to orchestrator` or a task note.

The `prove` mode keeps changed declarative manifests and lockfiles at the submitted sha so the reverted tree can still build. Only non-test paths can be kept as build files, and the summary names each one. Test paths and keep globs are used only by `prove`; `run-only` runs the submitted tree intact.

No general code suffix or arbitrary `*.lock` suffix is kept. Executable build files, including `Makefile`, `setup.py`, Gradle scripts, `*.bzl`, bundler configs, `flake.nix` and MSBuild projects, are reverted by default. A project can explicitly extend the keep set with `tests.keep`, for example `{ "tests": { "paths": ["test/**"], "keep": ["Makefile", "tools/**/*.gradle"] } }`. Set it with `tower-crane project set --tests-keep '["Makefile","tools/**/*.gradle"]'`. The globs use the same repository path rules as `tests.paths` below. A matched non-test path stays unreverted, even if it contains code, so keep these globs narrow and review them as part of the project's gate policy. An empty list or `--tests-keep null` restores only the defaults; it does not disable them. A path classified as a test is always excluded from the build file list.

By default a file is a test when it sits under a `test/`, `tests/`, `spec/`, `specs/` or `__tests__/` directory in any case (`Tests/`, `Test/`), under a directory named like `MyApp.Tests`, `MyApp.UnitTests` or `integration_test`, or a CamelCase one like `AppTests` or `androidTest`, or when its name looks like `foo.test.js`, `foo_test.go`, `foo_spec.rb`, `foo.spec.ts`, `test_foo.py`, `FooTest.java`, `FooTests.swift`, `FooSpec.scala`, `FooIT.java` or `TestFoo.java`. CamelCase forms need their capital, so `latest.js` and `contest.py` stay code. Fixtures and helpers are support code, not tests, even under a test directory: files under `fixtures/`, `__fixtures__/`, `__mocks__/`, `testdata/` or `helpers/` directories, and files named like `helpers.js`, `test_helper.rb`, `stack-fixture.js` or `conftest.py`, are reverted like other code, and editing one is not coverage for a change. `tests.paths`, for example `{ "tests": { "paths": ["src/test/**", "**/*Test.java"] } }`, replaces those defaults with the project's own globs over repository paths: `*` and `?` stay within one directory, `**/` spans any number of directories, `{a,b}` matches either, a trailing `/` takes everything beneath, and matching is case-sensitive. Set it with `tower-crane project set --tests-paths '["src/test/**","**/*Test.java"]'`. It must be a non-empty array of non-blank strings; the CLI trims leading and trailing whitespace before storing them. `--tests-paths null` removes `tests.paths` and restores the default layouts; `[]` is invalid.

`tests.host_only`, for example `{ "tests": { "host_only": ["tests/lab/**"] } }`, lists the test files that cannot run inside a worker sandbox. It takes the same globs as `tests.paths` and is set with `tower-crane project set --tests-host-only '["tests/lab/**"]'`; `[]` lists none and `null` clears it. Every spawned role gets the list as JSON in `TOWER_CRANE_HOST_ONLY`. A sandboxed run (`TOWER_CRANE_SANDBOX=1`) skips the matching files: the runner must honor the variable, and this repository's `test/run.js` does. While the list is set, that runner refuses a directory or a glob selection, since it expands one after the skip and could reach a listed file; a worker names the test files one by one. The worker brief names the same globs under `## Host-only tests`. The tests gate ignores the list: it sets `TOWER_CRANE_SANDBOX=0`, drops `TOWER_CRANE_HOST_ONLY` for its commands, and runs every test on the host.

The list and tests policy flags also work with `init`. Omitting a flag leaves its field unchanged. Setting a field replaces a non-object `tests` or `ci` section, and clearing removes that malformed section. Object sections keep their other settings; clearing removes the section when it becomes empty. `project set` and `project show` text output print the policy and lists, showing `prove`, `{}` and `false` for absent mode, kind overrides and expensive settings, `default layouts` when `tests.paths` is absent and `[]` when no extra build files or CI apps are configured. Invalid input exits 2 without writing state or events, even when passed alongside valid settings.

## tasks.json

Evidence that no gate decision reads any more is settled: an entry whose `sha` does not match the task's head or whose `revision` is older, every entry of a cancelled task, and every entry but the merge receipt of a task accepted with a passing merge at its head. Each write stores a settled entry's `summary`, `commands`, `receipt`, `gate_policy`, `ci_policy`, `test_failure` and `capped_review` over 1 KiB of compact JSON in `evidence/<task>/<sha256>.json`, and adds `evidence_refs` to the entry, mapping each stored field to `{sha256, bytes}`. The field itself keeps a placeholder of the same type: `[stored in evidence/<task>/<sha256>.json]` for `summary`, an empty array for `commands` and `capped_review`, null for the others. Evidence at the current head stays inline whatever its size, and unknown evidence types are never stored. So `tasks.json` grows by a bounded amount per receipt, not by the size of its output.

Readers load a stored field on first use and check its byte length and SHA-256; a missing or changed file refuses that read with the file's path. `task show` and other views show the entry as recorded, without `evidence_refs`. Writes that do not use a stored field keep its reference without reading the file. A write reads a stored field back into the entry when the entry becomes current again. The first write by this version moves existing settled fields out; the files are written before `tasks.json` names them. Copy `evidence/` with the rest of the state. Files are never deleted.

The format is additive within schema 1. A pinned older tool reads and preserves `evidence_refs` and the placeholders. Every value its gate, merge and readiness decisions read is at the current head and stays inline, so those decisions do not change. It shows placeholders for settled history, and its gate view of a merged task's earlier receipts sees empty commands. When an older tool writes its own value into a stored field, that value wins and the next write drops the reference.

```json
{
  "version": 1,
  "next": 4,
  "tasks": [
    {
      "id": "T1",
      "title": "Idempotency key on webhook retries",
      "kind": "code",
      "needs": [],
      "acceptance": ["a retried webhook with the same key is processed once", "test proves it"],
      "depends_on": [],
      "locks": [],
      "environment": null,
      "needs_owner": null,
      "size": "M",
      "tier": "medium",
      "status": "todo",
      "claim": null,
      "branch": null,
      "pr": null,
      "sha": null,
      "evidence": [],
      "submitted_by": null,
      "revision": 1,
      "spend": { "minutes": 0, "tokens": 0 },
      "notes": []
    }
  ]
}
```

- `kind`: `code`, `docs`, `research`, `design`, `ops`. Changing it is operational, except leaving `code` (owner-required) and any change on a submitted or accepted task (refused until `rework`) ([Authority](#authority)).
- `needs`: capability names, currently only `browser`; defaults to `[]` for new and legacy tasks. Set through `task add/update --needs JSON` or plan import. Duplicate names are removed. A change bumps the revision and requires rework for an accepted task. A `design` task requests the kit automatically; only explicit `needs: ["browser"]` requires a capable route before dispatch.
- `ci_local`: optional local CI override with exactly one of `command` or `args`, and optional `timeout`, using the `ci.local.by_kind` override shape above. Only `task update ID --ci-local JSON` by the orchestrator or the owner sets it; `--ci-local null` removes it. An accepted task needs `rework` before the override can change. Changing it does not bump the revision; receipt validation checks the current resolved variant, command and timeout.
- `size`: `S` (under an hour), `M` (a few hours), `L` (a day). Anything larger is split; `validate` reports it.
- `tier`: `easy`, `medium`, `hard` or `research`, the current ladder rung that does the task. When `task add` or `plan import` gives none: `research` for kind `research`, else `easy` for `S`, `medium` for `M`, `hard` for `L`. It changes through `--tier` or a ranged quality escalation; a later size or kind change does not move it. A task file without `tier` gets it the same way when it loads.
- `tier_range`: optional `{ "min": "easy", "max": "medium" }`, containing the current tier. `task add`, `task update` and `plan import` accept an ascending `tier` string such as `easy..medium`, store the range and start at its minimum. The order is easy, medium, hard, research. A single `--tier` clears the range; setting a new range resets its current tier to the minimum. Manual range changes use the operational `task.tier` authority, including clearing a range at its current rung from either the CLI or the board's `/api/tiers`; both record the setting audit.
- `escalations`: optional history of `{ at, agent, from, to, trigger, reason, source, spend_by_rung, decision? }`. `to: null` means the range top opened an owner decision. Sources deduplicate repeated recovery. `escalation_pending: true` means the rung already climbed but its fresh worker has not launched; a successful dispatch clears it under the spawn lock.
- `budget`: optional `{ "hours", "tokens" }`, each null or a non-negative number, set by `task update --budget-hours`, `--budget-tokens`. Enforced like the project budget on the task's own spend.
- `needs_owner`: null, or the reason the owner has to act (a credential, a purchase, a product call). `task add` and `plan import` trim this value; blank values become null. Such a task is never ready on its own; `tower-crane owner-done` clears it. Clearing it, there or by replacing an existing reason with `task update --needs-owner`, is operational: the orchestrator or the owner. Any agent may set a reason when none exists, or keep the same reason.
- `locks`: an array of unique non-empty resource names, such as `["lab/rdma", "gpu/0"]`; defaults to `[]` when absent. `task add --lock NAME` and `task update --lock NAME` accept repeated names, trim and deduplicate them; update replaces the list, and `--lock ''` clears it. `plan import` accepts the array too. Names are case-sensitive and independent of the environment label. Lock changes are refused under the state lock while the task holds a live lease or worker dispatch reservation; keeping the same set is allowed.
- `environment`: null or a non-empty informational label, such as `"lab"`; defaults to null when absent. Set with `--environment LABEL` on task add/update or the plan field. `--environment ''` clears it. It does not set process environment variables, select a harness or acquire a resource lock.
- `status`: `todo`, `in_progress`, `submitted`, `accepted`, `rework`, `cancelled`. `ready` and `blocked` are computed, never stored.
- `claim`: `{ "agent": "w-3", "since": "...", "until": "...", "from": "todo" }` while in progress; `from` is the status before the claim (`todo` or `rework`), which `release` restores. Repeating `claim` as the live holder extends `until` without changing `since` or `from`. An expired lease frees the task: it counts as `from` again and another agent may claim it. Until someone does, the original claimant can still submit it, or renew it if the task passes the same checks as a claim (no unmet dependency, owner blocker or open decision, and no held resource lock) and the workers limit has room: an expired lease no longer counts toward `limits.workers`, so renewing it takes a slot like a new claim.
- `retiring`: null, or `{ "since": "...", "pid": 4242, "host": "...", "start_ticks": "..." }` while the process that wrote it removes the task's worktree after a merge or cancel. `start_ticks` is set where the platform reports it. Claim, rework and spawn refuse the task while that process runs; a marker whose process has exited holds nothing, so a crash cannot strand the task. The removal clears the marker when it ends, whether or not it removed the worktree.
- `submitted_by`: the agent that submitted the current `sha`. Submission clears `claim`; while the task is `submitted`, only this agent can replace the submitted head.
- `evidence`: entries `{ "type", "ok", "sha", "agent", "at", "summary", "ref", "revision" }`, plus `"waived": true` on an owner waiver and `"via": "broker"` on evidence the state broker recorded for the agent it names (provenance, not proof: an unsandboxed process can write the same). Types: `tests`, `clean`, `sources`, `review`, `ci`, `merge`, `note`. Review evidence requires `--sha` for the commit reviewed. A spawned reviewer's verdict carries its dispatch revision, even when the brief, acceptance or rework changes the task before the verdict arrives. Review evidence from a reviewer spawn did not start carries the `--revision` it names, which is required and may not exceed the current revision. Other manual evidence records `--revision` when given and the current revision otherwise; `note` can default to the submitted sha. Software gates record the sha and revision they checked.
- `evidence.confirmed_failure`: optional boolean, emitted as true by tests, clean and CI runners when the check confirms a failed attempt. Unavailable test commands do not set it: shell exits 126/127, Windows exit 9009, or exit 1 with only cmd.exe's missing-command diagnostic. Failed-test output accompanied by that diagnostic still confirms a failure. CI sets it for completed uncapped failing runs, including a failing sibling of a capped review. Missing or pending required checks do not hide a completed uncapped failure in another run. Capped reviews alone, queued or pending runs, missing runs and observation errors do not set it. The same optional field appears in the gate event's `detail` and must match for audited software evidence to count. Legacy evidence without the field remains valid but supplies no confirmed-failure escalation signal.

- `revision`: incremented when acceptance, dependencies or capabilities (`needs`) change, on every `rework` including automatic quality escalation, and when `brief set` changes the brief after the first submission. Identical brief writes and brief edits before the first submission do not increment it. Evidence recorded against an older revision stays in the audit trail and does not count, even when the submitted sha is unchanged. An accepted task's brief, acceptance, dependencies, capabilities and kind cannot change; send it back with `rework` first. A refused brief change leaves the brief, task and audit log unchanged.
- `spend`: `{ "minutes", "tokens", "input"?, "cached"?, "output"?, "entries"? }`. Existing `{ "minutes", "tokens" }` files keep loading. Totals increase under the state lock. Token counts are non-negative safe integers. `input` includes cache reads and writes, `cached` is the cache-read subset of input, and `output` includes reasoning when reported. Do not add `cached` to `tokens` again. A total-only report increases `tokens` without inventing a breakdown; aggregate breakdown fields sum only the reports that supply them.
- `spend.entries`: one record per spend call or exited spawn route: `{ "at", "agent", "minutes", "tokens", "input", "cached", "output", "rung", "harness", "model", "profile", "source" }`, with optional `cache_write` from manual `--cache-write` and `provider` (`anthropic` or `bedrock`) for explicitly selected Claude routes. Unknown counts and metadata are `null`. `source` is `manual` or `spawn:<agent>`, with `:attempt:<n>` for resumed dispatches and `:route:<index>` for fallback routes. A spawn's rung, harness, configured model and profile come from its dispatch or fallback event; a model named in captured telemetry takes precedence. Model IDs are stored with whitespace trimmed and case folded; provider prefixes remain distinct; explicit Claude provider entries use plain Anthropic or global Bedrock ids and retain the provider that ran, including each fresh retry. Historical entries normalize the same way when compared with review prices. Only explicit Claude provider entries expand `BUILTIN.claude_aliases`. A profile-only dispatch without a reported model keeps `model: null` and the profile. Manual `--rung` resolves the current ladder; pass `--model` and `--harness` when a native subagent used different values.
- Live usage: while an agent runs, its supervisor reads the harness's own usage every `usage_ms` (default 30 s, minimum 1 s; the first periodic reading after one interval): claude's session file `<CLAUDE_CONFIG_DIR>/projects/<dir>/<session id>.jsonl` and captured usage, the codex rollout for the printed session id, and the captured log for opencode, pi and agy when they expose usage. Claude uses the larger total observed in its session or log during the run. Only session files named for the spawn's own session id are opened, and events never carry their paths. The reading is stored as the route segment's entry, with the `source` the exit collection uses, plus `"live": { "state", "interval_ms", "error"? }`: `state` is `live` with the tokens so far, or `unavailable` with `tokens: null` while the harness has exposed no usage; never a zero. An initial read exception records `unavailable` with the filesystem error class (for example `EACCES` or `EISDIR`, otherwise `Error`), without the error message or path. Later exceptions preserve and age a measured reading. If telemetry returns no usage or a smaller cumulative total after a measured reading, its counters, cost and `at` stay unchanged and its state becomes `stale`. Only an authoritative invocation result may lower the measured total. Recovery from missing telemetry restores `live`. A resumed session counts only what it adds after the dispatch. Only changed readings produce `spend live` events, quiet bookkeeping for the default waiter; `budget stop` still wakes the orchestrator; unchanged files do not refresh the timestamp, and views show a reading older than 10 effective intervals as `stale`. `status.spend.live` includes `at`, `stale_at` and any `error` class; the open board updates age, freshness and summaries each second without requiring a state write or SSE reload. Live tokens are in the totals. The exit collection replaces the live entry with the exit telemetry, or keeps its last reading without `live` when the exit reports none, so usage is counted once. Live entries are not counted as spawns without usage.
- When claude exits without a result, its supervisor reads the session once more after the process group and output streams close, before recording the exit that permits collection. This includes usage written after the last live sample, even when submission has ended supervision. The resumed-session baseline still applies. Partial assistant-message usage in the log does not skip this read. Collection and recollection keep the reconciled total when the partial log reports less; only a valid invocation result can replace it with a lower total. If this final read is unavailable, collection keeps the last live reading. If an exit collector finalized the entry before the supervisor read its final usage, the final reading replaces that source entry in place and rechecks budgets. It neither adds a second entry nor restores `live` on the collected entry.
- An explicit `interrupt` stops the process group and reconciles its spend on exit. The run keeps its `stopped` phase and the task keeps its revision; recollecting that usage does not count it twice.
- Entry counts include live snapshots and do not establish exit collection. An exit consumer waits for entries without `live` and, when observing a worker exit, the matching `worker-exited` receipt.
- Every completed attempt is sampled before scheduling a retry or selecting a fallback, even if it finishes before the first periodic sample. Claude's result, when present, supplies the invocation total; other harnesses use their own usage sources. A budget breach stops further attempts. The launch also checks the current budget under the state lock before starting a retry or fallback, so another agent's spend or a lowered limit cannot bypass the check.
- A budget stop does not trigger tier-range quality escalation. It leaves the current rung in place and waits for the owner to address the budget.
- Budgets: `project.json budget` and a task's optional `budget` `{ "hours", "tokens" }` (null is no limit) are checked against recorded and live usage at every supervisor sample, including when telemetry cannot be read. Submission ends lease renewal and retries, but accounting and budget enforcement continue until the process group and streams close. A crossing (usage above the limit) stops the agent: the supervisor records `budget stop` with the breaches and `authority: "operational"`, sets the run phase to `blocked: budget: ...`, terminates the process group without a rerun or fallback, cancels a retry still in backoff, and opens one decision per crossed budget with `escalation: { settings: ["budget.raise"], change: { scope, what, limit } }`. A task budget's decision blocks the task. `spawn` refuses while a project or the task's budget is crossed. Raising or removing a limit needs the owner directly or a setting approval for the orchestrator; answering the budget alert alone grants no change.
- Manual `spend --cache-write N` adds `cache_write` to the entry. It is included in `input` and separate from `cached`; their sum cannot exceed input. Omitted cache-write counts stay unknown for pricing older telemetry.
- New spend entries, including measured live entries, record `cost_usd` using the canonical model's configured `review.prices` at collection time. Claude aliases resolve through `BUILTIN.claude_aliases` for this lookup; the stored model ID remains unchanged, and explicit provider routes keep their provider identity. Missing prices or input, cache and output components produce null. Cost uses the review pricing rules, including conservative cache-write accounting. Missing telemetry preserves the last measured cost, and exit reconciliation prices the final entry once. `task show` exposes `spend_by_rung` with summed tokens and cost; an unknown entry makes that rung's corresponding total null. Escalation records include this breakdown at the climb, while later collection can enrich the task's current breakdown.
- Automatic collection happens for foreground and detached exits, including nonzero exits and killed processes whose logs report usage. Foreground collection, detached monitors and `wait` share one locked exit-observation path. A waiter attempts usage collection when it observes a worker exit. A detached monitor observes the original harness pid (including Linux zombies and pid reuse) and invokes the CLI after exit. Its checks are 500 ms apart; each collection takes the usual state lock with a command deadline of at most 30 s. Failed collection retries for up to 10 min, then logs a recovery command and exits with code 1. If the process cannot be observed for 10 min (another host, a permission error or unavailable Linux process metadata), the monitor exits with code 1 and a recovery command without assuming exit or recording usage. Both deadlines use monotonic time. A known live process is watched until exit; deleting the project stops the monitor. Successful collection stops the monitor. `spend --from-spawn AGENT` can retry collection. A known `source` is counted once even across concurrent retries. Without usage, the entry has `tokens: null`, totals stay unchanged, and status/sketch count spawns without usage. A retry enriches unknown or partial entries if telemetry arrives, applying only counter deltas. Explicitly reported zero is a measured zero.
- `notes`: `{ "at", "agent", "text" }` entries. The orchestrator folds what matters into the brief. A note starting with `split:` on an `L` task records why it stays whole.

`bench tokens` compares spend entries with every recorded spawn, including reviewers, resumed attempts, fallback routes and fresh retries. Its read-only report lists unmatched source IDs as `missing_spawns`; it does not add placeholder state entries. A matching native manual token report can cover its dispatch, while minute-only reports cannot. Tasks with missing sessions, unknown token entries or any entry marked `live` stay out of all token, category and USD medians and means, including rung and path groups; their recorded spend still contributes to the total cost per accepted task. Each live or unknown token entry contributes once to the report row's `unknown` count. Collection must remove the live marker before the task can become complete. See [bench.md](bench.md) for the labeling and pricing method.

Missing input, cached or output counts leave the corresponding task category total `null`, and category medians use only measured totals. Known token totals remain eligible for token medians even when their breakdown is incomplete.

The CLI never writes a dependency on a task that does not exist, a dependency cycle, or a task without acceptance. `validate` still checks files edited by hand.

Task ids are never reused. A new task takes the larger of `next` and one past the highest task id any `events.jsonl` record names, so a task that tasks.json lost keeps its id. `validate` reconciles tasks.json with the log and reports drift: a task id the log names that tasks.json lacks, a `task note` the log records that the task lacks, and a `next` at or below a logged id. It reads without the lock; every reader reads `events.jsonl` before tasks.json, and a commit writes tasks.json before it appends its events, so a commit between the two reads is never mistaken for drift.

Resource lock holders are derived from the same pure event-log, lease and clock view as worker slot holders. A task holds all its locks while its lease is live or its unclaimed worker dispatch reservation holds a slot. Claim, worker spawn and expired-lease renewal refuse conflicting locks under the state lock, naming the resource, task and agent holding it; the same task and agent can consume their own reservation. `ready`, blocked views and task descriptions include conflicts with other tasks. Submission, release and lease expiry free leased locks. Unclaimed reservations free their locks on the matching exit, inactive monitor record or reservation horizon, and retain them through supervised retry and fallback backoff. No process probe can free a lock for one observer alone. Reviewer and other non-worker dispatches acquire no resource locks. Lock and environment changes do not bump the task revision.

Changing acceptance, dependencies, capabilities (`needs`), kind or a local CI override while a claim's lease is live requires `task update --interrupt`. Only the explicit owner, `orchestrator`, or a generated agent with a recorded orchestrator role can authorize the stop. Validation, the requirements edit and the interruption event share one lock, so a refused edit stops nothing. Acceptance, dependency and capability edits retain their revision bump. Adding or clearing capabilities changes what the next spawn receives; repeating an unchanged capability set keeps the claim and revision. Unchanged requirements and metadata changes do not interrupt.

`interrupt ID` clears the claim and restores its `from` status without changing revision, branch, PR, head, evidence or worktree files. Its event records `{ holder, claim, status, revision, reason, phase, active }` and the matched supervisor's run identity when present. A live supervisor starts in `stopping`; a claim without a live supervisor records `stopped`. The supervisor consumes this request through its existing shutdown path, cancels retries, waits for process-group cleanup and output closure, then records `spawn phase` with `phase: "stopped", active: false` and the usual exit and spend receipts. An interrupted task with a live stopping supervisor still reserves one worker slot; claim and redispatch refuse until cleanup finishes. A manual claim has no active supervisor and releases immediately. Interrupted runs do not produce an exited-without-submit recovery wakeup.

Dispatch recognizes the interruption of the latest worker attempt independently of `submitted_by`. The usual matching-route Codex and command-adapter session policy applies; native Claude starts fresh. Resume restores the interrupted claim's original `since` and `from`, checks blockers and worker limits, and supplies the current requirements with an interruption note. A changed route, missing session or fallback starts fresh in the retained worktree. No session is resumed while the interrupted supervisor is still stopping.

Recorded `active: false` takes precedence over a monitor process that remains alive for usage collection. Interrupting such a claim records `stopped` directly. Final exit handling checks for a matching active interruption under the state lock after waiting for hooks, so a stop request committed during that wait also receives its `stopped` phase and exit receipt. A later `submit` or `rework` event for the task ends the preceding interruption's eligibility for both session selection and prompt construction. Rework resumes from the submission's claim and supplies current review feedback.

Software evidence also has `source` (`check tests`, `check clean`, `check sources`, `check ci` or `merge`) and `commands`, an array of `{ "command", "args", "cwd", "status", "signal" }` receipts. `command` is the executable name or shell command line, `args` holds its arguments, `cwd` is its working directory, and `status` and `signal` report how it ended (null when unavailable). All commands the gate ran are recorded, including failed commands and GitHub queries. A gate refused before running a process records an empty array; an ok entry needs at least one command to count. In tests mode `none`, the receipt is the Git command resolving the submitted sha; it does not claim that a suite ran. Tests evidence and event detail also carry `tests_mode`, the mode resolved from the project and task kind when checking started, or null for invalid policy. Gate evidence and its event carry the same receipts and revision.

When a test command fails, tests evidence and its audit event also carry `test_failure: { "names": [], "output_tail": "" }`. `names` collects node:test spec (`✖`) or TAP (`not ok`) failure lines. `output_tail` contains at most the last 40 lines and 8192 characters. Before storage or printing, the full output is redacted and only then cut to the tail, so a token across the cut is never left as a fragment. Names and tail are redacted against environment values that look like secrets: a value with a token shape, or the value of a credential-named variable (token, secret, password, passwd, credential, API key, access key, private key or cookie) that is 20 or more characters of letters and digits with no spaces. This covers the gate process environment and project, resolved rung and environment-file values. Token shapes are GitHub, API, AWS and Slack keys and `Authorization` header values. Paths, file names and commit SHAs are never redacted, and neither are numbers, booleans or short words such as `NODE_ENV=test` or `MAX_THINKING_TOKENS=1`. Environment-file contents are read during the gate and never stored. The check summary prints the same redacted names and bounded tail.

Hosted CI evidence and its audit event also carry `ci_policy`: `{ "required": [], "ignore_apps": [], "capped_review": [] }`, with the effective values captured when the check starts. Absent or null policy fields resolve to empty arrays. Capped rules record only `{ "app", "pattern" }`. A malformed policy records `ci_policy: null` on a failed check. The policy snapshot in evidence must match its audit event. Before an audited merge succeeds at the current head and revision, acceptance, merge and task gate reports require a successful hosted snapshot to match the current project's effective policy. A changed policy, malformed current policy or earlier evidence without `ci_policy` needs `tower-crane check ci ID` again. Unrelated fields under `ci` do not invalidate it. A local CI check uses its local receipt instead.

`tower-crane evidence` writes only `review` and `note`. Software types are refused for any agent, whether `--ok` or `--fail`; run their gate commands instead. State version 1 and older evidence remain readable. Software entries without the matching gate source and audit event do not satisfy acceptance, so their gates must run again.

`task show` marks software evidence with missing or mismatched gate proof, or an older sha, as `(does not count)` in its text output. Successful tests and clean entries also require their command policy to match current pins; tests entries require the current mode and the current `tests.paths`, `tests.keep` and `tests.expensive` settings. The board ledger validates each entry against the same policy, including after a fresh matching pass. An older revision keeps the `(revision N, does not count)` marker. Each command receipt is printed below its evidence entry, including merge receipts. Owner waivers count without command receipts. The JSON view keeps the stored evidence unchanged and reports the gates separately.

A tests or clean command stopped by its gate deadline records `ok: false`, `infrastructure_failure: true` and `timeout: {minutes, running_files, output_tail}` in both evidence and its audit event. The summary says `timed out after N min`. `running_files` contains paths reported by node:test interruption locations or unfinished top-level TAP file subtests; an empty list means the runner did not identify them. The output tail is captured before termination, redacted and bounded to 40 lines and 8192 characters. Cancellation messages printed after SIGTERM do not become `test_failure` names. A timeout at head, scoped proof or reversion fails the gate without `confirmed_failure`, so it never proves a change or triggers a quality climb.

Tests and clean evidence and their audit events carry `gate_policy`: `{tests_cmd, tests_proof_cmd, paths, keep, expensive}` for tests or `{clean_cmd}` for clean, captured when the check starts. The tests settings are the effective values: `paths` is `tests.paths` (null for the default layouts), `keep` is `tests.keep` (null when unset, which keeps the default manifests and lockfiles) and `expensive` is `tests.expensive === true`. While a map is pinned, the tests policy also snapshots `tests_map`, `ci_required` and `ci_local`. Command values are trimmed strings or null. Missing, malformed or changed policy makes previous evidence stale, even if the owner changes commands during a run. Successful receipts must also include the pinned test command or mapped head expansion (except none mode) or the pinned cleanup invocation with its appended arguments. Scoped proof records `receipt.proof_tests`, the changed test paths used to expand the pinned template; mapped head runs also record `receipt.head_tests`; every test shell receipt must match the full command, the mapped head expansion or the proof expansion. Map, expensive-policy and required-job changes invalidate mapped-policy receipts. Acceptance, merge and task reports use the same check. Old receipts without this snapshot require a new check; owner waivers retain their existing behavior.

The CLI refuses manual software verdicts, and software receipts require matching records in tasks.json and events.jsonl. Plain files cannot stop a writer running as the same user from forging those records or an owner waiver. Command receipts show what ran; acceptance checks them and their recorded policy against the pinned commands. The reviewer checks that the configured runners verify the change.

Research Claude fallback routes in the user file inherit the primary `web_mcp` unless they specify their own. The same `{name, command, args}` validation applies to an explicit fallback server. Other harnesses do not inherit it. A route combining an inherited or explicit web MCP with `mcp` is reported and skipped so only the web server loads.

### Research sources

`project.research` is optional and accepts only `min_sources`, a positive integer; it defaults to 10. The explicit owner sets it with `project set --research-min-sources N` (also accepted by `init`). Changing the minimum invalidates sources evidence recorded under a different minimum.

Tasks of kind `research` require sources evidence on every tier. Kind `research` selects the research tier by default. Changing only the kind preserves the existing tier and its role; verification follows the new kind. Tier changes do not remove the sources requirement or citation-review instructions. Code tasks may use the research tier for model selection and retain their code gates.

A research deliverable is committed at `research/<task id>.json`:

```json
{
  "sources": [{"id": "s1", "url": "https://example.org/page"}],
  "claims": [{"claim": "The supported conclusion", "quote": "Exact text from the page", "source": "s1"}]
}
```

The example shows one citation; the default requires at least ten. Every source has a unique non-blank id and an HTTP(S) URL without credentials. Every claim has non-blank `claim`, `quote` and `source` strings; the source names an entry, and every source must be cited. Multiple claims may cite one source. `check sources ID` reads this file through Git at the submitted sha, fetches each page at check time, and finds every quote in its page text. It normalizes Unicode and whitespace, removes inline tags without adding spaces, separates block boundaries, strips comments and script/style/template content, and decodes common and numeric HTML entities. A single-pass scanner tracks quoted tag attributes, nested comments and templates, and raw script/style blocks. Unfinished blocks stay hidden; an unfinished tag or an unquoted `<` inside a tag excludes the rest of the page from matching. Punctuation adjacent to inline markup stays adjacent. It accepts HTML and plain text; PDF, JavaScript-rendered, authenticated and other non-text pages need a publicly fetchable text alternative. Quote matching proves presence; independent review checks source credibility and whether each quote supports its claim, including uncited factual claims elsewhere in the deliverable.

Before each connection, the gate resolves the hostname and refuses any non-public IPv4 or IPv6 answer, including loopback, private, link-local, mapped and special-use addresses. It pins the full validated address list for the socket while retaining the hostname for HTTP Host, TLS SNI and certificate validation. Node can fall back between IPv6 and IPv4 without resolving again; every attempt shares the page timeout. Redirects are followed manually, with the same URL and DNS checks at every hop, up to five redirects. DNS resolution and all redirect hops share the page timeout. The CLI has no setting that permits private addresses; local tests inject a resolver and transport into the gate context.

The gate rejects duplicate URLs (fragments do not distinguish pages), duplicate final redirect URLs, pages with the same extracted text, dead links, missing quotes and uncited sources. Each fetch is limited to ten seconds and 5 MiB; the gate has a two minute deadline to bound stalled responses. Sources evidence carries a `receipt` with `min_sources`, `deliverable` and the fetched `sources`: id, requested and final URL, HTTP status, text SHA-256, fetch timestamp and cited claims. The audit event carries the same receipt; it also records the Git commands resolving and reading the submitted commit. The reviewer context includes this receipt and the instruction to map each claim to its source. A new check always fetches again; acceptance reuses evidence at the same sha, revision and minimum.

### Ready and blocked

A task is ready when its status is `todo` or `rework`, every dependency is `accepted`, `needs_owner` is null, and no open decision lists it in `blocks`. Otherwise `tower-crane ready --all` says what blocks it.

Ready tasks come in priority order: most outstanding dependents (direct or transitive, not yet accepted or cancelled) first, then by id.

### Spawned process exits

On Windows, an npm `.cmd` harness runs as a direct Node process with the shim's script and the original arguments. Spawn events retain the configured harness and route; the recorded pid belongs to the Node process. The supervisor uses the same resolution for retries and fallback routes.

`status` and `ready`, including `ready --all`, report a current claim when its matching spawned process has exited without submitting. This is a computed diagnostic, not a stored status. Their JSON includes `exited_claims: [{ id, agent, pid, log, code, size, tail }]`. `code` is the recorded foreground exit code or null when unknown; `size` is the log's size in bytes or null when unavailable. Text names the process and log, includes a tail of at most 20 lines from the final 8192 bytes, and directs any agent to recover the verified exit with `release --reason`. It never prints a command that supplies owner identity. Missing logs leave the exit visible with a `log unavailable` diagnostic. Foreground spawns retain logs; legacy events with `log: null` have an empty tail.

Only the current claimant's most recent spawn counts. A worker can claim after its spawn; earlier claims, release, submit and rework events fence off older spawn records. Reclaiming an expired lease under the same agent identity does not inherit the previous claim's spawn. A submitted task or a manual claim with no matching spawn is not an exited claim. Reading either view writes no state, changes no lease and starts no replacement.

The host recorded by `spawn` bounds local pid checks to that host; older events without it are assumed local. Permission errors and processes on another host do not establish an exit. Linux checks recognize zombie processes and compare the recorded process start time to catch a reused pid. Other platforms use missing pids and recorded foreground exits.

Any agent recovers a verified exited task with `release ID --reason R`. The detector rechecks under the lock; a live or unverified process requires the claimant or the owner; the orchestrator's attempt opens a decision. The usual prior `todo` or `rework` status is restored. The supplied reason stays in the release note; only the observed pid, log path, exit code and log size are preserved in an additional note and the release event's `detail.exited_spawn`. Release does not read or persist log text; the views read the tail live from the log file. Releasing clears the diagnostic; a new claim does not inherit the old process.

### Acceptance gates

`tower-crane accept` refuses unless the task's current revision has, at the submitted `sha`:

- `code` tasks: `tests` ok, `clean` ok, and `review` ok from an independent reviewer
- `research` tasks on any tier: `sources` ok and `review` ok from an independent reviewer
- other tasks: `review` ok from an independent reviewer
- any task with a PR, whatever its kind: `ci` ok as well

An independent reviewer is the owner, or a reviewer that `spawn` dispatched for that task at that sha and revision, never the submitter. Review evidence that does not count also does not hold back the review dispatch `accept` makes, does not raise the review rung and is not passed to a rework worker as a finding. The board keeps it in the ledger with a does-not-count reason; neither its pass nor its fail verdict sets the review gate indicator.

Tests modes change how `check tests` produces evidence, not which gates acceptance requires. A code task in mode `none` still needs audited tests evidence for its submitted sha, plus cleanup and independent review.

Successful tests evidence counts only when its audited `tests_mode` matches the mode currently resolved for the project and task kind. A mode change, a missing mode on older evidence or a malformed current policy needs a new tests check. The audit event must contain the same mode as the evidence; changing the mode in tasks.json alone cannot retarget evidence. Owner waivers still apply. Task views, board gate pips and evidence ledger (including accepted tasks), acceptance and merge use this same rule.

Before acceptance, `accept ID` runs unattempted software gates in order: tests and clean for code, sources for research kind on every tier, then CI for every task with a PR. Tests and clean use the pinned commands. Without a test pin, missing tests in prove or run-only mode block acceptance. None mode records its audited tests result without a command. Optional `--cmd` and `--proof-cmd` must match the pins. Expensive prove uses the pinned template with the `{tests}` placeholder. Eligible successful receipts are reused. Failed, stale local-CI or unaudited attempted receipts require an explicit `check` rerun. Results are recorded even if a later gate refuses acceptance. A head, revision or status change during a gate refuses the attempt. Review dispatch is guarded again under the state lock.

When software gates pass and no review has been attempted at the current head and revision, `accept` dispatches a reviewer and exits 0 with `review_pending: true` and its agent name in JSON; the task stays submitted. A repeated accept reuses a live review dispatch. Call accept again after review evidence arrives. Failed reviews require rework or an explicit stronger review dispatch. `spawn --role review` also refuses until all software gates pass; `--dry-run` checks them for a submitted task. For an unsubmitted task a dry run previews the fallback command only, and cannot dispatch a review.

Unfinished CI blocks dispatch without requiring rework. The orchestrator watches it through a gate runner, then re-runs `check ci` when it completes before accepting again. Reviewers judge code and acceptance; missing or unfinished CI evidence is reported to the orchestrator rather than recorded as a failed code review. Review policy and prices are operational: the orchestrator or the owner changes them, and a worker asks the orchestrator.

The reviewer receives the submitted diff, task acceptance, audited software gate results (including command receipts, sha, revision and tests mode) and only the brief's `## Reviewer` section. Claude and Codex put the role instructions, rule contents, standards and the repository's review contract sections in the system context; task JSON, brief, gates and diff stay in the user message. Claude writes it to `system.md` in its home and uses `--append-system-prompt-file` and `--exclude-dynamic-system-prompt-sections`; Codex uses its generated `AGENTS.md`. Repository rule labels are relative to the checkout, while external rule paths stay absolute, so moving to another worktree does not change unchanged contents. Every Claude spawn sets `FORCE_PROMPT_CACHING_5M=1`. See [ladder.md](ladder.md#reviewer-cache) for the measurements and cost per million tokens.

Reviewers use the supplied tests, clean and CI results. They do not re-run the full suite unless they change something in a scratch checkout to probe a specific concern, and run only the affected tests for that probe. The submitted worktree stays read-only. Packets over 12,000 characters put the diff in a context file; the user prompt still carries task context and gate results. This bounds diff arguments, not the static system text or unusually large gate receipts. Software waivers requested in the same accept remain atomic with acceptance and cannot authorize a review spawn; use audited software gate evidence or an owner accept that also waives review.

A gate passes when the latest eligible evidence of its type for the current revision, at a sha matching the submitted one, is ok. Shas match when one is a prefix of the other and the shorter has at least 7 characters. For `tests`, `clean`, `sources` and `ci`, evidence needs the matching gate `source` and an events.jsonl entry with `cmd === source`, the same task id and agent, and matching `type`, `source`, exact evidence `sha`, `ok`, `revision`, `commands` and optional `confirmed_failure` in `detail`. An ok entry also needs a non-empty commands list. Manual, forged and older unmarked entries are ignored, including later entries that would otherwise override a genuine pass or failure. For `review`, an entry counts only when its agent is `owner` or has a `spawn` event with `role: reviewer` for the task, at a sha matching the entry's and at the entry's revision, and is not the submitter. Recording review evidence needs no role, so a name no review dispatch started counts for nothing; its entry is kept, `task show` marks it `(does not count)` and the review gate names its agent. A waiver counts when its agent is `owner`; when the orchestrator recorded an operational waiver (`waive.review` for a capped or down reviewer); or when the orchestrator recorded it with `approved_by` naming an escalation the owner approved ([Authority](#authority)).

Local CI adds `receipt` to its evidence and event detail. Both copies must match exactly:

```json
{
  "variant": "default",
  "command": ["python3", "tools/check.py"],
  "timeout": 120,
  "exit": 0,
  "signal": null,
  "head_sha": "<full submitted commit SHA>",
  "base_sha": "<selected base commit SHA>",
  "tree_hash": "<Git tree object ID of base merged with head>",
  "source_digest": "<SHA-256 of git ls-tree -r -z TREE output>",
  "duration_ms": 1000
}
```

`source_digest` is a SHA-256 restatement of the tree for consumers that do not trust SHA-1, computed from its tracked paths, modes and object IDs, including source blob IDs. It is fully determined by `tree_hash`. The runner computes both identities before execution; it refuses tracked-source changes or a merge result that changes while the command runs. HEAD in its temporary worktree names the submitted head, while the index and checkout contain the merge result. A failing execution still records its exit, signal and duration.

With `ci.local` configured, an ok CI gate needs a local receipt with exit 0, no signal, nonnegative duration, the resolved argv and timeout, and a matching successful command receipt. The receipt's `variant` is `default`, `kind:KIND` or `task:ID`, matching the selected default, kind mapping or task override. A different or missing variant fails even when argv and timeout are identical. The full head SHA, tree hash and source digest must match the current submitted head merged with the selected base. The latest audited evidence is checked by acceptance, merge and task gate reports. A different head fails even if the tree is identical; a changed merge result fails even if the head is unchanged. Changing the resolved variant, command or timeout, or switching CI modes, invalidates its earlier pass. Changing an unselected mapping has no effect. Invalid local policy or task overrides fail closed. Base selection follows dispatch using existing local and origin refs without fetching during `check ci`, acceptance or task reports; metadata queries each have a 60 s deadline. Before merge validates a local receipt, it fetches origin's base with a 60 s timeout and requires that tip to equal the receipt's `base_sha`. Fetch failures and moved bases refuse before GitHub merge; a moved base needs `tower-crane check ci ID` again. Without origin, the local base is used. Once the latest audited merge evidence for the current head and revision is successful, reports retain the recorded CI result without validating it against later base changes, and repeated merges skip the fetch. An unaudited merge marker cannot bypass validation. No hosted API is needed for local CI. The existing hosted CI rules apply when local CI is absent.

Resubmitting replaces `sha` without changing `revision` or deleting evidence. Evidence at the older head stays in the audit trail and no longer counts for the new head. Resubmitting the same sha preserves gates only within the same revision; rework or a changed brief requires fresh evidence. The task remains `submitted`, with no claim lease; omitted branch and PR values stay unchanged. When `--branch` or `--pr` is supplied and the task already has a PR, `submit` reads its state and head branch with `gh pr view`. An open PR blocks a different PR number or a different submitted branch. If the old PR is closed or merged and the PR number changes, `submit` reads the new PR's head branch, uses it when `--branch` is omitted, and checks a supplied branch against it. Failed or unreadable lookups refuse without changing state. Accepted tasks must go through `rework` and a new claim before submission, and that claimant becomes the new `submitted_by` agent.

A submitted head can move at any time until acceptance or rework. Reviewers must pin `evidence --sha` to the commit they reviewed so a result recorded after a resubmission still belongs to the older head. After rework, a fresh worker needs a claim. A session resume through `spawn` restores the submitting worker's claim under the dispatch lock, keeping its agent and original `since` with a new default lease and `from: rework`. An existing live claim by that worker stays unchanged. If an isolated Codex session is missing while the prior worker holds the rework claim, `spawn` transfers the claim to the fresh worker with a new default lease and records `took_over_from` in the claim event. An expired claim must pass readiness and worker-limit checks before transfer. If preparation or launch fails before a child pid is created, `spawn` restores the prior claim and records `rollback: true` in a claim event. Another claimant cannot inherit the session.

The `rework` event records `previous_revision`, the originating rejected revision, and `revision`, the new revision. A repeated stack refresh while rework is pending advances `revision` but keeps that same `previous_revision`, including when a worker has claimed the rework. A new submission ends the pending rework; a later rejection records that submission's revision. Worker rework prompts include failed independent reviews at the originating revision and the reworked sha, including when later brief or acceptance edits advance the task again. Those reviews remain ineligible for the new revision's gates.

`merge` checks these gates again, for the current revision, before it merges.

The default method is squash. Commit text defaults to the task's `title` and `acceptance.join('\n')`; `merge ID --subject S --body B` overrides either independently without changing task state. Empty bodies and multiline text are preserved. Method `merge` uses the same text options; `rebase` omits them and refuses explicit text overrides. The command verifies the PR head matches the accepted SHA and always passes GitHub's full head SHA as `--match-head-commit`, including admin merges and merges that retain the branch. Merge command receipts record the selected text and options. When GitHub refuses `gh pr merge` for an unrecorded stack member, a squash or merge falls back to the asynchronous merge request (`merge_method` set to the squash or merge method, `expected_head_sha`, `commit_title` and `commit_message`); its receipts are the refused `gh pr merge` and the request, and the merge evidence records the merge commit. After confirmation the fallback deletes the head branch unless `merge.keep_branch` is set, and refuses when `merge.admin` is set, since the request has no admin option.

The ordinary merge gate refuses cross-repository PRs and a `baseRefName` different from the task's target base (`stack.base` or the project base). In unstacked fallback, every lower task must have merged before the project base becomes the target. Only a PR still targeting its recorded dependency branch may be retargeted, followed by a fresh state, head, repository and base check. Other wrong bases are refused without a PR write. Already-merged confirmation checks the base too, on the plain path and for every stack member, where the dependency branch or the project base is accepted. Summaries name GitHub's reported base; a merge confirmed into another base records failed evidence with the merge commit and asks for inspection of what landed.

For a stack member attempted in the current invocation, final confirmation requires the project base and a successful asynchronous result. The recorded dependency base is accepted only for members confirmed already merged before this invocation's attempts that have no prior audited asynchronous POST for the same repository, PR and accepted head. The gate reads command receipts from all merge events, including attempts recorded under a higher stack task. These receipts bind retries to the project base independently of stack sync. An asynchronous failure stays in the failed stack result; the member gets no successful merge evidence, while valid lower merges retain their own successful evidence.

The standards profile may add gates. `--waive TYPE --reason TEXT` records an owner waiver as evidence; only an explicit `--agent owner` or `TOWER_CRANE_AGENT=owner` can waive. A waiver satisfies its gate. If the accept is still refused, the waiver is not recorded.

## decisions.json

```json
{
  "version": 1,
  "next": 2,
  "decisions": [
    {
      "id": "D1",
      "question": "Store idempotency keys in Redis or Postgres?",
      "options": ["redis", "postgres"],
      "recommendation": "postgres",
      "why": "keys must survive a Redis flush; volume is 30/s",
      "blocks": ["T3"],
      "answerers": [],
      "kind": "technical",
      "technical": true,
      "status": "open",
      "answer": null,
      "note": null,
      "asked_by": "worker-T3-1",
      "asked_at": "...",
      "answered_by": null,
      "answered_at": null,
      "answer_rule": null,
      "withdrawn_by": null,
      "withdrawn_at": null,
      "withdraw_reason": null
    }
  ]
}
```

A decision the engine opened for an orchestrator's owner-required change also has `approval_request: true`, `escalation: { "settings": [...], "change": {...} }`, options `["approve", "decline"]`, and, once the orchestrator used an approval or the owner made the matching change, `applied: { "at", "by" }` ([Authority](#authority)). The generated request and its `ask` event carry `approval_request: true`; only marked requests can be reused or applied. Older unmarked decisions cannot authorize a command. A tagged question (`ask --question Q --kind K --setting KEY`) records `escalation` with `change: null` for owner-required tags and is not technical. It is never a one-use approval.

A decision blocks only the tasks it lists. Everything else keeps running. `status` is `open`, `answered` or `withdrawn`. When options are listed, the answer must be one of them. An explicit owner identity can answer every decision. `answerers` lists agents the owner named with `decision delegate DID --answerers JSON`; the owner can replace the list or clear it with `[]`. `decision delegate` is owner-required: an orchestrator request opens an approval for the target decision and supplied fields, then its identical rerun applies it once. The shared audit names `decision.delegate`; closed decisions refuse before opening or consuming an approval. `kind` is what the asker says the question is, and every `ask --question` gives one: `technical`, `spend`, `credential` or `setting` (other values are refused, and a missing kind is a usage error). The question text is never read, so routing depends on the kind alone. A decision is owner-only when it escalates an owner-required setting, when its `ask` carries `--owner-required REASON` (another call only the owner makes; stored as `owner_required`), or when its kind is `spend`, `credential` or `setting`. A decision the engine opens (an owner-required change, or an exhausted escalation range) has no `kind` and is owner-only. `technical` is stored at ask time: true only for a `technical` kind with no escalation and no reason. Open decisions keep their stored value, so an open technical decision is answerable under the default without re-asking. A decision with no `kind` (opened before kinds were stored) is answerable only when its stored `technical` is true. The owner sets `technical` through `decision delegate` (`--technical false` keeps a decision with the owner). The orchestrator can answer only when `technical` is true and `decision_delegation.orchestrator_technical` is not false. Owner-only decisions refuse every non-owner answer. The owner's `decision delegate DID --technical true` lifts a spend, credential or setting kind and an `--owner-required` reason (its stored `owner_required` becomes `null`), but never an escalated setting; a decision that keeps an owner-only kind or reason refuses `--answerers`. An answer stores `answered_by` and `answer_rule`; older decisions default to no named answerers, not technical, and no answer rule.

A withdrawal sets `status` to `withdrawn` while no answer exists. Its `withdrawn_by` is the verified identity that opened the decision (`asked_by`) or `owner`; `withdrawn_at` and a non-empty `withdraw_reason` are required with it. The `decision withdraw` event records `detail.decision`, `detail.reason`, `detail.blocks` and `detail.withdrawn_by`, and maps to `decision-withdrawn`. A withdrawn decision no longer blocks its tasks, is off the open list, and cannot be answered, delegated or withdrawn again; it stays in `decisions.json` and in event history. Each blocked task gets a note with the reason.

Answer rules are `owner`, `owner-named-agent` and `owner-technical-delegation`. The `answer` event records the caller in `agent` and `detail.answered_by`, and the rule in `detail.answer_rule`. Refused answers write no event. Answering adds a note with the answer to every task the decision blocked. Optional `notes` contains `{ "at", "agent", "text" }` comments added with `decision note`, including serve's owner form.

The orchestrator's technical rule takes precedence over `answerers`, including for a generated identity with a recorded orchestrator role. Listing that identity cannot authorize a nontechnical answer or one without project delegation. A sandboxed agent may answer through its broker only when the owner named its bound identity for that decision; successful brokered answer events retain the bound identity and carry `via: broker`.

## events.jsonl

Trusted watchers and dispatch supervisors consume lifecycle events as
software reactions. They run submission gates, dispatch review after the
tracked worker exits, accept independent passing review, merge accepted
PRs with green gates, and detect conflicting outstanding PRs after merges.
Conflict rework names the hand-written files. Generated-file repair can
advance the worker branch or leave a mixed merge prepared. Native
workers without an exit record need explicit review dispatch.
Tests, cleanup and source verification run when the submitted PR head
matches, even with unknown mergeability. CI, review dispatch and merging
retain their mergeability guards.

Generated outputs are declared by the fetched base's `package.json`
`tower-crane.generated` mapping, from exact relative file paths to npm script
names or `{script, blocks}`. Blocks use paired HTML `NAME:start` and
`NAME:end` comments; only their bodies are generated. Whole-file add/add
outputs require only the two branch versions. Partially generated documents
require an ancestor version to preserve hand-written text. See docs/cli.md for
the merge and regeneration contract. A matching GitHub conflict authorizes
the trusted automation executor to merge into an idle, clean task checkout
outside worker sandboxes and push without force. Other executors, live
workers, dirty checkouts and moved local or remote heads defer repair.
Trial conflicts involving generated outputs also defer when GitHub has not
confirmed a conflict at the matching submitted head, including stale clean
or unknown mergeability. Queue head checks wait without a merge gate or head
suite; post-merge sweeps leave the task unchanged. Subsequent reactions retry,
and mixed conflicts receive generated pre-resolution only after confirmation.

`generated merge` records `phase: prepared` before a generated-only push,
with `{previous_sha, sha, revision, base_sha, branch, path, generated, commands}`.
It also records `destination_sha`, a SHA-256 digest of the verified origin push
URL. The URL itself is not stored. The PR head repository must match the project;
the push destination must resolve to that same PR. Every push re-verifies it
and matches the digest, then uses the verified destination explicitly.
`commands` records generation command strings, exit statuses and summaries.
A prepared receipt retries the same commit after a failed push, or confirms
it after a push whose executor stopped before updating state.
The following automatic `submit` changes the sha and returns an accepted
task to `submitted`, preserving `submitted_by`, revision and historical
evidence. Its event adds `generated` and `base_sha`; gates and review at the
old sha no longer count. `generated merge` then records `phase: pushed`.
Mixed conflicts produce rework and a `phase: mixed` receipt with
`{sha, revision, base_sha, branch, path, generated, remaining, regenerated, commands}`.
Its `revision` is the new revision returned by rework; the executor refuses
the receipt if the task changes again before that receipt is recorded.
The checkout retains `MERGE_HEAD`, generated resolutions are staged and
`remaining` names the hand-written conflicts. `regenerated: false` means
source conflicts prevented generation; the worker must rerun the scripts
after resolving them. A generator failure in a generated-only merge aborts
the merge, restores the clean checkout and retains the submitted head.
Generators cannot change hand-written text outside declared blocks.

`ci completed` records a `ci-completed` hint with `sha` and `revision`.
The host delivers completion hints directly or through `ci webhook`
with GitHub check-run, check-suite or workflow-run JSON. The repository
must match, and only completed checks at active submitted heads count.
The hint triggers a new CI gate query; payload conclusions do not produce
evidence. There is no CI polling loop or webhook listener.

`automation` events record `{source, phase}` keyed by the triggering event
ID, or a stable digest for older records without IDs.
`running` adds executor `pid`, `host` and Linux `start_ticks`. `done`
deduplicates completed work. `deferred` keeps unknown or moved heads,
unknown mergeability and failed merge attempts retryable; `error` records
an exception. Terminal receipts include `error`, null without an exception.
Startup can retry deferred or errored work without a new lifecycle event.
A task has at most one observable executor.
An exited executor's start can be retried, while an unobservable executor
remains busy. At most `gates.executors` executors run on one host across
every watcher and supervisor. The running receipt in the event log is the
executor's lease: its terminal receipt releases it on exit, and its PID
identity releases it when the process dies. Running receipts from other
hosts do not count against this host's cap.
`automation queued` records a blocked notification's source, with
`executors` set to the cap when the cap blocked it rather than another
executor of the same task. Queued notifications run in drain order: submission
order, except that the queued notifications a `gates prioritize` event names
run first, the most recent request first. While one waits, a later
notification queues behind it even if a slot is free. A notification queued
after the request keeps submission order.
`gates prioritize ID --reason R` is operational ([Authority](#authority)); it
records a `gates prioritize` event with `reason`, `sources` (the sources of
the task's queued notifications at that moment), `queued` (their count) and
`authority`. Only those notifications move. It is refused when the task has
no queued notification, since it would change nothing. A notification queued
behind the task's own running reaction counts, but the running reaction does
not: its receipt is running and its executor is live, so it is no longer
queued. A dead executor's notification stays queued for its retry. `status`
lists the gate queue: running tasks, then the queued tasks in the order a free
executor takes them, then the tasks whose notification waits behind their own
running reaction, marked as blocked. `--json` carries it as `gate_queue` with
`running`, `queued` and `blocked`, each queued or blocked task with its
`prioritized` request or `null`. `inbox` carries the same `gate_queue`. Each executor drains the queue after releasing its slot; watchers
also retry their pending notifications on their next check. State locks cover only
reservation and receipts, never Git, GitHub, gates or model calls.
Automatic state changes and evidence use `agent: orchestrator` and
`via: automation`. Reactions establish an explicit authorization context
only after verifying the caller's authority or entering from the trusted
supervisor. Supervisors restore the dispatcher's command PATH for these
operations; agent commands retain their restrictive Git and GitHub shims.
This provenance does not replace gate command receipts.
`merge ID` takes the same reservation with source `merge:<uuid>`, waits
while a running executor is observable and records `done`, or `error` when
it refuses, as its release. It drains reactions queued behind it, as an
executor does. The merge queue takes the head of the line's reservation
with source `queue:<uuid>` around its merge, unless its own process
already holds it. Stack head checks ignore `automation`,
`automation queued`, `automation reconcile` and `gates prioritize` events,
which change no task state.
An accepted PR already merged remotely goes through the merge gate's
confirmation path. It records the matching accepted head and the PR's merge
commit without merging again, including after an executor dies before
writing its receipt. A PR GitHub reports merged at the accepted head needs
no current gate evidence or CI receipt base, so tasks accepted before merge
evidence existed are confirmed rather than refused. Stack members follow the
same path: confirmation reads only the member's own PR, runs no merge, retarget
or stack sync, writes no receipts for other tasks, and an open lower PR does
not block it. A lower member's failing review or stale CI receipt does not
block it either.
The confirmation lookup validates merge text and method before calling
GitHub. Failed current gates permit this read-only lookup; an open PR still
requires passing gates. Confirmation evidence records the lookup that
proved the accepted head merged, without querying and merging it again.
Waiters retain automatic events even when their actor matches the waiter.
Reactions run before event output filters, and active PRs catch up at
watcher startup except a default zero-timeout cursor snapshot.
`automation reconcile` records a fresh startup request for every active
submitted or accepted PR, with `{sha, revision, startup}`; `startup` is a
unique identifier for that watcher. It uses the same task reservation as
other reactions and queries current PR state regardless of earlier
completed receipts. A newly conflicting PR goes to rework even if its
base moved while no watcher ran. Matching gate evidence is reused rather
than rerun because of reconciliation. An idle startup writes no request.
A busy state lock defers the request to the existing watch notification
or fallback tick without holding the wait timeout.
`merge queue` events have no task and record `{phase}`: `running` with the
executor `pid`, `host` and Linux `start_ticks`, `requested` from a reaction
that found a live executor, then `done`, or `error` with `error`. `done` and
`error` also record `blocked`: `null` when the line drained, or
`{task, reason}` naming the first head of the pass that did not merge, and
`skipped`: the `{task, reason}` heads passed over in the pass. A head
waiting on GitHub's mergeability stops the line. A head refused for any
other reason (a closed or unreadable PR, a moved or differently merged head, failing
gates, a refused merge or head check) is passed over for the rest of the
pass and the next entry takes the line; each later pass tries it again.
PR lookup refusals and unreadable GitHub responses use this skip path;
unexpected execution errors still abort the queue.
An explicit `merge --accepted` requests a busy queue once and waits for
its observable executor to release the reservation before taking its own
pass. The wait uses `gates.tests_timeout_min` (20 minutes by default);
an unobservable executor or an expired wait refuses with a queue reason.
Its entries use the same task reservation and merge gate as `merge ID`,
after the head checks above. Passing CI evidence under `ci.capped_review`
permits a `MERGEABLE` PR whose merge state is `UNSTABLE`.
The command reports each task's merge, confirmation or refusal from the
queue and its recorded evidence, without fetching inbox findings. JSON
contains `results: [{task, ok, summary}]` and `remaining: [{task, reason}]`.
A skipped stack entry's refusal reason is reported for every unmerged
member, including the lower task whose PR or gates blocked the entry.
`queue skipped` records `{sha, revision, reason}` on that task once per
sha and revision. A `requested` after the
executor's latest `running` makes it record another `running` and drain
again with a fresh skipped set. A successful CI completion during the
previous pass can therefore advance a skipped head before the executor
releases the queue, without another notification. The line holds one entry
per accepted, unmerged PR task with no
unmerged task below it, extended up its stack by the accepted, linked tasks
directly above it; entries are ordered by their bottom task's latest
`accept` event at the current sha and revision.
`head check` records the head-of-line suite run on the entry's top task:
`{sha, revision, base_sha, command, members, ok, summary, commands}`, where
`base_sha` is the `project.base` tip merged into the head, `members` lists
the entry's task ids bottom up and `commands` lists the Git and shell
executions with their status. An ok check at the same sha, revision,
`base_sha` and command is reused. It is a merge precondition, not gate
evidence; it never changes `evidence`.

A timed-out head check also records `infrastructure_failure: true` and the same `timeout` detail as gate evidence. It stops that queue entry with its timeout summary, keeps the task accepted and performs no merge or rework. A later queue run can retry after the budget or stalled command is addressed.

The append-only log is the event source of truth. One JSON object per line: `{ "id", "type", "to", "at", "agent", "cmd", "task", "detail" }`, plus `"via": "broker"` on an event the state broker wrote for a sandboxed agent or `"via": "automation"` on a software reaction (provenance, not proof). Every append occurs under the state lock after validation and state writes. Refused commands append nothing, except the `ask` an orchestrator's owner-required change opens ([Authority](#authority)) and the `msg refused` a sandboxed agent's refused message records ([state broker](ladder.md#state-broker)). Each new event has a unique `E<uuid>` id. `cmd` preserves the command name (`task add`, `claim`, `spawn`, `check tests` and so on); `tower-crane spawn` counts its earlier `spawn` events to number agents. Older audit lines without ids remain readable; `wait` exposes their byte offsets for resuming.

A change of a guarded setting also logs one `setting` audit event before the command's own ([Authority](#authority)). A ladder change logs `ladder harness` and one `ladder set` per rung it changed, with the rung's new fields. A ladder or tier write made from the board or Settings carries `"via": "serve"` in `detail`. All serve writes require explicit owner identity and record `agent: "owner"`; other serve identities expose read-only views and refuse POSTs without state or event changes. Read-only Settings names `tower-crane serve --agent owner` as the command for enabling edits. CLI ladder and tier commands keep their existing agent rules.

The served board applies live state changes in place. Its fragment route, visible view, open task sheet, scroll offsets and focused control remain local to the browser and survive live updates; they are not written to the state directory. Form controls retain focus by their form's API action and button value. Removing the focused control from an open task sheet moves focus to the sheet heading. The server renders unique `data-preserve` attributes for controls, disclosures and scroll containers. Blocker rows use their reason kind and dependency or decision id; separate mentions within a row use their text offsets. Unexpected duplicate identities receive deterministic suffixes so rendering stays available; strict tests reject duplicates. Event rows use the log event id, with the existing log-index fallback for legacy events. Live updates restore open and closed disclosures before focus and scroll through one identity snapshot in every view. If the surviving focused control moves inside a closed disclosure, restoration opens its containing disclosures and preserves that open state. A control that remains unfocusable falls back to its nearest visible ancestor control. Settings carries that snapshot across reloads through a temporary entry in the tab's session storage, consumed on the next load. A reload before restoration completes retains the pending snapshot rather than capturing the new document's default position. The client sets `data-position-restored` on the document root only after restoring disclosures, focus and scroll, including the animation frame after a Settings reload, and clears it before the next replacement or reload. These browser identities add no state fields.

The initial view's animation frame resets fragment scrolling only if the route, page scroll and main scroll still match their positions at load. A delayed frame cannot overwrite the reader's subsequent scrolling or live restoration.

A `spawn` detail includes `role`, `rung`, `agent`, `harness`, `model`, `profile`, `pid`, `host`, `start_ticks`, `cwd` and `log`. `model` and `profile` may be null; `start_ticks` is the Linux process identity when available. Codex adds `codex_home` to find its exact session under a custom `CODEX_HOME`; legacy events fall back to the current `CODEX_HOME` or `~/.codex`. Both foreground and detached output has a log. A `spend` detail is the entry above; automatic entries name the spawned agent; the audit event names the collector or waiter that recorded them. `spawn exit` records the foreground exit code and rung. A release of an exited spawned claim records `{ reason, holder, status, exited_spawn }`, where `exited_spawn` contains only `{ pid, log, code, size }` observed at release. Unknown exit codes and unavailable log sizes are null. No log text is copied into task notes, release events or worker-exited events. The shared observer records exit wakeups and spend without releasing the claim.

Gate events have `{ "type", "ok", "sha", "ref", "revision", "source", "commands" }` in `detail`, plus optional `confirmed_failure` matching the evidence entry. Acceptance, merge, task views and the sketch match software evidence against these events; a missing or unreadable log supplies no gate proof, while malformed lines are skipped. Keep the log with tasks.json when copying or restoring state.

`type` identifies the event and `to` names the recipient. Every state change goes to `orchestrator` unless a message supplies an explicit `--to`. Commands map to notifications: submit to `submitted`, accept to `accepted`, rework to `rework`, successful merge evidence to `merged`, msg to `worker-message`, owner task or decision notes to `owner-comment`, ask to `decision-opened`, answer to `decision-answer`, decision withdraw to `decision-withdrawn`, release to `released`, and owner-done to `owner-done`. Review and other gate evidence wakes as `evidence`; other changes keep their command name as the type. There is no notification allowlist to hide a new state change: a default `wait` skips only the bookkeeping that arrives with every tool call or lease tick (`hook progress`, `hook report`, `hook inbox`, `renew`, `spend`, `spend live`, `spawn session`, `inbox snapshot`, `inbox ack`), and every event recorded as `owner` reaches the orchestrator whatever its `to`. A `msg` detail is `{ to, text }`, plus `steer: true` when it was sent with `--steer`.

Harness adapters use the CLI `hook` command under the identity fixed in `homes/<agent>/hook.json`. The binding contains `{agent, task, state, harness, attempt}` and cannot name owner. An orchestrator-rung home adds `role: "orchestrator"` and `after`, the byte length of `events.jsonl` when the home was built: its `inbox` and `stop` deliver the events a default `wait` would return after that offset, as a list of ids, kinds and authors without detail, and acknowledge them with `hook inbox` receipts. Its `stop` with nothing pending returns `{block:false, hold:true, offset}` while any task is still open or an accepted PR remains unmerged, and the bridge blocks in `wait --inbox --after offset` before asking again. The bridge resolves its own binding from the dispatch environment, accepts no binding path, and refuses a binding identity that differs from the caller. Claude and Codex sandboxes protect the generated home and hide every other agent home; Codex session storage is scoped to the agent. Agy has a generated startup configuration, but native enforcement is unsupported. Its emitted permission entries are requests, not a guarantee that other homes are hidden or that commands are confined. Its capabilities remain false, so it receives no broker token. Other harnesses have bindings and command shims but do not yet have permission renderers. Payload fields never override the binding.

Tool progress appends one `hook progress` row to `progress/<agent>.jsonl`. It takes no lock and reads no state, and a failed append drops the row. No state decision reads it; the supervisor counts a change to the file as activity, as it does for the agent's log and progress paths. Progress rows written to `events.jsonl` before this file existed stay in place, so byte cursors hold, but state snapshots skip them.

An inbox poll, the `UserPromptSubmit` hook and the poll after each tool hook, reads the event log without the lock and returns empty context at once when nothing is pending. With messages pending it tries the lock once, without waiting. A busy lock returns empty context and leaves the messages unread for the next hook. The bridge also turns a failed progress append or poll into empty context with a note on stderr, so neither fails the harness turn. Other hook calls, explicit acknowledgements with message ids, and supervisor writes keep the 65 s per-call limit, which covers the 60 s lock bound plus 5 s; generated registrations allow 135 s for the two calls after a tool. An orchestrator's `Stop` keeps its one-day event-wait allowance.

`homes/<agent>/policy.json` holds the shim permissions, the task's recorded `branch` and the project's recorded `repo` at dispatch. With `gitPush: branch`, a push to another machine must use `origin` in that GitHub repository, and every destination must resolve to `refs/heads/<branch>`. Origin's configured fetch URL must match `repo`; configured push URLs must equal the fetch URL, and all resolved push URLs must equal the resolved fetch URL after rewriting. The current checkout and environment cannot replace the recorded branch or repository. See [CLI](cli.md) for push restrictions and the local test repository exception.

Hook state lives in the event log, except tool activity, which goes to the agent's progress file:

| --- | --- |
| `hook inbox` | `{messages: [event id, ...]}` acknowledging messages delivered to this event's agent |
| `hook progress` | `{harness, tool}`, in `progress/<agent>.jsonl` only; activity for supervision |
| `hook background` | `{harness, attempt}`; a Bash call with `run_in_background` started in this dispatch attempt |

Unread messages are `msg` events with `detail.to` equal to the bound agent and ids absent from its `hook inbox` receipts. Receipts use the state lock; a poll with nothing pending reads the log without it. Payload `ack:false` returns context and message ids without a receipt; a later inbox call with those `ids` writes the receipt. OpenCode delivers only to the session captured by the dispatch's first chat callback and writes its idle delivery receipt after `promptAsync` succeeds. Failed requests leave messages unread. A stop held for unread messages acknowledges them without emitting a final report. Once stopping is allowed, `hook stop` also emits a `msg` to `orchestrator` describing submission state and the last report. Identical reports for a dispatch are deduplicated; a changed report or submission state emits a follow-up. A supervisor stop after process exit leaves unread messages queued. Rework and transient resume prompts include pending messages and acknowledge the included ids after launch. A dry run does not acknowledge. See [CLI: event wakeups](cli.md#event-wakeups) for each harness's injection and stop limits, including Codex notify and agy's missing resume adapter.

`tower-crane wait` watches this log from an exclusive id or byte cursor and returns the first matching notification as one JSON line (`--follow` prints an id-only line per notification instead and keeps running). Its `offset` is computed when reading and counts UTF-8 bytes through the newline; it is not stored in the log. Default `now` skips complete historical lines. Save the returned id or offset and pass it to the next wait so events during handling are not missed. Filters combine recipient, task (including a decision's `detail.blocks`) and event types. Writes by the waiter's agent are skipped, except events recorded as `owner`, `via: automation`, and `worker-exited` and `stall` observations. Owner input remains visible when the waiter also runs as `owner`; observations reach the waiter that appends them. Timeout is a separate `{"type":"timeout","offset":N}` result, not an event. Its cursor includes complete lines skipped by filters. See docs/cli.md for options.

Startup and resume without a saved cursor use `wait --timeout 0` to take the current complete-line offset before reading state once. This snapshot emits no observations. The next blocking wait starts from that offset and observes current exits and stalls, keeping events that arrived during reconciliation without replaying history. Owner POST routes preserve serve's identity and require it to be explicitly `owner`; non-owner serve renders no owner forms and refuses those writes.

`spawn` records the job in `role`, the ladder `rung`, generated agent, pid, host, Linux process start ticks when available, and log in its event. The wait engine uses the shared `lib/processes.js` detector for a worker's exit without submission, including failure before claiming, and appends `worker-exited` with agent, pid, attempt, log path, exit code and log size. Log tails remain in the log file; views read them live. It also appends `stall` when both the lease and claimant progress are stale (no progress within the most recently granted claim or renew lease interval). Other claimant writes advance progress; claim and renew do not. Submitted tasks do not produce these events.

Only `owner`, `orchestrator`, spawned agents whose recorded role is `orchestrator`, and verified spawn-monitor collectors run automatic exit and stall observations. The collector CLI must have the recorded monitor as its parent, with a locally visible process matching the recorded host and Linux start ticks when available. Sharing a worker's agent name grants no observer role. Worker, reviewer and other observer identities consume events through `wait` without probing peers or appending lifecycle observations; their explicit usage collection does not scan other tasks. Orchestrators and monitors must run with visibility of worker pids, since `ESRCH` in an agent sandbox can describe a live but hidden worker. Foreground collection keeps the dispatch caller's audit identity; spend entries still name the spawned agent.

New spawns run through the existing `spawn-monitor.js` exit observer, which is the harness parent in foreground and detached modes. It renews the same claimant's most recent lease duration when half the lease remains, while the child runs or a rerun is pending. This margin leaves half a lease for delayed state writes. A worker's submission, release, cancellation, replacement of its claim or a newer spawn stops lease keeping and retries. Reviewers launched on a submitted task keep their retry budget while its submitted sha and revision remain unchanged. Reruns preserve the generated agent, claim `since`, worktree, resolved route and log. A `spawn retry` event replaces the current harness pid without counting as another dispatch. Resumed retries share a spend source; fresh retries record `fresh: true`, `resumed: false` and a new log byte `log_start` for their separate usage receipt. A state-lock timeout keeps the scheduled attempt pending; it does not consume another retry.

Exit 75, SIGTERM, SIGINT, and nonzero exits with a harness-level provider 5xx or outage are transient. Evidence comes from Claude error records (`is_error` or `api_error_status`), Codex `error` or `turn.failed` events, or harness stderr. HTTP 429, rate-limit, temporarily-unavailable and overloaded messages also qualify when reported inside those harness error records. Plain text cannot substitute for an error envelope for these capacity signals. Assistant messages, tool results and other agent output do not classify an outage. The supervisor retries the same route with exponential backoff, capped by `max_backoff_ms`. A provider outage after the route's retry budget advances to its next configured fallback. Exit 75 or a signal alone does not switch routes. A permanent exit, exhausted fallback list, or missing supported session without fallback-enabled outage recovery records `blocked` with a reason and leaves the claim for recovery. A successful exit without submission records `waiting`. A live single-tier stalled process records `blocked: no progress paths or CPU activity`, emits `stall`, and keeps its lease; path, claimant or CPU progress restores `running`.

A structured harness policy refusal advances to the next fallback without outage retries, including when the harness exits zero. Codex and command adapters accept `refusal`, `response.refusal.done`, an `item.completed` refusal item, or an agent-message item with a non-empty `refusal` field. Claude and command adapters also accept `assistant` or `result` records with `stop_reason: "refusal"`, `subtype: "refusal"`, a message stop reason, or a refusal content block. Quoted policy text and tool output do not qualify. A refusal without a remaining fallback blocks and returns a nonzero dispatch result.

Every route switch starts fresh with the original brief and task, the same generated agent and worktree, and a rebuilt isolated harness home. It never passes the previous route's session id to resume, even if both routes use Codex. The claim remains unchanged, the retry counter resets to zero, and the new route has its own bounded retry budget. `spawn fallback` emits type `spawn-fallback` to the orchestrator, recording the new `route`, zero-based `route_index`, model, profile, harness, session, pid, log byte `log_start`, reason, and previous process/route detail. Retry, phase and exit records carry the current route metadata. A dispatch that switched routes is not eligible for rework resume; its next dispatch starts fresh after the previous worker has exited. Rework refuses another dispatch while that worker is live or its exit is unverified, even when a fresh session is required.

Ranged workers use a separate quality path. A failed independent review or confirmed tests, clean or CI gate failure at the current submission, an exit without submit (including exit zero and exits before claiming), or a confirmed supervisor stall climbs one tier within `tier_range`. CPU-based stall confirmation requires Linux process metadata. A stall terminates the old worker group and waits for pipe closure and group cleanup before recovery. Review failure waits for the submitted worker to exit. A brokered review records the climb but leaves launching to the host monitor or orchestrator wait; the broker executes no repository commands. Recovery collects its usage, clears the claim, sets rework, records `escalate` and dispatches a new agent with the original brief and rework reason. A climb never resumes a session, even when both rungs have identical models or routes. `recover ID` and concurrent observers deduplicate the same failure under the lock. If dispatch is unavailable or capacity is full, the recorded climb stays pending for `recover` or a subsequent orchestrator `wait`.

Quality recovery uses the latest eligible verdict per review or software gate at the current head and revision. `confirmed_failure: true` is recorded by the software gate runner and matched to its audit receipt. It denotes a failed test command, a completed cleanup scan with HIGH findings and no scan gaps, or a completed failing CI run. Configuration errors, incomplete observations, pending CI and missing workflow results remain unconfirmed. A later passing verdict for the same gate removes its failed-attempt trigger. A later passing verdict supersedes an earlier failure; self-reviews and stale verdicts do not replace it. While a worker monitor is running or its exit cannot be verified, recovery needs its matching terminal `spawn exit` receipt with `active: false`, even after submission. A parent's exited PID or an exit notification does not prove its descendants stopped. When the monitor is verified exited, authorized host observers must also verify that its worker process group is gone before recovery. POSIX harnesses start detached, so the recorded launch PID is their process group id. On Linux the host checks that group and ignores zombie members that cannot execute. A parent exit or `worker-exited` notification alone cannot authorize replacement. Live or unverifiable groups keep the failure eligible for retry and record a deduplicated `recover waiting` event and task note with the reason. `recover --json` returns that reason in `waiting`; unsupported platforms or inaccessible process metadata require a terminal cleanup receipt.

`rework` captures and records a known failed attempt before its submitted status is lost. The tier climbs immediately, or the range ceiling opens its owner decision, even if the worker still has pending cleanup. Its fresh dispatch remains pending until the cleanup guard passes. Usage collection can enrich current rung totals after cleanup; the recorded climb retains its snapshot.

Orchestrator `wait` treats recorded but unhandled failures as recovery candidates independently of exit-notification deduplication. Recording `worker-exited` through spend collection or an earlier wait does not consume a climb. A recovery lock timeout leaves the failure eligible for the next watcher or timer check; its notification remains recorded once.

At the maximum tier, recovery records `to: null` and opens one free-text decision blocking the task. The owner can change the plan, extend its range, retry or cancel; answering alone does not dispatch a worker. Availability failures exhausted on the same rung record `availability_failure: true` on the exit receipt and do not quality-escalate. Single-tier tasks retain manual recovery. A stopped or failed supervisor does not initiate a climb itself; `wait` can recover a verified worker exit after a lost supervisor. Unknown process identity or a live worker never authorizes replacement. Native workers without a spawn receipt keep manual exit and stall recovery.

Both rework and transient retries use the resumable-harness policy in `lib/spawn-session.js`. Codex resumes the exact thread id from its log. Command harnesses receive stable `TOWER_CRANE_SESSION` and the zero-based `TOWER_CRANE_RETRY` attempt counter within each route. Resumed attempts receive only a short interruption note, including the previous exit code or signal, through the prompt argument or `{prompt}` substitution. Claude reruns fresh with a new reserved session id, the original brief and the interruption note; measured native Claude resumes rewrote the fixture's cache. With a configured fallback list, provider outages without a supported session rerun fresh on the same route until its budget is exhausted. Other transient exits without a session adapter block. `--fork-session` is not used for transient reruns.

Child exit and pipe-close events wake the existing monitor immediately. Progress-path walks and CPU sampling run once per second, independent of state events. The monitor checks lease renewal on that interval or when events change, and caches loaded state until `events.jsonl` size or mtime changes. A one-second interval bounds normal lease and stall observation delay without walking a multi-hour agent's worktree ten times per second.

On POSIX, every natural agent exit terminates the agent's process group, including successful exits. Background processes deliberately left running by the agent are terminated too. The monitor sends SIGTERM to the remaining group, allows five seconds for cleanup, then sends SIGKILL to survivors. Stopping the monitor uses the same shutdown path. The grace period matches the software-gate command runner and lets a harness flush its output. Reruns wait for the previous group to stop and its output pipes to close, including descendants with redirected output. Windows uses `taskkill /T /F` when stopping a live harness. Natural Windows exits wait for pipe closure without sending a PID-based tree kill after the parent has exited.

Signal retries use the signal reported by Node's child-process observer. Windows self-termination reports an exit code instead; a Windows adapter can use exit 75 to identify a transient stop.

Command harness `{brief}` context is an exclusive mode-`0600` temporary file, with no per-copy directory. A single unlink removes the complete resource. The monitor removes the current route's copy after stream closure and process-group shutdown, and on startup or supervision failure. A failed dispatch stops its supervisor and waits for closure before removing any remaining copy and returning. `spawn --wait` removes its copy before returning on normal, nonzero and signal exits.

The CLI transfers a spawn job through a private file in its startup cache directory, then removes it after the monitor reads it and reports the harness pid. Prompt size stays bounded by the harness argument, without a duplicated supervisor argument. Foreground output is captured by the monitor through the inherited log descriptor before it is forwarded to the CLI. Exit classification waits for both harness pipes to close, including when the dispatch CLI is busy rendering.

`spawn` and `spawn phase` events record `{ agent, pid, monitor_pid, host, phase, retry, active, reason }`, plus process identity when available. `phase` is `running`, `retrying`, `waiting` or `blocked`; text views render `retrying N` and `blocked: text`. `status` JSON includes `runs: [{ id, run }]`; `task show` includes `run`, or null after a lifecycle boundary. The board and serve display the same recorded phase. Phase-only writes rerender saved sketches even when task data does not change. A live supervisor with an active run suppresses interim `worker-exited`, early spend collection and non-claimant recovery during backoff. Terminal exits use the shared locked observer to emit one exit notification and collect usage once per route and fresh retry invocation for the dispatch, using log byte boundaries to keep sessions, models, profiles and harnesses separate. The primary source remains `spawn:<agent>` (or its resumed attempt source); fallback sources append `:route:<index>` and fresh retry sources append `:retry:<retry>`. Each invocation contributes to task spend; cumulative usage within a resumed session is counted once. Repeating collection enriches or keeps those entries without double counting.

Exit and stall observations are rechecked and deduplicated under the lock, using a `detail.source` key for the current claim and pid or lease/progress deadline. Concurrent waits see the same event. For single-tier tasks, detection reports the condition without clearing the claim or changing task status. Recovery uses `release --reason`, followed by a new claim or spawn. Ranged tasks use the quality recovery above. Directory watching plus an internal one-second stat and process check keeps callers blocked until an event or their deadline. The engine closes all watchers and timers when a wait ends.

An incomplete final line remains unread until a subsequent append; after a crash, that append starts a fresh line without deleting the damaged bytes. Readers skip the damaged record and continue. The log must never be truncated or replaced; a cursor beyond its end is refused.

Each `spawn` also records `route`, `attempt`, `session_id` and `resumed`. A fresh spawn after an isolated session file is missing records `resume_fallback_reason` with the reason it did not resume. `route` holds the resolved rung fields. `attempt` counts spawns for this job and task, including resumed attempts that keep their agent name. Resumed attempts use a distinct log named `<task>-<agent>-attempt-<n>.log`. A resumed Codex dispatch includes `usage_before`, its session's cumulative counters before the new turn. Usage collection subtracts this snapshot; if it is unavailable, the resumed attempt's usage stays unknown. Its spend source is `spawn:<agent>:attempt:<n>`; fresh spawns keep `spawn:<agent>`. Dispatch collects the previous attempt before starting a resume, and repeated collectors update the same attempt receipt.

A `startup` event precedes each started agent's `spawn` event, and each route fallback's `spawn fallback` event: the receipt of what the agent was given, `{ agent, role, harness, goal, target: { id, title, acceptance }, rules: [{ path, scope, loaded, bytes }], rules_bytes, rules_tokens, instructions_file, prompt_bytes, prompt_tokens, resumed, receives_prompt, attempt }`. `target.acceptance` is the number of acceptance items, not their text. `scope` is `global`, `project` or `import`; `loaded` is `harness` (importable by the harness at start), `read` (the prompt tells it to read the file, without claiming it was read), or `system` (a Claude/Codex review snapshot). For agents using path imports, Claude quotes paths containing tabs with literal tabs, and marks paths containing line breaks `read`. Claude imports include the generated home's hop in its five-hop limit; files beyond that limit are marked `read`. Codex prefers `AGENTS.override.md` over `AGENTS.md` per directory. Other harnesses receive their global files as `read`. A command dispatch requires `{prompt}` or `{brief}` in its command argv; without either, spawn refuses before writing a startup receipt. Isolated reviewers also record `system_bytes` and `system_tokens`, separately from the task's user prompt. Claude's reviewer `instructions_file` names an empty `CLAUDE.md`, since its static text is passed by flag; Codex's names the populated `AGENTS.md`. Token estimates are bytes divided by four, rounded up, not measured API cache usage. A resumed session got these with its first prompt.

`session_id` is null on a fresh dispatch and names the reused session on resume. Once stdout exposes the id, an append-only `spawn session` event repeats the attempt's spawn detail with its `session_id`. Match by task, agent, pid and attempt; do not rewrite an earlier event. Codex reports it in `thread.started.thread_id` and Claude in its JSON result. A command harness can emit either record. Session ids stay out of prompts and briefs. On rework, resume selects the most recent worker attempt only when it belongs to `submitted_by`, its session is known, its route and worktree match, and the previous process has exited. Before an isolated Codex resume, spawn checks for the matching rollout under `homes/.codex/<agent>/sessions`. Native Codex resumes; native Claude starts fresh with the review note because measured resumes rewrote its cache. A command adapter can resume through its `{session}` protocol. A missing session or changed rung, route, harness or worktree permits a fresh spawn with the full brief and review note. Review spawns do not resume.

Foreground and detached `spawn exit` events and `worker-exited` observations record the attempt as well as the agent, pid and exit code. A receipt with an attempt matches that attempt's launch by task, agent and pid. A receipt without an attempt matches the latest preceding `spawn`, `spawn retry` or `spawn fallback` with the same task, agent and pid. Both formats release an unclaimed reservation and prove exit for resume, usage collection and recovery. An earlier receipt cannot prove that a later launch exited, even when its pid is reused. The shared resolver is `lib/processes.js`'s `exitSpawn`; `lib/spawn-session.js` exports the shared `exitedAttempt` and `eligible` checks for dispatch and usage collection. When observing an older spawn without an attempt field, the writer derives its attempt from its position in that task and job's spawn history.

A `submit` event's `detail` records `previous_sha` (null on the first submission), `sha`, `branch`, `pr`, `summary` and `scope`, the scope gate's `{ basis, named, outside }` or `{ error }` ([CLI](cli.md)). A named path of `./` represents the whole repository when the brief names a checkout or registered worktree root. A spawned worker's first submission also records its `claim` for restoring the same worker on rework. Resubmission with no lease leaves that receipt intact in the audit trail. Both the replaced head and the new head are recorded, including a submission after rework and a new claim: rework preserves the old sha.

Agy homes place native settings and the rendered `agents/gishra-<job>.md` below `homes/<agent>/home/.gemini/`. Startup receipts name that generated file and mark project house rules as `read`. Original user memory and modular rules are excluded from the prompt, receipt and generated read grants, including imports that resolve to them. Agy permits `tools` and `mcp` opt-ins; its only safe `args` flag is `--print-timeout`, and output remains JSON. Agy has no live message or session-resume adapter. Command shims remain available; real agy is unbrokered and owner-required because its sandbox capabilities remain false. The generated settings do not provide a native enforcement guarantee; failed probe attempts are recorded in ladder.md. See [ladder.md](ladder.md#agent-files-and-homes) for the documented native configuration.

## Orchestrator inbox

`inbox` derives a snapshot from one state read and current GitHub observations. It does not change tasks or consume messages. JSON has `items`, live gate `executors` and `gate_queue`, the same queue `status` shows; text ends with the executor count and a `gate queue` line. Each item has a stable `id`, `kind`, nullable `task`, finding data, and `action: {command, argv}`. Text output includes the same findings and command. Kinds include `gate_failed`, `review_failed`, `rework_ready`, `ready`, `dead_claim`, `decision`, `accepted_unmerged`, `revuto_failed`, `codeql_alert`, `head_changed`, `message`, `stall`, `decision_answer`, `owner_comment` and `github_error`. Open decisions carry their question and options. A technical decision is answered by the orchestrator under the existing answer authority; an owner-only decision (one with `escalation`, `owner_required`, or a `kind` other than `technical`) needs the owner's supplied choice. Answered decisions retain their choice, note, author and blocked tasks until acknowledged. Owner task and decision comments retain their text and target until acknowledged; a later comment creates a new item.

`gate_failed` items report the latest audited failure for each software gate (`tests`, `clean`, `sources`, `ci`) at the current head and revision of an unmerged submitted or accepted task. They include the gate name, summary, ref, audited `confirmed_failure` flag and any `test_failure` names and output tail. Confirmed code failures resolve through rework carrying the failure summary and its test names. Pending checks, observation failures and infrastructure failures offer `check GATE ID`; infrastructure findings also retain their timeout metadata. A later pass, rework, a new head or revision, or a confirmed merge clears the finding. Failed gates cannot be acknowledged away. On an open mergeable accepted PR, a stale or unconfirmed failed required software gate offers its check command instead of `merge --accepted`; confirmed code failures offer rework instead; after that rerun passes, the inbox advances to the next blocker or merge. Review blockers still require rework.

Review findings use the latest eligible failed evidence at the current head and revision. `review_failed.findings` contains the last `Review (Tower Crane` issue comment whose header names that SHA, read from all pages of the linked PR's comments. `finding_count` uses the finding lines or declared count and is null when an unposted summary has no count. `findings_source` names `comment` or `evidence`. A failed linked-comment fetch leaves `findings_complete: false`, the evidence summary and an explicit `github_error`. Unposted reviews without a matching comment retain their full evidence summary. Rework items include the engine reason and readiness blockers. Process observations use the shared PID, host and start identity detector; unknown processes stay live. Accepted PR items include GitHub state, mergeability and the refusal reason. A PR already merged at its accepted head remains an `accepted_unmerged` item with `confirmation: true` and `merge --accepted` until the audited local merge receipt exists. Its obsolete gate and review findings are replaced by that confirmation action. Reading the inbox does not record a merge, and a remotely merged different head still requires rework. Submitted PRs include uncapped, nonignored revuto failures and its inline comments at that head, and open CodeQL alerts from `refs/pull/N/head` and `refs/pull/N/merge`. The PR API resolves the current head, base and synthetic merge commit; both merge parents must match the submitted head and current base before merge-ref alerts count. Alert instances must match the resolved ref and commit. Stale merge parents produce an explicit GitHub error. Duplicate alerts across refs appear once. List endpoints paginate. GitHub errors are explicit findings, never empty success. A moved PR head returns to rework so a worker verifies and resubmits it through the existing claim ownership path.

`inbox --ack ITEM` emits `inbox ack` with `{item}` for a handled message, stall, decision answer or owner comment. It cannot dismiss task or GitHub findings. `wait --inbox` refreshes at startup and once per minute, bounding GitHub requests independently of local hook traffic. It emits `inbox item` for new or changed findings and `inbox snapshot` with item fingerprints to deduplicate concurrent followers. A finding that clears and later returns wakes again. Snapshot and acknowledgement receipts are quiet bookkeeping. T98's plugin watch and orchestrator Stop hooks enable this refresh and direct the session to `inbox`.

Inbox reads, acknowledgements, observation and batch actions require a verified orchestrator or owner role; a verified worker identity alone grants no access. Batch actions preserve the authority table and existing checks. `spawn --ready` selects ready todo and rework tasks without live workers and dispatches serially within the worker limit, rechecking under the spawn lock. `release --dead` rechecks each claim under the release lock and never releases an unknown process. The worker broker rejects this unscoped batch before executing it; a worker can still release its own named task with `release ID --reason R`. `rework --from-review ID` retrieves the full matching review body outside the state lock and copies it, including every finding and the comment link, into the rework reason and brief. A linked comment that is unavailable or does not match the submitted SHA refuses without a state change. The command rechecks the head, revision, repository, PR and exact failed review under the rework lock after fetching; a newer verdict or changed task refuses. `merge --accepted` holds the existing queue executor and runs current-base checks and pinned stack merges; refused and pending entries remain for the next invocation while independent mergeable entries proceed. Automatic queue reactions still wait for unknown GitHub mergeability. Already merged PRs at the accepted head are confirmed without current gate evidence. Linked members still require every lower head to pass.

`mcp` serves newline-delimited JSON-RPC on stdio with `inbox`, `spawn_ready`, `merge_accepted`, `rework_from_review` and `release_dead` tools. Initialization, ping and tool discovery do not read or require project state, including outside a Git repository. Each tool call resolves the bound project location and verifies the caller role; missing-project and authorization errors return MCP tool errors without closing the connection. It validates tool arguments and offers no shell, identity or state overrides. Spawned Claude and Codex orchestrators receive this server in their generated homes; workers do not. The plugin ships the server registration and five matching command documents. No new authority class or owner grant is introduced.
