# CLI

Command tables are generated from `COMMANDS` in `bin/tower-crane.js` with `npm run docs:generate`. CI rejects drift; keep further contract details outside the generated blocks.

`tower-crane <command> [args]`. `tower-crane --version` prints the package version. Every command accepts `--state DIR`, `--agent NAME`, `--json` (machine output on stdout: the task, decision, project or list the command touched) and `--help`. Exit status: 0 done, 1 refused (with the reason on stderr), 2 usage error or wait timeout, 3 lock not acquired within 60 s. `validate` and a failing gate print their report on stdout and exit 1; `spawn --wait` exits with the agent's code, or 1 when a harness login failure ended the dispatch. `wait` always prints one compact JSON line, including with `--json`. If a reader closes stdout or stderr, the CLI treats the resulting `EPIPE` as a quiet close, finishes the command and any state write, lets the other output stream drain, then exits with that command's status.

Agent identity comes from `--agent NAME`, then `TOWER_CRANE_AGENT`. With neither, `owner` is used only when stdin and stdout are both TTYs and `TOWER_CRANE_TASK` is unset. Otherwise the command exits 2 with `no agent: pass --agent NAME or set TOWER_CRANE_AGENT` and writes nothing. An empty or whitespace-only identity exits 2 with the same message. Help needs no agent.

Resolving either identity source to `owner` (the terminal fallback included) is refused unless the owner runs the process, and the refusal starts with `owner identity needs a process the owner runs (docs/state.md#agent-identity)` and names the rule that failed ([state.md: Agent identity](state.md#agent-identity)):

- `TOWER_CRANE_TASK` is set: a task process never acts as owner.
- `TOWER_CRANE_AGENT` names any identity other than `owner`: a process started as another identity, such as `orchestrator` or a spawned `worker-T1-1`, never acts as owner, whatever `--agent` it passes.
- stdin or stdout is not a terminal, and `TOWER_CRANE_OWNER_KEY` does not hold the owner key. The key is the owner's own credential for scripts and other non-interactive owner commands: `tower-crane owner-key --agent owner`, run at a terminal, creates it (mode 600, in a mode 700 directory) as `owner/key` under the canonical `owner_config_dir` recorded in `project.json` (`~/.config/tower-crane/owner/key` by default) and prints its path, never the key. Every spawn creates that directory and hides it from claude's and codex's sandboxes, so no sandboxed agent reads the key. The CLI captures `TOWER_CRANE_OWNER_KEY` privately and removes it from its environment at command entry, before state discovery or authentication can start a child. Nothing it starts, including Git used to discover the state directory, agents or gates, inherits the key. Terminal checks leave piped stdin unchanged for hooks and command input. An unsandboxed process running as the same user can read the user's files, the key included; the key keeps owner identity out of reach of `--agent owner` alone, not of a process that deliberately reads the owner's secrets.

The credential location for an initialized project comes only from `project.json`, never from the command's `TOWER_CRANE_CONFIG`, `HOME` or `USERPROFILE`. Only an explicit owner's `init` at a terminal records the user file's folder there. Any other `init` records the default `~/.config/tower-crane` under the account's home directory, and a headless owner `init` checks the owner key in that default directory. Changing those variables does not redirect authentication or a pinned sandbox denial. An absent, invalid or missing recorded credential refuses headless owner access. For a project without `owner_config_dir`, only an explicit owner at a terminal can record it with `owner-key`; an existing binding is never replaced. Until it is recorded, spawning still works and hides `owner/` under the spawning environment's resolved Tower Crane config directory, where a terminal `owner-key` would create the key. This denial does not establish a binding or allow owner authentication.

Guarded settings and commands are operational or owner-required, per the one table in [state.md: Authority](state.md#authority). The orchestrator or the owner makes operational changes; the orchestrator's owner-required change opens a decision for the owner (exit 1, naming the decision) and changes nothing until the owner answers `approve`; the orchestrator then runs the same command again, which applies that approval once. Every allowed change of a guarded setting, from the CLI or the board, appends one `setting` audit event ([state.md: Authority](state.md#authority)). `tower-crane authority` lists the table. The owner is the resolved name `owner`, supplied explicitly by `--agent owner` or `TOWER_CRANE_AGENT=owner`; the terminal fallback never grants authority. Workers and reviewers ask the orchestrator for operational changes with `tower-crane msg --to orchestrator` or a task note. Any agent may release a spawned claim verified exited under the lock.

Decision delegation (`decision delegate` and `project set --decision-delegation`), waiving tests, clean or CI, waiving review when no reviewer is capped or down at the submitted head, and releasing another agent's live or unverified claim are owner-required. The owner acts with explicit identity; the orchestrator can apply the identical request after the owner's one-use approval. The terminal fallback never grants owner authority. Clearing or replacing an existing `needs_owner` reason and `owner-done` are operational; waiving a capped or down review is operational. An agent requests owner-required action with `tower-crane ask --question Q --kind K --setting KEY` or a task note.

If the owner's successful write satisfies a request's fields, it retires the matching open or approved request even when the same command also writes additional settings. Targets and replacement field values must match; JSON formatting and object key order do not change the value. A subsequent orchestrator attempt opens a new decision; it cannot use that old approval to overwrite a later owner choice. Failed writes, including acceptance or spawn failures, leave the approval available.

For budgets, retirement matches the requested hours and tokens even if writing them now lowers or repeats the current limit. The owner setting 20, then the approved amount 10, then 5 leaves no approval the orchestrator can reuse to restore 10. Authorization and audit still use the current raise/lower classification.

Use `project set --budget-hours null` or `--budget-tokens null` to remove a project limit; use `task update ID` with the same flags for a task limit. Removing a finite limit is owner-required: the orchestrator's command opens a decision and must be rerun after approval. Task and project budget requests have distinct targets. The same flags accept `null` during `init`.

For personal fallbacks, the owner writes the whole replacement list. A write of the requested list retires its approval even if only an operational field differs or the list is unchanged; the audit still describes the actual field changes. A different file, rung or replacement list does not satisfy the request.

A fallback route that carries authority (a grant, an unsandboxed or `command` harness, `web_mcp`, `mcp` or a non-built-in tool) counts only as `ladder set --fallbacks` wrote it at that position: spawn skips a route another edit of the user file put there or changed, with a notice, and `ladder show` lists it with the command that approves it. Routes that only name a model, profile, provider or effort on a sandboxed harness need no approval ([Authority](state.md#fallback-route-grants)).

Personal fallback grants are compared only with the previous personal routes, never a project's primary. Routes that inherit their harness are checked across compatible harnesses; switching between inherited and explicit harness selection needs any new reach grants approved. An explicit sandboxed harness avoids dependence on another project's primary. Once a personal grant exists, model tuning remains operational.

Owner primary-ladder writes settle matching reach requests for the tools, harness and arguments they write, including grants already present. Owner task-kind writes likewise settle a pending downgrade request after the kind has changed, including a repeated kind value. This retirement does not change which edits are operational or owner-required.

Waiver approvals are bound to the task, SHA and revision. After an acceptance, dependency or capability change, rerunning the same `accept --waive` command opens a new decision even at the same commit. Old approvals without a revision cannot authorize acceptance or back orchestrator waiver evidence.

Release approvals identify the task, holder and claim start time. A lease renewal preserves that identity; a replacement claim requires fresh approval even for the same holder. Browser-kit approvals identify the resolved personal-config file as well as the server list, so a retry with a different `TOWER_CRANE_CONFIG` cannot reuse the approval. Legacy requests without these target bindings require new decisions.

In a sandboxed claude or codex agent (`TOWER_CRANE_BROKER` set by its spawn), commands that only read run as usual, and `worktree` runs as a read too: it prints the worktree spawn made, with no stack refresh and no branch record, so it takes no state lock. `wait` runs in the agent too, scoped: on its own task (`--task` defaults to `TOWER_CRANE_TASK`), as its own identity, with `--timeout SEC`, and with `--for` absent, `orchestrator` or its own name; `--follow`, `--observe` and `--inbox` are refused. A wait by an identity that is neither the orchestrator nor the owner runs no reactions, dispatch or observation, so it writes nothing. The variable counts only for the broker's own state directory: a `worktree` or `wait` for another state directory, such as a test fixture's, runs as usual. Every other command on the spawn's state directory is sent to the [state broker](ladder.md#state-broker), which runs it as the spawned agent if its role allows it on its own task, and prints its output and exits with its code. A refused command exits 1 and writes nothing, except a refused `msg` (below). The broker refuses `check`: it runs outside the sandbox and never runs the agent's code, so a worker runs its tests directly and the orchestrator runs the gates.

Writes take the lock, re-read the files, validate, write atomically and append to `events.jsonl`. The Git/gh runner refuses commands inside mutation transactions, and while the repository's common directory holds a `commondir` file ([ladder.md](ladder.md#the-common-directorys-commondir)). Rendering follows after the mutation releases its lock and reads current state under its own lock. A refused command writes nothing, except a refused brokered `msg`, which appends a `msg refused` event.

Orchestrator writes also require the calling session lease. Scripts and intermediate shells under the nearest harness or session shell (login, interactive, or with a terminal on stdin) share its identity; a different harness process or session id still refuses writes. A recorded harness exit releases its lease immediately; a caller fallback keeps the idle window. Native commands renew its idle window; engine reactions, collectors and hook writers never acquire or renew it. Automation binds to the recorded holder while its process lives, even after heartbeat expiry, so it keeps running when the holder returns and renews; a native writer replacing the expired lease stops it. `orchestrator release` and owner-only `orchestrator takeover` clear it for the next native writer. MCP discovery needs no lease, and actual actions check the lease before running. Inbox reads stay open to competing sessions. `authority`, `bench gates` and `bench tokens` also remain open to competing readers and never acquire a vacant lease. Wait startup does not block its timeout behind a lease transaction. See [state.md: Orchestrator lease](state.md#orchestrator-lease).

`hook tool` appends the agent's tool activity to `progress/<agent>.jsonl` without the state lock or a state read; a failed append drops that line. An inbox poll (`UserPromptSubmit`, and the poll after each tool hook) reads the event log without the lock and returns at once when nothing is pending. With messages pending it tries the lock once: a busy lock returns empty context and leaves them unread for the next hook. The bridge turns any failed progress append or poll into empty context, so neither fails the harness turn. Background-job, Stop and acknowledgement hooks still write audit events under the lock.

Evidence that no gate decision reads any more moves out of `tasks.json` on the next write: entries at an older head or revision, every entry of a cancelled task, and all but the merge receipt of a merged task. Their fields over 1 KiB go to `evidence/<task>/<sha256>.json`, with a reference in `tasks.json`. Evidence at the task's current head stays inline whatever its size. `task show` and every reader get the full checked value back. Copy the evidence directory with the state. See [state.md](state.md#tasksjson) for the format and what older tools see.

State readers preserve additive fields and enum values from newer tools. Commands still reject unsupported input values; dispatch refuses a task whose routing fields it cannot interpret. `init` records `project.json.schema_version: 1`, with absent values in older projects treated as `1`. A higher schema refuses reads, writes and new spawns with exit `1` and an upgrade message. An active supervisor stops state activity and retries but lets its worker finish, then exits `1`; recover the lease and usage with an upgraded tool. See [state.md: Schema compatibility](state.md#schema-compatibility) for the migration ordering and rollout rule.

An unfamiliar task status keeps an unexpired claim counted for locks and worker capacity. `recover` reports `waiting` when routing values require an upgrade, preserving failed review evidence without selecting a tier or sending the task back. `rework` refuses those values before changing state or the brief.

Lock attempts use private staging directories named with the process pid and a fresh random nonce. Every CLI, hook and broker write retries with jittered exponential backoff for up to 60 s per acquisition, measured with a monotonic clock. Linux markers record process start ticks and the kernel boot id. A holder verified by matching start ticks is never reclaimed by age; a missing process, zombie, mismatched start ticks or a different boot id on the same host permits immediate reclaim, including at the deadline. Older markers and platforms without a readable process identity retain the 60 s age fallback, so a reused live PID cannot keep an unverifiable marker locked forever. Successful stale-marker and empty-lock cleanup retries use that same deadline and backoff, with at most one final acquisition attempt after cleanup at the deadline. Concurrent staging cleanup retries within that bound; it does not expose a staging `ENOENT` as a command or supervisor failure. Persistent live contention or unremovable stale locks and cleanup races exit 3. The hook bridge and supervisor event writers allow 65 s per CLI call, and generated hooks allow 135 s for two calls, so transient contention within the bound does not block a prompt with a hook error. See [state.md: Lock](state.md#lock).

`project set --tests-paths '["src/test/**","**/*Test.java"]'` replaces `tests.paths` with a non-empty JSON array of non-blank strings. `--tests-paths null` removes the field and restores the default test layouts; `[]` is invalid.

`project set --tests-keep '["Makefile","tools/**/*.gradle"]'` sets `tests.keep`, an array of extra build file globs to keep at the submitted sha during the tests gate's revert run. These extend the default declarative manifests and lockfiles listed in state.md. Executable build files such as `Makefile`, `setup.py`, Gradle scripts and bundler configs require this explicit setting. Use narrow globs: any matched non-test code stays unreverted. `--tests-keep '[]'` or `--tests-keep null` restores the default keep set; neither disables it. Test paths take priority and are not listed as kept build files.

`project set --tests-host-only '["tests/lab/**"]'` sets `tests.host_only`, the test file globs a sandboxed worker cannot run. The worker brief lists them, and a sandboxed run skips them when its runner honors `TOWER_CRANE_HOST_ONLY`, and refuses directory and glob selections while the list is set. The gate excludes them from ordinary commands through the JSON `TOWER_CRANE_TEST_EXCLUDE` runner contract and selects tracked test files using `tests.paths` or the default layouts, excludes fixtures and support files, and runs each selected file separately on the host with pinned `gates.tests_proof_cmd` containing `{tests}`. Default host-only selection also requires a source or test-format suffix (for example `.js`, `.py`, `.sh` or `.feature`); use `tests.paths` for other formats or extensionless tests. `[]` lists none; `null` clears the list.

`project set --tests-host-env '{"TOWER_CRANE_LIVE_CLAUDE":"1"}'` sets the operational `tests.host_env` map of variable names to string values. Only the separate host-only gate commands receive it. `{}` empties the map; `null` clears it. The receipt lists host-only files that ran, skipped or did not report readable TAP or Node spec counts, with counts per file. A file with mixed cases appears in both run and skipped lists; skips and unreported results do not count as proof for a changed host-only test file.

`project set --tests-mode prove --tests-by-kind '{"code":"run-only"}'` sets the tests policy for a project with inline tests. Modes are `prove` (default, pass at head and fail after reverting other changes), `run-only` (pass at head once), and `none` (skip the suite and verify the submitted commit). Kind overrides replace the whole map and take priority over the project mode; keys must be `code`, `docs`, `research`, `design` or `ops`. Only code tasks require tests evidence for acceptance; other kinds already use independent review, and their modes apply to explicit tests checks. Use `run-only` for Rust inline `#[cfg(test)]` modules in production source files. `--tests-mode null`, `--tests-by-kind null` and `--tests-expensive null` remove their respective fields. `{}` clears kind overrides and false restores normal proof. These flags also work with `init` and preserve other tests settings.

All seven tests settings flags (`--tests-mode`, `--tests-by-kind`, `--tests-expensive`, `--tests-paths`, `--tests-keep`, `--tests-host-only`, `--tests-map`) are operational on `init` and `project set`, including clearing or setting the same value: the orchestrator or the owner. A refused call writes no state, including any other settings in that call. Workers ask the orchestrator through `tower-crane msg --to orchestrator` or a task note.

Gate commands come from `project.json gates`. The orchestrator or the owner pins them with `project set --tests-cmd "npm test" --clean-cmd "node /path/to/deslop/scripts/detect.js"`. `init` accepts the same settings. The cleanup value is a command prefix; the gate appends its checkout directory, `--base=SHA` and `--json`. `--tests-cmd null`, `--clean-cmd null` and `--tests-proof-cmd null` clear the respective pins. Non-blank strings without NUL bytes are required. An unpinned project does not block: when the orchestrator or the owner runs `check tests`, `check clean` or `accept` with a needed pin missing, the engine first pins `npm test` (when `package.json` has a real test script) and the configured cleanup tool (`TOWER_CRANE_CLEAN_CMD`, `deslop` on PATH or the deslop plugin script), logs a `gates pin` event and lists it in `status`. Otherwise missing pins refuse execution, except tests mode `none`, which needs no test command; workers and reviewers pin nothing.

The documented default for projects is expensive proof: the orchestrator or the owner sets `project set --tests-expensive true --tests-proof-cmd "node --test {tests}"` (or the same flags on `init`), then callers run `check tests ID`. Leave it off only for a suite cheap enough to run twice. The head suite runs once, using the mapped selection below when configured. `{tests}` is replaced with the shell-quoted added or changed test paths, and that scoped command must pass at head and fail with non-test files reverted. A pinned scoped template containing `{tests}` is required before the full suite runs when there are changed tests and revertible files. A nonempty diff containing only test paths and kept files runs the pinned head command once, even for a fixture-only fix with no changed test. Its receipt records `mode: "run-only (test-only diff)"` and the complete `changed_files` list; the summary names both. Any other changed path retains prove behavior. The orchestrator or the owner chooses the scoped runner and the reviewer checks that it selects those files. `run-only` and `none` are unaffected by the expensive setting.


`project set --tests-map '{"lib/gates/tests.js":["test/gates/tests.test.js"]}'` pins source paths or repository globs to arrays of literal test paths. `--tests-map null` clears it; `{}` maps nothing. Empty arrays explicitly mark paths needing no additional suites. Matching source globs combine their suites. Paths must be relative, without parent components, backslashes or NUL bytes; suite paths cannot be globs. `init` accepts the same operational setting and `project show` prints it.

In expensive `prove` mode, a pinned map and nonempty `ci.required` select the changed test files plus mapped suites for the head run through `gates.tests_proof_cmd`. A task without a PR retains the full head command because hosted CI is not required. A configured `ci.local` retains the full head command because hosted required jobs no longer run. Helpers and fixtures need source mappings even under broad test globs. The orchestrator must name the full-suite CI job in `ci.required`; the engine cannot infer job contents from a name. Every changed non-test path, including deleted paths, build files and test support files, must match the map. An unmapped path, a mapped suite missing at head or outside `tests.paths`, or an empty selection runs `gates.tests_cmd` in full and names the reason. Missing prerequisites also retain the full run. Deleted tests are excluded from the changed-test selection. The scoped failing-before proof still uses only added or changed tests. Evidence records `receipt.head_mode` (`mapped` or `full`), `head_reason`, and mapped `head_tests`, with the same mode and reason in the summary. `run-only` and `none` retain their behavior.

The repository seed is `tools/tests-map.json`; regenerate it with `node tools/tests-map.js > tools/tests-map.json`, inspect the coverage, then have the orchestrator pin its JSON through `project set --tests-map`. An optional commit argument, `node tools/tests-map.js SHA`, derives the seed from that head for older submitted tasks. Static imports seed coverage and shared CLI infrastructure maps to every suite. Uncovered executable paths stay unmapped. The seed marks Markdown with an empty array; it does not skip the changed-test proof or CI.

Optional `--cmd` and `--proof-cmd` flags must match the corresponding pin after trimming surrounding whitespace; they cannot select another command, including when passed to `accept` or in tests mode `none`. A non-blank `TOWER_CRANE_CLEAN_CMD` must match `gates.clean_cmd` too. Only the orchestrator or the owner can set or clear pins, including setting the current value. A changed pin makes the affected gate's previous receipts stale; rerun that gate before acceptance or merge.

`project set --tests-timeout-min 40 --clean-timeout-min 10` sets the budget in minutes per test or cleanup command. These operational settings also apply to automation, including the merged-head suite. `init` accepts the same flags. Positive fractions are allowed within Node's timer range (1 to 2147483647 ms); `null` restores the original 20-minute default. `project show` prints the effective budgets. `--tmp-root DIR` sets the absolute directory where gate worktrees and scratch are created; `null` restores the default, `tc/g` under the user's cache directory (`XDG_CACHE_HOME`, else `~/.cache`; `%LOCALAPPDATA%` on Windows). The default is on disk because `/tmp` is often a RAM-backed tmpfs, and some suites refuse to run there. Choose them from measured run time under local load. Each full-suite, scoped-proof and reverted-proof invocation gets its own test budget. Changes apply to subsequent runs and preserve successful command evidence. A merged-head timeout stops the queue entry without reworking or merging the accepted task.

`project set --ci-ignore-apps '["claude","cursor"]'` replaces `ci.ignore_apps` with a JSON array of non-blank strings naming GitHub apps. `--ci-ignore-apps '[]'` stores an empty ignore list; `--ci-ignore-apps null` removes the field. Both make the CI gate check every app again.

`project set --ci-required '["test (","lint"]'` sets `ci.required`, an array of required check-run names or literal, case-sensitive prefixes. Each entry must match at least one run outside ignored apps at the submitted sha, and every matching run must be completed with conclusion `success`. Skipped, neutral and capped runs cannot satisfy required jobs. A prefix such as `"test ("` covers jobs that ran but cannot detect an absent matrix member; list each full job name to require every member. `--ci-required '[]'` or `--ci-required null` clears this requirement. `init` accepts the same flag.

Same-repository Tower Crane PRs run one hosted job, `checks (shared files)`, so the project pins `["checks (shared files)"]` and runs the full suite in the local tests gate. Fork PR test jobs are `["test (windows-latest, node 26, shard 1/3)","test (windows-latest, node 26, shard 2/3)","test (windows-latest, node 26, shard 3/3)"]`. To require every fork PR shard, use this three-name list as `ci.required`. Pushes to `main`, the daily schedule and manual runs add the six Linux jobs: `test (ubuntu-latest, node 26, shard <i>/3)` and `test (ubuntu-latest, node 24, shard <i>/3)`, each with `i` equal to 1, 2 and 3. Those runs have nine test jobs in total, plus `repeat (windows-latest, node 26)` for the Windows flake repeats. Requiring the Linux or repeat names at a PR head fails the CI gate because those jobs run only in the full matrix.

`project set --ci-capped-review '[{"app":"cursor","pattern":"usage limit"}]'` sets `ci.capped_review`: a failed check run of that GitHub app whose output title or summary matches the case-insensitive pattern is a nonblocking capped review. `[]` or `null` clears it.

Changing the effective `ci.required`, `ci.ignore_apps` or `ci.capped_review` policy makes a previous hosted CI pass stale. Acceptance and the merge recheck require `tower-crane check ci ID` again, even at the same submitted head.

All list settings trim leading and trailing whitespace from each entry. Setting a list replaces a non-object `tests` or `ci` section; clearing it removes that malformed section. Object sections keep their other fields. Text output from `project set` and `project show` prints these lists, with `default layouts` for absent test paths and `[]` when no extra build files, CI apps or required checks are configured. Test and CI gate hints name the corresponding `project set` flags.

`project set --ci-local '{"command":["python3","tools/check.py"],"timeout":120}'` configures local CI. `command` is a nonempty argv array with a nonblank executable and string arguments, passed verbatim without a shell. Empty arguments are allowed; NUL bytes are refused. `timeout` is required, in positive seconds, within Node's timer range of 2147483647 milliseconds. There is no default timeout. `--ci-local null` removes local CI and restores hosted checks. Other `ci` fields are preserved. `init` accepts the same setting; `project show` prints `ci.local: hosted` when it is absent. Every use of `init --ci-local` and `project set --ci-local`, including clearing or setting the current value, is operational: the orchestrator or the owner.

`ci.local.artifacts` optionally lists globs of files the command writes in the gate worktree, relative to it and without `..`, such as `[".local/checks/*.json"]`. `ci.local.artifact_pattern` is an optional regular expression matched against each output line. Its first capture group, or the whole match without one, names a file the command printed, such as `"^Local check receipt: (.+)$"`; a relative path resolves from the worktree. When the command fails, `check ci` copies these files out of the worktree and its scratch directory before removal, printed paths first, into the state directory's `ci-artifacts/`, which agent sandboxes cannot read. Text files are redacted like the log. Files elsewhere outlive the gate and are only listed as skipped. Neither field changes which receipt counts.

```sh
tower-crane project set --ci-local '{"command":["python3","tools/check.py"],"timeout":3600,"artifacts":[".local/checks/*.json"],"artifact_pattern":"^Local check receipt: (.+)$"}'
```

`project set --merge-keep-branch true` sets `merge.keep_branch` and omits `gh pr merge --delete-branch`. It keeps the remote branch. Stale local worktrees and their local branches still retire. `--merge-admin true` sets `merge.admin` and adds `gh pr merge --admin`, for repositories solely owned by the project owner per SHARED.md. Setting or clearing admin policy is owner-required; `--merge-keep-branch` is operational. Both settings also work with `init`, accept JSON true, false or null, and preserve other merge settings. False disables the option; null removes the field. Both default to false and appear in `project show`.

`ci.local.by_kind` optionally maps `code`, `docs`, `research`, `design` or `ops` to overrides. Each override has exactly one of `command` (replace the default argv) or `args` (append to the default argv), plus an optional `timeout` in seconds. An omitted timeout inherits `ci.local.timeout`. Empty `args` selects the default command as a distinct variant. Unknown kinds, unknown override fields and invalid argv or timeouts are refused without writing state.

```sh
tower-crane project set --ci-local '{"command":["python3","tools/check.py"],"timeout":120,"by_kind":{"code":{"args":["--native-extended"]},"ops":{"args":["--lab"],"timeout":300}}}'
tower-crane task update T1 --ci-local '{"args":["--s3"],"timeout":600}' --agent owner
tower-crane task update T1 --ci-local null --agent owner
```

`task update --ci-local` stores `ci_local` on the task; setting or clearing it is operational. Its shape is the same as a kind override. A task override takes precedence over the kind mapping and resolves against the project default command and timeout. Clearing it restores the kind mapping, or the default if that kind has no mapping. Overrides apply only while project local CI is configured; they do not select local CI on a hosted project. `task show` prints a stored override. Workers ask the orchestrator for a different tier through `msg --to orchestrator` or a task note.

`merge` defaults to `--method squash`, with the task title as the commit subject and its acceptance lines joined by newlines as the body. `--subject` and `--body` override these independently, preserving multiline text and an explicitly empty body. A subject must be non-blank. `--method merge` uses the same commit text options; `--method rebase` omits them and refuses explicit subject or body overrides. Every merge invocation uses GitHub's full head SHA with `--match-head-commit` after verifying it matches the accepted SHA. When GitHub refuses `gh pr merge` because the PR is part of a stack that no task records, a squash or merge retries through the asynchronous merge API with the same method, `--subject` and `--body`, and pins the accepted head with `expected_head_sha`. After the merge is confirmed, that fallback deletes the head branch under the same rule as the ordinary merge. A rebase keeps the refusal, since the API cannot rebase. Branch deletion is requested unless `merge.keep_branch` is true. Only owner-set `merge.admin: true` adds GitHub's admin option for solely owned repositories; the fallback refuses instead, since the API has no admin option. There is no one-off `merge --admin` flag; acceptance, review, CI and head checks still apply.

`project set --review-policy JSON --agent owner` replaces `review` with optional diff limits, risk paths, a minimum reviewer rung and prices. Only an explicitly identified owner can set this policy or its prices. For example:

```sh
tower-crane project set --review-policy '{"small_lines":100,"small_files":5,"risk_paths":["auth/**"],"prices":{"openai.gpt-6-luna":{"input":0.10,"cache_write":0.125,"cache_read":0.01,"output":0.50},"openai.gpt-6.1-sol":{"input":2,"cache_write":2.50,"cache_read":0.10,"output":10},"claude-opus-5-5":{"input":4,"cache_write":5,"cache_read":0.20,"output":20}}}' --agent owner
```

Rates are dollars per million tokens; use the actual provider model IDs and rates. Model IDs compare after trimming whitespace and folding case; provider prefixes remain distinct. Codex profiles resolve their model from the user's origin configuration, matching dispatch even when the caller's home is isolated: `<profile>.config.toml` or `[profiles.<profile>]` in `config.toml`; a readable standalone profile or a named profile table can inherit the base config's top-level model. Unknown profiles retain their configured identity, so a Codex profile rung is priced under the model its Codex config names, or under the profile name when no config names one. Set prices for the actual resolved model ID; every Claude rung expands `BUILTIN.claude_aliases` to the release ID its spend records, and native Claude review-spend aliases use the same table when matching samples to prices and recording `cost_usd` without rewriting the stored ID, and explicit provider routes also add their provider prefix. The example uses Bedrock global rates with five-minute cache writes. Selection starts at the task tier, raises easy to medium for diffs over 100 lines or 5 files by default, and raises to hard for matching risk globs or binary changes. `min_rung` raises the start to a named tier and escalation never drops below it. With `review` it starts on the `review` rung and stays there after failed reviews until the failure rules reach hard; it never picks easy or medium. It promotes to a stronger tier when T31's recorded review spend has a median priced cost no higher. Each failed independent review at the current head climbs one tier. The `review` rung is the fallback when no tier rung can run. The reviewer may use the builder's model because its context is clean. Missing complete usage prevents cost promotion. `--review-policy null` restores diff defaults without prices. See state.md for the pricing limits of older inclusive telemetry.

Briefs can use `## Shared`, `## Worker` and `## Reviewer` level-two headings. Matching is case-insensitive, and headings inside fenced code blocks are ordinary text. Content before the first role heading is shared; each section runs to the next role heading. `## Rework notes` also starts a shared section, so corrections appended by `rework` stay visible to role-filtered brief readers. `brief get ID` infers worker or reviewer from the `--agent` or `TOWER_CRANE_AGENT` name. Use `--role worker` or `--role reviewer` to select explicitly. Owner and orchestrator identities see the full brief by default.

`init --review-policy JSON` accepts the same operational setting.

The list settings also work with `init`. Omitted options leave their fields unchanged. Removing a field keeps other settings in its object section and removes the section itself only when empty. Invalid JSON, a value other than an array or `null`, or a blank or non-string array entry exits 2 and writes no state or event, including when combined with valid settings.

Harness sandbox support comes from `CAPABILITIES` in [lib/agents.js](../lib/agents.js). Its `sandbox` flag selects the ladder authority rule: moving a role that requests confinement to a harness with `sandbox: false` is owner-required. The separate `osSandbox` flag controls the OS-isolated state broker and nested browser setup; it does not classify ladder reach. Opencode keeps its private home and native file-tool permissions, with both sandbox capabilities false; those rules do not constrain Bash writes.

## Already-merged hotfixes

The orchestrator records a merged PR, then uses the normal acceptance path:

```sh
tower-crane hotfix T207 --pr 199 --agent orchestrator
tower-crane accept T207 --agent orchestrator
```

`--sha` defaults to the PR's merge commit. A task merged natively, with a
clean-context review already posted on its PR, names that exact comment by
URL or id:

```sh
tower-crane hotfix T235 --pr 235 --review https://github.com/agent-sh/tower-crane/pull/235#issuecomment-N --agent orchestrator
tower-crane accept T235 --agent orchestrator
```

The comment's first line is `Review (native, clean context)` or
`Review (Tower Crane, clean context)`. Its `SHA:` must be the PR head that
merged, and its `Verdict:` line or `Blocking findings` section decides it.
Its author must be an `OWNER`, `MEMBER` or `COLLABORATOR` of the repository.
Only squash and merge-commit merges are recorded; a rebase merge of several
commits is refused. A posted review of an earlier head is refused; omit `--review` and `accept`
dispatches a fresh review of the landed diff.

A trusted watcher also advances the `hotfix` event. Tests and cleanup use
that merge commit and its first parent, even after main moves. CI requires
the successful push workflows on the recorded base at that commit. Main pushes
share one concurrency group, so on a busy main a newer push cancels the merge
commit's pending run. When that run was cancelled or never ran, the first
successful push, scheduled or manual run of the same workflows at the merge
commit or a later commit on the base that contains it stands for it, and the
CI evidence names that commit and run in `hotfix_ci`. A failed run or job at
the merge commit itself still fails; a later green run does not mask it.
The exception is a base that was already red: when each failing test of each
failed job also failed in an earlier run of the workflow on the base, at a
commit the merge commit contains and within the last 30 completed runs of
the past 7 days, in the same job once the shard is set aside and with the
same first error line, the failure is `main_red` and CI waits for a later
green run as for a cancelled one. A test in the hotfix's diff counts only at
the parent run (the nearest earlier run, the first parent's unless it was
cancelled), and so does a test failing with a generic error such as a
timeout. A job that names no failing test counts only for a proof, probe,
check or lint job that failed at the parent run with the same error line from
its failing step; a timed out or cancelled job never counts. The evidence records `hotfix_ci.failure` with
the classification, the parent run and, per failing test, the earlier run,
job and error line that matched it. A failure new at the
merge commit stays confirmed. Until a later run is green, CI stays pending. The later run vouches for the
tree at its commit; the tests gate still proves the merge commit. A required
job skipped in that run does not apply only when it also skipped at the merge
commit or its own `if:` is false for the run's event, such as a
pull-request-only job; a job a path filter skipped stays required. Each check
looks at up to five later commits and records the ones it rejected in
`hotfix_ci.rejected`, so the next check goes on from there. When a changed host-only test only skipped, the tests
gate names the skip reasons and leaves a `gate_config` inbox item for
`tests.host_env`; set the opt-ins it names, then run `gates retry ID`. Once
software gates pass, a counted posted review or normal independent review
of the landed diff decides; call `accept` again after a dispatched verdict if
no watcher is running. A pass shows `accepted (hotfix)`, and `accept` then
confirms the merge and records merge evidence at the merge commit; it does
not merge the PR again. A failed confirmation is retried with `merge ID`.
Waivers are refused.
A confirmed gate failure or failed review creates one follow-up rework task against the
project base and retains the historical merge on the original task. Pending
CI and infrastructure errors stay submitted: rerun the gate with `check ci ID`
(or `check tests ID`, `check clean ID`), or let `ci completed` rerun CI, then
`accept` again. A tests failure whose every failing name also fails at the
merge's first parent is infrastructure too: the hotfix stays submitted and
opens no follow-up; rerun `check tests ID` when the environment recovers.
The newest main contains the merge, so it is not the comparison.

When the failure that cancelled a hotfix was not the change's, such as main
red at the merge commit, record the same PR again:

```sh
tower-crane hotfix T166 --pr 163 --reason 'main was red on Windows shards at the merge commit' --agent orchestrator
tower-crane accept T166 --agent orchestrator
```

Re-recording alone does not change what the gates see. When the push run at
the merge commit is still red, `accept` reads that same run and opens a new
follow-up. Rerun that CI first, or record the re-record once the CI gate
classifies main-wide red as not the change's (T349).

The task returns to `submitted` at a new revision, so the old failure no
longer counts and `accept` runs the gates again. The follow-up is cancelled
with `superseded_by` naming the task and the reason in its notes. A follow-up
that is claimed, or has a branch, PR or commit of its own, is refused: finish
or cancel it instead. Dropping a follow-up that carries an owner ask is
owner-required, the same as `task update --status cancelled`. So is dropping
one opened by a failed independent review, or one whose failure is not
recorded (`task.rerecord_review`): `--reason` cannot set aside a review
verdict. `--reason` is refused on any other record.

A tests failure that already failed at the merge's first parent fails there
on every rerun, since both commits are fixed. The owner ends it with
`accept ID --waive tests --reason R`. That is the only waiver a hotfix takes,
and only while every failing name also fails at the first parent; the waived
evidence and the `accept` event record it as `base_failure: {base_sha, names}`. An accepted hotfix cannot be sent back with `rework`. See
[state.md](state.md#already-merged-hotfixes) for fields and counts.

## Run

Dependent tasks can start while a single dependency chain is submitted or accepted but unmerged. `worktree` and `spawn` check the GitHub stacks endpoint, verify the dependency PR's current head and repository, fetch its branch, and create the upper branch at that head. The worker prompt names the dependency branch as the PR base. `ready` and `claim` allow submitted dependencies when they form one chain with a PR, branch and sha; dispatch still verifies availability. Claim readiness checks task status, dependencies, stack state, decisions, locks and worker slots. Worker spawn runs the same check before any worktree work and refuses with the claim reason. When an existing stacked PR affects readiness, spawn re-reads its membership from `gh api repos/OWNER/REPO/stacks` before dispatch. A claim of the task a spawn dispatched, by the agent it dispatched, reads that recorded result; any other claim re-reads it. A chain with fewer than two unmerged PRs is not read. Transient API errors require retry and do not mark stacks disabled. Independent dependency chains and forks wait for the ordinary accepted-dependency flow. A worktree made before its dependency was submitted is revalidated at dispatch: a clean branch with no commits of its own moves onto the dependency head, and one holding its own work is refused until the worktree is removed or the dependency merges. A branch that already contains the dependency head is used as it is. A rework whose branch is gone starts from its own pushed head, never from its dependency. Two siblings prepared at once on the same dependency cannot both record it as their stack parent; the second dispatch is refused under the lock and waits as a fork.

The dispatch supervisor links submitted PRs with `gh stack link <lower-pr> <upper-pr>` in bottom-to-top order. Native dispatches use `stack link ID` after recording the PR with `submit`. Linking verifies every member's submitted head, PR base and same-repository origin. Auto-merge must be disabled. Workers retain their existing gh permissions; linking and synchronization run under the dispatcher's policy.

Stack operations that contact GitHub and change task metadata, including dispatch and merge, share one snapshot of the project, members and member events, execute GitHub commands without the state lock, then compare against freshly read state before applying. Linking, retirement and unstacking preserve concurrent claims and refuse changed member or project inputs. A refusal can follow a successful remote operation, so inspect the PRs and branches before retrying. Automatic linking follows the collector's state write.

When stacks become available again, a successful `stack link ID` clears ordinary-merge fallback markers for that chain and restores the stack merge guard.

If every lower task merges before an unlinked dependent submits its PR, `stack link` retargets that PR to the project base and clears its local stack. The submitted head is preserved and the ordinary merge gate applies. Supervisors perform the same transition when observing a submission.

`merge ID` verifies remote stack membership and refuses unknown lower PRs, checks every task below the target is accepted with passing gates, and checks every PR head before any member merges. GitHub refuses `gh pr merge` for a stack member, so it merges linked stacks bottom up through the asynchronous merge REST API: `POST repos/{owner}/{repo}/pulls/{n}/merge-async` with `merge_method=merge` and `expected_head_sha=<full accepted head>`, then polls `GET .../merge-async/{id}` and `gh pr view` until the PR is merged at that head. `gh stack merge` is not used, since it lands every lower PR in one request and pins no member's head. The PR state is the source of truth: the job status only explains a wait or a refusal, and a failed poll (a 5xx, or a 404 once GitHub retires a finished job) leads to a PR read. The last terminal failure and its reason from the POST or a status poll survive later read errors, including a retired job returning 404. The gate reports that refusal when the PR is still open, or at the deadline if its state cannot be read, instead of reporting a queued merge. A confirmed merge at the accepted head takes precedence. Polling backs off from one second to ten. The member is confirmed once its PR is merged at the accepted head; it fails at once if the PR closes, its head moves, or GitHub reports the job failed while the PR is still open, and a PR still open after ten minutes is treated as queued. Merge commits preserve the accepted dependency heads as ancestors, so retargeting an upper PR after a lower merge does not lose its merge base. Each lower merge must be confirmed before an upper PR is retargeted to the project base, if GitHub has not already done so, and merged. The asynchronous API does not delete branches, so upper PR bases survive. The gate refuses further merges if project settings, stack members or their events changed since it started. Hook, startup and spawn session receipts, automation reservation receipts and the orchestrator notice a hook stop writes do not count as changes, so workers logging progress or stopping during the head checks do not stop a merge. Ordinary messages from members still count. A member already merged into a base other than its dependency branch or the project base is refused before any merge, and confirmation names the base each PR landed on. A moved head, refusal, failed confirmation or queued merge stops the chain. Earlier confirmed accepted members may have landed; each gets separate merge evidence even when the target fails. A queued member gets no successful evidence until GitHub confirms its accepted head merged. After a stack merge, each dependent whose PR head GitHub moved (a rebase onto the new base) takes the new head, returns to `submitted` and needs its gates again.

Before each asynchronous request, the gate checks the PR again and retargets only its recorded dependency branch to the project base. It reads the PR again after retargeting. A confirmation into another base stops the chain before any upper merge. Final confirmation requires the project base for every member attempted in this invocation and preserves any asynchronous failure, even when the reported base is the recorded dependency branch. Valid lower merges get separate successful evidence; the failed member does not.

Retries also require the project base when an earlier audited merge event contains an asynchronous POST for the same repository, PR and accepted head. Receipts from higher stack tasks count when confirming a lower member alone. A failed stack sync cannot make the rejected dependency-base merge eligible for successful confirmation.

After a lower merge, or when a later `worktree` or `spawn` observes main or a dependency moving, Tower Crane refreshes upper worktrees through `gh stack sync`. A dependent prepared before its PR is linked is revalidated at each `worktree` and `spawn`: when its dependency was resubmitted, a branch with no work of its own moves onto the new dependency head, and a branch with its own commits is refused until it contains that head (merge it in, or remove the worktree and branch). Every worktree in that stack must be idle and clean; otherwise refresh is deferred and an event names the blocker. Unknown remote PRs must be recorded before sync. Sync snapshots the project, stack members and their events under a short state lock, runs gh and Git unlocked, then re-takes the lock to compare and apply. Changes to the project or affected tasks refuse application and preserve current claims; unrelated task writes are retained. Git may already have moved branches when application is refused, so inspect their heads before retrying. The allowed gh-stack extension owns its rebases and atomic lease-protected pushes under the dispatcher's policy. An explicit conflict report sends outstanding tasks to rework with the failure in their briefs. A changed branch also goes to rework and needs a new submission and gates, even if sync then fails to push; evidence for the old head remains historical. Tooling and transport errors, including failures listing worktrees or an unavailable extension, record the parsed abort reason and preserve unchanged submissions and gates. The next refresh retries the linked stack. A failed sync exits 1 and reports whether work needs rework or a later retry.

When every lower task has confirmed merge evidence and no unmerged task
remains above it, the upper task becomes an ordinary PR. Submit and refresh do not run `gh stack sync`; task show,
status and the board omit the completed chain. Refresh and explicit
`stack sync ID` validate and retarget the PR to the project base, then
clear its local stack record without changing its head. `stack unstack ID`
does the same when all other members are merged, without asking GitHub
to unstack merged PRs. Merge uses ordinary options and defaults to squash.
If GitHub still lists it in a stack and refuses `gh pr merge`, squash and
merge methods use the asynchronous API for that single PR at its accepted
head, with the same method and commit text. Admin and rebase retain the
ordinary fallback refusals.
Middle tasks keep their stack records while an upper task is open, preserving
the merged lower PRs that sync and stack merge must still recognize.

Before every automatic synchronization, including after a confirmed merge
and from `worktree` or `spawn`, submitted or accepted upper heads are checked
against the fetched project base. Stacks
with declared generated conflicts defer synchronization. When all lower
dependencies have merged, the completed dependency is retired with the normal PR head, branch,
repository and base checks. Its PR is retargeted to main and the generated
repair path runs first. Generated-only repairs keep the upper task submitted;
mixed repairs prepare its merge before rework. Unknown mergeability defers
repair without invoking stack sync. Unaffected stacks still synchronize.

Stacks require the GitHub repository setting and the gh-stack extension (v0.2.0 or newer). A missing extension (gh exits non-zero pointing at the gh-stack extension), a disabled stacks endpoint, or `gh stack` exit 9 falls back to ordinary dispatch for accepted dependencies. Submitted dependencies wait for acceptance when stacks are unavailable. Generic 404s are reported as errors without disabling stacks; 5xx responses and network errors require retry and do not mark stacks disabled. If linking or merging becomes unavailable after dispatch, the branch is retained and the task is marked for ordinary merging: lower tasks must land before its PR can target main. A refused stack merge reports that fallback and the next merge uses the ordinary gate. Authentication and other unexpected failures are reported rather than treated as disabled stacks.

Stacks support only PRs in the same repository, one chain per stack, merge commits and no auto-merge or admin bypass. The repository must allow merge commits. Linked stacks default to `--method merge`; explicit squash and rebase methods are refused because they remove accepted dependency heads from the base ancestry. A repository requiring `--admin` uses the owner's `merge.admin` policy, `stack unstack ID`, then ordinary `merge ID` on the lower tasks first. Ordinary merges accept `--method squash|merge|rebase` and retain `--match-head-commit`. Admin policy is refused for a linked stack. The webhook command consumes an already authenticated payload; it is not a public HTTP webhook receiver.

The owner can configure toolchain homes, writable caches and an environment file at project level, then override fields on a rung:

`init` accepts the same `--sandbox JSON`, `--env JSON`, `--env_file FILE` and `--scope JSON` flags. `project set` replaces the named project field; `null` removes it. `ladder set --clear sandbox`, `--clear env`, `--clear env_file` or `--clear scope` restores the project default for that rung. Setting, repeating and clearing are owner-required. Rung `env` merges over project `env`; these override the env file, which overrides the spawning environment. A rung file replaces the project file. Each rung sandbox field replaces the corresponding project field. A rung `scope` replaces the entire project scope; `{}` disables it for that rung.

`sandbox.write` extends the standard writable paths in Claude and Codex. `sandbox.read` adds paths under the user's home that sandboxed Claude and Codex agents may read; the rest of the home is hidden ([Home reads](ladder.md#home-reads)), and a path that is the whole home, or a directory that holds it such as `/`, refuses dispatch, as does a `sandbox.read` or `sandbox.write` path inside the state's `homes/` or `brokers/` or the owner key directory, and a `sandbox.write` path that holds one of them. `~` in sandbox paths or the env-file path refers to the original user's home; relative paths start at the repository root. Environment values are literal; provide absolute paths for `CARGO_HOME` and `RUSTUP_HOME`. Home, PATH, harness-home and `TOWER_CRANE_*` variables are reserved. `env` is saved and shown as configuration, so keep secrets in `env_file`. That file uses systemd EnvironmentFile quoting, without shell evaluation. Only its path is stored; dry-run does not read it, and the CLI does not log its variable names or contents. Agents must keep secrets out of printed output and prompts because harness logs and transcripts persist.

`task add --lock lab/rdma --lock gpu/0 --environment lab` stores exclusive resource names and an informational environment label. Names are case-sensitive, trimmed and deduplicated. Tasks with any shared lock cannot hold worker leases or dispatch reservations at the same time, regardless of `limits.workers` or environment labels. Claim, worker spawn and expired renewal check under the state lock and name the holding task and agent on refusal. An unclaimed spawn reserves its locks with its worker slot, including retry backoff; its generated agent consumes that reservation on claim. Reviewer and other non-worker dispatches do not acquire resource locks. Environment labels do not select a harness or change its environment variables.

Failed review evidence can supply `--findings '[{"kind":"false-claim","path":"PR body","claim":"The diagnostic is printed."}]'`. List every blocker with non-blank `kind`, `path` and `claim` strings and no other fields; this flag is refused for notes and passing reviews. A false claim qualifies only when correcting prose resolves it without a behavior or contract change. All blockers must be false claims confined to `PR body`, `CHANGELOG.md` or single Markdown fragments under `changelog.d/` for the light path. Missing metadata, mixed blockers and contract claims, including `docs/cli.md` and `docs/state.md`, retain full review and rework.

When every finding is in the PR body, correct it with `gh pr edit --body-file`, then run `accept ID` to request a light reviewer check without a new revision. `rework --from-review` refuses these failures without changing state, and the inbox's `prose_only: true` item supplies `accept ID` with correction instructions. If the body cannot be corrected, `rework ID --reason R` sends the task back. Automatic reactions do not retry a failed light check at an unchanged head.

Changelog claims need a new head, so they go through `rework --from-review` like other failures. The next revision's review is a light check when the diff since the failed review changes only the named changelog fragments. The new head requires software gates as usual. Other source changes restore full review. The reviewer checks every corrected claim against its code or probe and records fresh evidence; an uncorrected claim still blocks. Prose-only failures do not escalate rungs.

`submit` stores the full lowercase commit SHA in the task and submit event. Full 40-character SHA-1 or 64-character SHA-256 IDs are accepted as given without requiring their objects locally; a commit may exist only in another checkout. Abbreviations are resolved with `git rev-parse --verify <sha>^{commit}` in the task repository. If local resolution fails, submit fetches the supplied or recorded task branch from origin and retries. A prefix that remains unknown or ambiguous, or resolves to a non-commit object, refuses without changing state. A sandboxed worker resolves inside its sandbox before forwarding the full SHA; the host broker runs no Git. Existing abbreviated submitted SHAs stay unchanged and match review and gate evidence by prefix, including active reviewer dispatches, so a full-SHA failed review remains actionable through `rework --from-review`.

When `--branch` or `--pr` is supplied and the task already records a PR, `submit` reads that PR with `gh pr view`. An open PR blocks a different PR number or a different submitted branch. If the old PR is closed or merged and the PR number changes, `submit` reads the new PR's head branch, uses it when `--branch` is omitted, and checks a supplied branch against it. If GitHub cannot be queried or its response cannot be read, submission refuses without changing state.

With a PR (`--pr`, or the one already recorded), `submit` reads the PR's checks at the submitted sha the way `check ci` does: check runs, check suites and Actions workflow runs, with superseded runs set aside. A failing check refuses with the failing jobs and the first failing lines of their logs, read with `gh run view --log-failed`. The first three failing jobs print their logs; each other failing job prints its name and the `gh run view --job ID --log-failed -R REPO` command that reads its log. A failing check refuses even while other checks are still running. A pending check, a required check that has not started, or a mergeability GitHub has not computed does not refuse: submit records the head, prints the names still running with a line telling the worker not to wait for CI, and notes them on the task as `submitted with CI pending: ...`. `check ci` then waits for them on the host: it records `pending` until they finish, and its failure summary, which rework carries to the worker, names the failing jobs and prints the first failing lines of their logs the same way. Log excerpts pass the redactor the tests, clean and local CI gates use (token shapes and host secret values), and a required run that was skipped or neutral prints no log. A worker that waited for CI before submitting re-read its whole context on every poll. A PR that GitHub reports CONFLICTING or DIRTY refuses with the conflict diagnostic `check ci` gives: GitHub does not start `pull_request` workflows for it, so submit names the conflict instead of waiting for those checks. Revuto's open inline comments print with their file, line and body; a comment stays open until the latest reply from anyone else starts with `[resolved]` on its own line. An open comment marked `[P1]` or `[P2]` whose path has not changed between the commit it was left on and the submitted sha refuses the submit, the rule review ok applies; the refusal names each with its comment id and points to `ci resolve`. Submit reads the findings already posted and does not wait for revuto to finish. `ci.capped_review` reviews do not block. When the agent's `gh` policy refuses `gh api`, submit prints that the head was not checked and goes ahead. With `--json`, the same report is the `ci_report` field.

`submit` runs the scope gate on the submitted diff before taking the state lock: the changed files are compared with the repository paths named in the task's title, acceptance and brief (a token with a slash whose directory exists at the base or the head; a glob such as `test/**` works too). Absolute paths under the main checkout or a registered worktree become repository-relative paths; quote paths containing spaces. Naming a checkout or worktree root scopes the whole repository. Quoted commands such as `node lib/scope.js` scope the paths inside them when the complete span is not a repository path. The diff starts at the newest merge base with the configured base's local and origin refs, so files changed only by a merged base update are excluded even when the local base is stale. Test files under the project's test layouts and `CHANGELOG.md` are always in scope; a task naming no path is scoped to the whole repository. Out-of-scope files are not refused: the output gains a `scope:` line, `--json` adds `scope: { basis, named, outside }` (or `{ error }` when git cannot read the diff), the `submit` event records it, a task note lists the files for the orchestrator, and the review packet's `## Scope` section lists them for the reviewer.

While a task is `submitted`, its recorded `submitted_by` agent can submit another head without claiming again. The task stays `submitted`; omitted `--branch` and `--pr` keep their current values. Evidence stays in the audit trail, but evidence at the older head stops satisfying gates for the new head. Submitting the same sha keeps its evidence valid only within the same revision. Rework and a changed brief after the first submission start a new revision and require fresh evidence. The `submit` event records `previous_sha` and `sha`. Once accepted, the task needs `rework` and a new claim before another submission.

`--precheck pass|fail|skipped` is the submitter's own pre-submit review of the diff at that head: the reviewer checklist run before `submit` ([worker skill](../skills/tower-crane-work/SKILL.md)). The event carries it as `precheck`, next to the submitted `sha`, and omitting the flag leaves the field out. It is a record for measurement, not a gate: `submit` never refuses or waits on it, and reviews and gates do not read it.

When a resumed worker fails with context overflow, `spawn` supervision records a `spawn fallback` with reason `session context overflow` and retries once with a fresh session on the same route. The full prompt, brief and rework notes are rebuilt; the agent, claim and worktree are kept. The failed session is excluded from later resumes. A fresh attempt that also overflows blocks. Native Claude workers already start fresh. No prelaunch size cutoff is applied.

The trusted `wait` watcher and dispatch supervisor react to submissions,
worker exits, review evidence, acceptance, CI completions and confirmed
merges. Submission runs unattempted tests, cleanup and source verification
once the PR head matches, including while mergeability is unknown. CI,
review dispatch and merging still require known mergeability.
A tracked worker must exit before automatic review dispatch. Native
workers without a recorded exit use explicit `accept` to dispatch review.
A reviewer that exits with code 0, no signal and no availability failure
but without review evidence at the current head and revision is not
replaced automatically: the next reaction holds dispatch
until the head, the revision or a revuto thread on the PR changes, records
one `review held` event naming the reviewer's last report or note, and
lists a `review_held` inbox item whose `accept ID` dispatches again.
A reviewer that crashes (nonzero code or a signal), whose supervisor fails,
or whose monitor dies without a receipt is replaced, up to 3 such ends at one
head and revision; the third holds dispatch the same way, with a
`review held` reason naming the count, the reviewer that ended last, how it
ended and its log. Outages, interrupts and budget stops do not count.
Failed independent review at the current submitted head and revision sends
the task to rework through `rework --from-review`, with the full findings
and comment link in its reason and brief. Findings all in the PR body are
the exception: the task stays submitted for a correction and an explicit `accept`. Pending software gates do not
delay it. Stale or superseded reviews cannot rework the current submission;
replaying a review never increments the revision twice.
Ranged recovery uses the same full-findings rework action before recording
its climb. Reviewer and broker callbacks leave that step to the trusted host.
An unavailable or mismatched linked comment leaves that submission unchanged
and reports a recovery refusal without stopping the wait host, other tasks'
gate reactions or worker refill.
`wait --observe` retains ranged quality recovery, including full-findings
rework, while skipping submission automation and capacity refill.
`accept` and a real `spawn --role review` also send a current independent FAIL
to full-findings rework and exit 1, rather than repeating review at that head.
PR-body-only failures are excepted.
If findings cannot be retrieved, the task stays submitted. Dry-run review
previews do not change state.
After draining event reactions, the trusted `wait` host releases verified
dead claims through `release --dead`. Worker exits, releases, rework and confirmed merges refill
free slots through `spawn --ready`, including ready rework tasks. The same
worker limit, unblocking-first order, routing, fallback and locked reservations
apply; concurrent watchers cannot dispatch above the limit. Worker dispatches,
batch or single, run one at a time under the state directory's dispatch lock,
so a watcher never skips a higher-ranked task that another dispatch is still
preparing and gives its slot to a lower one. A dispatch lock that outlasts its
wait (`worker dispatch is locked by ...`) stops the batch at that task and is
retried on the next pass rather than reported as a refusal. The host does not
wait for the lock: a refill or a recovered climb that finds another dispatch
holding it, or loses the one try, is deferred to the next pass, so events and
signals keep reaching the host ([Dispatch lock](state.md#dispatch-lock)). Before counting
capacity, the host clears verified dead reservations under the state lock,
including reservations from cancelled tasks. Dispatch refusals
are reported once on stderr per wait while dispatch inputs are unchanged.
Changed task or brief data, routing, project settings or worker holders retry
the batch. Progress notes and fallback ticks alone do not retry a refusal.
After fixing external availability or filesystem conditions, use
`spawn --ready` or restart the wait to retry.
Startup and the existing fallback tick also check capacity, recovering slots
freed before the wait cursor. These capacity checks run only in a trusted
wait without `--observe`.

A worker that exits without submitting is relaunched by the next refill, so
the refill caps it. The supervisor records each worker exit, and in the same
write counts the task's worker exits without a submit at its current
revision since its last submit or cleared owner ask. When a monitor dies,
the observer's `worker-exited` record stands in for its exit and applies the
same count. Exits marked `availability_failure` (outages, login failures,
supervisor stops), interrupts, budget stops and sessions that released the
task for an open decision do not count. At 3 counted exits the task gets
`needs_owner` naming the count, the last worker and its exit code, so it is
no longer ready: refill, `spawn --ready` and `spawn --task` skip or refuse it,
and the write appends a `respawn cap` event. The cap is 3 because the
supervisor already retries transient exits inside one dispatch: each counted
exit is a whole session that ended without a submission. The first relaunch
resumes that session, which covers a run cut short by a turn limit; a second
identical end at the same brief is a pattern, and a third only spends.
`task show` prints the last worker's log path and its tail, read from the log
at show time. Fix the cause, then run `owner-done ID`; the count starts again
from there, and also after a revision change such as a new brief.
Automatic dead release waits for confirmed monitor cleanup or a verified
empty process group, then rechecks under the release lock. Ranged recovery
keeps claims while the exit awaits classification or a quality climb, so
their exit still triggers the planned climb.
Passing independent review accepts the task; accepted PRs with green
gates merge through the existing head guards. A watcher creates a fresh
reconciliation request for every active PR when starting, except a default
`wait --timeout 0` cursor snapshot. It queries current mergeability even
when the last reaction completed, recovering conflicts after merges that
happened without a waiter. Audited evidence at the same head and revision
is reused when its policy still matches. Missing evidence, including an
entry without its matching gate audit receipt or evidence from an earlier
revision or another sha, runs in the next submission or reconciliation reaction.
An audited failure from another revision or sha cannot suppress a gate;
only a current configuration failure (`gate_config`) waits for an explicit `gates retry`.
At a submitted head, an ordinary failed `tests`, `clean` or `ci` verdict reworks immediately and stops later gates from running.
Infrastructure failures retry once before rework. A configuration failure waits
for its command to be pinned, while later software gates still collect missing
evidence and settle any independent failure. Pending CI waits for completion.
Queued or running CI and UNKNOWN mergeability print `PENDING`, block
acceptance and preserve the infrastructure retry. The trusted wait host
rechecks pending CI once per minute without a completion notification. An
unchanged pending result records nothing new. Pending CI with nothing queued
or running for 30 minutes, or on a PR closed without merging, prints
`STALLED`, gets a `ci_stalled` inbox item and no more scheduled rechecks until
`check ci`, a CI notification or a new head. Status and the board distinguish
failed, stalled, pending and missing gates by name.
An earlier completed reaction does not suppress those gates.
Reconciliation does not wait on a busy state lock; the next notification
or existing fallback tick retries it within the wait's timeout.
Filters apply to the returned event, not to the software reactions.

After a confirmed merge, outstanding submitted or accepted PRs are checked
against their fetched base in temporary detached worktrees. Hand-written
conflicts send the task to rework with Git's filenames in its note and brief.
Generated conflicts follow the repair path below. Unknown PR heads,
unknown mergeability and failed GitHub transport cannot authorize merging.

Repositories declare generated outputs in `package.json`:

```json
{
  "scripts": { "docs:generate": "node scripts/cli-docs.js" },
  "tower-crane": {
    "generated": {
      "generated.txt": "docs:generate",
      "docs/cli.md": { "script": "docs:generate", "blocks": ["commands:Run"] }
    }
  }
}
```

The mapping uses exact repository-relative file paths and existing npm script
names. A string declares an entire generated file, including add/add outputs
with no ancestor blob. `blocks` declares only the
bodies between `<!-- NAME:start -->` and `<!-- NAME:end -->`; text outside
those markers remains hand-written. Every declared marker must occur exactly
once in all three merge versions. Tower Crane's own mapping lists every
command-table block in `docs/cli.md`. Deletions, renames, symlinks and missing
markers remain worker conflicts.

Only the fetched base's mapping authorizes repair. When GitHub reports an
open PR `CONFLICTING` or `DIRTY` at the submitted head, automation merges the
fetched base into its idle, clean task worktree outside the worker sandbox.
It pre-resolves declared outputs, runs their npm scripts, stages every
declared output of those scripts, commits and pushes normally. A generated-only
merge keeps the task submitted, preserves its submitter and revision, and
runs gates again at the new sha. An accepted task returns to submitted for
fresh gates and review. There is no rework or worker dispatch for that repair.
If a queue head check or post-merge sweep finds generated conflicts before
GitHub confirms them at the submitted head, the task keeps its status, sha
and checkout. The queue waits and later reactions retry. Mixed conflicts also
wait, so their generated resolutions can be prepared before worker rework.
Dirty or moved branches and live workers defer it. Generator failures abort
generated-only merges and restore the clean checkout, including removing new
untracked files from that attempt; push failures retain a prepared merge for
retry. Generation must preserve text outside declared blocks. Before changing
the branch and again before pushing, automation verifies the PR head repository
and the single origin push destination against the project and PR. Fork heads
and mismatched or changed push destinations defer repair.

For mixed conflicts, the task goes to rework with its merge already prepared.
Generated files are staged; only hand-written conflicts remain unresolved,
including text outside generated blocks in the same file. The note and brief
name the worktree, remaining files and scripts to rerun before committing.
If a generator cannot run until source conflicts are resolved, the merge
keeps the branch's generated bodies staged and the worker reruns the scripts
after resolving the hand-written files.

In the gate executor queue, accepted tasks' merge reactions run ahead of
queued submitted-task gates, in acceptance order. Their merged-tree tests
keep that priority. A running gate finishes before the next reaction starts.
`gates prioritize` moves submitted work within the submitted queue; it
cannot move it ahead of accepted merges or change acceptance order.
`status` and `inbox` show the order the next free executor takes.

Accepted PRs merge through a merge queue in the order of their `accept`
events. A stack is one entry, ordered by its lowest unmerged task: it holds
that task and the accepted, linked tasks directly above it, and an upper
task whose lower task is not accepted waits outside the line. Only the head
of the line runs anything. A head GitHub reports `CONFLICTING` or `DIRTY`
uses generated-file repair or goes to rework with its hand-written files
and leaves the line. Unknown mergeability
stops the line until a later reaction. A head the queue cannot advance (a
closed or unreadable PR, a moved or differently merged head, failing gates, a refused
merge or head check) is reported once in a `queue skipped` event and passed
over, so the next entry merges; later passes try it again. The executor's
next pass starts with no skipped heads, including when a concurrent CI
completion requests that pass while the executor is still running. Its
`done` event names the first head that did not merge and lists the skipped
ones. An accepted PR already merged on GitHub at its accepted head is
confirmed through the merge gate without current gate evidence.
`merge --accepted` waits for an observable queue executor to release its
reservation, up to `gates.tests_timeout_min` (20 minutes by default), then
drains the queue through the same reserved merge path as `merge ID`.
An unobservable executor refuses with its PID and host. Each task reports
its merge or confirmation summary, refusal or pending reason. JSON returns
`results` with `{task, ok, summary}` and `remaining` with `{task, reason}`.
A skipped stack entry reports its refusal reason for every unmerged member.
`MERGEABLE` PRs with an `UNSTABLE` merge state use the same passing CI
evidence and `ci.capped_review` policy as a single merge.
Merge text and method are validated before any GitHub call. Current gates do
not bind that read-only PR lookup: it confirms a completed merge even when the
task's gates fail, or a lower stack member's review fails or its CI receipt
is stale. An open PR is refused until its gates pass.
Gate evidence belongs to the submitted sha, so a base move alone reruns no
gate. The fail-before proof reruns only for a new head. Before merging, the
head runs the pinned `gates.tests_cmd` once on the merge of `project.base`'s
current tip into its top task's head, which for a stack carries every task
in the entry, never on a stacked task's lower branch. The suite runs on a
clean checkout of a commit of that merge, with the tip and the head as
parents, made like the local CI merge commit ([state](state.md)); no ref
names it. It first trial-merges
each task bottom up and sends the lowest conflicting one to rework with its
files. The suite is skipped when the head already contains that tip or an
earlier `head check` covered the same head, revision, base tip and command.
Entries without a tests gate, or with tests mode `none`, skip it. A failing
check sends the top task to rework with the output tail, and the tasks
below it take the line again on their own. A failure under heads, stack
metadata or project settings that changed while the suite ran sends nothing
to rework; the line starts over on the current state. The rest of the line runs no
gate and no suite. The merge is bound to what the check covered: if the
entry's heads, revisions, statuses, PRs or stack metadata, or the project
settings, changed while the suite ran, the merge gate does not run and the
line starts over on the current state. A head that a reaction sends to
rework for a conflict drains the line in the same reaction, so the PRs
behind a blocked head move on. After the check the executor fetches the base
again and checks again if it moved; `gh pr merge --match-head-commit` pins the head,
but nothing pins the base, so a push to the base in the seconds between
that fetch and the merge call is not checked. A branch protection rule that
requires up-to-date branches closes that window. Hosted CI evidence comes
from GitHub's `pull_request` run, which already tests the merge ref. Merge
the base into a PR only for conflict repair, never to refresh evidence or
pick up a workflow change.
One executor drains the queue; a reaction that finds it busy records a
request, and the executor makes another pass before releasing. Manual
`merge ID` bypasses the queue and its head check: it keeps only the merge
gate's own guards.

The host's webhook or job integration can deliver CI completion with
`ci webhook` or `ci completed`. Without one, the trusted `wait` watcher
rechecks pending CI once a minute until it finishes or stalls: 30 minutes
with nothing queued or running, a check queued past GitHub's 24-hour queue
limit, or a check in progress past its 6-hour job limit ([state](state.md)).
A stall only flags the inbox. No webhook listener is installed. The notification's conclusion is never evidence: the
CI gate queries GitHub at the current submitted head. A pending or failing
gate remains failing until an explicit retry or another completion. `gates
retry ID` is the explicit retry for failed software gates: it reruns them at
unchanged inputs. A passing gate whose inputs changed, such as the pinned
command or tests policy, reruns in the next reaction without one.
Automatic failures are recorded in `automation` events. Concurrent
consumers serialize per task and reuse completed event receipts; commands
execute outside the state lock. Deferred or errored reactions remain
retryable at watcher startup. Accepted PRs already merged remotely are
confirmed through the merge gate, preserving the accepted head check.
`merge ID` holds the same task reservation as reactions. It waits while
an observable reaction runs on the task, then merges or, when the reaction
already merged, confirms the accepted head through the merge gate. A
reaction that starts during a manual merge queues; the merge drains it
after releasing the task, and it finds the task merged. A reservation
held by an unobservable executor refuses the merge.
The merge queue takes the same reservation for the head of the line
around its merge, since the queue can run under another task's reaction.
Supervisors use the dispatcher's PATH and an explicit trusted
authorization context; workers and reviewers keep their restrictive
command shims. Software reactions may finish their
bounded gate commands after a wait's timeout expires. The broker retains
its command restrictions and never executes gates.

Pass the commit actually reviewed to `evidence --sha S`. A submitted head can move while a review is running; `tower-crane evidence ID --type review --ok --sha S --agent REVIEWER` pins the result to that commit. A spawned reviewer's result also keeps the revision from its dispatch, so a verdict arriving after a brief change, acceptance change or rework cannot satisfy the new revision's review gate. A reviewer that `spawn` did not start must pass `--revision N` with the revision it read when it started; review evidence without it is refused (exit 1), and `--revision` above the current revision is refused for every type. Missing `--sha` on `review` evidence is a usage error (exit 2) and writes nothing. Software evidence types are refused first (exit 1), with or without `--sha`. A review `--ok` is refused (exit 1) and names the comment when the reviewer dispatch at that sha recorded a revuto `[P1]`/`[P2]` comment with no resolving reply and, as read at dispatch, no change to its file since the comment's commit; brokered evidence gets the same check. The comment path is a literal filename, including brackets and other Git pattern characters. A resolving reply is the latest non-revuto reply whose entire first line is `[resolved]` (case-insensitive). Put an explanation on later lines. Ordinary discussion, quoted markers and later replies without the marker leave the finding open. A reply or fix after dispatch requires a fresh review dispatch. The refusal names how a finding gets resolved: the worker or the orchestrator runs `ci resolve COMMENT_ID --task ID --reason TEXT`, which posts that reply. The reason is at most 1000 characters, each `@` in it is followed by a zero-width joiner so it mentions no one, and the reply ends with `by worker AGENT`, or `by AGENT` for the orchestrator or the owner. A reviewer that cannot record ok exits without a verdict, and automation holds review dispatch at that head until the thread changes. A `note` without `--sha` needs an existing submitted sha. Software gates record their own sha.

`spend --cache-write N` records cache-write input separately from `--cached` cache reads. Both are included in `--input`; their sum cannot exceed input. Review pricing uses the entry when available and conservatively prices non-cached input in older records at the higher input or cache-write rate.

For a supervised claude exit without a result, the supervisor reads the session again after the process group exits. Exit collection includes that final usage and replaces the live entry. Repeating `spend --from-spawn` keeps the same total. If collection runs before the supervisor finishes its final read, that reading updates the collected entry in place and rechecks budgets without double counting.

A live entry can exist before exit collection finishes. Wait for its `live` field to disappear, and use the matching `worker-exited` receipt when waiting for a worker exit.

Readers preserve future live-spend state and error-class strings. If supervision stops for incompatible state, it also skips the final live sample after the worker exits.

Submitting ends lease renewal and retries; live usage collection and budget enforcement continue until the harness closes. Missing telemetry or a smaller cumulative reading retains known spend and its age, and marks it stale. Only an explicit invocation result may lower that total. A fresh reading restores live status. The open board ages each reading every five seconds, even when no state change arrives: past its stale limit the page draws the agent row and the Spend row stale itself, then asks serve to redraw the queue and status sentence.

A budget stop keeps a ranged task on its current rung and asks the owner about the budget. Live and final spend use configured model prices in the task's per-rung cost breakdown.

`supervision.usage_ms` defaults to 30000 ms and is clamped to a minimum of 1000 ms at runtime. State-file notifications cannot shorten that interval. Unchanged readings write no usage event and retain their age. Each completed attempt is also sampled before a retry or fallback, and the launch checks its budget under the state lock. An initial read failure appears as unavailable telemetry with an error class, without the message or session path.

## Decisions

`--tier` accepts a single rung or an ascending range such as `easy..medium` in `task add`, `task update` and `plan import`. A range starts at its minimum and lets spawned workers climb after quality failure. A single tier does not climb; trusted `wait` still reworks its current failed reviews and releases verified dead claims before refilling worker slots. Setting a new range resets the current tier to its minimum, while a single tier clears the range.

`recover ID` handles a ranged task's failed independent review or confirmed tests, clean or CI gate failure at the current submitted head, exit without submit, or confirmed supervisor stall. The engine calls it after review failure and supervised exit; orchestrator `wait` also recovers observed exits and retries pending climbs. It waits for the old worker to stop, collects usage, records the climb and reason, sets rework, and starts a fresh session one rung higher in the same worktree. Provider outages and harness refusals follow same-rung availability fallback. Failed launches, full worker capacity and reviewer sandbox permission denials leave a pending climb that can be retried with `recover ID`. The reviewer's host monitor or orchestrator `wait` can complete a climb that its sandbox cannot launch.

A passing latest eligible verdict cancels an older failure of the same gate as a climb trigger. Gate runners mark `confirmed_failure` only for a failed test command, a completed cleanup scan with HIGH findings, or a completed failing CI run. Missing configuration, incomplete scans and pending CI do not climb. `rework` records a known failed attempt before changing task status, even while worker cleanup is pending; dispatch still waits for verified cleanup. Submitted workers still need their live monitor's terminal receipt before another worker starts; parent exit alone does not finish descendant cleanup. `wait` retries recorded failures that have no climb record, including after spend already recorded the exit notification or recovery timed out on the state lock. If a supervisor is lost without a terminal receipt, host recovery must verify that the old process group stopped. A live or unverifiable group leaves recovery waiting, with the reason in CLI output, task notes and a deduplicated `recover waiting` event; JSON exposes `waiting`. Linux supports this group probe.

Automatic quality escalation starts a new revision when sending work back, so earlier gate evidence no longer counts at the same commit. Its rework event records `previous_revision` for the originating rejected review. Further failures while rework is pending retain that origin until a new submission.

Failure at the range top opens one blocking owner decision. Answer it and apply the chosen plan before dispatching again. `task show --json` includes `tier_range`, `escalations` and `spend_by_rung`; text output shows the range and rung totals. New spend entries include `cost_usd` priced with configured `review.prices`. Missing prices or telemetry remain null. Each escalation records a spend snapshot; later usage collection can enrich the current task totals.

## Event wakeups

`wait` and the automation it hosts tail `events.jsonl` while running. Idle fallback checks do not reread historical event bytes or unchanged validated state snapshots. Partial lines stay buffered. Truncating or replacing the log rebuilds retained history from its beginning; active waits resume wake delivery from the new end and do not replay restored records. Byte cursors belong to one log, so restart clients with a fresh cursor after replacing it. The automation, and a `task show` or `status` run after `wait` returns, see the state change of the event that woke it: a read without the lock includes a logged commit whose files are still being renamed into place ([Durability and write order](state.md#durability-and-write-order)).

The orchestrator does not run a waiter of its own. Its harness delivers events into the session (table below); `tower-crane wait` is the interface underneath and the fallback for a harness with nothing better.

In Claude Code, arm the mod once after the startup snapshot: the model calls the `mcp__tower-crane__watch` tool with `after` set to the snapshot's offset (and `agent` or `state` when they differ from `TOWER_CRANE_AGENT`, `TOWER_CRANE_STATE` or the state found from the working directory), or the person runs `/tower-crane-watch [cursor]`. A session started with `TOWER_CRANE_AGENT=orchestrator` arms itself at session start. Arming again restarts the follower from the given cursor or from where the last one stopped. If the follower exits, a toast says so and names the command.

A push carries ids, never content: one line per event (`- E…: decision-answer D5 from owner`, `- E…: worker-message T3 from worker-T3-1`), then `Run tower-crane inbox for findings and resolving commands` and the cursor. Spawned orchestrator homes acknowledge what they delivered with `hook inbox` receipts and count events from the log offset their home was built at (`after` in `hook.json`).

`tower-crane wait [--after CURSOR] [--for NAME] [--task ID] [--types TYPES] [--timeout SEC | --follow] [--observe]` blocks until the first matching event. Run this single command in your harness's background executor and act on its completion.

- `--after` is an event `id` or a byte `offset` returned by a previous wait. The default, `now`, starts at the log's end when the command starts, so events written during its startup (orchestrator process discovery takes seconds on a cold Windows host) are delivered; `0` replays from the beginning. Cursors are exclusive. A numeric cursor must be zero or immediately after a complete line, within the current log. Unknown ids and invalid offsets exit 2.
- `--for` defaults to `orchestrator`. A message addressed to the waiter's own agent name also wakes it, and every event recorded as `owner` wakes an `orchestrator` waiter whoever it was addressed to (an owner message to a worker included). `--task` restricts to that task, including comments and answers on decisions that block it. `--types` is a comma-separated list of event types; `all` adds the bookkeeping the default skips: `hook report`, `hook inbox`, `renew`, `spend`, `spend live`, `spawn session`, `inbox snapshot`, `inbox ack` and `gate run`, plus `hook progress` rows written to the log before tool progress moved to its own files. The orchestrator never needs a type list. Filters are combined. The wait skips writes from its own agent identity, except events recorded as `owner`, `via: automation` and engine observations (`worker-exited`, `stall` and `inbox item`). Owner input and automatic results reach the waiter that shares their actor, and observations wake their observer too.
- `--observe` watches without software reactions: no startup reconciliation and no automatic gates, review dispatch, accepts or merges. Use it for a waiter that must not act, such as a second observer or a test of manual commands.
- SIGTERM or SIGINT stops new automation reservations and gates. The active gate finishes, its evidence is recorded, and `wait` releases its executor lease and exits 0. Signal shutdown prints `stopped by SIGTERM after draining 1 gate`, using the received signal and the number of gates that finished during the drain. `--json` and `--follow` print `{"reason":"signal","signal":"SIGTERM","drained":1}` instead. Idle waits and `--observe` waits also exit 0, with `drained: 0`. A second signal kills the active gate command tree immediately or cancels its source-page fetch; interrupted gates do not count as drained. These notices are distinct from wake events and timeout records. Interrupted reactions remain retryable at the next `wait` startup; an interrupted gate records a failure without a confirmed test failure and can be rerun with `gates retry`. A second signal during the tests gate's base rerun kills that rerun, so the failure records `base_rerun_killed` with signal `SIGKILL` and automation retries it once at the same head instead of reworking.
- No timeout is imposed unless `--timeout` supplies seconds (fractions allowed). On timeout, stdout is `{"type":"timeout","offset":N}` followed by a newline and the exit code is 2. The offset follows the last complete line scanned, including filtered events.
- An event line contains `id`, `type`, `to`, `at`, `agent`, `cmd`, `task`, `detail`, and `offset`. `offset` is the byte position after that event's newline. Use either returned cursor for the next wait to retain events that arrived while handling the first.
- `--follow` never exits on an event: it prints `{"type":"ready","offset":N}` once its cursor is set, then one line per matching event with `id`, `type`, `to`, `agent`, `task`, `offset`, `decision` for decision events and `steer: true` for a steered message, and no `detail`. It runs until interrupted or until its reader closes stdout, and refuses `--timeout`.

Automatic stack maintenance still uses synchronous Git/GitHub commands and can delay signal handling until the current command returns. Software gate commands and PR inspection run asynchronously and remain cancellable.

Post-merge conflict probes check the drain signal before inspecting another PR, requesting rework or reserving a generated repair. A pending inspection or trial command can finish; cancelled probes add no conflict-error notes.
If a gate fails while draining, its evidence is retained and automatic retry or rework waits for a later reaction.

The second signal also cancels asynchronous stack merge polling and its backoff. GitHub's merge request can remain pending remotely; rerun `merge ID` to confirm its state before continuing.

`tower-crane event ID` remains a read-only audit lookup. Orchestrators use `tower-crane inbox` after a wake to get current findings and resolving commands instead of interpreting the event log. `wait --inbox` refreshes GitHub once per minute and emits deduplicated `inbox item` wakeups. The plugin watch and spawned orchestrator Stop hooks enable it.

On startup or resume without a saved cursor, run `tower-crane wait --timeout 0` once. It exits 2 with a timeout and the current cursor, without observing worker exits or stalls. Save that offset, read state once, then start the background wait with `--after <offset>`. Events during the state read remain available, and the blocking wait observes current exits and stalls. With an explicit earlier `--after`, a zero timeout returns an already available matching event or a timeout cursor.

Every state change goes to `orchestrator`, including `submitted`, `accepted`, `rework`, `merged`, `worker-exited`, `spawn-fallback`, `stall`, `worker-message`, `owner-comment`, `decision-opened`, `decision-answer`, `decision-withdrawn`, `owner-done`, `released`, and `evidence` (including review, CI and gate results, and the CI gate's conflict refusal). `merged` requires successful merge evidence. Other changes keep their command name as the type; use `--types` to select a subset. Messages use their explicit recipient.

`tower-crane msg --to NAME [--task ID] [--steer] TEXT` appends a message under the state lock. Its task defaults to `TOWER_CRANE_TASK`, otherwise null. The worker's identity is recorded; only the named recipient wakes, and the orchestrator too when the sender is `owner`. `--steer` records `steer: true`: a harness that can join a running turn delivers it there instead of after the turn. A sandboxed claude or codex worker or reviewer messages only `orchestrator` or `owner`: the [state broker](ladder.md#state-broker) refuses any other `--to` and sends nothing, but appends a `msg refused` event naming the agent, the task and the intended recipient, never the text. The orchestrator answers the owner with `msg --to owner`, which reaches the owner's channel on `serve` (below).

Spawned harnesses deliver messages automatically through the adapters below. Messages are addressed to the generated agent name, across all tasks. `wait` remains the orchestrator's event interface.

| Harness | Inbound delivery | Stop with unread messages |
| --- | --- | --- |
| Claude | Home `PostToolUse` and `UserPromptSubmit` hooks return `additionalContext` | `Stop` returns `decision: block` with the messages as its reason |
| pi | Home extension appends context before the agent starts and to tool results | `agent_end` sends a message with `triggerTurn: true` |
| OpenCode | Home plugin binds to the dispatch's first chat session and appends text to its chat input and tool output | That session's `session.idle` starts another prompt; unrelated and child sessions leave its inbox alone |
| Codex | Native home hooks return `additionalContext`; notify captures completed turns on versions without hooks | Native `Stop` blocks with unread messages; notify-only versions retain messages for the next rework or transient resume |
| agy | No supported injection callback; messages stay queued | No stop veto or native session resume adapter yet |
| command | `TOWER_CRANE_HOOK` names a binding an adapter can use; otherwise messages join the next supported resume prompt | An adapter must implement its own live injection or stop veto |

`tower-crane hook ACTION --binding FILE [--payload JSON|-]` is the adapter write path. Actions are `inbox`, `tool`, `report`, `stop`, `git-push`, and `pr-created`. `-` reads JSON from stdin, keeping reports out of command arguments. Codex receives `-c bypass_hook_trust=true` for the generated hook commands; its filtered home omits project trust and user plugins, so repository hook sources stay disabled. A binding is generated at `homes/<agent>/hook.json` for each dispatch. It fixes the agent, task, state, harness and dispatch attempt; `--agent` and `--state` must match it, and owner identity is refused. Harness payloads cannot choose an identity, recipient or task. The bridge resolves only the invoking dispatch's binding from `TOWER_CRANE_STATE` and `TOWER_CRANE_AGENT`, refuses a mismatched `TOWER_CRANE_HOOK` or binding identity, and accepts no binding path argument. Hooks and shims invoke the shipped CLI by absolute path. Claude and Codex sandboxes deny reads of other agent homes, including homes created later.

`inbox` returns `{block:false, context:TEXT, ids:[event id, ...]}` and acknowledges only messages included in that context. Payload `ack:false` reads the pending context without acknowledging; a later `inbox` with `ids` acknowledges only those messages. OpenCode uses this sequence for idle delivery, acknowledging after `promptAsync` accepts the prompt. A rejection or SDK error leaves the messages queued for another idle event. A `stop` with unread messages returns `{block:true, context:TEXT}` and acknowledges the messages it used to hold the turn. Delivered ids persist in the event log across rebuilt homes. Dispatch and retry prompts acknowledge their included messages after launch; dry runs acknowledge nothing. When a process has already exited, the supervisor uses `stop` with `hold:false`, preserving unread messages for resume. Spawn refuses a command rung whose command argv contains neither `{prompt}` nor `{brief}`, including dry runs, because it cannot deliver the goal, task and house rules. Command adapters must consume `{prompt}` or `{brief}` for dispatch delivery and `{prompt}` for transient retry delivery; otherwise messages stay queued. agy currently lacks a native resume adapter, so its pending messages require an adapter before automatic delivery is possible.

Tool hooks and recognized JSON tool events append `hook progress` to the agent's `progress/<agent>.jsonl`, whose changes the supervisor counts as claimant progress while renewing leases. A `PostToolUse` for a Bash call with `run_in_background` also publishes `hook background`. A headless `claude -p` worker whose task is still claimed and unsubmitted gets one hold, at the first stop where the attempt started a background job or the stop's own final message is empty (an earlier report does not count): the bridge returns `decision: block` with an instruction to finish in the foreground, and `hook wait` records it. Later stops are not held. A stop that is allowed through while a background job is pending sends `orchestrator` no stop notice, because the worker may resume; a process that then exits is reported by its exit event. The generated Git and gh shims publish `hook git-push` and `hook pr-created` after successful `git push` and `gh pr create`, except a sandboxed codex agent's: its sandbox hides its binding, so its shims publish neither ([ladder.md: Home reads](ladder.md#home-reads)). The supervisor reads assistant reports from harness output and publishes a final message to `orchestrator` after stream closure. A stop without submit includes the last captured report, or says none was captured. Repeated stops with the same dispatch, report and submission state do not duplicate the message; a later result can supply a follow-up report. Plain tool output never counts as a report or nested event. Output observation ignores JSON lines larger than 1 MiB. `hook git-push` and `hook pr-created` are hints, not proof: an agent can record either through its own hook binding without running a command, so each carries `unverified: true`. Anything that acts on them checks GitHub or the repository first.

`worker-exited` covers a spawned worker that exits without submitting, including failure before claiming. It includes `agent`, `pid`, `attempt`, `log`, exit `code` and log `size`; an existing claim remains for explicit recovery. Log text stays in the log file and is read live by `status` and `ready`. Detection uses `lib/processes.js`, shared with dead-spawn diagnostics. Local pid checks recognize Linux zombies and reused pids; another host's pid is never probed.

Automatic exit and stall observations run only for `owner`, `orchestrator`, an agent recorded by `spawn` with `role: orchestrator`, or a collector CLI whose visible parent is its recorded spawn monitor. Worker and reviewer `wait` calls consume recorded events without detecting exits or stalls. Their `spend --from-spawn` calls collect the requested usage without scanning peers. A sandbox can hide a live peer's pid, so its failed local probe cannot establish that the peer exited. Run the orchestrator and monitors where worker pids are visible.

For manual and legacy runs, `stall` means the claim lease expired and there has been no claimant progress for at least the most recently granted lease interval (`claim --lease` or `renew --lease`, defaulting to `limits.lease_minutes`). Claimant writes other than claim and renew count as progress. Renewing extends the lease but is not progress. Supervised spawns emit `stall` after `supervision.stall_ms` without progress paths, claimant writes or CPU activity, even while their lease stays live. Exit and stall events are deduplicated under the lock for the current claim and source; owner comments do not postpone a worker's stall.

The engine watches the state directory with `fs.watch`. A one-second internal stat and process fallback covers missed or unavailable notifications and detached exits, including Windows. The caller never queries in a repetition to discover completion.

## Board writes

`serve` binds to `127.0.0.1`. Owner forms and routes require serve itself to run with explicit `--agent owner` or `TOWER_CRANE_AGENT=owner`. Other identities see messages and comments without owner forms, and these POST routes return 403 without writing. Each permitted request calls the same locked task or decision function as its CLI command, using the serve process's identity.

Stop posts to `/api/tasks/T1/stop`: `interrupt` stops the agent through its supervisor, without a retry, releases the claim and sets the owner ask in the same write, so no dispatch restarts the task until the owner runs `owner-done` (the board's Resume). An approval's Approve and Decline post the decision's own options, `approve` and `decline`, to `/api/decisions/D1/answer`; Approve lets the orchestrator make the recorded change once ([Authority](state.md#authority)). In a decision's note field, Enter answers the recommended option and does nothing when there is none; a form sends one write at a time.

A task sheet's tier control posts to `/api/tiers` (below), as Settings does. Both `/api/tiers` and `/api/ladder` require the same explicit owner identity as the other board writes. Other serve identities see the ladder and tiers as read-only values. The Controls view (`/controls`) adds project and task settings, approvals, claim release, interrupt, acceptance with waivers and orchestrator delegation. Merge, claim, submit and evidence remain CLI operations.

Successful writes return the command's JSON data plus the board's `version` token. These endpoints share Settings' POST handling: send the run's token (below) as `x-tower-crane-token`. Invalid input or a refused change returns 400, missing or wrong token/host/origin 403, wrong content type 415, oversized body 413, and lock timeout 503. Bodies require `application/json` and are limited to 64 KiB to bound a local request's memory. Messages and comments appear on the served board, with state changes delivered through its reload stream.

The token protects against foreign web origins and against local processes that read the pages: only the page opened from the owner's one-time link carries it. A local process can still supply an owner identity to the CLI.

The status sentence, the Needs you heading, the Now navigation count, the page title and the icon share one count. A budget item shows minutes for hours under ten. An agent row shows the current claimant's message from the current claim; the Review room shows the submitter's summary for submitted work. Other authors' notes remain in the conversation.

The initial view starts at the top after the browser's fragment jump. If that animation frame runs late, it skips the reset when the route, page scroll or main scroll has changed since load, preserving the reader's position before and after live updates.

With scripts enabled, a task sheet contains keyboard focus and makes the background inert. Tab cycles within it, Escape closes it, and focus returns to the invoking link, including after a live update. Without scripts, the snapshot still opens every task record by its plain fragment link. Gate pips and the evidence ledger use the current mode-aware gate report, including for accepted tasks; an old-mode tests pass or a tests/clean pass with stale command policy is marked as no longer counting. Each ledger entry is checked independently, so a fresh pass does not hide the stale marker on earlier receipts.

The Settings view (`/settings`) edits the default harness, every rung and each task's tier when serve runs as the explicit owner. Other identities get a read-only Settings view with no edit controls and the command `tower-crane serve --agent owner` for enabling edits. Live Settings reloads use the same identity snapshot to restore disclosures, the focused control and every scroll container, including the ladder and tier panels, for both owners and read-only viewers. Position is kept in the tab's session storage only until the reload restores it. Further live writes arriving before restoration reuse the pending snapshot, and notifications for the displayed version are ignored. While a form has unsaved edits, a change on disk shows a notice instead of reloading the page. A form is read-only while its save is in flight, with its Save button showing `Saving...`. Saving a form reloads the page only when the other form has nothing unsaved; otherwise the saved form shows the server's state in place and the other keeps its edits. A save sends the values its edit was based on, so one made against a rung, default harness or tier that changed since the page loaded is refused, and the page says to reload.

### serve endpoints

The server tails the event log for reloads and owner messages, and retains history for repeated page and message requests. Its directory watch has a one-second fallback check even when no watch error occurs. A replaced or truncated log rebuilds queryable message history, but SSE wakes resume from the new end without replaying restored messages.

|---|---|

| `GET /settings` | the Settings view |

The Controls page links every row of `tower-crane authority` to its form. Project controls cover limits, pause, budgets, test and cleanup commands, CI and review policies, merge options, decision delegation and spawn grants. Rung controls cover every ladder field; Settings keeps its ladder table and default harness selector. Personal controls edit fallback routes (`ladder set RUNG --fallbacks`), save the ladder defaults, and set the browser kit. Task controls edit kind, tier, owner blockers, CI overrides, budgets and cancellation, release claims, interrupt running work, prioritize gate work, accept with gate waivers, delegate a decision and delegate orchestration. The publication form records approval; publication itself remains the orchestrator's work.

`POST /api/controls` accepts `project set`, `ladder set`, `ladder harness`, `ladder save-user`, `browser-kit set`, `task update`, `gates prioritize`, `decision delegate`, `owner-done`, `release`, `interrupt`, `accept`, `spawn` (`task` and role `orchestrator`, without `ready`, `wait` or `dry-run`), and `ask` (setting `publish`, without a question). Flag values are strings, repeatable flags are arrays of strings, and positional arguments are strings. Flags are the CLI's names, so a rung's `web_mcp` field is sent as `web-mcp`. Global options and unknown commands or flags are refused. For example:

```json
{"command":"project set","flags":{"workers":"4"},"pos":[]}
```

The command parser and handler perform the same validation as the CLI; `Authority.enforce` checks and audits the write. Operational writes return `{ok: true, data, message, version}`. Owner-required writes, including a release of another agent's live claim, return `{ok: true, decision: "D1", message, version}` after opening the shared escalation, without changing the setting. For a request the owner made from Controls, Approve runs the recorded request through the same handler as the owner, consumes the approval once and records `approved_by`; decline makes no setting change. A failed application leaves the approval available for retry, with the refusal shown inline. For an orchestrator's escalation, including an owner's request the orchestrator then asked for too (`repeat_by` on the decision), Approve only records the answer: the orchestrator's refusal told it to run the same command again, and that repeat uses the approval, so the change is made once and no second decision opens. That repeat carries only the owner-required change, so the reply and the page name any other flag of the owner's request that did not apply. A publish request (`ask --setting publish`) is answered the same way, since the orchestrator publishes. A later write uses only an approval the owner asked for from Controls that no orchestrator repeats. While an orchestrator's approval of the same change is pending, a write opens the owner's own confirmation and leaves that approval for the repeat; sending the same publish request again returns `{ok: true, data, message}` naming the existing approval, without using it. Ordinary decisions use the board's existing answer form.

`GET /api/controls` also returns the state `version`. Controls send `x-tower-crane-version` with the page's version; a mismatch returns 409 before the command runs. Unsaved input delays live reloads. Saving disables the submitted form until its reply. When another form holds unsaved input, the page stays and reloads its data from `GET /api/controls`, so selectors that fill a rung, fallback or task value show the saved state and the other form keeps its edits. On this in-place path the form stays disabled until that data reload also ends, so the reply never shows before the saved values. The reload gives up after 10 seconds. If it fails or times out, the form shows the save's reply, says the page could not load the saved state, shows the reload notice and is enabled again. The JSON API also accepts clients that omit this optional version header.

`project set --paused REASON` records `limits.paused` and blocks new claims and task dispatches. Running processes and their retries continue until interrupted; `--paused ''` resumes dispatch. Dry-run previews remain available.

Every POST needs:

- `x-tower-crane-token: <token>`, the random token of this serve run. Only the page opened from the printed link gets it, so a local process that reads the pages, with or without an `Origin` header, cannot write. The page keeps the token in the origin's local storage, scoped to this host and port, so reloads and other tabs keep writing; it drops the key from the address bar. Another browser needs a restart of serve and its new link;
- `content-type: application/json` and a body of at most 64 KiB;
- an `Origin`, if the browser sends one, of `http://127.0.0.1:<port>` or `http://localhost:<port>`.

serve answers any request only when its `Host` is `127.0.0.1:<port>` or `localhost:<port>`, so a page on another site cannot reach it through a name rebound to 127.0.0.1 and read the token.

### Owner channel

The owner talks to the orchestrator the way a phone client talks to an agent: a message stream, push wake-ups and the decisions to approve. A client reads the token from the board's `<meta name="tower-crane-token">`, keeps an `EventSource` on `/events`, and on each `wake` fetches `/api/messages?after=<cursor>` for the text, so a wake-up never carries content. It sends with `POST /api/messages` (`queue` waits for the orchestrator's turn to end, `steer` joins the running one) and answers a decision with `POST /api/decisions/D<n>/answer`, the board's own route. Both wake the orchestrator session through its harness delivery; the orchestrator replies with `tower-crane msg --to owner`, which arrives on the same stream. Board comments and answers take the same path.

`POST /api/ladder` body, with `harness` and `rungs` optional but at least one change, and `base` required:

```json
{
  "harness": "pi",
  "rungs": {
    "easy": { "harness": "", "model": "provider/fixture-model", "profile": "", "effort": "low", "args": "[\"--no-session\"]" }
  },
  "base": { "harness": "codex", "rungs": { "easy": { "profile": "fixture-light", "effort": "medium" } } }
}
```

`base` is what the edit was made against: the default harness, and the own fields of each rung in `rungs` (as `ladder show` prints them, without `harness_from` and `from`, and with `harness` only when the rung names its own). If any of them differs from the state under the lock, the request is refused with 409 and writes nothing, so a form cannot undo a change made elsewhere with fields nobody touched.

Each rung lists the primary fields to change, as strings. An empty string clears the field; a field left out keeps its value. `args`, `command`, `tools` and `mcp` are JSON array text, as on the command line. The Settings view has no columns for `tools` and `mcp`; it keeps them as they are. Personal fallbacks are read from the user file and cannot be changed through this API. The whole request is one write: if it leaves a rung unable to run that could run before, nothing is written. The reply is `{ "ok": true, ... }` plus the resolved ladder (`harness`, `harness_from`, `user_file`, `user_file_exists`, `ladder`).

`POST /api/tiers` body: `{ "tiers": { "T1": "hard", "T4": "research" }, "base": { "T1": "medium", "T4": "medium" } }`, where `base` holds each task's tier as the edit saw it; a task whose tier differs now is refused with 409. All tiers are written in one write, or none. The reply is `{ "ok": true, "tiers": [{ "id": "T1", "tier": "hard" }, ...] }`.

Every successful reply also carries `version`, the state's version after the write, the same token the `reload` event for that write carries; the page uses it to tell its own write from one made elsewhere.

A rung saved onto another harness keeps the fields the page changed and drops the ones it sent as loaded that do not fit there; the reply lists them in `dropped`, and the page's last-change line names them. Both write under the lock, validate, log events (`ladder harness`, `ladder set` per rung, `task update` per task) with `"via": "serve"` and the agent serve runs as, and re-render the sketch. Refusals reply `{ "error": "<reason>" }`: 400 for a refused or malformed change (the reason is the one the CLI gives, prefixed with the rung or task it is about), 409 when `base` no longer matches the state, 403 for a missing or wrong token, a foreign origin or a foreign host, 404 for an unknown POST path, 405 for a method other than GET or POST, 413 for an oversize body, 415 for a body that is not JSON, 503 when the state lock is busy, 500 for anything else.

`spawn` passes an absolute `TOWER_CRANE_CONFIG` path to every harness, preserving the original user file when an isolated orchestrator dispatches workers. Command fallback executables containing placeholders are checked after expansion during preparation; `ladder show` defers their executable lookup until task context is available.

Before creating a new task branch, `worktree` fetches `base` from `origin` into `origin/<base>`, even when the remote's fetch configuration excludes that branch. It starts from the fetched commit when the local base is missing or is an ancestor of it. A local base that is ahead of or diverges from origin remains the starting point, with both commit SHAs reported on stderr; the local base branch is never moved. Task branches start from the selected commit SHA. When origin exists, the branch tracks `origin/<branch>` unless an upstream is already set, so a plain `git push` publishes it from a sandbox that cannot write the repository config. If origin has no such branch, it uses the local base and reports that fallback on stderr, or refuses if the local base is missing too. Without an origin remote, it uses the available local base or `origin/<base>`.

Prepare a dispatch with one `tower-crane worktree T1 T2 ...` call before starting workers. It validates every task id, fetches the base once if any task needs a new branch, then creates the worktrees serially from that selected SHA. With multiple ids, `--json` prints an array in task order; one id keeps the existing object output. Plain output lists one path per line. Duplicate ids are prepared once. A later dispatch fetches again; existing branches and completed worktrees remain usable offline. Start parallel `spawn` calls only after preparation, so they reuse the completed worktrees. Callers must serialize preparation within a repository, including calls from different worktrees or state directories; independent creation calls are not coordinated by a repository lock.

A `cannot lock ref` or `incorrect old value` fetch failure waits 100 ms and retries once before reading the tracking ref. Each fetch and missing-branch verification times out after 60 s. An unpack failure is usable only if a fresh origin read proves another caller already imported that exact tip. Other fetch failures, including a second ref-race failure, refuse before a task branch is created or recorded. Git worktree creation and checkout have no added timeout. Worktree creation uses Git's native initialization lock and unlocks only after checkout and its hooks finish. A killed or failed add leaves any surviving registration locked; `worktree` and `spawn` refuse to reuse it. If any task in a batch has an unfinished registration, the whole batch call refuses; worktrees prepared earlier in the call can remain. After Git and its children finish, inspect the worktree, then run `git worktree unlock <path>` for a complete checkout or `git worktree remove --force <path>` for an incomplete one. The CLI never reclaims that lock based on the parent's pid or elapsed time. `spawn` with an unprepared task uses the same single-task creation behavior, so run it serially. A rework whose branch is missing fetches that branch from origin before it is recreated. It continues from the origin tip only when the tip contains the submitted commit, and otherwise from the submitted commit. A failed branch fetch refuses before any branch is created.

Preparation and stack sync prune orphan Git worktree registrations before use. Temporary gate worktrees also prune before creation and after every removal attempt. A sandbox can recreate empty read-only `commondir` and `config.worktree` mount points after a worktree is removed; prune clears those orphan entries. Empty read-only `*.lock` files in the git directory that no process holds, such as `config.lock`, are removed and logged before those git calls. Locked initializing registrations remain protected while checkout and its hooks run. Git writes the admin files; the CLI does not reconstruct partial metadata.

If Git reports a missing `commondir` while adding a worktree during another gate's removal, preparation waits 100 ms and retries once. The retry replans the worktree and still refuses an unfinished locked registration. A persistent error is reported.

`spawn` checks the rung, the brief (`brief set`) and the harness program (on `PATH`, or at the path the rung gives) before it creates anything. If the program still fails to start, or the lock cannot be taken, it records nothing and exits with the reason, naming the worktree it created; the worktree and branch stay, and the next spawn of the task reuses them. `spawn` never deletes a worktree or branch. Worker scratch persists at the task's recorded `scratch` path across attempts and rework. The worker prompt and command-harness brief name it; `XDG_CACHE_HOME` points there. Merge, cancel and superseding cancellation remove scratch when they remove the worktree, and keep it when worktree retirement is deferred. The agent is named `<job>-<task>-<n>`, where the job is `worker` for the four tiers, `reviewer` for `review`, and the rung's name otherwise, numbered from earlier spawns of that job on that task.

On Windows, harness lookup also accepts npm `.cmd` shims whose quoted `%dp0%` or `%~dp0` target exists. The supervisor runs that script with Tower Crane's Node executable, without a shell, preserving multiline prompts and literal shell characters on initial launches, retries and fallback routes. Other batch files are not supported. Linux and macOS launch commands as before.

Worker spawns check `limits.workers` under the state lock using the same count as `claim` and expired-lease `renew`: live leases plus unclaimed worker spawn reservations. A full limit exits non-zero naming the task and agent holding each slot, before launching a process, writing a home or recording spend. On Windows or a host without `/bin/sh`, the dispatch takes the worker's lease before its harness starts, so it reserves nothing. Behind the POSIX lease gate a successful dispatch records `reserved: true` and holds a reservation until the supervisor takes the generated worker's lease for that task, an exit receipt or the monitor records that its supervised attempt ended, or one default lease passes since the attempt's last monitor record with no lease taken. Retry backoff keeps it until one lease after the scheduled relaunch; session receipts do not extend it, and a lapsed reservation is never revived. Claim consumes that worker's reservation without counting it twice. Launch failure holds no reservation. `--role review` and other non-worker rungs are unaffected; `--dry-run` only previews the command and reserves nothing.

`spawn exit` and `worker-exited` receipts release the matching unclaimed reservation. New receipts include `attempt`. Receipts without it match the latest preceding spawn, retry or fallback by task, agent and pid; the same match proves exit for resume, usage collection and recovery.

Reservations are read from the event log alone, so a sandboxed claimer and an unsandboxed spawner count the same holders. Only a worker spawn, or a batch `spawn --ready` before it counts free slots, probes processes, under the lock: a reservation whose monitor and harness process group have both exited gets a `reservation clear` event and holds no slot after it. On Linux the group is read from `/proc`; on macOS a signal to the group must find no member; on Windows, which has no process groups, the harness's own exit stands for the group. Hidden, unknown or other-host pids never clear one. A worker spawn for a task that a live reservation holds exits non-zero naming the holder. Spawns recorded before reservations existed carry no `reserved` marker and hold no slot.

An expired pre-claim held by the generated worker is renewed to the default lease duration under the spawn lock, preserving its agent, `since` and `from`. This lease holds the slot before the supervisor can renew it. A failed launch leaves the pre-claim and receipts unchanged, except on Windows or a host without `/bin/sh` once the handshake has committed the lease. There the rollback restores the prior claim with a `claim` event carrying `rollback: true`, or, for a task with no prior claim, records a `release` event carrying `rollback: true`.

Worker dispatch and role-filtered `brief get` use the shared text of briefs without role headings. For role-specific text, use level-two headings `## Shared`, `## Worker` and `## Reviewer`. Matching is case-insensitive, and headings inside fenced code blocks are ordinary text. Text before the first role heading is shared, and each section ends at the next role heading. `## Rework notes` starts a shared section. The worker prompt includes shared text and the `Worker` section; the reviewer packet includes only the `Reviewer` section alongside the diff, acceptance and gate results.

```md
## Shared
Constraints and task context for both roles.

## Worker
Implementation instructions.

## Reviewer
Review instructions.
```

Agy house-rule prompts and startup receipts contain project instructions only. Original user memory and modular rules are excluded, and their paths receive no generated read grant. Agy remains owner-required and unbrokered while its sandbox capabilities are false.

For worker and reviewer jobs, a `claude`, `codex`, `opencode` or `agy` prompt starts with the body of the matching `skills/tower-crane-work/SKILL.md` or `skills/tower-crane-review/SKILL.md`, with frontmatter removed. If that `SKILL.md` is missing, `spawn` warns on stderr and continues without the role skill. A fresh prompt then contains a `## Goal` section (the project goal, the task's target, and an instruction to restate both in the first message), a `## House rules` section listing the rule files by path ([Agent files and homes](ladder.md#agent-files-and-homes)), the worker brief or reviewer packet, the task's id, title, acceptance and kind as JSON, and a line telling the agent to use the `tower-crane` CLI for every state change. It says `you are not the owner; never pass --agent owner`. Its closing instruction says `run tower-crane with --agent <name> if TOWER_CRANE_AGENT is missing`, using the same name passed in the environment. A resumed worker gets its rework note without another copy of the skill body. Rework, interrupt and review prompts name the role skill by its absolute path in the state directory's [skill store](state.md#files), `skills/<key>/<skill>/SKILL.md`, since the task's worktree has no `skills/` directory. A prompt never names the dispatcher's package root, which can be another agent's tool snapshot that goes when that agent exits, nor a path under `homes/`, which the claude and codex sandboxes hide from the agent itself. When the role skill is missing, the prompt names the skill without a path. A pi worker or reviewer receives its matching skill through `--skill` instead, without a duplicate in the prompt; if its `SKILL.md` is missing, `spawn` warns on stderr and omits `--skill`. A fresh custom `command` rung receives the worker brief or reviewer packet and task prompt without an automatically embedded skill body. Its `{brief}` argument is a temporary copy of that context with the same `## Goal` and `## House rules` sections first and the task JSON after it, so an adapter that reads only `{brief}` still gets the goal, rules and acceptance; the copy is removed after foreground completion or a verified background exit. The prompt runs in the task's worktree, which is created if missing; `--dry-run` creates nothing. Both streams go to `logs/<task>-<agent>.log`; the `spawn` event records the harness pid and dispatch metadata. In the background the agent is detached and a monitor collects usage after exit through the same locked observer used by `wait`. A waiter that observes an exit also attempts collection; concurrent observers count the spawn once. With `--wait` output is also streamed to the terminal (stdout goes to stderr under `--json`), usage is collected after stream closure, and tower-crane exits with the agent code.

Command `{brief}` copies are single files named `tower-crane-brief-<pid>-<uuid>-brief.md` under `TOWER_CRANE_TMP`, then `TOWER_CRANE_TEST_TMP`, then `~/.cache/tower-crane` (`XDG_CACHE_HOME/tower-crane` when set). Windows uses `LOCALAPPDATA/tower-crane`, falling back to `~/AppData/Local/tower-crane`. Creation is exclusive with mode `0600`. Cleanup unlinks the whole copy in one operation, leaving no per-copy directory. Foreground completion and startup failures remove the copy before returning; detached supervision removes it after the harness and its process group finish, including signal exits.

`spawn --role review` selects a reviewer per task and requires a submitted head with passing software gates, including CI for a PR. It checks again under the dispatch lock and refuses a second live reviewer at that head and revision. Review prompts contain the diff, acceptance, gate results, the brief's `## Reviewer` section and, for a PR, a `## Revuto findings` section with revuto's open inline comments at the head (path, line, body, `[P1]`/`[P2]` marked), which the spawn event records as `revuto`. They ask the reviewer to use the supplied results and re-run tests only for a focused probe. The CLI writes `reviews/<task>-<full-sha>.md`; packets over 12,000 characters are referenced from a short prompt so Windows command limits do not drop the diff. `rung` stays `review` for role and spend accounting; `review_rung` names the selected tier or fallback, `review_level` the complexity level selection computed, and review dispatch adds the submitted `sha` and `revision`. An unsubmitted `--dry-run` previews the fallback command only; a submitted dry run checks gates and selection but writes no packet.
Spawn logs are created exclusively with mode `0600` on POSIX. On Windows, logs inherit the state directory's ACL; the state directory normally lives under the user's profile. An occupied log name, including a leaf symlink, refuses the spawn without writing to the file or recording a spawn. Move the occupied log before retrying. The state directory and its parent directories remain trusted local storage.

The packet's `## Review scope` names either a full review or a re-review. An eligible failed independent review at the current revision narrows the scope. After rework, dispatch uses the latest eligible verdict at the rework event's `sha` and `previous_revision` when it failed and the task is still at that event's new revision. A brief, acceptance, dependency, needs or kind edit after that review resets the scope to full. Passing verdicts and reviews without an independent dispatch do not supply a narrowed scope.

A re-review carries the prior reviewer, SHA, revision, summary, comment ref, recorded findings and rework reason. Its supplied diff starts at the reviewed SHA when that commit still exists, is an ancestor of the submitted head and contains the current merge base with the project base. A missing reviewed SHA, rewritten history or base update gets a full review from the project base's merge base, excluding upstream changes; its packet still lists the prior blockers for the reviewer to confirm. ## Gates

GitHub command failures include the child exit status, signal and startup error code and message in the summary, alongside stderr or stdout. Empty output is reported as `no output`. These diagnostics do not retry the command or change its timeout.

The CLI's git and gh calls neutralize repository-supplied commands and refuse to run if the Git config scan fails or exceeds its output buffer. Git proxies use the caller's `GIT_PROXY_COMMAND`, or no proxy command when it is absent. The tests and clean commands themselves run outside the worker sandbox with the caller's full environment. See [the gate environment contract](state.md#worker-written-code-and-config-outside-the-sandbox).

Each gate runs software, then records evidence on the task. Gate commands run in a temporary worktree under `TOWER_CRANE_TMP`, the project's `gates.tmp_root` or `tc/g` under the user's cache directory, with `TMPDIR`, `TMP` and `TEMP` set to a directory inside it (a caller's `NODE_COMPILE_CACHE` moves into that directory too); the git commands the gate runs in that worktree, and the hooks they start, get the same environment. The worktree and that directory are removed when the gate ends, whatever its outcome. Only `check tests`, `check clean`, `check sources`, `check ci` and `merge` record their respective software evidence types. Each result carries `source` naming that command and `commands` listing the processes it ran, with their arguments, working directory, exit status and signal. This includes the test command at head and, in `prove` mode, without the change, the cleanup invocation, GitHub queries and the merge invocation. Expensive proof records the full or mapped head run and both scoped runs. Gate commands' stdout and stderr are joined by whole lines: each stream is held until its newline, so a chunk of one stream never splits a line, or a secret in it, of the other, and lines appear in the order their newlines arrived ([state.md](state.md) has the order a block-buffered command gets). A failed test command records `test_failure.names` from node:test spec (`✖`) or TAP (`not ok`) output and `test_failure.output_tail`, bounded to the last 40 lines and 8192 characters; the summary prints both. Names and tails redact environment values that look like secrets before storage or printing. A value looks like a secret when it has a token shape (GitHub, API, AWS and Slack keys, `Authorization` header values), or when its name is credential-named (token, secret, password, passwd, credential, API key, access key, private key or cookie) and it is 20 or more characters of letters and digits with no spaces. This covers the process environment and project, resolved rung and environment-file values. Numbers, booleans and short words are never redacted, whatever the name. Paths, file names and commit SHAs are never redacted. Environment-file contents are never stored. Tests mode `none` records only the Git command verifying the submitted commit and names the skip policy in its summary. Tests evidence and audit detail record the resolved `tests_mode`; successful tests evidence with a missing or mismatched mode no longer counts against the current project policy. A precondition failure can have no commands; an ok entry needs at least one command to count. The audit event carries the same receipts and revision.

For the `check tests` run without the code change in `prove` mode, changed declarative manifests, lockfiles and `tests.keep` matches stay at the submitted sha. This includes files such as `package.json`, `package-lock.json`, `Cargo.toml`, `Cargo.lock`, `go.mod`, `go.sum`, `pyproject.toml` and `requirements*.txt`; executable build files such as `Makefile` need an explicit keep glob. The summary names each kept path.

The gate itself lives in `lib/gates/<name>.js` and exports `async run(ctx)` returning `{ ok, summary, ref?, sha?, receipt? }`, where `ctx` is `{ root, worktree, task, project, args, log, exec }`. A gate that can start more than one timed command also exports `plan(project, root, task)`, the most it starts in one run; the gate-run lease deadline counts that many timeouts, and one without it counts one. Gates run commands through the shared helpers in `lib/gates/common.js`, which use the CLI's `exec` to capture receipts. The CLI runs the gate without holding the lock, then records the result as evidence of the gate's type by `--agent`, at the returned `sha` or the submitted one, against the revision the gate started on. A local CI `receipt` is copied into evidence and its audit event. Hosted CI records `ci_policy` from the project settings when the check starts, in both evidence and the audit event. A gate that reports `ok: false` exits 1 after recording. A missing gate module exits 1 with "gate not installed".

Acceptance counts software evidence only when events.jsonl has a matching gate event: `cmd === source`, the same task and agent, and matching type, source, exact evidence sha, verdict, revision and command receipts. It ignores entries without that event and ok entries with no commands. Writes separate an unterminated audit-log tail from new events so a torn line cannot hide a gate receipt. Existing entries stay readable; run the gates again for the submitted sha to replace their proof. Merge and the task views use the same check. A waiver counts when its agent is `owner`; when the orchestrator recorded an operational waiver (`waive.review` for a capped or down reviewer); or when the orchestrator recorded it with `approved_by` naming an escalation the owner approved ([Authority](state.md#authority)).

Review evidence counts only from the owner or a reviewer spawned for the task at that sha and revision, never the submitter. Other review evidence stays visible as not counting. Its pass or fail verdict does not set the board's review gate indicator.

A gate shell command runs in its own process group, and the gate stops that group when the command exits or times out. On Linux the stop also reaches processes the command moved out of its group, such as a test fixture's detached process in a new session. Each run sets its own environment variable, `TOWERCRANE_GATE_RUN_<pid>_<hex>=1`, and the gate stops every process that carries it, plus every descendant of the group or of a marked process that is still linked by parent. A process that clears its environment and whose parent has already exited escapes this. Processes a gate command starts stop when the gate ends, including per-user daemons it happens to launch, such as build servers, tmux, an ssh ControlPersist master or gpg-agent. Gate commands run with `gc.autoDetach=false`, appended to any `GIT_CONFIG_*` entries already set, so an automatic `git gc` finishes inside the command instead of being stopped mid-write.

A tests or clean command stopped by its gate deadline records `ok: false`, `infrastructure_failure: true` and `timeout: {minutes, running_files, output_tail}` in both evidence and its audit event. The summary says `timed out after N min`. `running_files` contains paths reported by node:test interruption locations or unfinished top-level TAP file subtests; an empty list means the runner did not identify them. The output tail is captured before termination, redacted and bounded to 40 lines and 8192 characters. Cancellation messages printed after SIGTERM do not become `test_failure` names. A timeout at head, scoped proof or reversion fails the gate without `confirmed_failure`, so it never proves a change or triggers a quality climb.

A command killed by a signal records `runner_crash: true` without `confirmed_failure`. A shell reports that signal as exit 128 plus its number, so such an exit counts the same. A CI check whose failing runs all timed out, were cancelled or never started records `infrastructure_failure: true`; a failing run with conclusion `failure` records `confirmed_failure`, and any other failing conclusion, such as `action_required`, or a required run that completed without success, records `worker_failure: true`. A CI check with runs still in progress records `pending: true`. GitHub observation errors record `infrastructure_failure: true`: a failed `gh pr view`, unreadable GitHub output, or a failed check-runs, check-suites or Actions API read. Unknown mergeability is pending, not an observation error. At a submitted head these errors retry once; a recovered read uses the new CI verdict, and a repeated observation error reworks with its diagnostic. A local CI command (`ci.local`) that times out records the same, and one killed by a signal records `runner_crash: true`. Automation retries any of these once at the same head, as it does a timeout. A change the worker must fix records `worker_failure: true` without a command verdict: no test covers the change, or it has no changes against the base; automation reworks it at once. A failed `tests`, `clean` or `ci` gate that no flag names records no classification and reworks at once. A pending CI run records `pending: true`, and automation keeps it submitted. Pending CI that has nothing queued or running for 30 minutes, or whose PR closed without merging, records `stalled: true`; it also stays submitted. A pinned command that is missing or not installed records `config_failure: {key}`, where `key` names the setting (`tests_cmd`, `tests_proof_cmd` or `clean_cmd`). The configuration receipt waits for `gates retry` once the command is pinned, and the inbox shows a `gate_config` item addressed to the orchestrator that names `gates.KEY`. Automation still inspects later software gates; an independent failed verdict retries or reworks normally, while successful or pending later gates leave the task submitted. A test that also fails on the base branch records `main_failure: {base, names}` with the names that fail there too, when every failing name does; automation retries it once like an infrastructure failure. The base is the newer of the local and `origin` branch. Such a run records no `confirmed_failure`, so it never climbs a rung. A run with a name that does not fail on the base keeps its verdict and names the shared ones in its summary. A base rerun killed by a signal checked nothing: the run records `base_rerun_killed: {base, signal, status}` and no `confirmed_failure`, its summary says `Base rerun at BASE was killed (SIGNAL); shared failures were not checked.`, and automation retries it once like a timeout. A base rerun stopped by the gate deadline checked nothing either: the run records `base_rerun_timed_out: {base, minutes}` and no `confirmed_failure`, its summary says `Base rerun at BASE timed out after N min; shared failures were not checked.`, and automation retries it once. Both flags appear in the evidence and its audit event. A cleanup scan with checks that did not run records `infrastructure_failure: true`.

Tests and clean evidence and their audit events carry `gate_policy`: `{tests_cmd, tests_proof_cmd, paths, keep, expensive}` for tests or `{clean_cmd}` for clean, captured when the check starts. The tests settings are the effective values: `paths` is `tests.paths` (null for the default layouts), `keep` is `tests.keep` (null when unset, which keeps the default manifests and lockfiles) and `expensive` is `tests.expensive === true`. While a map is pinned, the tests policy also snapshots `tests_map`, `ci_required` and `ci_local`. Command values are trimmed strings or null. Missing, malformed or changed policy makes previous evidence stale, even if the owner changes commands during a run. Successful receipts must also include the pinned test command or mapped head expansion (except none mode) or the pinned cleanup invocation with its appended arguments. Scoped proof records `receipt.proof_tests`, the changed test paths used to expand the pinned template; mapped head runs also record `receipt.head_tests`; every test shell receipt must match the full command, the mapped head expansion, the proof expansion or a host-only expansion of the pinned proof template for one file in `receipt.host_only.results`. Host-only expansions count even when all cases in the recorded file skipped. The proof command from the run without the change still counts; any other extra shell command is rejected. Map, expensive-policy and required-job changes invalidate mapped-policy receipts. Acceptance, merge and task reports use the same check. Old receipts without this snapshot require a new check; owner waivers retain their existing behavior.

The CLI refuses manual software verdicts, and software receipts require matching records in tasks.json and events.jsonl. Plain files cannot stop a writer running as the same user from forging those records or an owner waiver. The owner pins test and cleanup commands; acceptance compares their recorded policy and command receipts with the pins. Reviewers check that the configured runners verify the change.

For a ranged task, `check tests` climbs after a confirmed test failure. A missing test command, including cmd.exe's command-not-found results on Windows, leaves the rung unchanged. Fix the pinned command and run the gate again.

`check ci` records a completed uncapped failure even when a required check is missing or still pending. Those required checks continue to block acceptance, and the known failure can trigger a rung climb. Missing or pending checks alone do not trigger a climb.

`check sources` scans HTML without using tag replacement expressions. It preserves inline punctuation, skips nested comments and templates plus script/style blocks, and excludes unfinished or ambiguous markup from quote matching. Its pinned DNS lookup supplies all validated public addresses for IPv6/IPv4 fallback within the same page deadline. See [Research sources](state.md#research-sources) for the deliverable and fetch limits.

Ordinary `merge` defaults to `--method squash`, with the task title as the commit subject and its acceptance lines joined by newlines as the body. `--subject` and `--body` override these independently, preserving multiline text and an explicitly empty body. A subject must be non-blank. `--method merge` uses the same commit text options; `--method rebase` omits them and refuses explicit subject or body overrides. Every ordinary merge invocation uses GitHub's full head SHA with `--match-head-commit` after verifying it matches the accepted SHA. Branch deletion is requested unless `merge.keep_branch` is true. Only owner-set `merge.admin: true` adds GitHub's admin option for solely owned repositories. There is no one-off `merge --admin` flag; acceptance, review, CI and head checks still apply. Stacks use the bottom-up pinned asynchronous merges described under Run; that API takes no commit text, so GitHub writes each merge commit message and `--subject` and `--body` apply only to ordinary merges.

Ordinary merges require same-repository PRs whose `baseRefName` matches the task's target base: the recorded dependency branch for a stack, otherwise the project base. Unstacked fallback waits for lower tasks to land, then may retarget only the recorded dependency base to the project base; it re-reads the PR before merging. An unrelated base is refused without editing or merging the PR. Already-merged confirmation also checks the base, and merge summaries name the base reported by GitHub. A different base on confirmation fails and asks for inspection of what landed.

Configure review caps in project.json, for example `"ci": { "capped_review": [{ "app": "revuto-review", "pattern": "reached the \\d+-round review limit" }] }`. `app` is the exact GitHub app slug without surrounding whitespace; `pattern` is a case-insensitive regular expression searched across the check output title and summary. Output text is not searched because review findings can quote a cap message. Only completed runs with conclusion `failure` qualify. A failed suite qualifies only when it is linked to a matched run and its complete set of runs is green or capped. At least one run outside ignored apps and matched caps must exist; a capped review alone does not prove CI ran. Other failures from that app and all unfinished checks still block. Missing configuration grants no exception; malformed rules fail the gate. The independent review gate remains required.

Hosted CI reads `headRefOid,mergeable,mergeStateStatus` with `gh pr view` before fetching checks. A `CONFLICTING` PR or `DIRTY` merge state fails with a conflict diagnostic because GitHub does not run `pull_request` workflows on conflicting PRs. Unknown or missing mergeability fails with an instruction to retry later. A mergeable PR may still have a `BLOCKED` merge state while waiting for checks or reviews; the CI gate checks its runs and suites independently. Without a task PR, the gate checks only the submitted commit. `ci.required` defaults to empty; malformed lists fail closed. Required runs cannot be satisfied by ignored apps or capped failures. These hosted policies do not change local CI.

For non-ignored GitHub Actions suites, hosted CI reads every page of Actions workflow runs at the submitted head and groups them by workflow path (or name when path is absent) and event. Only the latest run by `created_at`, then `id`, supplies the current suite; missing timestamps use `id`. Older runs with distinct suite ids appear under `Superseded workflow runs` in the receipt summary, and their Actions suites and linked check runs are excluded even when their old jobs are no longer listed. A latest failed or pending suite still blocks. Different workflows, events, heads and apps stay separate. Missing identity or event grants no supersession, and the latest run must map to a listed Actions suite; unmapped suites keep the check-run supersession rule. An Actions API failure fails the gate.

Hosted `ci_policy` contains the effective `required`, `ignore_apps` and `capped_review` arrays, defaulting absent or null fields to `[]`. Only the `app` and `pattern` fields of capped rules affect the snapshot. Invalid policy records `null` on the failed check. Audit events must match the evidence policy. Acceptance, merge and task gate reports refuse an unrecorded policy, a malformed current policy or a snapshot that differs from the current project. A stale pass requires a new `check ci`; acceptance does not rerun an already attempted gate automatically. Other `ci` fields do not affect the snapshot. Once an audited merge succeeds at that head and revision, reports keep its recorded CI result.

Local CI needs a Git version that supports `merge-tree --write-tree`. It reads the current local base and `origin/<base>`, choosing the remote ref when it contains the local base or the local base is absent, as dispatch does. `check ci` does not fetch; refresh the base refs before checking when needed. Before merging with a local receipt, `merge` fetches the base from origin into `origin/<base>` with a 60 s timeout, even if origin's fetch configuration excludes it. A failed fetch or a fetched base different from the receipt's `base_sha` refuses the merge. Run `tower-crane check ci ID` again after the base moves. Repositories without origin still validate against their local base. The command runs in a temporary detached worktree under `TOWER_CRANE_TMP`, then `gates.tmp_root`, then `tc/g` under the user's cache directory. The worktree is a clean checkout of `merge_sha`, a commit of the merged tree with the base and the head as parents, so `git status` is clean. The merge reads `.gitattributes` from the head, so its merge drivers apply. Conflicts fail before the command runs. Missing commands, nonzero exits, signals, timeouts, tracked-source changes and a merged tree that moves during execution fail. The process group is stopped on exit or timeout and the worktree is removed on every outcome. A head that edits the checker edits its own gate; reviewers must inspect checker changes.

Only the gate runner produces the local receipt. It records `variant`, `command`, `timeout`, `exit`, `signal`, `head_sha`, `base_sha`, `tree_hash`, `source_digest`, `merge_sha` (the commit of the merged tree the command ran on) and `duration_ms`; see state.md for the digest definition. `variant` is `default`, `kind:KIND` or `task:ID`. Acceptance, merge and task gate reports require the audited receipt to match the submitted head, the current merged tree and the resolved variant, argv and timeout, with exit 0 and a matching command execution. A new head, changed merge result, variant, command or timeout needs a new check. Different variants cannot share receipts even with identical argv and timeout. Earlier receipts without a variant need a new check too. Changes to an unselected kind mapping do not invalidate a task override. Once successful audited merge evidence exists for that head and revision, these reports keep the recorded CI result without recomputing the current merged tree, and a repeated merge skips the base fetch. Untracked build outputs do not change the tracked source identity. Local CI does not query hosted checks or require `project.repo`; absence of `ci.local` keeps hosted behavior.

Each local CI run also records `local_ci` on its evidence and audit event: `log`, the state-relative path of the run's full stdout and stderr, joined by whole lines, and `artifacts`, the files it copied. A failed run adds `output_tail`, the last 200 lines and at most 16384 characters, and its summary names the full log and counts the saved artifacts after the last 20 output lines. Terminal escapes are removed and the text redacted with the tests gate's rules. The newest 5 runs per task are kept. [state.md](state.md#local-ci-output) has the layout and the limits.

Agy spawn selects the generated `gishra-<job>` agent in its private HOME. `--tools` takes native agy tool names such as `search_web`; `--mcp` takes names from the original user’s `~/.gemini/config/mcp_config.json`. Both appear in `spawn --dry-run`. Workspace MCP configurations or a workspace agent overriding the generated role refuse dispatch. See [Agent files and homes](ladder.md#agent-files-and-homes) for permissions and authentication.

### Orchestrator tools

Windows orchestrator commands discover their persistent caller from one CIM process snapshot before taking the state lock. PowerShell returns only the caller's ancestry. A failed or timed-out snapshot refuses the command; retry it rather than changing the identity.

`tower-crane mcp --agent orchestrator` serves the inbox and batch actions as MCP tools over stdio. Pass `--state DIR` outside the project. The plugin registers it for Claude Code, and spawned Claude and Codex orchestrators receive it in their generated homes. The Codex plugin command surface exposes `/tower-crane-inbox`, `/tower-crane-spawn-ready`, `/tower-crane-merge-accepted`, `/tower-crane-rework-from-review ID` and `/tower-crane-release-dead`.

Use `inbox --json` for typed findings with `action.command` and `action.argv`; use the returned command to resolve each item. Messages, stalls, decision answers and owner comments can be acknowledged after handling with `inbox --ack ITEM`. Owner-only decisions require the owner's answer; technical decisions are the orchestrator's to answer unless `decision_delegation.orchestrator_technical` is false. GitHub observation failures remain visible as `github_error` items. Batch merge refusals remain in the inbox while independent mergeable entries continue through the existing current-base and stack checks.

`task update ID --superseded-by TARGET` cancels ID and records its replacement. TARGET must exist, differ from ID and be uncancelled. Task show and board task details show the replacement; worktree retirement follows the same saved-work and failure rules as cancel.

Recovery saves include `commits.bundle` when the task head is not already reachable from the local base. The bundle retains local commits after branch deletion, including when the checkout is missing. Git patches stream directly to files; large patches and ignored-file lists do not hit a child-process output cap.

Worktree recovery retries compare the retained branch head with actual saved bundle heads. New commits get a new recovery directory linked to the earlier save by `previous` in its manifest. Ownership is checked under the lock that reserves removal; a reservation blocks other tasks from assigning or preparing that path or branch. A partial stack merge retires confirmed merged members after the merge attempt finishes and preserves every still-open upper branch and worktree.

Orphan removal with `worktree prune --orphans` checks current task ownership and reserves both the path and branch under the state lock before saving, removing the checkout or deleting its branch. Task assignment and preparation honor that reservation. Adoption before the locked check preserves the live checkout; adoption during removal is refused. Each cleanup releases only its own reservation, including a failed attempt.

## Review churn

`project set --review-policy '{"churn_after":3}'` sets the failed-review threshold; it defaults to 3 and must be a positive safe integer. The orchestrator or owner can change it. `--review-policy null` restores the review defaults.

`inbox` surfaces `review_churn` for active tasks at the threshold with each failed review's one-line findings, explicit acceptance-line and finding-location comparisons, and recorded spend. It asks the orchestrator to bound scope, split the task or change tier, while rework proceeds. Findings without comparable scope references are marked `unknown`. Counts span heads and rework revision bumps, and reset on an acceptance revision change. Later stack refreshes preserve that reset. `status`, the board and both sketches show the count per task. See [Orchestrator inbox](state.md#orchestrator-inbox) for the fields and revision rules.
