# Storage

Tower Crane keeps a project's plan and progress in plain files. People and dashboards read them; the `tower-crane` CLI and serve's owner forms write through the same locked, validated functions. An agent that needs to change state runs a command.

## Where

The state directory is the first of:

1. `--state DIR` on the command line
2. `TOWER_CRANE_STATE` in the environment (`tower-crane spawn` sets it for every agent it starts)
3. `.tower-crane/` at the root of the main checkout, found through `git rev-parse --git-common-dir`, so every worktree of the repo shares one state

`tower-crane init` adds `.tower-crane/` to `.git/info/exclude`. State is not committed unless the project chooses to. In a bare repository, `.tower-crane/` sits inside the common git directory.

Commands that need the repository (`worktree`, `spawn`, the gates) use the one Tower Crane runs in; outside a repository, the one that holds the state directory.

## Files

| File | Holds |

| `project.json` | name, goal, repo, base branch, default harness and model ladder, limits, budgets, standards profile, owner policies |
| `tasks.json` | every task and its status, evidence and spend |
| `decisions.json` | questions for the owner and their answers |
| `briefs/<task>.md` | shared task context and optional worker or reviewer sections, kept current by the orchestrator |
| `reviews/<task>-<sha>.md` | the brief's reviewer sections, diff and software gate results prepared by review dispatch; large packets are read from this file to keep argv within Windows limits |

| `events.cuts.jsonl` | one line per cut lock recovery made to `events.jsonl`: `{ "at", "id", "size", "from", "ends" }`, the last event id of the commit whose append it cut, the length it cut the log back to, the length before and the offsets where the removed lines ended, plus `"late": true` for a cut an older tool made that a later holder recorded; only appended to, so its length counts the cuts and is the generation byte cursors carry ([Durability and write order](#durability-and-write-order)) |
| `progress/<agent>.jsonl` | the agent's tool activity, `hook progress` rows appended without the state lock; the supervisor watches the file for activity, and no state decision reads it |
| `evidence/<task>/<sha256>.json` | one settled evidence field over 1 KiB, as compact JSON named by its SHA-256; never changes once written ([tasks.json](tasks.md#tasksjson)) |
| `sketch.md`, `sketch.html` | rendered views; regenerated by `tower-crane render` and after every write |

| `lock` | the write lock, a directory; never edit |
| `dispatch/lock` | the worker dispatch lock, a directory taken the same way as `lock`, held by a worker `spawn` from its readiness check until its spawn is recorded or refused, while it may run git ([Dispatch lock](#dispatch-lock)); never edit |
| `logs/<task>-<agent>.log` | output of agents started by `tower-crane spawn` |
| `logs/<task>-<agent>-startup-failed-<time>.log` | the output of a supervisor that did not report its start, kept when it wrote any or when the dispatch's startup wait ran out. Its last line is `tower-crane: startup phases in ms: ` and the JSON of the spawn event's `startup_ms`, with the phases that finished; the refusal prints its path and last lines. The newest 5 per task, by modification time, are kept; each new or moved-aside one counts as the newest and removes the older ones |
| `logs/ci-<task>-<sha>-<unique>/output.log` | one local CI run's stdout and stderr joined by whole lines, escapes removed and redacted; the newest 5 runs per task are kept ([Local CI output](ci.md#local-ci-output)) |
| `ci-artifacts/<run>/` | the files a failed local CI run named, copied out of the gate worktree before removal, text redacted; hidden from every agent sandbox; `ci-artifacts/.gitignore` ignores everything ([Local CI output](ci.md#local-ci-output)) |
| `homes/<agent>/` | the home `tower-crane spawn` builds fresh for each claude, codex and agy agent: its harness config directory with generated settings, instructions and permission profile, `git` and `gh` shims, links to the user's credentials, for a sandboxed claude agent `tmp`, its `CLAUDE_CODE_TMPDIR` ([agent files and homes](../ladder.md#agent-files-and-homes)), and `home/`, the agent's `HOME`, which for a sandboxed codex agent also holds the shims it runs, `home/.tower-crane-shims/` (`bin/`, `policy.json` and `tool/`, a copy of the snapshot), since its sandbox hides the rest of `homes/<agent>/`; plus what the harness writes there (transcripts). Private to the user; `homes/.gitignore` ignores everything. A spawn removes a home only after the agent and every live controller using its tool snapshot have exited. `homes/.codex/<agent>/sessions/` keeps that agent's codex sessions for usage after its home is gone ([Agent files and homes](../ladder.md#agent-files-and-homes)) |
| `brokers/<agent>/` | `broker.json`, the [state broker](../ladder.md#state-broker)'s address and token for a sandboxed agent (and its `broker.sock` for claude), while the agent runs; only that agent's sandbox can read it. The broker writes `brokers/<agent>/.gitignore` when it creates that directory, never in an existing directory or its parent. Closing removes a directory it created; an existing directory keeps its other files |
| `push/` | the [state broker](../ladder.md#state-broker)'s repository for the pushes sandboxed agents ask for: `cache.git`, which holds only objects git hashed on arrival and stays between pushes, and the `cache.lock` directory while a push uses it; no sandbox can write here. `push/.gitignore` ignores everything |
| `skills/<key>/` | the role skills every spawned agent is told to read: a copy of `skills/` from `TOWER_CRANE_PLUGIN_ROOT` or the dispatching package, named by the first 16 hex digits of the SHA-256 of its file names and contents. Spawn copies the skills to a temporary directory beside it and renames that to the key, retrying a rename the system refuses for a moment (EPERM, EACCES or EBUSY, as Windows does while a scanner holds new files) for up to 2 s; a key another dispatch wrote first is kept, and the retry stops once it is there. Spawn writes a key once and never removes it, so a path an agent was given stays valid after any agent exits. Prompts, home instructions, the codex, opencode and agy skill links, pi's `--skill` and `reviews/<task>-<sha>.md` name it. It is outside `homes/`, so the claude and codex sandboxes, which open the state directory read-only, can read it |
| `gitconfig/<agent>` | the global git config of a sandboxed claude or codex agent and its harness (`GIT_CONFIG_GLOBAL`), rendered from the user's global git config ([Shared git directory](../ladder.md#shared-git-directory)); their sandboxes read it and never write it. A spawn removes it with the agent's home. `gitconfig/.gitignore` ignores everything |

Each spawn pins its tool runtime in `homes/<agent>/tool/`. `homes/<agent>/tool.json` and the `spawn` event's `detail.tool` record `{sha, version, path}`. `sha` is the tool checkout's HEAD, or null for an installed package without Git metadata; `version` is the package version. The snapshot copies `bin/`, `lib/`, `agents/`, `skills/`, `standards/` and `package.json`, without links back to the checkout. Skill paths the agent is given name the skill store (`skills/<key>/`), not this snapshot, which claude's Read tool and codex's sandbox cannot read. The generated Git and gh shims, a sandboxed agent's `tower-crane`, harness hooks, notify command, claude's credential helper and supervisor resolve this snapshot. A sandboxed agent's sandbox reads it (codex a copy in `home/.tower-crane-shims/tool/`) and no Tower Crane checkout, so retiring the checkout a dispatch ran from leaves live agents working. Its policy is generated by the same tool version. Supervisors, containment keepers and host CLI controllers hold the snapshot they execute, even when it belongs to another agent. The engine writes PID identity holds under `tool/.users/`; launchers register child holds before releasing their own, and pruning removes dead holds only after verifying exit. An unobservable user keeps its hold. A home rebuild preserves a held `tool/` and its holds. After all users exit, a later spawn prunes it with the home, and a new dispatch gets the tool version then installed.

Pinning keeps upgrades independent of live dispatches. On 2026-10-08, moving the orchestrator checkout to T112 (`33d7eb5`) made existing shims read new requirements against policies without `branch` or `repo`. Pushes from T30 and T79 had to be completed by hand. Copying the runtime at dispatch prevents a checkout move from changing a live agent's policy reader or hook protocol. Upgrades take effect on the next dispatch, with no feature flag.

The shim defaults missing `gitPush` to `none`, `gh` to `[]` and `hook` to null. Missing branch and repository default to null and deny remote pushes. Before checking permissions, a pre-T112 branch policy with absent `branch` or `repo` migrates those fields in memory from its recorded task and project; a field state does not record migrates to null, which refuses remote pushes (no branch or no repository to bind them to) and leaves every other command allowed. Migration requires its protected `hook.json` in the same home and matching dispatch agent, task and state environment; it never infers authority from the current Git branch or remote. Missing recorded values or a mismatched binding refuse the call. The policy file stays read-only, and all calls use the same migrated shape and push checks. The historical policy fixture is generated from `lib/agents.js` and the worker frontmatter at `e034a4325677ada9d0752a1acee60483acfd8849`, T112's parent.

Codex homes rebuild `config.toml` and every `<profile>.config.toml` with explicit allowlists for provider, MCP server and per-tool fields. Provider sub-tables keep only named fields: `aws.region` and `aws.profile`, and `query_params.api-version`; a credential-shaped name (containing key, bearer, token, secret or password) never crosses from a sub-table, and `aws.credential_export` and `aws.auth_refresh` stay outside. Unknown fields, credential fields, literal env and headers, and fields with unexpected types are omitted. Named environment-variable references remain for explicit MCP opt-ins; the browser kit also removes `env_vars` and `env_http_headers`. Auth files remain linked to the user's originals.

Codex model and auth-store fields also require their expected scalar types in base configs, profile files and legacy `[profiles.NAME]` tables; arrays and tables are omitted. Claude's `mcp.json` keeps only string `type`, `command` and `url` fields and `args` arrays containing only strings. A nested credential table cannot cross through these settings.

A brief without role headings is shared by worker dispatch and role-filtered brief readers. A brief can add level-two headings `## Shared`, `## Worker` and `## Reviewer`; matching is case-insensitive and headings inside fenced code blocks are ignored. Text before the first role heading is shared; each section ends at the next role heading. The `## Rework notes` heading is also a shared section boundary, so corrections appended by `rework` stay visible to each role. Worker dispatch and `brief get` send shared text followed by the matching role section, and omit the other role's section. Review dispatch sends only reviewer sections alongside the diff, acceptance and gate results. `brief get` infers the role from a `worker-` or `reviewer-` agent name, or accepts an explicit `--role`; owner and orchestrator identities see the full brief by default. `brief set` warns on stderr when it finds a reviewer section without a worker section.

All JSON files carry `"version": 1`. Writes go to a temp file in the same directory, synced, and are renamed into place; the directory is then synced so the rename survives a power loss. Windows cannot open a directory to sync it, so there the rename is as durable as the file system makes it; file systems that refuse a directory sync are treated the same way. Windows refuses to open or stat a state file while another process renames a new copy over it, or while a scanner or the indexer holds it, with EPERM, EACCES or EBUSY, until that process closes it. A writer retries such a refused rename, and a reader retries such a refused stat, open or read of `project.json`, `tasks.json`, `decisions.json`, `events.jsonl`, `events.cuts.jsonl`, a commit's staged files, an agent's progress file or its harness log, with backoff from 5 ms to 100 ms between attempts, for up to 2 s. A refusal that lasts longer fails the command with its code and path and `(still refused after 2000 ms; another process holds the file)`; it never reads as a missing file or an empty event log. A lock-free read can therefore wait up to 2 s per file on Windows; the supervisor's periodic read, `wait` and the gates' state reads are such reads, so a concurrent commit or a scan does not stop a worker. On other platforms these codes are a permission failure, and a read fails on the first one. A refused state mutation writes nothing. `accept` can record software gate results before refusing acceptance.

### Durability and write order

A command returns only after its writes are on disk. The event append to `events.jsonl` is synced before the command reports success, so an acknowledged `msg`, hook delivery or mutation survives a power loss.

A commit that changes `project.json`, `tasks.json` or `decisions.json` and logs events writes in this order:

1. `commit.<id>.json` is written in the state directory, where `<id>` is the id of the commit's last event. It records the device, inode and byte length of `events.jsonl` before the append and the ids of all the commit's events. The inode is in `ino` as a JSON number, as released tools write and read it, and in `ino_exact` as a decimal string. A number rounds Windows file ids past 2^53, so recovery compares `ino_exact` when the manifest has it and `ino` otherwise. Each changed file is written in full and synced as `<name>.json.<id>.commit`. The directory is synced.
2. The events are appended to `events.jsonl` and the log is synced. This is the commit point.
3. Each staged file is renamed over its target, the directory is synced and `commit.<id>.json` is removed.

A commit with events and no file change does step 2 only. A commit that changes files and logs no event writes each file with a synced temp file and a rename, then syncs the directory.

The next process to take the state lock, before it reads anything, finishes a commit whose holder died. A staged file whose `<id>` is the id on the last complete line of `events.jsonl` reached its commit point: the log is synced, then the file is renamed into place. Any other staged file is deleted; its last event was never logged and the command never returned. A power loss can tear the append and keep the commit's first lines, or a last line missing only its newline, which the next append would complete. Recovery cuts those bytes off, truncating the log back to the recorded length, only when `events.jsonl` is still the same file (device and inode) and every line after that length, complete or torn, is one of the commit's own events. Before the cut it writes the cut to `cut.<id>.json`; after the cut is synced, and before the holder appends anything, it appends `{ "at", "id", "size", "from", "ends" }` to `events.cuts.jsonl`, starting with a newline when a torn record ends the file, and syncs it. It removes `cut.<id>.json` after the staged files and the manifest. A holder that dies between the cut and the record leaves `cut.<id>.json` beside the manifest, and the next holder, finding the log at the cut's length, appends the record unless one with the same `id` is already there, so two cuts at the same place and of the same length are both recorded. Tools through 0.1.2 finish such a recovery without recording the cut: they remove the staged files and the manifest and leave `cut.<id>.json`. The next holder that finds `cut.<id>.json` alone appends the record with `"late": true`, since the older tool may have appended past the cut meanwhile. Anything else after it, such as an event an older tool appended or a log restored from a copy, stays, and the staged files are only deleted. A command whose append fails keeps its staged files when its last event reached the log anyway (a failed sync after the write), so the next holder renames them into place; otherwise it applies the same rule. A staged file that cannot be removed (Windows keeps a file another process holds open) stops the holder with an error before it appends anything, so no later write is judged against an old commit. Only a dead or failed holder leaves staged files, and nothing is appended to the log until the next holder has recovered, so a crash never leaves a state change without its events. Between steps 2 and 3, and after a crash until the next lock holder, the log holds events the files do not show yet. A reader without the lock reads the log, then the files, and keeps the result only if the log did not change meanwhile: same size, device and inode, and the bytes before that size still end with the last line it read. The inode is compared exactly: Windows file ids run past 2^53, where a Number would round neighbouring files to one id. The last line catches recovery cutting a torn tail off the same file and the next commit appending as many bytes, which keeps the size and the inode. The reader skips reading that line when the log's modification and change times are the ones it read and its last change was at least one timestamp step (20 ms, or 2 s for a time in whole seconds) before the read began, since any later change gets a later time; an idle log then costs no read. That needs file times from this machine's clock that move on every write, so it holds only on local disks. On Linux those are the local filesystem types (ext2/3/4, xfs, btrfs, tmpfs, ramfs, f2fs, zfs, bcachefs, overlayfs); on NFS, SMB, 9p, virtiofs or FUSE the reader always compares the line. macOS numbers filesystem types as it registers them (statfs `f_type`; Node does not report the name, `f_fstypename`), so there it holds when the state directory's filesystem has the same type as the root, which is APFS on every macOS Node runs on; SMB, NFS, AFP, WebDAV, FUSE and HFS+ mounts compare. On Windows a state directory whose real path is a UNC share (`\\server\share`, which a mapped network drive also resolves to) compares, and one on a drive letter does not. Other platforms, and a directory whose type cannot be read, always compare. A process that keeps one event reader compares on every read of it, so no read vouches for bytes it did not check. A commit appends before it renames, so then no rename landed during the read but those of the commit the log ends with. When the last event it read is the last complete line of the log and staged files carry that id, the commit reached its commit point, and the reader reads those staged files in place of the files they replace; a staged file renamed meanwhile is read from its target, which holds the same text. Staged files of any other id are never used: their commit point was not reached, or other lines follow it in the log, and recovery deletes them. A reader can open and drop the staged files of a torn last line it parsed. A reader whose log changed reads again. One that loses five times in a row waits up to 500 ms for the lock and reads once under it, so a lock-free reader can briefly wait. If it cannot take the lock in that time, or cannot write the state directory, it returns files with events read after them, which are never older than the files, as every read was before. So a reader that has an event also sees the change it records: `wait`, and a command run after `wait` returns, read the state the woken event's commit left. `validate` still takes the lock, to recover an interrupted commit before it reports. Every release from 0.1.0 on stages, logs and recovers commits this way, so released versions can share a state directory: whichever takes the lock after a crash finishes or discards the commit by the same rules, and `validate` recovers under the lock before it reports, so it reports no drift for a commit another version left half done. Development builds from before staged commits do not recover them; a commit they make after a crash leaves the staged files unmatched, and the next recovering holder deletes them and leaves the log alone. Recovery checks `project.json.schema_version` before it touches staged files: under a newer schema it refuses, as a read does, and leaves them for the newer tool ([Schema compatibility](#schema-compatibility)). A change to how commits are staged or recovered raises the schema and gives the staged files new names, so released tools that do not check the schema first never match them. `cut.<id>.json` is the exception: it adds a file beside the staged ones and changes neither their names nor what an older tool does with them. A tool through 0.1.2 that finishes such a recovery cuts the same bytes the newer one would, by the same rule, or finds them already cut; it only leaves the cut unrecorded and the file in place. The next newer holder records it as `late` from that file, and readers treat a late record by what they read, so the older tool's events appended after the cut are neither skipped nor read twice.

Windows keeps a file while another process (a scanner, a backup tool) holds it open without delete sharing. When that stops recovery for longer than 2 s, renaming a staged file into place or removing one, the holder releases the lock and the attempt counts as a busy lock: a writer retries until its deadline and then exits 3 with `state is busy: another process holds an interrupted commit's file open`, and a try-lock (the orchestrator lease renewal of a read command) reports exit 3 at once and leaves the renewal to a later command.

A writer killed between writing a temp file (`<name>.<pid>.<random>.tmp`, used for writes that log no event) and renaming it leaves the file behind. Each lock holder deletes such files in the state directory whose pid is not alive and that are older than 60 s; a recent one may belong to a writer in another pid namespace.

On macOS, Node's file sync is `fcntl(F_FULLFSYNC)`, which flushes the drive's write cache; libuv falls back to `F_BARRIERFSYNC` and then plain `fsync` where a filesystem refuses it. Linux `fsync` flushes the cache already. Windows syncs a file with `FlushFileBuffers` and cannot sync a directory, so a rename there is as durable as NTFS makes it.

A reader that tails the log without the lock (`wait`, `serve`, the `wait` host's state history, a gate run it joined) checks the length of `events.cuts.jsonl` on each read that finds the log's times changed. When it grew and a new record's `size` is below where the reader stopped, the reader goes back to that `size` and reads on from there, so it neither resumes in the middle of a line nor skips the events appended after the cut, even when the log has grown past where it stopped. The events it had read past that point were never committed: `wait` has delivered them, `serve` drops them from its message history, and the state history is read again. `wait`, `GET /api/messages`, the `mcp__tower-crane__watch` follower and the orchestrator's Stop hold hand out a byte cursor with the length of `events.cuts.jsonl` its reader had applied (`OFFSET:CUTS` for `wait --after`, `after` and `cuts` for the API). Given back, it is read from the `size` of every cut recorded after that length whose range holds the offset, and from the offset otherwise, so it resolves exactly. A plain byte cursor (`wait --after OFFSET`, `GET /api/messages?after=OFFSET`) does not say when it was taken. It is read from a recorded cut's `size` when it ends one of the lines the cut removed and does not end a line of the log as it is now. Every cursor handed out after a cut ends a line of the log as it is then, so it never moves and a wait re-armed with its own cursor does not see its event again. A plain cursor from before the cut whose offset a new line happens to end at too stays where it is, and its reader misses the events between the cut and that offset. A late record moves any cursor only by that plain rule, and moves a tailing reader back only when the bytes it last read are no longer the log's. `wait` carries the length of `events.cuts.jsonl` from the moment it took its cursor to its reader, so a cut recorded in between also moves it. A reader checks the length again after each read of the log. A cut recorded during the read joins the cursor it hands out when its `size` is at or past the offset the read reached, or when the read started at or before its `size` and the last line and fragment the read took are still the log's. Otherwise the cursor keeps the earlier length, so the cut still moves it: a read that started past a cut's `size` may follow bytes an earlier read took before the cut. A cut no record explains (a tool from before this record, or a log replaced in place) still makes a tailing reader start over when the log is shorter than where it stopped, and the state history also compares its last whole line and fragment.

### Schema compatibility

`project.json.schema_version` is the project-wide compatibility version, currently `1`. `init` records it; an absent field in an older project means `1`. File `version` fields describe the individual envelopes. A malformed known field still fails validation.

Additive fields, decision and task enum members, evidence types, and event commands do not require a schema bump. Readers retain unknown fields and non-empty enum strings when writing unrelated records. Unknown evidence types remain opaque and cannot satisfy known gates. Readiness, dispatch and gate acceptance refuse task values that this tool cannot interpret, including unknown kinds, tiers, sizes, statuses and capabilities. They also refuse an unknown decision status when that decision lists the task in `blocks`; unrelated tasks remain usable. Command arguments still accept only supported values. A new status whose semantics cannot be handled by these rules needs a breaking bump.

Live-spend readers also retain future non-empty state and error-class strings. They still require a positive integer sampling interval. An incompatible supervisor skips its final live sample after worker closure, leaving reconciliation to a compatible collector.

An unfamiliar task status retains its unexpired claim in both resource-lock and worker-capacity accounting. The recorded lease deadline still applies; a status change alone never frees a live lease. Automatic recovery keeps failed review evidence but reports `waiting` for an upgrade when task routing values are unsupported. It leaves the tier, range, status, claim and escalation history unchanged. Manual rework refuses before changing state or the brief.

A breaking change raises `schema_version` before publishing incompatible payloads. The migration writer must hold the state lock and atomically publish the project marker before changing other files; readers check it before validation and again before returning a snapshot or reporting a payload error. A tool refuses reads, mutations and new spawns when the version exceeds its supported schema, with an upgrade message. There is no automatic downgrade or generic migration command.

A running supervisor that encounters the marker, or an unsupported value affecting its own task, stops lease renewal, state writes, retries and automation. This includes an unfamiliar decision status that lists the task in `blocks`. It reports the incompatibility and keeps output capture and the broker alive until the current worker exits, without signaling that worker. The broker refuses incompatible state commands. The supervisor then exits `1`; an upgraded tool must recover the lease and collect usage. Supervision stays stopped even if the marker is subsequently reverted. Tools pinned before this compatibility contract cannot gain it at runtime; drain those supervisors before the first breaking migration.

### Lock

Every command that writes in the state directory holds the lock while it reads and writes. Reads take no lock, except `validate`, which holds it only to catch up with the log and recover an interrupted commit, and a read that lost five races in a row to commits, which waits for it at most 500 ms ([Durability and write order](#durability-and-write-order)).

A write parses the event log and the three snapshot files before it waits for the lock, and keys the parse by each file's device, inode, size and times, and by the log it read them with: its file and size, its event count and its last event's id. A new file can reuse a replaced one's inode, and on a coarse clock its size and times too, but a commit that replaced one logged its events first. Under the lock it reads only the events appended since its own read and keeps its parsed files when none was replaced in between and nothing was appended to the log; otherwise it reads them again. It then validates, commits its files and events in the order [Durability and write order](#durability-and-write-order) gives, and releases. A CLI command keeps one event reader for its whole run, so its later reads parse only what was appended. Rendering runs after the lock is released: the write draws the sketch from the state it committed, stamped while it held the lock, and takes the lock again only to publish the files. `render` stamps before it reads. A stamp is the length of `events.cuts.jsonl`, which grows with each cut lock recovery makes to the event log, then the event log size, which grows between cuts, then the time for writes that append no event. Publishing keeps a sketch with more cuts, or as many cuts and a longer log, or the same and a later time; a time later than the clock means the clock went back and is replaced. A render that stamped torn bytes a later recovery cut off is older than every write after the cut.

`TOWER_CRANE_LOCK_TRACE=FILE` appends one JSON line per lock holding to FILE: `pid`, the first command words in `argv`, `label` (the mutation's command, `orchestrator lease`, `render`, `validate`, `state read` or `dispatch`, the [dispatch lock](#dispatch-lock)), `wait_ms`, `hold_ms` and `event_bytes`, the event log bytes read while holding. It is off by default and never fails the write it measures.

`TOWER_CRANE_INTERVALS` is a JSON object of interval name to positive milliseconds that replaces production waits, so tests drive a timeout path in short real time: `lock_wait` (60000, a write's wait for this lock), `lock_refresh` (10000, how often a marked lock kept fresh while held, the [dispatch lock](#dispatch-lock) and a base rerun's result lock, touches its marker), `startup` (10000, the window a dispatch gives its supervisor to report ready and a supervisor gives its spawn and, without the lease gate, its lease to be recorded) and `governor_lock_wait` and `governor_bind_wait` (5000 and 10000, the [host governor](containment.md#host-resource-governor)'s registry lock wait and a bind's further retries) and `test_grant` (3000, how often a test run rechecks its [test-thread grant](containment.md#test-threads)). It is read on every wait, so it applies to the process that sets it and to every CLI, supervisor and hook that inherits it. An unknown name or a value that is not a positive number fails the command. Production leaves it unset.

A writer prepares a private `lock.<pid>.<random nonce>.new` directory for each attempt and takes the lock with one atomic rename to `lock`. That directory holds one file named after the writer's random nonce, with its pid, host, pid namespace (`pidns`, the target of `/proc/self/ns/pid`, or null where there is none), process identity and time. Linux markers record `start_ticks` from `/proc/<pid>/stat` and `boot_id` from `/proc/sys/kernel/random/boot_id`; unreadable start ticks are omitted, and an unreadable boot id is null. The rename fails while `lock` holds such a file, so one writer holds it at a time. CLI commands, harness hooks and brokered writes use the same acquisition bound of 60 s, matching the stale-marker window and allowing startup bursts to drain. While a live holder has the lock, a waiter checks every 2 ms whether `lock` is gone and retries at once when it is. The check for a stale holder runs on a backoff that starts at 10-19 ms, doubles to 100-199 ms and includes random jitter; each wait is capped by the remaining time. After a reclaim, an empty lock or a staging cleanup race, the waiter sleeps the whole backoff. The deadline uses a monotonic clock, so wall-clock changes do not shorten or extend it. A holder still alive at the deadline causes exit 3. An `ENOENT` or `EEXIST` from concurrent cleanup retries within the same deadline with a fresh private directory. A missing state directory is still refused with the initialization instructions.

After acquisition, a writer sweeps abandoned staging directories older than 60 s. A staging name whose pid is visible and alive is left alone, even if its marker is not written yet or its timestamps look old. Cleanup only unlinks that directory's marker and removes the directory if empty. A writer whose staging is removed by a sweeper in another pid namespace retries; a rename that arrives without its marker does not grant the lock.

A marker's holder and modification time are read through one opened file descriptor, so they refer to the same file even if its path is replaced. The holder is checked by pid and start ticks only when it ran on the same host in the same pid namespace: a command sandbox gives each command a namespace of its own, where a live holder in another one looks gone, and breaking its lock would let two writers save over each other. Matching start ticks identify a live holder, which keeps its lock regardless of marker age. A missing process, a zombie or mismatched start ticks identifies a dead holder and permits immediate reclaim. A mismatched readable boot id on the same host also permits immediate reclaim, even if the pid namespace changed after reboot. An unverifiable holder becomes stale after 60 s: this includes older markers without start ticks and platforms without a readable process identity. A marker without `pidns`, from an older writer, counts only by age on hosts that have pid namespaces. The next writer breaks it by deleting that file by its name, then the directory if it is empty. A name is never reused, so breaking a stale lock cannot remove a newer holder's, however the writers interleave. Successful cleanup retries consume the same deadline and jittered backoff as contention retries. Reclaiming a dead holder or removing an empty lock at the deadline permits at most one final acquisition attempt; another failed attempt exits 3. If a stale lock cannot be removed, or staging cleanup prevents acquisition throughout the bound, writers exit 3 after 60 s and say so. A process that released a lock but could not delete its own marker within 2 s (Windows, while a scanner holds it open) treats that marker as gone at its next look, whatever its age, and retries the deletion each time; until it succeeds the marker counts as one that cannot be removed.

### Dispatch lock

`dispatch/lock` takes the same marker and rename as `lock`, with one difference in who counts as stale. A holder on this host in this pid namespace whose pid is alive keeps it whatever its marker's age, also without start ticks (macOS, Windows), since one dispatch can wait out the worktree lock, the state lock and two supervisor startup windows. Mismatched start ticks, a missing process or another boot still free it at once. Windows gives a freed pid to a new process within seconds, so there the marker also records `created`, when Windows created the holder, in UTC epoch milliseconds (its `StartTime` read as a FILETIME through one PowerShell call of at most 5 s, once per process). A live pid whose creation time, read at that check, differs from `created` belongs to another process, and the next contended check after the reuse frees the lock. A waiter reads a holder's time once and keeps the holder without reading again for 60 s while that time equals `created`, so a waiter that read the holder before it died keeps its lock up to 60 s longer. A cached time never frees a lock: a holder counts as gone only by a read made at that check, so a process that took a dead holder's pid and then its lock is not mistaken for it. A marker without `created`, or a time that cannot be read, keeps the holder as before. The worktree lock judges its holders the same way. A holder on another host or in another pid namespace counts as gone 60 s after its marker last changed. A holder touches its marker every 10 s, from a timer while its event loop runs and from inside its synchronous waits for other locks; one synchronous command, such as a long git checkout, delays the touch. It is not a state lock: a reader inside it still reads as one outside any lock does. `TOWER_CRANE_LOCK_TRACE` records each holding with the label `dispatch`.

A CLI `spawn`, and a spawn supervisor's own reactions, wait for it up to 140 s without blocking the event loop, then exit 3 with `worker dispatch is locked by ...`. Inside the trusted `wait` host, every worker dispatch tries it once: its refill and the climbs its recovery dispatches. A pass that finds a live holder skips the dispatch before any stack read or fetch; a refill tries again on the next pass (a fallback tick, at most 1 s later, or an event), and a climb stays `escalation_pending` until the next pass's recovery, or `recover ID`, dispatches it. Events and signals reach the host meanwhile, so a `SIGINT` or `SIGTERM` drains at once. A gone holder's marker that cannot be removed holds the lock until a person removes the directory; the host reports it on stderr once per wait.

`tower-crane init` writes the default harness and ladder (see below), `limits` as shown, empty `resources` unless explicit caps are given, and `budget` values of `null` (no budget) until `tower-crane project set` gives them. `limits.workers` caps worker slots held by live leases, unclaimed worker spawns and interrupted supervisors still stopping; `lease_minutes` is the default lease. Optional `limits.paused` is a non-blank reason blocking new claims and dispatches; clearing it resumes the project. Optional `limits.owners` (a whole number, default twice `limits.workers`) caps the spawned workers that wait on their own submitted task as its PR owner, and `limits.owner_idle_minutes` (a positive number, default 180) is how long such an owner waits with no event for its task before it exits ([PR owners](tasks.md#pr-owners)). Waiting owners hold no worker slot. Running processes continue until interrupted. `repo` defaults to the GitHub slug of the `origin` remote, `base` to the branch checked out in the main checkout.

`owner_config_dir` implements the credential trust rule for T101 F3 ([review #92](https://github.com/agent-sh/tower-crane/pull/92)). Only an explicit owner at a terminal chooses the directory: that first `init` pins the folder of the user file (`TOWER_CRANE_CONFIG`, else `~/.config/tower-crane/config.json`) as an absolute, canonical path into `project.json`. Every other `init` records the default `~/.config/tower-crane` under the account's home directory, read from the account rather than from `HOME`, `USERPROFILE` or `TOWER_CRANE_CONFIG`. A headless owner `init` checks `TOWER_CRANE_OWNER_KEY` against `owner/key` in that default directory, never against a key beside a file `TOWER_CRANE_CONFIG` names, which any process could have made. Each prints a `notice:` line when the user file is elsewhere. An account whose home is missing or the filesystem root (such as `/nonexistent` or `/`) has no default: such an `init` is refused, and the owner inits at a terminal. So a process that is not the owner cannot choose where the owner key and the owner's records live. Once bound, owner authentication and sandbox denials use only this recorded directory; the caller's environment is never consulted for the credential location. No `project set` flag changes the binding. When `project.json` already exists, even `init` authenticates against its recorded directory and refuses to replace the project. A project without a binding requires an owner-authorized repair: an explicit terminal owner runs `owner-key`, which records the directory under the state lock and logs an `owner-key` event. Owner authentication has no automatic fallback to the environment. Unbound projects can spawn sandboxed agents: their denial hides the owner directory under the spawning environment's resolved config directory without recording a binding. Invalid bindings still refuse validation and sandboxed spawning.

Worker dispatch, claim and expired-lease renewal use the same slot count under the state lock. A successful worker `spawn` event without a claim of its own records `reserved: true` and reserves one slot until the supervisor takes the generated agent's lease, a matching exit receipt is recorded, the monitor records the attempt with `active: false`, or `lease_minutes` pass with no lease taken since the attempt's latest `spawn`, `spawn retry`, `spawn fallback` or `spawn phase` event, counted from the scheduled relaunch when a `retrying` phase records `backoff_ms`. `spawn session` receipts replay an earlier attempt's detail and neither move the reservation's pid nor extend it. A lapsed reservation stays lapsed: later monitor records do not revive it, because another holder may have taken the slot. The supervisor's lease claim consumes the reservation and then holds the slot by lease, without counting twice. Reservations persist through supervised retries, route fallbacks and backoff. Launch failure commits no spawn event and holds no reservation. Worker spawns hold the dispatch lock (`dispatch/lock`) from the readiness check, before the worktree is prepared, until the spawn is recorded or refused, so they take slots one at a time and a batch that waits sees the slot the other took instead of skipping the task the other was preparing. Stack refreshes run before the lock. So do the fetches a new worktree needs (its own head on origin, the base), once the readiness check passes and only for a task without dependencies; a dependency can merge while the spawn waits, so a dependent task reads its stack and fetches its base under the lock. A spawn waits for the lock as long as a holder can wait inside it: the worktree lock, the state lock and two supervisor startup windows, 140 s. A dependent task's dispatch adds its GitHub reads and fetch to that and can exceed it on a slow GitHub or origin. A spawn still waiting then fails with exit 3, "worker dispatch is locked by ..."; `spawn --ready` stops its batch there, and the wait host's refill does not cache that failure and retries on its next pass. A task worktree prepared outside a dispatch (`tower-crane worktree`, stack linking) can still be found initializing and skipped. A full limit refuses dispatch before launching a process, writing a home or recording spend, and names the task and agent holding each slot. A worker spawn for a task that a live reservation holds is refused the same way, naming that reservation. Reviewer and other non-worker jobs do not reserve worker slots.

The holders are a function of the event log, the task leases and the clock, identical for every observer. Claim and expired-lease renewal count them without probing: a sandboxed worker cannot see peer pids, and a probe that freed slots only for the orchestrator would let dispatch pass and the claim fail. Worker spawn, batch `spawn --ready` and the trusted wait capacity check probe under the state lock, only to clear dead reservations before counting free slots. For each reservation whose monitor and harness process group have both exited, it records a `reservation clear` event with the agent, attempt and reason `process gone`, and the reservation holds no slot from then on. Until this cleanup records that, claim still counts such a reservation until its horizon. Hidden, unknown or other-host pids never clear one. Without `/proc`, a process counts as gone only when the signal probe reports no such process, so a zombie, which still answers that probe, holds its slot until it is reaped. Spawns without the `reserved` marker, recorded before reservations existed, hold none.

A supervised worker's first harness does not start until the generated agent's lease is taken, so no worktree write can precede it. On POSIX the monitor claims for the agent after the spawn event commits and holds the harness behind a gate that starts it only once that claim lands. The gate is a `/bin/sh` script. Windows has no such gate, nor does a host without `/bin/sh`, so the spawn handshakes with its monitor under the dispatch lock instead: the monitor starts and reports ready without launching anything, the dispatch takes the lease (the same `claim` event, in the agent's name, that the agent's own claim would record) and commits it alone (the branch, stack and collected usage it also records wait for the spawn event), then the monitor launches the harness and reports the harness's own pid, which the spawn event records. A worker spawn on Windows or a host without `/bin/sh` therefore holds a lease, never a reservation. If the monitor gets no go within 10 seconds of reporting ready, it exits without launching and the spawn exits non-zero with `no lease:`; a launch that fails after the lease was committed restores the prior claim, recording a `claim` event with `rollback: true`, or a `release` event with `rollback: true` when there was none. The agent's own `claim` renews the lease it holds. On the handshake path a lease that is refused refuses the spawn itself, with claim's reason. A POSIX monitor's claim that is refused or cannot be written, including a state lock still busy after the lock wait, stops the worker before it runs: the attempt's blocked phase names the reason, beginning `no lease:`, the same reason goes to the dispatch's stderr, the spawn exits non-zero, and nothing is rerun. A spawn whose task another agent's live lease holds before the gate opens stops the same way, and its reason goes to the dispatch's stderr, since it records no phase. A supervisor whose spawn is not recorded within 10 seconds stops the same way, with the same stderr reason. So does a supervisor whose state turns incompatible before its first lease: the gate is stopped rather than left waiting for a lease no one will take. Its exit releases its reservation. Retries and route fallbacks keep the lease they hold and take none of their own.

If an expired pre-claim already belongs to the generated worker, dispatch renews it under the spawn lock to the default lease duration, preserving its agent, `since` and `from`. The live lease holds the slot before supervision begins. Launch failure commits neither the lease renewal nor its receipt, except on Windows or a host without `/bin/sh` once the handshake has committed the lease, where the rollback above restores it.

`base` names the branch used to create new task branches. `worktree` and `spawn` fetch it from origin into `origin/<base>` before creating a branch, then use the fetched commit if the local base is missing or is its ancestor. A local base that is ahead or has diverged is kept, with both commit SHAs reported on stderr, and the local branch is never moved. Task branches start from the selected commit SHA. When origin exists, the branch tracks `origin/<branch>` (`branch.<branch>.remote` and `.merge`, set on the host) unless an upstream is already set, so a sandboxed worker publishes it with a plain `git push`. When origin has no such branch, the local base is used with a stderr note; if neither has it, the command refuses. Repositories without origin use the available local base or `origin/<base>`. For a dispatch, the caller runs `worktree ID [ID ...]` once before starting workers. It validates every task id, fetches the base once if any task needs a new branch, and creates all worktrees serially from that SHA. Callers serialize preparation within the repository across worktrees and state directories; parallel workers then reuse the prepared trees without fetching. A later dispatch fetches again even if the tracking ref did not move. A `cannot lock ref` or `incorrect old value` failure retries once after 100 ms before reading the tracking ref. Each fetch and missing-branch verification has a 60 s timeout. An unpack failure is usable only if a fresh origin read proves another caller already imported that exact tip. Other fetch failures, including a second ref-race failure, create no task branch and record no branch or event in state.

`ci.local`, when present, selects local CI instead of hosted checks: `{ "command": ["python3", "tools/check.py"], "timeout": 120 }`. The CLI writes it through `project set --ci-local JSON` or `init --ci-local JSON`; `null` clears it. The command is a nonempty string argv with a nonblank executable and no NUL bytes. Arguments are preserved, including empty strings. The timeout is required in positive seconds and must fit Node's 2147483647-millisecond timer range. No timeout is chosen implicitly. Other fields under `ci` are preserved.

`gates` is an optional object with `tests_cmd` (the full test shell command), `clean_cmd` (the cleanup shell command prefix) and `tests_proof_cmd` (the expensive-mode scoped shell template with `{tests}`). Commands must be non-blank strings without NUL bytes; absent or null means unpinned. They are operational ([Authority](decisions.md#authority)): the orchestrator or the owner sets or clears them through `init` or `project set --tests-cmd CMD --clean-cmd CMD --tests-proof-cmd CMD`. Prove and run-only require `tests_cmd`; clean requires `clean_cmd`. An unpinned project does not block: when the orchestrator or the owner runs `check tests`, `check clean` or `accept` and a needed pin is missing, the engine pins the detected command under that identity first. `tests_cmd` becomes `npm test` when the repository's `package.json` has a test script other than npm's placeholder; `clean_cmd` becomes the configured cleanup tool: `TOWER_CRANE_CLEAN_CMD`, else `deslop` on PATH, else the deslop plugin's `~/.agentsys/plugins/deslop/scripts/detect.js`. Each pin logs a `gates pin` event with `key`, `value`, `from` and `authority`, and `status` lists pins that still stand. Workers and reviewers pin nothing, and a gate with nothing detected refuses as before. Tests mode none needs no command. Gate flags `--cmd`, `--proof-cmd` and a non-blank `TOWER_CRANE_CLEAN_CMD` can only repeat the corresponding pinned value after whitespace trimming. They refuse a different value before any process runs. Clean appends the checkout directory, `--base=SHA` and `--json` to its prefix. A report with `"scope": "diff"` is judged whole, since the tool tied each finding to the change. Any other report is cut to the change: a finding counts only when its file is one merge base..head changes and its line, when it names one, is a line the change adds or rewrites. The rest are listed as out of scope and fail nothing, with a note to install the diff-scoped deslop rewrite (agent-sh/deslop `main` from commit e669dbc). Such a report capped below its `total` fails as an incomplete scan, since the cap may hide a finding in the change. Output in the old deslop plugin's shape (`findings`, no `items`) fails with that note and a `clean_cmd` config failure.

`gates.clean_paths` is an optional JSON array of absolute or `~/` paths, set by the orchestrator or owner with `init --clean-paths JSON` or `project set --clean-paths JSON`; `[]` removes the extra paths and `null` clears the setting. At dispatch, sandboxed Claude and Codex agents can read existing absolute executable paths and direct script arguments to Node, Python, shell, Ruby or Perl in `gates.clean_cmd` and `gates.tests_proof_cmd` commands, their containing directories, and declared dependency files or directories outside the task worktree. Paths resolve on the host, and `~/` declarations use the spawning user's home. These tool paths are read-only so workers cannot change the cleanup or proof implementation. Automatic detection covers executable files and the first argument of a recognized interpreter before any shell expansion when the script has its language suffix or a shebang. Non-executable command prefixes and unrecognized data arguments are excluded. Script paths after interpreter options, expanded paths and wrapper dependencies require declarations. Command pins and dependency declarations share operational authority because they select the code gates run on the host; workers and reviewers cannot change them. Wrapper scripts must declare any dependencies outside their own directory; spawn does not execute wrappers to discover dependencies. Missing declared paths, hidden credential stores, directories holding the user's home or worktree, and writable paths inside tool directories refuse dispatch. Use dedicated tool directories and separate writable caches. Worktree tools retain the task's normal permissions.

`gates.executors` is a positive integer, default 2, that caps the CPU work automation runs at once on this host ([events.jsonl](#eventsjsonl)). Only work that runs the project's commands here takes an executor: the tests gate with its host probes, the clean gate, local CI (`ci.local`) and the merge line's head check. Review dispatch, a reaction waiting on a reviewer, hosted CI reads and the ci gate's waits for GitHub take none and never wait for one. A tests gate in mode `none` runs nothing and takes none. The default fits one full suite at tests concurrency 3, about 6 processes, so two keep tests under half the cores of a 24-core box. The orchestrator or the owner raises it with `project set --executors N` on a larger machine.

`gates.tests_timeout_min` and `gates.clean_timeout_min` set positive minutes per test or cleanup shell invocation. Fractions are allowed; the rounded duration must be at least 1 ms and the duration cannot exceed Node's 2147483647 ms timer range. Each defaults to 20 minutes when absent or null, preserving the original gate budget for existing projects. Set a budget that fits the project's measured suite under local load. `init` and `project set` accept `--tests-timeout-min MIN` and `--clean-timeout-min MIN`; `null` clears either setting. Both are operational, and `project show` prints their effective values. Tests uses its budget separately for the full suite, scoped head proof and reverted proof. Automation uses these same settings for gate executors and the merged-head suite. A budget change applies to the next invocation and does not invalidate successful command evidence.

`gates.host_probe_timeout_min` sets positive minutes per declared host probe, default 10 when absent or null. It uses the same fractional-minute and timer-range validation as the test timeout. Set or clear it with `init --host-probe-timeout-min MIN` or `project set --host-probe-timeout-min MIN|null`; it is operational, and `project show` prints its effective value. A changed probe timeout invalidates successful probe evidence. Each declared probe adds its timeout plus a metadata minute to the tests gate lease, including in none mode.

`gates.rework_hold_min` is a non-negative number of minutes, default 5, that automatic refill waits after an automatic gate rework before it dispatches a worker, while `gates retry ID --from-rework` can still undo the rework. The wait host refills worker slots as soon as a task is reworked, so without the hold the paid worker round starts before the orchestrator can restore. Five minutes covers reading the inbox item, fixing a setting such as `gates.tmp_root` and starting the restore, and it is a small delay before a worker round on a real code failure. `spawn --ready` by hand dispatches the task at once. When the task's PR owner waits on it, refill hands the task back to that owner when the hold ends instead ([PR owners](tasks.md#pr-owners)). Zero disables the hold; null restores the default.

`gates.final_review` names an external reviewer that `accept` asks once more about a head its own check skipped, for example `{ "command": ["revuto", "review", "{repo}", "{pr}", "--final"], "when": "capped", "capped_pattern": "reached the \\d+-round review limit", "timeout": 1200, "concerns_exit": 2 }`. `command` is a nonempty argv array; in each argument `{repo}`, `{pr}` and `{sha}` become the project's `repo`, the task's PR number and the full submitted commit. `when` is `capped` (the default: run only when a completed check run at the head has an output title or summary matching `capped_pattern`, a case-insensitive regular expression that `capped` requires) or `always`. `timeout` is in seconds (default 1200, the default budget of the other gate commands), and `concerns_exit` is the exit code that means blocking concerns (default 2, Revuto's). Unknown keys, an empty command and an invalid pattern fail validation. `project set --final-review JSON` sets it and `null` turns it off. See [Final review](gates.md#final-review).

`gates.tmp_root` is an absolute directory where `check tests`, `check ci` (local CI) and `check clean` create their detached worktrees and scratch, and where automation's stack head checks do the same. `TOWER_CRANE_TMP` overrides it for one process (gates a dispatch supervisor runs use the setting when it is set, not the dispatcher's override). When both are unset the root is `tc/g` under the user's cache directory: `XDG_CACHE_HOME`, else `~/.cache`, or `%LOCALAPPDATA%` on Windows, taken from the user's own home when the gate runs inside an agent's home. A gate's scratch directory, its commands' `TMPDIR`, is `<root>/tower-crane-XXXXXX/tmp`, and full Chromium aborts with "Socket path too long" when `TMPDIR` is longer than 62 bytes. When that cache is too deep for the path to fit, the default is `tc/g` under the `.cache` of the home in the password database, and the OS temporary directory when that does not fit either (source `system`). `XDG_RUNTIME_DIR` is never used: it is a small tmpfs. It is not the OS temporary directory: `/tmp` is often a RAM-backed tmpfs where a build tree competes with memory, and some suites refuse to run there. ginza's SSD campaign guard refuses dry media under `/tmp` or on tmpfs, so its local CI failed in a gate worktree under `/tmp` and passed under `~/.cache`. `project set --tmp-root DIR` pins it and `--tmp-root null` clears it; a relative path is refused. Each gate's evidence records the `tmp_root` it used, `project show` prints the setting, and `status` prints the root in use with the source that chose it (`TOWER_CRANE_TMP`, `gates.tmp_root`, `cache` or `system`). The setting does not change evidence matching, so moving the root does not rerun a passing gate.

Each gate directory holds `owner.json`, `{pid, host, started}` of the process that made it. Unlike `/tmp`, the cache is not emptied at boot, so a gate first removes the `tower-crane-*` directories in its root whose owner is on this host, is gone, and started longer ago than the project's longest command budget (the tests, clean and host probe timeouts and the `ci.local` timeouts). A directory without `owner.json` was made by an older Tower Crane that may still be running a gate there, and is left alone. The next `git worktree prune` drops the removed worktree's registration.

`merge` is an optional object with boolean `keep_branch` and `admin` fields, both defaulting to false. `keep_branch: true` omits remote head-branch deletion. Local stale worktrees and their branches still retire. Only owner-set `admin: true` (owner-required) adds `--admin` for repositories solely owned by the project owner, as allowed by SHARED.md. A command argument cannot enable admin merging; `merge --admin` is refused. Neither option skips Tower Crane's acceptance gates or its accepted-head check.

Set these fields through `project set --merge-keep-branch true --merge-admin true`, or the same flags on `init`. They accept JSON true, false or null. Null clears that field, preserving other merge settings and removing an empty merge object. Changes to `merge.admin`, including clearing or setting an unchanged value, are owner-required; `keep_branch` is operational ([Authority](decisions.md#authority)). Refused changes write no settings. `project show` prints both resolved defaults.

`decision_delegation` is an optional owner-required policy. Its `orchestrator_technical` and `orchestrator_escalated_questions` booleans both default to true when the policy or the key is absent. The orchestrator answers technical decisions and escalated questions by default. The owner sets technical delegation to false with `project set --decision-delegation '{"orchestrator_technical":false}'` (or the same flag on `init`) to keep technical decisions with the owner; `null` clears it back to the default. Setting, repeating or clearing it is owner-required and uses the shared approval and audit path. `publish_policy` is the owner's optional standing publish policy, `{ "conditions": [...] }` ([Authority](decisions.md#publish-policy)). While `orchestrator_technical` is not false, the orchestrator may answer a decision that is technical: an `ask` with `--kind technical` starts technical unless it names an owner-required setting or carries `--owner-required`, and the owner marks or unmarks one decision with `decision delegate DID --technical true|false`; `--technical true` also lifts a spend, credential, setting or `--owner-required` reason, without changing an escalation. Escalated questions (`escalation` set and `approval_request` not true) are answerable by the orchestrator when both booleans are not false, only when no independent owner restriction remains. The exception ignores only escalation; `owner_required` and non-technical kinds, including crisis, still keep the question with the owner unless the owner lifts them. `project set --decision-delegation '{"orchestrator_escalated_questions":false}'` restores the old owner-only refusal for them. Their answers apply no settings and grant no authority; the next widening command still opens a separate owner approval request, which applies only after the owner approves and the command is repeated.

For technical delegation, `lib/authority.js` must resolve the explicit caller as the orchestrator. A generated name such as `orchestrator-T1-1` is recognized through its recorded spawn role; an unsandboxed worker cannot claim the literal `orchestrator` identity by passing `--agent orchestrator`. Answers keep the caller's identity in `answered_by` and the event's actor fields.

Every use of `init --ci-local` or `project set --ci-local`, including setting the current value or clearing it with `null`, is operational: the orchestrator or the owner. Refused calls write no settings or events.

`ci.local.artifacts` is an optional array of globs naming files the command writes in the gate worktree, for example `[".local/checks/*.json"]`. Each is a non-blank relative path without a `..` segment. `ci.local.artifact_pattern` is an optional regular expression, for example `"^Local check receipt: (.+)$"`. Each output line is matched against it, and its first capture group, or the whole match without one, names a file; a relative path resolves from the worktree. Both select files to keep for diagnosis only: they are not part of the receipt or the tests gate's `gate_policy.ci_local` snapshot, so changing them reruns nothing.

`ci.local.receipts` is an optional array of globs with the same relative-path validation as `artifacts`. It selects files to keep in the hidden `ci-artifacts/` area on both pass and fail, before removing the gate worktree. The private directory uses the log's run name. Like the artifact settings, it is diagnostic only and excluded from receipt validity and `gate_policy.ci_local`.

`ci.local.by_kind` is an optional object mapping known task kinds (`code`, `docs`, `research`, `design`, `ops`) to overrides, for example `{ "code": { "args": ["--native-extended"] }, "ops": { "args": ["--lab"], "timeout": 300 } }`. An override has exactly one of `command` (a replacement argv with the same validation as the default) or `args` (a string argv appended to the default, allowing an empty array). Optional `timeout` replaces the project timeout and uses the same range. Unknown fields and invalid mappings are refused. Missing kinds inherit the default. A task's `ci_local` override takes precedence and resolves directly against the project default, without combining with its kind mapping. These overrides apply only when `ci.local` is present.

`review`, set through `project set --review-policy JSON` or `init --review-policy JSON` by the orchestrator or the owner, holds optional `small_lines`, `small_files`, `risk_paths`, `min_rung`, `churn_after` and `prices`. `churn_after` is a positive safe integer, defaulting to 3 failed reviews before the inbox surfaces review churn. The line and file limits are non-negative safe integers, defaulting to 100 changed lines and 5 files: a short patch across a handful of files fits a focused review. They raise an easy task to medium when exceeded; they never lower the task's tier. `risk_paths` is an array of repository-path globs with the tests gate's glob syntax, defaulting to empty. A matching old or new path, or a binary diff, raises review to at least hard. `min_rung` is `easy`, `medium`, `hard`, `research` or `review`, defaulting to none. A tier name raises review to at least that tier, so escalation never picks a lower tier. `review` starts the reviewer on the `review` rung itself, skipping the tiers; the rung's own fallbacks handle a weaker model. After a failed review at the current head and revision it stays on the `review` rung until the failure rules below reach hard or research. When the `review` rung cannot run, it takes the first runnable tier at hard or above. It never picks easy or medium. `prices` maps configured model IDs to non-negative dollar rates per million tokens: `{ "input", "cache_write", "cache_read", "output" }`. All four rates are required for each model. IDs compare with whitespace trimmed and case folded; provider prefixes remain distinct. `null` clears the policy and restores diff defaults without cost promotion.

`governor`, set through `project set --governor JSON` or `init --governor JSON` by the orchestrator or the owner, holds the lines this project's admissions use: `defer_at`, `stop_at`, `psi_memory_defer`, `psi_memory_stop`, `psi_cpu_defer`, `load_defer`, `others_window_min`, `growth_window_min`, `growth_samples_min` and `expected_mb`. Unknown keys and out-of-range values are refused; `null` restores the defaults. [Host resource governor](containment.md#host-resource-governor) gives each one's meaning, default and reason.

Review selection starts at the task's tier, raised by the diff, `min_rung` or failed reviews at the current head and revision. A re-review runs at or above the failed review it follows up, at that review's `review_rung` and `review_level`, whether its diff is narrowed or falls back to a full review. One exception is deliberate: with `min_rung: "review"`, a re-review with no failed review at the current head and revision, such as one after rework, starts on the `review` rung even when the floor is hard or above. A light claim check ignores the PR diff's size and risk paths, since it reads only the claims and the changelog correction. Each failed independent review climbs one tier, capped at research. It takes the first runnable tier at that level or above, then promotes to a stronger tier when its measured median review cost is no higher. The `review` rung is the fallback when no tier rung can run. The reviewer may use the builder's model because it receives a clean context. Builder identity comes from the submitter's worker spawn route, not its reported spend; without a recorded route it uses the current task tier. Explicit model names take precedence over profiles; readable Codex profiles resolve to their model. Profiles resolve from the user's origin configuration, matching dispatch even when the caller's home is isolated: `<profile>.config.toml` or `[profiles.<profile>]` in `config.toml`. A readable standalone profile or a named profile table can inherit the base config's top-level model. Unknown profiles retain their profile identity, rather than inheriting the caller's default model. Spend entries and rung models use the same case-folded price identity before cost comparisons. A running reviewer's live entry is not a cost sample until exit collection finalizes it. `validate` warns per open task only when no reviewer rung can run.

Review dispatch computes the submitted diff before taking the spawn state lock. Under the lock it rechecks software gates and refuses if the submitted SHA or configured base changed. It chooses the reviewer from the current tier, policy, history and ladder. A refusal starts no reviewer and writes no review packet; retry to prepare the current diff.

Cost samples use T31's `spend.entries` across all tasks, restricted to native `rung: review` or spawned reviewer entries. Worker usage, including usage by the submitter, is excluded. Inclusive input, cached input and output must all be known. Recorded `cache_write`, when available, is subtracted from fresh input and priced separately; older records price non-cached input at the higher of input and cache-write rates. Unknown components cannot justify promotion. Price lookup first matches the exact configured model id with whitespace trimmed and case folded. Without an exact row, it falls back to the canonical identity: the Claude provider prefix (`global.`, `us.`, `eu.`, `apac.` or bare `anthropic.`) and the `[1m]` and Bedrock `-v<N>:<M>` suffixes dropped. Release dates remain part of the pricing identity. Every Claude rung expands `BUILTIN.claude_aliases` to the release ID its spend records, and native Claude review-spend aliases use the same table when matching samples to prices. Explicit Claude reviewer candidates keep the same plain Anthropic or global Bedrock route identity as spend. An exact `global.anthropic.claude-opus-5-5` row preserves that route's rates; without it, `claude-opus-5-5` is the fallback row. A run on several models is not one model's sample and is left out. Use rates for the provider, cache lifetime and context size being measured. Aggregate T31 records cannot reconstruct per-request long-context surcharges or unlogged thinking tokens; missing output remains a measurement limit.

Worktree creation has no added timeout and uses Git's native initialization lock. The CLI unlocks only after checkout and its hooks finish. It refuses to reuse an unfinished locked registration, including one whose CLI died while a Git child survived or before HEAD was written. An unfinished registration for any task refuses the whole batch call; worktrees prepared earlier in the call can remain. There is no automatic recovery by pid or age. After Git and its children finish, inspect the worktree, then run `git worktree unlock <path>` for a complete checkout or `git worktree remove --force <path>` for an incomplete one. Existing branches and completed worktrees are reused offline. If an add later in a batch fails, earlier tasks can remain prepared.

An add that reports a missing `commondir` while a gate's worktree is being removed is retried once after 100 ms. Preparation replans before retrying; unfinished locked registrations remain refused, and a persistent error is reported.

While the registration is still locked, the CLI moves the task worktree's admin directory (HEAD, index, `commondir`) out of the git directory's `worktrees/<name>` to `.git-admin/<name>` under the worktrees root, points the worktree's `.git` file at it and leaves a link at `worktrees/<name>`, so `git worktree list`, `prune` and `remove` still find it. The `.git` file, `commondir` and the link are relative, so moving the project directory, which holds the repository and the worktrees root side by side, keeps the worktree working. The admin directory's `gitdir` is git's own absolute back-pointer, which `git worktree prune` trusts: before each prune (task preparation, gate preparation and cleanup, stack sync) and before `worktree` reads the registrations, the CLI writes it again for each relocated worktree whose `.git` file names its admin directory and whose `commondir` names this repository's git directory, and restores the relative paths and the link. A repository named `r.git` beside `r` shares its worktrees root, and neither relinks the other's worktrees. Moving a new worktree's admin directory, each relink, each prune, the removal of a task worktree, and gate preparation and cleanup take the repository's worktree lock, so a relink never meets a worktree whose admin directory is moved but not yet linked, or one git is emptying. The lock is `worktree/lock` in the state directory. No sandboxed agent writes there: claude's sandbox lists the state directory in `denyWrite` and codex's profile marks it `read`; a sandboxed role cannot name `state` or `worktrees` in `writeOutside` ([agent files](../ladder.md#agent-files-and-homes)), and spawn refuses a `sandbox.write` path inside the state directory or holding it or the worktrees root. The git directory is no place for it, since a worker writes that, and a submodule's git directory lies inside the superproject's. Without a state directory there is no project and no agent, and the lock is `tower-crane-worktree/lock` in the git directory. The lock holds its holder's marker, as the state lock does. A holder whose pid is alive on this host and in this pid namespace keeps it whatever its age; on Linux its start time must also match, so a reused pid does not keep it. On macOS and Windows a live pid is enough, so when a holder crashes and another process reuses its pid, the lock stays held until that process exits; waiters are refused after 60 s with a message that names the directory to remove. A holder that is gone holds nothing: the next process that wants the lock clears it. A holder on another host or in another pid namespace (a container on the same repository) counts as gone 60 s after its marker last changed. A holder touches its marker every 10 s only while its git runs asynchronously, as the gates do under automation. A manual `tower-crane check` runs the gates' git synchronously, and a task worktree removal does too, so neither refreshes it: a waiter on another host or in another pid namespace can take the lock over when one of their git calls outlasts 60 s. A waiter still waiting after 60 s on a holder it counts as live is refused with a message that names the directory. The lock belongs to the state directory, not the repository: two projects on one repository, each with its own state directory, take different locks over the same worktrees root and do not exclude each other. Tower Crane 0.1.2 and earlier took the lock as `tower-crane-worktree.lock` in the git directory, which a sandboxed worker writes. A holder of the new lock also makes that directory, with its marker inside, while it is free, so an older process still running waits for it. One a killed holder left is cleared by its marker. Any other is never waited for, and each process that finds it prints a notice that names it, once. Stop older Tower Crane processes after upgrading, then remove it. A sandboxed agent writes the git directory but not its `worktrees/`, so it cannot write another worktree's admin directory, one added after it started included ([shared git directory](../ladder.md#shared-git-directory)). Removal and prune remove the admin directories git emptied. On Windows, whose links need privileges, and when the worktrees root is on another filesystem, the admin directory stays in `worktrees/<name>`. Worktrees created before this layout keep theirs there too.

Task preparation, temporary gate preparation and stack sync run `git worktree prune` before using worktree registrations. Gate commands and the git commands run in the gate worktree, with their hooks, use `TMPDIR`, `TMP` and `TEMP` pointing at a directory inside the gate's temporary parent, which gate cleanup removes with the worktree. A `NODE_COMPILE_CACHE` the caller set points at `node-compile-cache` in that directory. Gate cleanup prunes after every removal attempt, including successful removals. This clears orphan admin directories, including empty read-only `commondir` and `config.worktree` mount points recreated by a sandbox after removal. Git owns admin-file writes and initialization ordering; Tower Crane only moves a task worktree's admin directory, as above, and does not synthesize or repair those files. Prune preserves locked registrations while another checkout or its hooks are running. Before those git calls, and before each git command an agent's shim runs, empty read-only `*.lock` files directly in the git directory, such as `config.lock`, are removed when no process holds them and each removal is logged to stderr. A sandbox leaves such a file where it masks a path the host lacks, so sandbox masks name only paths that exist on the host. Cleanups take turns through `.git/tower-crane-reap`, which holds a marker naming its holder's pid, host, boot id, pid namespace and Linux start time, with the boottime offset of its time namespace (`boottime_offset_ns`, from `/proc/self/timens_offsets`): a cleanup that finds it held waits up to 5 s, then keeps every placeholder and says so on stderr, naming the directory. A holder that is alive keeps the directory whatever its age, since it may only be paused. A cleanup killed while it holds the directory, such as an agent's git shim when the agent is stopped, leaves a marker naming a process that is gone; the next cleanup removes that marker and takes the directory. A marker is written and synced before it is renamed into place. A marker from an earlier boot of this host is gone; one from another host is kept. `/proc` shows a start time shifted by the reader's time namespace, so a cleanup moves the recorded start by the difference of the two boottime offsets before it compares them, and a holder under `unshare -T --boottime N` stays alive. A marker without an offset, from an earlier version, counts as alive on a start mismatch unless the process runs in the cleanup's own time namespace. A marker with this boot id and another host name comes from another UTS namespace on this kernel, such as a devcontainer or docker container on the same repository, or a sandbox that names its own host: only a cleanup in the initial pid namespace judges it, since only it sees every process on the kernel, and any other cleanup keeps it. A host whose own processes run outside the initial pid namespace, such as a WSL2 distribution, an LXD container or a devcontainer, has no such cleanup: there a marker left by a killed holder under another host name, such as one from a container or a UTS sandbox sharing the repository, stays until `.git/tower-crane-reap` is removed by hand, and every cleanup until then waits 5 s. A marker from another pid namespace, such as a shim in an agent's command sandbox, is judged by its holder: it is gone once no process readable through `/proc` has that namespace, the marker's pid as its innermost `NSpid` and the marker's start time. A process whose namespace cannot be read counts when its `NSpid` shows a nested namespace and the rest matches. Only a cleanup outside every command sandbox judges such a marker, since a sandbox shows none of the host's processes; `TOWER_CRANE_SANDBOX=1`, `SANDBOX_RUNTIME=1` (claude's sandbox) and a non-empty `CODEX_SANDBOX` (codex's) each mark a cleanup as inside one. A marker that does not parse is gone once its file predates this boot, as a crash of the machine leaves it. When the supervisor sees its agent's process group end, it runs a cleanup on the host that does not wait, so a shim killed with the group does not keep other sandboxed agents' git calls waiting. A sandbox can run the shim in a session of its own that ends only when the sandbox is torn down, so while the directory is still held the supervisor tries again every 100 ms for 1 s. Prepared `tower-crane-reap.<pid>.<nonce>.new` directories of takers that are gone are swept the same way, and so is one with no marker that is older than the 5 s wait. An empty directory, left by a version without markers, names no holder and is taken. Without a readable process table, as on Windows and macOS, no placeholder can be shown unheld, so a cleanup does not take the directory. Holders of placeholders are found through `/proc`. A process of the same user whose descriptors cannot be read keeps the file, since it may hold it; a zombie holds nothing. Another user's processes cannot be read, so they are not counted. Without `/proc` nothing is removed.

Task worktrees are recorded in `task.worktree`: `path`, `branch`, `base`, `created_at` and `head` (the last observed commit). Preparation and submission refresh the head; list reads Git's current HEAD. `task update ID --superseded-by TARGET` records `superseded_by` and cancels the task, folding it into a different uncancelled replacement. Task show and the board task details show the replacement id. Accepted tasks must go through rework first. Existing worktrees with an older task branch record are matched by branch, so prune covers the backlog without requiring recreation.

`tower-crane worktree list` reports task status and `live`, `stale` or `orphan`, with counts and paths. A cancelled or superseded task is stale. A PR becomes stale only with audited successful merge evidence at its current head and revision. Accepted-but-unmerged, rework and interrupted worktrees remain live, including dirty files. A Git worktree under the managed root without a matching task record is an orphan. Registrations outside that root are excluded. Retired records do not reclaim a branch or path reused by a live task. The board and inbox show stale and orphan counts and paths; inbox supplies a resolving prune command.

Merge, cancel and supersede retire the worktree and delete its local branch in the same command. Removal uses `git worktree remove`, never directory deletion. Before removal of local work or its branch, `worktree-saves/<task>-<unique>/` under the state directory receives binary tracked, staged and unstaged patches, untracked and ignored files, a commit bundle when HEAD is not already reachable from the local base, and a manifest. A missing checkout still gets a bundle before its branch is deleted. Every retry checks the current branch head against the saved bundle heads. A newer head receives a new recovery directory whose manifest links the earlier save through `previous`, preserving its patches and files. Initialized submodules are saved recursively with their local refs, dirty files and patches; the parent manifest names each recovery directory. Patches stream to files and Git file-list reads have no output-size cap; the CLI prints that path and keeps it on the task. The absent unstaged `.mcp.json` sandbox mask is restored when possible and excluded from the saved patch. Real edits and staged deletions of that file are preserved.

Locked registrations, paths whose resolved location leaves the managed root, running agents and Git or filesystem failures keep a stale record with a reason. Each outcome emits `worktree removed` or `worktree kept`. The task and current path/branch ownership are checked together under the state lock before removal. The same write reserves the actual path and branch in `retiring`; Git runs outside the lock. Claim, rework, submit and worktree preparation refuse a live reservation on either resource, including one held by another task. A stale worker receives an exit notice through its next tool or inbox hook. Its supervisor stops the process group, waits for closure, records exit, and retries retirement.

`tower-crane worktree prune` retries every stale task and lists orphans. `--orphans` explicitly includes orphan removal and local-branch deletion, with the same dirty-work saving. `--dry-run` prints the plan without changes. Prune is operational (orchestrator or owner). Accepted status alone never authorizes removal.

Worker scratch is recorded as the task's `scratch` path on spawn: `tower-crane/tasks/<state hash>/<task id>` under the spawning user's cache root. Every later worker attempt, including rework, mounts that path read-write and sets `XDG_CACHE_HOME` there; Go and npm caches also stay inside it. The recorded path is reused even when a later dispatch changes its cache-root environment. Worker prompts and command-harness brief copies name the path, including resume prompts. Homes and reviewer caches remain per spawn and can be pruned independently. A sandboxed codex or claude agent's temp directory is `tmp` inside its writable cache: the task scratch for a worker, its own agent cache for other roles. `TMPDIR`, `TMP` and `TEMP` name it (Windows programs, and codex's Windows sandbox, read the last two), and `JAVA_TOOL_OPTIONS` gains `-Djava.io.tmpdir=<it>`, since the JVM otherwise uses `/tmp`. The JVM splits that variable on whitespace, so a path with whitespace or a quote gets no `java.io.tmpdir`. These four win over the project's `env` and `env_file`; other options in a `JAVA_TOOL_OPTIONS` there stay. A browser that the agent or its MCP server starts makes its singleton socket in that directory, and Playwright's Chromium fails with "Socket path too long" when the directory is over 62 bytes (Chrome: 66). So when `tmp` in the cache is longer, the agent gets `tc/<12 hex>` under the cache root instead, named from the resolved cache path (a root behind a link, such as `/home` to `/var/home`, names the same directory when it is made and when it is removed), the same for every attempt and removed with the cache. It fits for a cache root of up to 46 bytes; under a deeper one, such as a test fixture's, a browser the agent starts fails. A file or link left at either path is replaced by a directory, never followed; the directory is made without recursion and must then be a directory of this user's, or spawn refuses. The permission profile names the directory and never `:tmpdir`, which codex resolves from the `TMPDIR` it starts with, nor `:slash_tmp`, the host's `/tmp`. So a caller temp directory under the home or at `/tmp`, which can hold other tasks' scratch and test fixtures, is not in the sandbox. One elsewhere, such as `/var/tmp/x` on Linux or macOS's `/var/folders/...` under `/private`, would be readable through the entry of `/` that holds it, so the profile hides it, together with macOS's `/private/tmp`. It stays readable only when a path the agent needs, such as its worktree, lies inside it. codex keeps its `codex-bwrap-synthetic-mount-targets-<uid>` directory in the agent's temp directory too. claude makes its proxy bridge sockets there, which its sandbox reads and writes; socat takes at most 73 bytes there, so a claude agent under a cache root deeper than 57 bytes keeps the caller's `TMPDIR`, and spawn prints a notice. Successful task worktree retirement removes scratch, including read-only module trees, and clears `scratch`; each reason that keeps the worktree also keeps scratch. Superseding a task uses cancellation and the same retirement rules.

On POSIX, each sandboxed spawn also gets a short writable socket leaf, `tc-<12 hex of its home path>`. Spawn tries `XDG_RUNTIME_DIR`, then `tc` in the account's own `.cache` (from the password database, not `HOME` or `XDG_CACHE_HOME`, which can name a deep agent home or test root; made 0700 when missing), then the leaf an enclosing sandbox granted in `TOWER_CRANE_SOCKET_DIR`. It selects the first writable root whose resolved leaf and a `tc-XXXXXX/s` child fit 103 UTF-8 bytes. No socket, socket directory or fallback goes under `/tmp` or `TMPDIR`. When none fits, a rung whose sandboxed routes are all codex spawns without a leaf, since its broker listens on loopback TCP; any other refuses, naming each path tried with its length in bytes or the error that passed it over. Only the leaf is granted read-write, and `TOWER_CRANE_SOCKET_DIR` names it for tests and commands. The monitor receives it as `agent_socket_dir`; Claude and mixed-route brokers listen at its `s`, and Codex-only brokers retain loopback TCP. The broker removes its socket and owner record, then the empty leaf when it closes. While it runs, it watches its socket directory, and its supervisor checks it every second: when something removed the socket or the owner record, as a sweep from an older tree's tests in the agent's sandbox did, the broker listens at `s` again and writes the record again. A socket directory that is gone or replaced was removed outside the sandbox, which may still hold the old one, so the supervisor stops the agent and its `spawn phase` records `blocked` with the reason `state broker lost: its socket directory <dir> is gone`. Before listening it sweeps the leaf's root and each socket root for old directories whose owner record proves their monitor exited and whose socket, when there, refuses connections. The owner record names the monitor's pid namespace (`pidns`, the target of `/proc/self/ns/pid`), and a pid recorded in another namespace, or checked by a caller that cannot read its own, is never judged exited: inside a sandbox's pid namespace a live monitor outside it is missing. The socket answers for a record from before records named the namespace. A direct broker caller without this grant listens at `broker.sock` in its broker directory when that fits, otherwise in a fresh `tower-crane-XXXXXX` directory under the same roots; with none it refuses, naming its own path and each root path with their lengths. Windows brokers use named pipes.

On POSIX, an inherited `XDG_CACHE_HOME` is recognized only when it names the exact `tower-crane/{tasks,agents}/<state hash>/<id>` cache leaf. An explicit test cache below that leaf remains an explicit root, so fixtures inside worker scratch can select their own cache directories.

The sweep before home construction scans both `homes/` and `brokers/`. An orphan broker directory can retire even after its home has gone. Broker removal requires no unexpired claim for the agent, a verified exit of its last recorded worker and supervising monitor (or no recorded spawn), and `ECONNREFUSED` or `ENOENT` from every endpoint in `broker.json`. Unix sockets, Windows named pipes and loopback TCP endpoints are probed without sending a token or command. Invalid or unreadable metadata, unknown process states, other connection errors and timeouts preserve the directory.

`ci log JOB_ID [--failed-tests]` reads a job on the task's current branch head with gh's `--allow-escape-sequences` flag and writes its cleaned log to `ci-job-JOB_ID.log` directly in `scratch`. Terminal sequences (including CSI and OSC), bare ESC, and other control characters are removed before saving or printing job output; tabs and newlines are preserved. A carriage return becomes a newline (CRLF becomes LF), so a progress bar's redraws read as lines; other controls go, so text a Windows tool prints in UTF-16 (a NUL after every character) reads normally. Two exceptions keep redaction working: a control run inside a token shape (a GitHub, API, AWS or Slack key, or an `Authorization` value), or inside a redacted environment value, found with the controls removed goes even when it is a carriage return, so the token stays whole; and a run at the edge of a token shape found with each run made a space becomes a space, so the pattern still finds the token's word boundary. A terminal reads a lone ESC, `ESC (` or `ESC [` with the letter after it as one escape, and an OSC string without its terminator to the line end, so the cleanup can take a token's first character or head; when a second escape also splits that token, or a line break splits a token, no pattern finds what is left. An environment value is found in the raw text with any escapes, controls and line breaks between its characters, at most 1024 of them between two of its characters, each escape read both as an escape and as text: a CSI's parameters and final and a two-character escape's intermediate bytes may be the value's own characters, and the value may go on inside a string's body or after it. These readings of a value's own characters as escape bytes are made only after the reading a terminal makes finds nothing there, and only where the value's head shows: such a value yields to every other secret it meets, a token, a header, another value or another copy of itself, and is not redacted where it would take one of their characters. Where a token found in a view meets a value and the view's text would cut it, the value is put back as itself next to the token, with a space at each word boundary. So a value is redacted under every split but one: a value that runs on from another secret and needs an escape's own bytes read as its characters keeps part of its text, as before; a planted-secret fuzz shows about 10 such values in 25,000 cases, against about 800 before. A redactor that cleans text (gate output, local CI artifacts, failed-job excerpts) also redacts every raw character that the cleanup reading escapes only as a terminal does would redact. A placeholder covers what either redacts, so the readings above never show a character that cleanup redacts. An `Authorization:` header that an escape the cleanup removes glues to a word before it is read as a header with a space put before it, so its value is redacted; when the word is a token whose run took the header word, the header word goes back to the header if what is left is still a whole token, and a binary artifact with such a header value is not copied. A token shape is found in a view of the raw text that removes a CSI sequence or a terminated string whole but only the introducer of anything else (read only when an escape would take a character), and in that view across line breaks. A join across lines starts at a token prefix, counts each removed line break as a word boundary, and takes at most 256 characters and 8 line breaks. The cleaned characters of such a secret are replaced by the whole value or token, so it is redacted, and a token split across lines joins them. Token shapes are found as well as these views allow, not under every split. Known misses: a token whose part before a line break is already a whole token shape keeps its tail on the next line (the line may end there); a CSI with parameters before a token (`ESC [1;` then the token) takes its first letter; two two-character escapes in one token, one stray and one real, can hide it; so can a real two-character escape (`ESC (B`, `ESC 7`, `ESC =`) inside a token that a line break also splits, in the log and its tail and text artifacts (a binary artifact holding such a token is not copied); a line break inside a token's prefix joins only with at least two of the prefix's characters before it or three after it, so `g` then a line `hp_...` is joined but `s` then a line `k-...` is not (`0.3 s` then a line `K-long` would read as an API key), nor is a prefix that two line breaks split; such a token also stays as written where it overlaps an environment value or a secret the cleaned text or a gentle view shows, since its joined text would cut that one; and in a binary artifact an 8-bit CSI byte is not read as an escape (there such a byte is half of a UTF-16 or UTF-8 character), so a token with one inside whose parameters break its shape (`0x9b 1;31m`, or any inside an AWS key) is copied. A line that ends with a whole token shape keeps the next line apart, as does an `Authorization` value. A token put back whole can give a header glued after it a word boundary, so the header then redacts its value to the line's end under `AUTHORIZATION`, where the cleaned text alone gave other labels; every secret stays redacted. Known false positives of a prefix joined across a line break, found in no real log: a line that ends in the word `sk` before a line that starts with an 8-character flag such as `-DCMAKE_BUILD_TYPE=Release` reads as an API key, and `Plan A` before a line that starts with `KIA` and 16 capitals or digits as an AWS key. The same cleanup applies to failed-job log excerpts in `submit`, and check output, annotations and alerts from `ci checks` in text and JSON output. It needs the task's recorded `branch` and `scratch`, so it can read feedback before `submit` records a PR or SHA. `ci alerts` needs the recorded `pr` and reads open code-scanning alerts at `refs/pull/N/head`. Both default `--task` to `TOWER_CRANE_TASK`; the worker broker restricts them to its own task. Neither command changes state.

`ci checks [ID] [--task ID]` resolves the current PR head from the recorded PR number or branch, so it also works before the first submit. It reads all non-green check runs with title, summary and paginated annotations. The same `ci.ignore_apps` and `ci.capped_review` rules as the CI gate mark matching runs nonblocking and name the policy reason. Superseded review rounds, check reruns and replaced workflow runs stay visible as nonblocking using the gate's judgment. These exceptions do not satisfy `ci.required`. Open code-scanning alerts include rule, path, line and message from the head ref and the current merge ref. A merge analysis counts only when both parents match the PR's current head and base; stale alert instances are excluded. An alert fetch error is reported as `alerts_error` with `alerts: null`, while check output stays visible. It also lists every open revuto inline finding with path:line, numeric comment id and body, stripping terminal controls and removing HTML comment blocks that start a line with up to three spaces outside Markdown code. Inline prose markers, escaped markers, code spans, indented code and fenced blocks are preserved. An unclosed block removes the rest of the body and is counted. Text caps each body at 4000 Unicode characters and appends `[body truncated after 4000 characters]` when cut. Text prints one note per finding with removed blocks, `[n characters of HTML comment removed]`, where n is the total Unicode characters removed across all its blocks. Each block contributes the characters from its opener through its closer or the end of the body. JSON returns the complete body after block removal as `findings[].body`, with `html_comment_chars_removed` when nonzero. The reader removes blocks once; the text formatter only caps the body and prints the notes. Findings without a current line and findings whose latest non-revuto reply starts with `[resolved]` on its own line are omitted. Submit reports and rework worker prompts use the same text formatter. A failed finding read leaves check output visible and reports `findings_error` with `findings: null`. It ends with the task's latest dispatched run (`ci dispatch`): its run id, head, status and jobs, and once the run completed, each failing job's failing tests with their first error lines, parsed by the CI gate's `main_red` log parser. A run recorded without its id is looked up again; a dispatch at an older head is marked as such. Dispatched runs' jobs are not listed among the PR's check runs. JSON carries the run in `dispatch`, null without one, and a failed read as `dispatch_error` while the rest stays visible. The command changes no state and the worker broker restricts it to its own task. Submit's failing or pending CI refusal points workers to this command before an orchestrator question.

## events.jsonl

Long-lived wait hosts, spawn supervisors and board servers retain parsed history and a byte offset. They read only appended bytes, buffer incomplete lines until a newline arrives, go back to where a recorded cut left the log ([Durability and write order](#durability-and-write-order)), and reset on any other truncation or on file replacement. Reset rebuilds retained history from the beginning. A restore that also brings back a shorter `events.cuts.jsonl` makes a saved `OFFSET:CUTS` cursor whose `CUTS` is past the restored file's length exit 2 from `wait` and 400 from `GET /api/messages`, as an offset past a restored log does; restart those clients with a fresh cursor. A live reader whose log was replaced starts over with the restored length; one whose log was rewritten in place ignores cut records until `events.cuts.jsonl` grows past the length it had read. Active waits and board SSE do not wake for restored records, across as many reads as the restore takes. They keep the ids of the records they read since they started: after a reset a record with one of those ids is history, and so is history from before a reader's start cursor up to the line that ended at that cursor. Any other record wakes, whatever its writer's clock. A restore that lacks the start line, an older backup, leaves only time: records whose `at` is no later than the reader's start are history. Project, task and decision snapshots whose files are unchanged and whose event log has had nothing appended since they were read retain their validation and parsed values; mutations always load fresh writable copies. Directory watches wake readers promptly; bounded fallback checks also cover lost notifications. The broker handles requests through command subprocesses and does not poll the log.

## Audit and board updates

The log is the event source of truth. It is only appended to, except that lock recovery cuts off the torn append of an unfinished commit ([Durability and write order](#durability-and-write-order)). One JSON object per line: `{ "id", "type", "to", "at", "agent", "cmd", "task", "detail" }`, plus `"via": "broker"` on an event the state broker wrote for a sandboxed agent or `"via": "automation"` on a software reaction (provenance, not proof). Every append occurs under the state lock after validation and state writes. Refused commands append nothing, except the `ask` an orchestrator's owner-required change opens ([Authority](decisions.md#authority)) and the `msg refused` a sandboxed agent's refused message records ([state broker](../ladder.md#state-broker)). Each new event has a unique `E<uuid>` id. `cmd` preserves the command name (`task add`, `claim`, `spawn`, `check tests` and so on); `tower-crane spawn` counts its earlier `spawn` events to number agents. Older audit lines without ids remain readable; `wait` exposes their byte offsets for resuming.

A change of a guarded setting also logs one `setting` audit event before the command's own ([Authority](decisions.md#authority)). A ladder change logs `ladder harness` and one `ladder set` per rung it changed, with the rung's new fields and, when the edit moved the rung to another harness, `dropped`: the fields it removed because they do not fit there (for `tools`, only the names the new harness does not know; the rest stay). A ladder or tier write made from the board or Settings carries `"via": "serve"` in `detail`. All serve writes require explicit owner identity and record `agent: "owner"`; other serve identities expose read-only views and refuse POSTs without state or event changes. Read-only Settings names `tower-crane serve --agent owner` as the command for enabling edits. CLI ladder and tier commands keep their existing agent rules.

The served board applies live state changes in place. Its fragment route, visible view, open task sheet, scroll offsets and focused control remain local to the browser and survive live updates; they are not written to the state directory. Form controls retain focus by their form's API action and button value. Removing the focused control from an open task sheet moves focus to the sheet heading. The server renders unique `data-preserve` attributes for controls, disclosures and scroll containers. Blocker rows use their reason kind and dependency or decision id; separate mentions within a row use their text offsets. Unexpected duplicate identities receive deterministic suffixes so rendering stays available; strict tests reject duplicates. Event rows use the log event id, with the existing log-index fallback for legacy events. Live updates restore open and closed disclosures before focus and scroll through one identity snapshot in every view. If the surviving focused control moves inside a closed disclosure, restoration opens its containing disclosures and preserves that open state. A control that remains unfocusable falls back to its nearest visible ancestor control. Settings carries that snapshot across reloads through a temporary entry in the tab's session storage, consumed on the next load. A reload before restoration completes retains the pending snapshot rather than capturing the new document's default position. The client sets `data-position-restored` on the document root only after restoring disclosures, focus and scroll, including the animation frame after a Settings reload, and clears it before the next replacement or reload. These browser identities add no state fields.

The initial view's animation frame resets fragment scrolling only if the route, page scroll and main scroll still match their positions at load. A delayed frame cannot overwrite the reader's subsequent scrolling or live restoration.

## Torn event lines

An incomplete final line remains unread until a subsequent append; after a crash, that append starts a fresh line without deleting the damaged bytes. Readers skip the damaged record and continue. Only lock recovery truncates the log, and it records each cut in `events.cuts.jsonl`; a cursor inside a recorded cut reads from where the cut left the log. Nothing else may truncate or replace it; a cursor beyond its end is refused.
