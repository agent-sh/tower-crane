# Tasks and lifecycle

## Orchestrator lease

The first orchestrator write takes `tasks.json.orchestrator_lease` under the state lock. Older state files can omit it; null means released. It holds `{ session_id, harness_session_id, agent, pid, host, heartbeat }`, plus `pidns`, Linux `start_ticks` and `persistent`. The selected harness or session shell records `persistent: true`; a caller fallback records `persistent: false`. `pid` identifies the selected session ancestor or fallback caller, rather than the short-lived CLI process.

The session key binds the host and nearest harness ancestor (`claude`, `codex`, `opencode`, `agy`, `pi`, `gemini`, `aider`, `goose` or `cursor-agent`, including Node and Python entrypoints) or session shell to the first available `CLAUDE_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID` or `CODEX_SESSION_ID`. A session shell is a shell that runs neither `-c` nor a script file and is a login shell (`-bash`, the `-zsh` that macOS `ps` prints for a Terminal login shell, `-l` or `--login`, so `bash --posix --login` counts), runs with `-i` or `--interactive`, or, on Linux, has a terminal on stdin. fish's `-C` takes its init command as a value, so `fish -i -C 'source x'` counts. A shell with `-c` is a per-command shell on every platform. Windows command lines are split by CommandLineToArgvW rules, so a backslash-escaped quote stays inside its argument and `"a""b"` is `a"b`; macOS `ps` output is split on spaces. Any other agent CLI started from a session shell is not a session ancestor: it shares that shell's lease, so two such CLIs run from one shell share one identity. Intermediate shells and script files share that ancestor's identity. Without such an ancestor, it keeps the first non-transient caller from the parent process chain and does not release that fallback lease on process exit. Without a harness id it uses the host and selected process identity alone. Linux start ticks and Windows creation ticks identify that process; changes to ancestors above it do not change the key. Linux process start times and pid namespace distinguish reused pids and namespaces. Windows does not reparent orphans, so the ancestor walk stops at a parent whose creation time is later than its child's: that pid was reused by an unrelated process. A different harness process or session id cannot share a live lease, including two live copies of the same resumed harness id. In-process subagents, such as Claude Code's Agent tool, run inside the orchestrator's harness process and share its session id, so they share its lease identity; only `--agent` (or `TOWER_CRANE_AGENT`) separates their role from the orchestrator's.

Windows parent discovery runs before taking the state lock. One CIM process snapshot supplies every ancestor; only the caller's chain is returned from PowerShell. This avoids one provider round trip per ancestor while keeping command-line output within the pipe buffer. The existing 60-second hang guard allows cold PowerShell startup under load. A failed or timed-out snapshot refuses the command without choosing a fallback identity.

Native orchestrator commands renew the matching holder's heartbeat at command entry, including reads, once it is a sixtieth of `lease_minutes` old (one minute by default). The check reads the files without the state lock; only a renewal, acquisition or replacement takes it. A read tries the lock once and never waits: a busy lock leaves the renewal to a later command. A read never takes a vacant lease or renews another session's lease. Writes from another live session exit 1 naming the holder, pid, host, heartbeat and recovery commands. The guard runs before CLI commands start external work and again inside every state mutation. MCP initialization and discovery need no project or lease; actual tool actions use the same guard. Pure inbox reads stay open. `authority`, `bench gates` and `bench tokens` also remain open to competing readers and never acquire a vacant lease. Wait startup tries its lease transaction without blocking behind the state lock, so its event deadline stays effective; any later mutation still checks the lease under the lock. Workers and owner commands keep their existing authority.

Harness session ids in the environment can be copied by unrelated processes, so they do not prove lease identity. Native commands keep the process ancestry rule. A caller carrying the holder's harness session id outside the holder's process tree gets a refusal naming that mismatch as detached, without telling it to release its own lease. A loop launched with `setsid` or `nohup` can leave that tree when its intermediate parent exits; starting a new process group alone does not remove ancestry. Run native commands as children of the holding session, or let `tower-crane wait` and authenticated engine automation run gates for that session. Callers with unrelated session ids retain the existing release, expiry and owner-takeover guidance.

The lease expires after `project.limits.lease_minutes` of idle time, using the existing project lease window (60 minutes by default). After expiry the next orchestrator write replaces it. A persistent holder whose process has exited on the same host (and, on Linux, the same recorded pid namespace) releases the lease at once, so a restarted session does not wait out the idle window; on Linux the recorded start ticks mean a reused pid does not keep it. A fallback holder, or a lease recorded without these fields, still expires by idle time. The persistent holder is the selected harness or session shell. Intermediate scripts and per-command wrappers cannot release its lease by exiting. A holder's exit also ends engine reactions bound to it. `tower-crane orchestrator release` clears the calling holder's lease. Only the owner can run `tower-crane orchestrator takeover --agent owner`, which clears a live holder explicitly; the next orchestrator write acquires it. Both commands record the previous holder in the audit log.

Engine reactions marked `via: automation` bind to the session in the lease record whose process has not exited, including reactions from a monitor or owner waiter. The heartbeat's age does not matter: a reaction that starts after the holder idled out binds to that holder, so the holder's next command, which renews its own heartbeat, does not stop it. Engine work never acquires a lease or renews its heartbeat. Usage collectors and harness hook writers use the same engine provenance, so short-lived helper processes cannot become lease holders. With no lease, or a holder whose process has exited, engine work runs without taking a lease and leaves the lease available for the next native writer; an expired lease stays available too. An active reaction retains its captured binding, including a vacant binding. Release, takeover, a new holder replacing the expired lease, or the holder's exit refuses its later state writes. Fresh engine work can resume under the current holder. This lease coordinates trusted sessions, like the existing state lock; it is not an authentication boundary for processes that can write state files directly.

Engine provenance comes from the process doing the engine work, never from the environment. In-process reactions, collectors and observers mark their own context. A CLI child of an engine helper (the spawn supervisor's usage collector and hook writer, and the harness hook bridge) sets `TOWER_CRANE_VIA=automation` and presents the key from the dispatched agent's home, `homes/<agent>/automation.key`, as the first line of the child's stdin, with `TOWER_CRANE_AUTOMATION_KEY_FD=0` naming that descriptor. The key is never in an environment: Linux keeps a process's initial environment readable in `/proc/<pid>/environ` for its whole life, and the Stop hold's `wait --inbox` lives as long as the orchestrator idles. Each home build writes a new random key with mode `0600` to a staged file beside it and renames it into place, so a helper reading it during a rebuild finds a whole key or none, never an empty or partial one. The CLI reads the key line at startup, before any input the command reads, removes `TOWER_CRANE_AUTOMATION_KEY_FD` from its environment and checks the key against that agent's home. Without a matching key, `TOWER_CRANE_VIA=automation` is ignored: the command runs as its caller's native command, so a second session that sets it is refused like any other. Spawned agents do not inherit `TOWER_CRANE_VIA`, `TOWER_CRANE_AUTOMATION_KEY_FD` or the dispatcher's `CLAUDE_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID` and `CODEX_SESSION_ID`, so an agent's lease names its own harness session.

### Ladder

The ladder says which harness, model and effort runs each kind of work. It has seven rungs:

Pi uses a generated config home and tool allowlist, with credential files linked to the original user. Pi has no command sandbox or native MCP; a rung with `mcp` on pi is refused. Its `args` accept only `--no-session` and `--verbose`. Moving a sandboxed role to pi remains owner-required. Dry-run reports `home.mcp_supported: false` and `home.sandbox: false`; its startup receipt names the generated instruction file and marks every house rule as `read`, since context discovery is disabled, and records `sandbox: false` with `confinement: "unconfined"`.

| Rung | Runs |
|---|---|
| `orchestrator` | planning, briefs, dispatch, gates and merges |
| `easy`, `medium`, `hard`, `research` | a task at that tier (see `tier` under tasks.json) |
| `review` | clean-context reviews |
| `small` | small mechanical checks |

`harness` is the default for every rung that does not name its own, so moving everything to pi or opencode is one field (`tower-crane ladder harness pi`), and a rung with its own `harness` keeps it (a split setup). `harness` is one of `claude`, `codex`, `opencode`, `agy`, `pi`, or `command`. A rung's fields:

| Field | Applies to | Meaning |
|---|---|---|
| `harness` | all | overrides the default harness for this rung |
| `model` | all but `command` | model id; pi also takes `provider/id`, opencode takes `provider/model` |
| `profile` | `codex` | codex config profile |
| `provider` | `pi`, `claude` | pi provider name; claude takes `anthropic` or `bedrock` |
| `effort` | all but `command` | reasoning effort in the harness's own terms: claude `low` `medium` `high` `xhigh` `max`; codex `none` `minimal` `low` `medium` `high` `xhigh` `max`; agy `low` `medium` `high` `max`; pi `off` `minimal` `low` `medium` `high` `xhigh` `max`; opencode passes it as `--variant`, whose names each provider defines, so any single word |
| `args` | all | extra arguments appended verbatim to the command |
| `command` | `command` | owner-required: argv array; `{task}`, `{brief}`, `{prompt}` and `{cwd}` are substituted (`{brief}` is the brief file's path) |
| `tools` | `claude`, `codex`, `opencode`, `agy`, `pi` | tools the role's agent file leaves out that this rung opts back in to: claude tool names (`WebFetch`), codex feature names (`multi_agent`) or `web_search`; opencode native names (`webfetch`) or agent-file names (`WebFetch`), normalized before authority classification; agy native names (`search_web`); pi built-ins (`read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`) |
| `mcp` | `claude`, `codex`, `opencode`, `agy` | MCP servers this rung opts in to, by the name the user's harness config gives them (claude config directory's `mcp.json`, falling back to `~/.claude.json` `mcpServers`; codex `[mcp_servers.NAME]` in `config.toml`; opencode `mcp.NAME` in the original user JSON/JSONC config and `OPENCODE_CONFIG_CONTENT`, merged recursively across config layers, without copied environment or headers; agy `mcpServers` in `~/.gemini/config/mcp_config.json`) |
| `web_mcp` | research on `claude` | owner-required: explicit `{name, command, args}` web server, with no env, headers or secrets; cannot combine with `mcp` |
| `supervision` | all | per-rung `{ retries, backoff_ms, max_backoff_ms, stall_ms, usage_ms, progress_paths }`; omitted fields use the defaults below |
| `fallbacks` | all, user file only | personal ordered array of route objects to try after provider outage retries, a harness refusal or a harness login failure (the last one only on another harness); each route takes rung fields except `fallbacks`; refused in project.json |
| `sandbox` | `claude`, `codex`, `agy` | owner-required: `{ write: [paths], read: [paths], session_bus: true or false, domains: [host patterns] }`; `write` extends writable paths on Claude/Codex, `read` adds readable paths under the user's home, which Claude/Codex sandboxes otherwise hide ([home reads](../ladder.md#home-reads)), `session_bus`, on claude and codex, reaches the session bus socket, and `domains` adds hosts claude's sandbox lets commands reach (a rung's list adds to the project's; [ladder.md](../ladder.md) has the default list and the pattern rule); agy emits requested settings without a confinement guarantee. `session_bus` is also set alone with `project set --session-bus`, owner-required like the rest of `sandbox` |
| `env` | all | owner-required: extra environment variables as an object of string values; kept in `project.json`, so `env_file` keeps secrets out of the state directory |
| `env_file` | all | owner-required: path to a systemd-quoted environment file; its contents are read at real spawn and given only to the agent process |
| `credential` | `claude` with `provider` `bedrock` or `anthropic`, `codex` | owner-required, rung only: the name of a credential in the OS store, which the harness gets at the moment it needs it and never in its environment ([credentials](#credentials)) |
| `scope` | all | owner-required: systemd user scope properties as an object of non-blank string values, e.g. `{"CPUQuota":"200%"}`; `{}` clears optional properties; mandatory resource caps remain, and containment replaces `TasksMax`, `MemoryMax`, `MemorySwapMax`, `OOMPolicy`, `Delegate` and `Slice` with a `warning:` line when they are set |

`sandbox`, `env`, `env_file` and `scope` also apply at project level. They are owner-required ([Authority](decisions.md#authority)): the owner may set, clear or repeat them through `init`, `project set` or `ladder set`; once state exists, an orchestrator may apply the identical request after owner approval. Rung environment variables override project variables with the same name; both override the environment file, which overrides the inherited process environment. A rung's `env_file` replaces the project file. Each specified rung sandbox field replaces that project field: `write: []` removes the project extra paths for that rung, and `read: []` the extra readable ones. A rung `scope` replaces the whole project scope, so `{}` clears its optional properties for that rung; the containment caps remain. Clearing the rung field restores the project default. Extra writes are added to the role's normal writable paths. Harnesses without a sandbox renderer receive environment settings but do not enforce `sandbox`.

Agents do not inherit the dispatcher's Node injection variables: `NODE_OPTIONS`, `NODE_PATH`, `NODE_REPL_EXTERNAL_MODULE`, `NODE_PRESERVE_SYMLINKS`, `NODE_PRESERVE_SYMLINKS_MAIN` and `NODE_COMPILE_CACHE`. Filtering precedes project and rung `env` and `env_file` values, so those settings can explicitly supply a preload or module path. This holds on initial launches, retries and fallback routes; names are case-insensitive on Windows. The supervisor keeps its own Node settings for host commands. The git and gh shims clear these variables even when the agent sets them explicitly.

`broker` holds the [broker verbs](containment.md#broker-verbs) granted tasks run through the state broker; `project set --broker-verbs` writes it and pins each verb's source.

`sandbox.session_bus: true` (`project set --session-bus true`) lets claude and codex worker sandboxes reach the owner's session bus. It is off by default, and `false` removes it. The grant gives read and write on one socket under the runtime directory the worker's environment names (`XDG_RUNTIME_DIR` after `env_file` and `env`): `bus`. Each of the two variables the worker's environment leaves empty is filled in at launch from that directory, so the address names the granted socket. Other entries in that runtime directory stay denied, apart from the independently granted per-spawn socket leaf when it lies there; spawn refuses while the bus socket is missing. It does not make `systemd-run --user --scope` start inside the sandbox; the `scope` paragraph below has the evidence. For codex the bus socket is a readable path in the profile, mounted alone, since codex mounts `/run` only where a rule names it. A runtime directory outside `/run` that a readable rule exposes, such as `/var` for one in `/var/tmp`, is left unmounted too: codex mounts readable paths before hidden ones, so hiding it would hide the bus, and a writable path must be a directory. That rule gives way to the entries of each directory on the way down to the runtime directory, all but the one on that way. For both harnesses the setting grants the bus socket alongside any per-spawn socket leaf in that runtime. Other entries made there after spawn stay out of reach. An entry made after spawn in a directory on the way, such as `/var/tmp`, is not mounted either. codex binds each listed path again for every command and follows a link there, so a listed entry must stay what it was at spawn: links are left out, and so is an entry unless root or the user owns both it and its directory and that directory is writable by its owner alone or sticky. Each listed entry adds a rule, and codex passes its sandbox the profile in one argument of at most 128 KiB; spawn refuses a profile past that and names the directory and its entry count. Spawn also refuses the setting for a codex worker whose runtime directory lies in a writable path (`sandbox.write`), in the agent's worktree, which codex mounts whole as its workspace root, or in a directory `:minimal` mounts whole (`/usr`, `/etc`, `/bin`, `/sbin`, `/lib`, `/lib64`), since codex would mount the runtime directory whole there. Without the setting both sandboxes hide `/run` whole but the DNS resolver, and any runtime directory elsewhere, except the independently granted per-spawn socket leaf.

The risk: a command in the sandbox can reach every session bus service the bus policy lets a user process call, such as a running secret service, and a unit started through the user manager runs outside the command sandbox as the owner. Set it only for a project whose commands need the session bus and whose session services you accept them using. Spawn refuses a route that names a [credential](#credentials) under this grant, whatever its store: such a unit reads the Secret Service, decrypts systemd-creds and runs the credential helper as the owner. Clear `sandbox.session_bus`, or drop the credential from that route.

<a id="credentials"></a>**Credentials.** A rung's `credential` names a provider credential kept in the OS secret store, never in an env file, argv, `project.json`, events or logs. `ladder set RUNG --credential NAME` is owner-required, like `env_file`; `tower-crane credentials set NAME` stores or rotates the value ([cli.md](../cli.md#plan)). Each harness gets the value at the moment it needs it, outside its command sandbox, through `lib/credential-helper.js` (`value NAME` prints it and nothing else; `check NAME` answers by exit status; errors name the stores and the fix, never the value):

- **claude, `provider: "bedrock"`.** The supervisor runs a broker for as long as it supervises the agent. It listens on 127.0.0.1 at an ephemeral port and answers only under a random path nonce. It adds `Authorization: Bearer` with the token the helper reads, and forwards `POST /model/...` to the region's `bedrock-runtime` endpoint and `GET /inference-profiles` to its `bedrock` endpoint, streaming bodies and keeping headers and status. When the user's Claude settings or the launch environment set `ANTHROPIC_BEDROCK_BASE_URL`, it forwards there instead. claude starts with `ANTHROPIC_BEDROCK_BASE_URL` naming the broker and `CLAUDE_CODE_SKIP_BEDROCK_AUTH=1`, and without `AWS_BEARER_TOKEN_BEDROCK`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` or `AWS_SESSION_TOKEN`, wherever they came from. Its settings deny `ANTHROPIC_BEDROCK_BASE_URL` to its commands (`sandbox.credentials.envVars`), and claude's sandbox has no host loopback, so a command reaches neither the nonce nor the broker. Codex commands share the host network; the nonce keeps them out. A token read from the store serves for a minute; a 401 or 403 from Bedrock drops it, so a rotated token is read on the next request. Claude Code 2.1.305 has no helper setting for a Bedrock bearer token, which is why the broker exists.
- **claude, `provider: "anthropic"`.** The agent's `settings.json` names the helper as `apiKeyHelper`, and claude starts without `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`. The user's own `apiKeyHelper`, `awsAuthRefresh` and `awsCredentialExport` are not used on a route with a credential.
- **codex.** The agent's `config.toml` gives the route's provider (`amazon-bedrock` for the `sol` and `astra` profiles, or a custom provider) `auth = { command = <node>, args = [<helper>, "value", NAME, "--config", <user file>] }`, and so does each `<profile>.config.toml` that defines that provider. codex runs it outside its command sandbox and refreshes the token every five minutes. codex starts without `AWS_BEARER_TOKEN_BEDROCK` and the other AWS credential variables, and no codex home links the user's `.env`. A codex rung whose provider is `openai` or a local one cannot name a credential.

The store for each name is the machine's, set in the user file (`TOWER_CRANE_CONFIG`, else `~/.config/tower-crane/config.json`): `"credentials": {"NAME": {"store": S}}`. `auto`, the default, tries the Secret Service (libsecret through `secret-tool`, attributes `service=tower-crane name=NAME`), then systemd-creds (`credentials/NAME.cred` beside the user file, encrypted with `systemd-creds --user`) on Linux. A lookup gives the Secret Service 3 seconds, since a locked keyring answers with an unlock prompt that may never show, and leaves codex's 5-second limit for systemd-creds. `keychain` (macOS, service `tower-crane`, account `NAME`) and `wincred` (Windows Credential Manager, target `tower-crane:NAME`) follow the documented behaviour of `security` and `CredReadW`, are untested, and run only when the user file names them; `auto` names no store on macOS or Windows. `"store": "env", "env_file": FILE, "var": VAR` reads VAR from an env file the owner keeps, at each use: the per-machine fallback for a host with no store, which `ladder show` names in a `notice:` on every show. The value still reaches the harness only through the broker, `apiKeyHelper` or the auth command. `ladder show` also names every rung with an `env_file`, which puts its variables in the harness environment.

Before spawn starts a route that names a credential, it reads the credential from its store, and refuses with the stores it tried and the fix (unlock the login keyring, or `tower-crane credentials set NAME`) when it cannot. A fallback route that fails the check is skipped. A helper that fails while the harness runs (`apiKeyHelper failed`, `Your apiKeyHelper script is failing`, `awsCredentialExport did not return`, `Error getting AWS credentials from awsCredentialExport`, `Failed to resolve external auth: provider auth command`, `AWS credential export command`, or Tower Crane's own `tower-crane credential ...` from the helper and the broker) is a harness login failure, as an expired login is ([spawned process exits](#spawned-process-exits)). Sandboxed commands reach neither store on Linux: both sandboxes hide `/run`, where the session bus and the `io.systemd.Credentials` socket live, and the home that holds `credentials/`. `sandbox.session_bus` breaks that: a command can then start a user unit, which runs outside the sandbox as the owner and reaches every store, so spawn refuses a credential on a route with that grant. `docs/research/credentials-keyring.md` has the measurements.

Moving a rung from `env_file` to a credential: `tower-crane credentials import --env-file FILE --var AWS_BEARER_TOKEN_BEDROCK --name NAME`, then `ladder set RUNG --credential NAME --clear env_file` on each rung, with the file's non-secret lines (`CLAUDE_CODE_USE_BEDROCK`, `AWS_REGION`, the `ANTHROPIC_DEFAULT_*_MODEL` pins) moved to the rung's `env` where the rung still needs them. Remove the secret line from the file once nothing else reads it.

Paths in `sandbox.write`, `sandbox.read` and `env_file` accept `~` for the original user's home, even when spawn runs from an isolated orchestrator home. Relative paths resolve from the repository root. Sandbox grants use real paths, including symlink targets. A `sandbox.read` path that resolves to the whole home, or to a directory that holds it such as `/`, refuses dispatch. Environment values are literal strings and do not expand `~`, `$VARIABLE` or commands. Variable names use letters, digits and underscores and cannot begin with a digit. `HOME`, `USERPROFILE`, `PATH`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR` and `TOWER_CRANE_*` are reserved so environment settings cannot replace the isolated home, command shims or task identity. NUL bytes are refused.

Sandboxed claude and codex children read nothing under the original user's home but the [home reads](../ladder.md#home-reads), so every credential store there is hidden without a list of them: the default locations, a file an environment variable, setting, `env_file` or profile key points at under the home, and any tool's dotfile. Paths outside the home are not covered. The list is computed at spawn from existing real paths.

<a id="command-environment"></a>A sandboxed codex agent's `config.toml` sets a `shell_environment_policy` for the commands it runs: `inherit = "all"`, `ignore_default_excludes = true` and an `exclude` list. Codex matches the patterns without regard to case. They exclude `AWS_*` names and names containing `SECRET`, `TOKEN`, `PASSWORD`, `PASSWD`, `PASSPHRASE` or `CREDENTIAL`. For names made of ASCII letters, digits and underscores, the KEY patterns exclude a name containing `KEY` unless that occurrence is followed by an underscore and a digit. The exception is general: `FOO_KEY_1`, `FOO_KEY_1X` and `GIT_CONFIG_KEY_12` all pass that KEY check. Another matching word or KEY occurrence still excludes the name, so `FOO_KEY_1_TOKEN` and `FOO_KEY_1_API_KEY` do not pass. The exception preserves git's `GIT_CONFIG_KEY_<n>` entries beside `GIT_CONFIG_COUNT`; git stops when a count lacks its keys.

The policy also adds names the user's codex `.env` sets, except `PATH`, `HOME`, `USERPROFILE`, `CODEX_HOME`, `TMPDIR`, `TMP`, `TEMP`, `GH_CONFIG_DIR`, `TOWER_CRANE_*`, `GIT_*` and `XDG_*`. These names bypass only the additional `.env` exclusion, not the credential-name patterns: `GIT_TOKEN` is still excluded. The policy filters names, not values. A credential stored under a name that matches no exclusion can reach a command. The policy leaves codex's own environment unchanged; variables supplied through the dispatcher's environment, `env` or `env_file` are subject to the same command exclusions. Names from `env_file` are not added to the policy. The rendered policy replaces any the user's codex config sets, and a rung cannot set one. Unsandboxed codex agents get no policy.

A sandboxed claude agent's commands get no credential-shaped variable either. claude gives the commands it runs its own environment, which holds its provider credentials. So the monitor launches claude with `--settings` setting `sandbox.credentials.envVars`: each name, with mode `deny`, is unset for the commands claude's sandbox runs, and claude keeps it. claude takes names there, not patterns, so on each launch, retry and fallback route the monitor lists every name in claude's launch environment that codex's `exclude` list would match, whether it comes from the dispatcher's environment, `env`, `env_file` or the provider routing. Tower Crane's own variables, `PATH`, `HOME`, `TMPDIR`, `GH_CONFIG_DIR` and the `GIT_*` and `XDG_*` variables are not listed. The list holds names, never values, and is on claude's command line only, not in `settings.json`, so `env_file` names stay out of every file. On Linux, bubblewrap, which starts each command, keeps the environment claude gave it, where a command could still read it; only a name that never reaches claude is out of reach. Keep a credential a claude agent's commands must not hold out of the dispatcher's environment, `env` and `env_file`, apart from claude's own provider credential. Spawn does not set Claude Code's `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, which removes those names before the sandbox starts. In Claude Code 2.1.305 it forces the permission mode to `default`, writes empty `package.json`, lock, `.npmrc`, `.gitmodules` and `.env` files into the worktree, and makes `package.json`, the lock files, `node_modules/.bin`, `scripts/` and `.github/` there read-only to commands, so `git add -A` fails. Measured 2026-10-22 with Claude Code 2.1.305 and a local stand-in for the model API: before, a command saw the dispatcher's and `env_file`'s fake credentials; after, it sees none, while claude itself still holds them and the agent's edits, git commits and the `tower-crane` CLI work.

Sandboxed claude and codex children set `GH_CONFIG_DIR` to their isolated `HOME/.config/gh`, which links to no gh config and holds no token; their gh runs through the broker ([What the git and gh shims guard](containment.md#what-the-git-and-gh-shims-guard)). They also set `GIT_CONFIG_GLOBAL` to `gitconfig/<agent>` in the state directory, which no agent writes (a copy is the `.gitconfig` in that home), rendered from the user's global git config before the state lock and recorded in the dispatch as `gitConfig: { text, reads }` for fallback routes. The text has no `credential.*` or `http.*.extraHeader` key; `reads` names the ignore and attributes files it points at.

The supervisor applies the enforced gh path at the final launch boundary, after settings and `env_file` values, on initial launches, retries and fallbacks. A settings overlay cannot replace it.

Only global rule files, project rule files above the repository and their imports outside the repository become home reads. Trust stops when an import chain enters the repository, including through a symlink. Repository rules and imports cannot authorize reads; startup refuses a rule under the home outside the readable paths before the harness runs.

Agent launches discard `NODE_TEST_*` values from all environment sources after merging them, including on retries and fallback routes. The supervisor also drops inherited test-runner variables. A parent `node --test` runner's context must not make an agent's own test run skip every file.

The env file supports blank lines, `#` and `;` comment lines, `NAME=value`, unquoted backslash escapes and line continuations, single-quoted multiline values, and double-quoted multiline values with systemd's escapes for `"`, `\`, `$` and backticks. There is no shell evaluation, variable substitution or `export` prefix. An initial quote delimits the whole value; quotes inside unquoted text remain literal. A name set twice keeps the last value. Invalid lines, reserved names, unfinished quotes and unreadable files fail the spawn with a path and line or error code, without printing contents. The CLI supervisor reads the file once for each route and keeps those values for same-route retries; a route switch reads the target route's file and a fresh dispatch rereads it. Dry-run never reads the file. Only the path is saved in project, rung and dispatch configuration. File variable names and values are absent from generated settings, events, job files and CLI output. The monitor's state-writing subprocesses do not inherit them. `env` values from the project or a rung are stored only in `project.json`, and those of a personal fallback route only in the user file: events (including `ladder set`, `project set` and every spawn, retry, fallback and exit event), the spawn receipt, the spawn job file in `~/.cache/tower-crane` and spawn output name each variable with the value `[redacted]`. The dispatching CLI hands the values to the spawn monitor once each, however many job fields name them, in its `TOWER_CRANE_SPAWN_SECRETS` environment variable, which the monitor removes before it starts any process. Values too large for one environment entry (Linux caps one at 128 KiB, Windows at 32767 characters) go instead to a 0600 `secrets.json` beside the job file, named by `TOWER_CRANE_SPAWN_SECRETS_FILE`, which the monitor deletes when it reads it; a monitor that never starts leaves that file until the dispatch removes its spawn directory. No value travels in argv. A process listing (`ps -eww`, `/proc/<pid>/cmdline`) shows no value; a claude sandbox's own PID namespace hides other agents' `/proc/<pid>/environ`. Session resume compares routes by variable names, so a changed value alone does not prevent a resume. `test/secret-canary.test.js` places a unique canary in rung and project env, an env_file and the harness credentials, then scans every file, event, output and process listing a run leaves, on success, a harness crash, a fallback switch and a supervisor stop; its opt-in live tests (`TOWER_CRANE_LIVE_CLAUDE=1`, `TOWER_CRANE_LIVE_CODEX=1`) also probe another agent's view of a running agent's `/proc` entries and home and scan the real harness transcripts and sessions. Harness output and transcripts are persisted as usual, so agents must not print secrets or put them in prompts.

`scope` adds optional owner properties to the outer containment scope through `systemd-run --user --scope --quiet --expand-environment=no -p PROPERTY=VALUE ... -- COMMAND`; mandatory containment properties follow them. Nested launches use delegated child cgroups and preserve the ancestor caps. Every cgroup launch sets `TOWER_CRANE_SCOPED=1` after its scope is ready. Property names contain ASCII letters and digits and begin with a letter; values are non-blank strings without NUL bytes or newlines. Systemd validates property support and values. A configured outer scope requires Linux and a reachable manager; selected cgroup setup failures fail the launch. A non-delegated caller fence uses the watchdog in place and reports the fence and omitted owner properties. Dry-run prints the real containment runner or systemd argv, limits and scoped environment without launching a scope or creating report files. Environment expansion of command arguments is disabled so literal `$VAR` and `${VAR}` in briefs and diffs cannot expose agent environment values in prompts. Systemd versions that lack `--expand-environment=no` reject the scoped launch; there is no fallback with expansion enabled. The host CLI needs a working user systemd session. The command sandbox gets no session bus unless the owner sets `sandbox.session_bus` (`project set --session-bus true`; off by default). With it, a claude or codex worker sandbox can reach one socket: the bus at `$XDG_RUNTIME_DIR/bus`. Its commands receive `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS`. The per-spawn socket leaf stays granted independently; other runtime entries stay denied, and spawn refuses while the bus socket is missing. The grant does not make `systemd-run --user --scope` start inside the sandbox. That command connects to the user manager's socket, `$XDG_RUNTIME_DIR/systemd/private`, which stays denied. A live run that granted that socket as well still failed with `Failed to connect to user scope bus via local transport: No data available` from a claude sandbox on systemd 259, and the cause is not known. The risk: a sandboxed command that talks to the bus can start a user unit, and the user manager runs that unit outside the command sandbox, as the user. The unit reaches what the user reaches: the owner key, which every sandbox hides; the gh, claude and codex logins; the user's other files and services. The sandbox confines nothing for such a command. Turn it on only for a project whose commands need the session bus. Codex's sandbox blocks Unix socket connections only with network off; Tower Crane runs it with network on, so before 2026-10-14 every codex agent could reach the bus and run a command on the host with `systemd-run --user`, measured with codex-cli 0.162.1. Both profiles now hide `/run` whole, the bus included unless this setting grants it.

Both rendered sandboxes enable network access, including TCP loopback binds and connections. The opt-in real Codex worker test in `test/sandbox-extensions.test.js` checks a loopback server and client along with the toolchain-cache lock and environment-file delivery.

<a id="host-tmp"></a>On Linux, claude's command sandbox hides the host's `/tmp`, where X11, session bus and agent sockets can live, with read exceptions. `hostTmp` reopens every existing outside-home `agentReads` path under `/tmp`: the worktree, git directories, writable directories, agent home, state directory, plugin, Node and harness paths, git-config reads, trusted rules, `sandbox.read` grants and gate paths. It also reopens a retained caller temp directory under `/tmp`, selected from the launch environment after `env` and `env_file`. Existing PATH entries there and outside the user's home contribute their parent as an install prefix, except an entry directly inside `/tmp` contributes itself. A PATH entry equal to `/tmp` therefore contributes `/`. These are directory grants, not a check that the contents belong to this agent. Claude's own temp paths are granted separately.

If an outside `agentReads` path or a retained caller temp directory equals or contains `/tmp`, `hostTmp` adds no `/tmp` denial. In particular, a retained caller `TMPDIR` of `/tmp` keeps claude's proxy sockets reachable. Claude's Read, Grep and Glob tools still read `/tmp`; they cannot connect to a socket, and a deny rule would take no exception for a worktree there. With `allowAllUnixSockets`, a command can connect to sockets in reopened paths. Codex does not mount `/tmp` by default, but explicitly granted paths there can be mounted. The Linux `hostTmp` rule does not apply on other platforms.

Inside a worker sandbox there is no root mapping: the harnesses launch bwrap with `--unshare-user` and no `--uid`, so a root-owned host file appears as uid/gid 65534, and a test that asserts root ownership fails there. Gate commands run on the host, outside the sandbox, so the tests gate sees the real ownership of the submitted commit. Tests that need the host are listed in `tests.host_only` (see below).

Spawn replaces the inherited `TOWER_CRANE_SANDBOX` value with `1` for sandboxed claude and codex roles and `0` for unsandboxed roles and other harnesses. The board browser test helper uses it to disable Chrome's nested sandbox under the outer command sandbox. Only sandboxed launches redirect browser HOME, crashpad, cache and shared-memory temp files into a per-browser temporary directory; no extra writable paths are granted. Host launches retain the original environment, ignored stderr and flags, including the existing root `--no-sandbox` exception. See [ladder.md](../ladder.md#agent-files-and-homes) for the opt-in live worker probe.

Supervision defaults are `retries: 5`, `backoff_ms: 30000`, `max_backoff_ms: 600000`, `stall_ms: 300000`, `usage_ms: 30000`, and `progress_paths: []`. `usage_ms` is how often the supervisor reads live usage (see `spend.entries`). Values below `1000` are clamped to `1000` ms when the rung runs. A monotonic deadline bounds periodic reads even when state-file notifications wake the supervisor; unchanged readings write nothing. Each launch resets the deadline, and every completed attempt gets a final reading before any retry or fallback. The 2026-10-07 Bedrock/Luna incident lasted more than ten minutes and ended worker-T8-1 attempts 2 and 3 with a rate-limit and temporary-unavailability error ([incident receipt](https://github.com/agent-sh/tower-crane/pull/21#issuecomment-6027888067), [recorded harness fixture](https://github.com/agent-sh/tower-crane/blob/main/test/fixtures/bedrock-outage.json)). Five additional reruns wait 30, 60, 120, 240 and 480 seconds, totaling 930 seconds (15 minutes 30 seconds). This extends recovery past that observed window while bounding the paid loop at six attempts. Harness-internal reconnect time adds to the scheduled waits. Each delay remains below the ten-minute cap; rungs with larger budgets reach that cap. The supervisor keeps the lease throughout the waits. A five-minute quiet interval avoids flagging brief pauses between tool calls. A stall requires both stale progress and unchanged CPU ticks, so a busy build remains running.

`progress_paths` adds relative files or directories inside the worktree to the durable log and claimant events that always count as progress. Directory checks skip symlinks, `.git`, `.tower-crane` and `node_modules`. Absolute paths and `..` components are refused. Linux samples the harness and descendant CPU ticks. Without CPU metadata, the supervisor keeps the lease but does not infer a stall from quiet output alone.

`fallbacks` lives only in the user file `~/.config/tower-crane/config.json` (or `TOWER_CRANE_CONFIG`), under `ladder.RUNG.fallbacks`. For example, `{ "ladder": { "hard": { "fallbacks": [{ "harness": "codex", "profile": "astra", "effort": "high" }, { "harness": "claude", "model": "fable", "effort": "high" }] } } }` applies the same personal routes to every project's hard rung, even when the project defines its own primary. A user rung containing only fallbacks does not replace the primary defaults. Remove the field or set `[]` to disable it. `ladder set RUNG --fallbacks JSON` replaces that personal list; `--clear fallbacks` removes the override and `--fallbacks '[]'` empties it. These edits cannot be combined with primary-field edits. They preserve other personal settings and project primaries; clearing a fallback-only rung removes the empty rung so defaults still resolve. Project fallbacks remain refused. Each changed route field uses the primary field's authority class, including clearing owner-required fields. Tools, MCP opt-ins and newly unconfined routes use the same checks as primary routes. A one-use approval binds the user file path, rung and complete replacement list; invalid lists and refused requests write neither the user file nor a setting audit.

An owner fallback write replaces the whole list and retires matching requests independently of which route fields currently differ. This includes writes that only tune a model or repeat the existing list. Authorization and audit still classify the actual changed fields, so operational orchestrator tuning leaves an unused owner approval pending.

Personal fallback authorization compares the old and proposed personal routes for that rung. A grant on a project's primary cannot authorize a grant in this shared file. Inherited and explicit harness selections are distinct: an inherited route does not authorize forcing that harness in another project. A route without a harness is checked across every harness compatible with its fields, since other projects may resolve it differently. New privileged tools, unconfined routes and argument grants require the owner under the existing authority rules; existing personal grants still permit operational model tuning. Specifying a sandboxed harness keeps the route's interpretation fixed.

Claude primaries and personal routes may name `provider: "anthropic"` or `"bedrock"`. For an Anthropic hard primary on Opus, `{ "ladder": { "hard": { "fallbacks": [{ "provider": "bedrock", "model": "opus" }] } } }` tries the same model on Bedrock first after the primary exhausts its outage retries. Reverse the provider names for a Bedrock primary. No provider switch is enabled by default. Without `provider`, Claude keeps the user's harness provider settings.

An explicit Claude provider overrides every inherited provider selector (`CLAUDE_CODE_USE_BEDROCK`, `_VERTEX`, `_FOUNDRY`, `_ANTHROPIC_AWS`, `_ANTHROPIC_GOOGLE_CLOUD`, `_MANTLE` and `_GATEWAY`) and model settings. A Bedrock route keeps an inherited `CLAUDE_CODE_USE_MANTLE`, which selects a Bedrock endpoint. The aliases in `BUILTIN.claude_aliases` (`lib/ladder.js`, snapshot in `docs/builtin-ladder.json`) resolve to full ids: `opus`, `fable`, `sonnet` and `haiku` to `claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5` and `claude-haiku-5-5`. Bedrock uses `global.anthropic.` model ids; Anthropic uses plain ids. An `ANTHROPIC_DEFAULT_<ALIAS>_MODEL` pin the user already set is kept, and the table fills only the pins that are missing. On a Bedrock route, a bare word that is not a table alias is refused at `ladder set`, with the valid aliases listed. Regional Bedrock ids supplied on an explicit route are converted to the global inference profile. Provider routing settings come from the original user's Claude config and environment, even through isolated homes. Bedrock receives absolute paths to that user's AWS config and credentials files, never copies of their contents.

`ladder show` reports missing configuration for explicit Claude providers. Anthropic needs the presence of `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `CLAUDE_CODE_OAUTH_TOKEN` in the inherited or configured launch environment, a linked `.credentials.json` login file, or the user's `apiKeyHelper`. Bedrock needs an AWS region from environment, Claude settings or the selected AWS config profile, plus local authentication configuration: AWS credential variable names, web identity or container credential variable names, an AWS credentials file, SSO/role/process configuration for the selected profile, or a Claude AWS helper. Checks include project and rung `env` using variable names and safe routing fields; they do not inspect credential values, execute helpers, validate logins or query provider access. A configured `env_file` defers readiness to the real launcher, which reads the file and fails on read or parse errors. Preview and `ladder show` never read that file. Generated Claude settings leave AWS routing in the launch environment so file and literal overrides take effect. Credentials stored only in Claude settings env must already be inherited by the spawning process. Missing primary configuration refuses dispatch; unavailable fallback providers are skipped by the existing supervisor. A rung that names a [credential](#credentials) needs no credential variable or helper: spawn reads the store before launch, and `ladder show` reports a credential the store cannot give.

Every spawned harness receives `TOWER_CRANE_CONFIG` with the absolute path resolved in the spawning environment. This preserves the original user file through isolated orchestrator homes, nested worker dispatches and fallback switches, including when the caller uses the default location or a relative override.

A fallback without `harness` uses the primary route's resolved harness. It inherits the primary `supervision` unless it names its own. Research Claude fallbacks also inherit the primary `web_mcp` unless they supply their own. Other harnesses do not inherit it. An inherited or explicit web MCP cannot combine with `mcp`. Other route fields are independent, so model, profile, provider, args, tools and environment settings from one route cannot bleed into another. Project environment, sandbox and scope defaults still apply to each route. Nested fallback lists and malformed route shapes are refused. `ladder show` prints the list and its user-file source; JSON rungs carry `fallbacks` and `fallbacks_from: "user"` when configured. Its `problems` reports routes with incompatible harness fields, missing models, missing executables or unavailable Codex profiles. Profiles may come from `[profiles.NAME]` in `config.toml` or `NAME.config.toml`; a profile needs a model there, in the base config, or in the route. These local checks do not query providers for model access. Unavailable routes do not invalidate the primary rung: the supervisor skips them and routes that fail preparation, then tries the next personal route. If none remain, it records the primary or last running route's blocked exit. The list is captured under the spawn lock with the primary route; later user-file edits apply to new dispatches.

A command fallback may use placeholders in its executable, such as `["{cwd}/scripts/fallback", "{prompt}"]`. `ladder show` defers executable lookup for templates that need task context. During fallback preparation, the supervisor expands the command and checks the resulting executable before launch; a missing expanded executable is skipped.

Every rung must be able to run on the harness it resolves to: a `codex` rung needs a `model` or a `profile`, `claude`, `opencode`, `agy` and `pi` rungs need a `model`, and a `command` rung needs a `command`. A field the resolved harness does not use (a `profile` on pi, say) is refused, not ignored, so a switch of harness never quietly runs a model nobody chose. A ladder write is refused when it leaves a rung unable to run that could run before; `spawn` refuses a rung that cannot run, and `validate` reports every such rung. Loading checks only the shape (known rungs, harnesses and field types): a rung that falls back to the user file can break when that file changes, and the project must still load so `tower-crane ladder set` can repair it, one rung at a time.

Defaults come from the user file `~/.config/tower-crane/config.json` (or the path in `TOWER_CRANE_CONFIG`), which holds `{ "harness", "ladder" }`, else from the built-in ladder in [builtin-ladder.json](../builtin-ladder.json). The built-in model `claude-haiku-5-5` is `global.anthropic.claude-haiku-5-5` on Bedrock. `tower-crane init` copies primary settings into the project, excluding personal fallbacks; an init by anyone but the owner leaves out what only the owner grants ([Authority](decisions.md#authority)). The default harness and each primary rung come whole from the first layer that has them: project, user file, built-in. Personal fallbacks always come from the user file, which is read even when the project supplies every rung. A project that leaves a primary rung out follows the user file for it; `tower-crane ladder show` prints each source. `tower-crane ladder save-user` writes the default harness and each primary rung the project defines to the user file, preserving its personal fallbacks and any other keys. It never writes a value the project did not set: a default harness or rung the project leaves out keeps whatever the user file has, or stays unset so the built-in applies.

The user file also accepts `"browser_kit": ["playwright"]`, a deduplicated list of MCP server names. The omitted default is `["playwright"]`; `[]` disables automatic server attachment. `browser-kit set --servers JSON` writes this setting as the explicit owner or through a one-use owner approval bound to the resolved user file and server list. It is not copied into projects and `ladder save-user` preserves it. Every dispatch of a `design` task or a task with `needs: ["browser"]` resolves the kit from the original user's file, even inside an isolated orchestrator home, and merges its servers with explicit rung `mcp`. Claude/Codex/agy spawns attach those named user server definitions and pre-approve their tools; kit server env and headers are excluded. Missing definitions and unsupported harnesses omit those kit servers and continue with a warning. Only a task explicitly declaring `needs: ["browser"]` is refused when no primary or fallback route can attach a configured kit server. Each browser-task `spawn` and `spawn fallback` event carries `browser_kit: { requested, attached, omitted, warning }`, also shown in spawn output. Other tasks receive no automatic kit, and no task gets wider filesystem grants: installed Chrome is read-only and its test profiles use existing temp writes.

`standards` is `default` (the profile shipped with Tower Crane) or a path to a Markdown file. A path is checked for readability and recorded relative to the repository root; only the default gates apply for now.

`ci` is optional. `ci.ignore_apps` is an array of GitHub app slugs, for example `{ "ci": { "ignore_apps": ["claude", "cursor"] } }`, whose check suites and check runs `tower-crane check ci` skips. It is for apps that open a check suite on every push and never report on it, such as review bots; their suites stay queued and would otherwise hold the gate forever. It defaults to empty, and Tower Crane never infers which apps to skip. Set it with `tower-crane project set --ci-ignore-apps '["claude","cursor"]'`. Entries must be non-blank strings; the CLI trims leading and trailing whitespace before storing them. `--ci-ignore-apps '[]'` stores an empty list; `--ci-ignore-apps null` removes `ci.ignore_apps`, so no apps are skipped.

`ci.required` is an optional array of non-blank strings naming hosted check runs or literal, case-sensitive prefixes. Each entry must match at least one non-ignored run at the submitted sha. Every matching run must have status `completed` and conclusion `success`; skipped, neutral, unfinished and capped runs do not satisfy it. A prefix requires all matching runs that exist, so enumerate full matrix job names to detect a missing member. Only the latest run of each check name and app counts, ordered by `started_at` and then `id`; a run that has not started has no `started_at` and is current when its `id` is above the latest started run's. A rerun or a reopened PR supersedes the older runs of that name, so a failed run that a later run replaced does not block. For suites without workflow-run mapping, a completed, failed suite does not block when every run it reports was read and superseded by a newer run; an unfinished suite, or one whose reported runs were not all read, still blocks. Configure it with `project set --ci-required JSON` or `init --ci-required JSON`; entries are trimmed. An empty list, `null` or an absent field imposes no named-run requirements. The CLI preserves other `ci` fields; `--ci-required null` removes only `required`. Malformed lists fail the hosted CI gate.

Same-repository Tower Crane PRs and pushes to `main` run one hosted job, `checks (shared files)`, so the project pins `["checks (shared files)"]`; tasks run their crucial and mapped suites in the local tests gate. Fork PR test jobs are `["test (ubuntu-latest, node 26, shard 1/3)","test (ubuntu-latest, node 26, shard 2/3)","test (ubuntu-latest, node 26, shard 3/3)","test (ubuntu-latest, node 24, shard 1/3)","test (ubuntu-latest, node 24, shard 2/3)","test (ubuntu-latest, node 24, shard 3/3)","test (windows-latest, node 26, shard 1/4)","test (windows-latest, node 26, shard 2/4)","test (windows-latest, node 26, shard 3/4)","test (windows-latest, node 26, shard 4/4)"]`. To require every fork PR shard, use this ten-name list as `ci.required`. Fork PRs, `v*` release tags, the daily schedule and manual runs run those ten test jobs, `repeat (windows-latest, node 26)` for the Windows flake repeats and the two proofs. Requiring a test job name at a same-repository PR head fails the CI gate because those PRs run only `checks (shared files)`.

Hosted CI fetches all pages of GitHub Actions workflow runs for the submitted head when a non-ignored `github-actions` suite exists. Runs are grouped by workflow path (name when path is absent) and event. The latest run is ordered by `created_at`, then `id`; missing timestamps fall back to `id`. Older runs with a distinct `check_suite_id` are recorded as superseded in the receipt summary. Their Actions suites and linked check runs are excluded even when the old jobs are absent from the commit check-run listing. The latest suite still must be green. Different paths, events, heads and apps cannot supersede each other; missing workflow identity or event cannot prove supersession. Supersession also requires the latest run to map to a listed Actions suite; unmapped suites retain the check-run rule above. Failure to fetch workflow runs fails the gate.

`ci.capped_review` optionally lists `{ "app", "pattern" }` rules. The app slug must be exact without surrounding whitespace, and the pattern is a nonempty case-insensitive regular expression matched against a completed failed run's output title and summary. A matched cap is nonblocking only outside required jobs. Its failed suite also needs its complete set of runs to be green or capped. Other failures and unfinished checks still block; a capped review alone cannot prove CI ran. Absent or null rules default to `[]`; malformed rules fail closed.

Hosted CI first verifies the PR's head and reads `mergeable` and `mergeStateStatus`. `CONFLICTING` or `DIRTY` fails because GitHub does not run `pull_request` workflows on conflicting PRs. Unknown or missing mergeability requires a later retry. `MERGEABLE` with a known state such as `BLOCKED` permits checking CI, leaving reviews and merge protection to their own gates. Tasks without a PR still enforce required runs at their submitted sha. With `ci.local` configured, the local merged-tree check applies instead.

A `workflow_dispatch` run at the head, from `ci dispatch` or started by hand, is not a PR check. Outside a hotfix, the CI gate and submit set aside its check suite and the check runs in it, using the Actions workflow runs at the head, before they judge the PR's checks. GitHub's default check-run list keeps only the newest run of each name, so with such a run at the head they read the check runs again with `filter=all` first, and name it in the summary as `Not PR checks, set aside`. Its pull-request-only jobs skip, so a skipped `checks (shared files)` there never stands for, or replaces, the PR's run of that job, and its failing or pending full-matrix jobs never block the PR. A hotfix keeps judging its base's push, scheduled and manual runs as before.

`ci.dispatch` optionally configures `ci dispatch`: `{ "workflow": "ci.yml", "per_hour": 4 }`. `workflow` is a workflow file name under `.github/workflows` or its numeric id; without it, `ci dispatch` uses the one workflow whose `pull_request` runs are on the task's branch and refuses when there are none or several. `per_hour` is a positive integer, the dispatches one task may record in an hour, default 4. Unknown keys and other values are refused. Set it with `project set --ci-dispatch JSON`; `null` removes it. Other fields under `ci` are preserved.

`ci.capped_review` is an array of `{ "app": "<GitHub app slug>", "pattern": "<regular expression>" }`, for example `{ "ci": { "capped_review": [{ "app": "revuto-review", "pattern": "reached the \\d+-round review limit" }] } }`. The app slug must be exact and have no surrounding whitespace. A completed check run with conclusion `failure` from that app is nonblocking when its output title or summary matches the case-insensitive regular expression. Output text is not searched because review findings can quote a cap message. The gate summary names every matched run and app, including when another check still blocks. At least one run outside ignored apps and matched caps must exist; a capped review alone does not prove CI ran. The linked completed, failed suite is nonblocking only when all its reported runs were read and each is green or a matching capped review. Other suites from that app, other failures, cancellations and unfinished checks still block. This defaults to empty; malformed rules or invalid regular expressions fail the gate. It implements the project's policy that a capped review bot can be replaced by the independent review, whose separate acceptance gate still applies.

`tower-crane project set --ci-capped-review '<json array>'` sets it (`null` clears it). The ci evidence keeps the matched runs as `capped_review`, which lets the orchestrator waive review for that head ([Authority](decisions.md#authority)).

`tests` is optional too. `tests.mode` selects how `tower-crane check tests` verifies the submitted commit:

| Mode | Behavior |
|---|---|
| `prove` (default) | The command must pass at the submitted sha. A nonempty diff of only tests and kept files uses run-only semantics. Otherwise, code tasks must add or change a test file. Keep changed tests and build files, revert other changed files to the merge base, and require the command to fail. A non-code task that changed no tests passes after the head run. |
| `run-only` | The command must pass once at the submitted sha. No changed test path or merge base is required, and no file is reverted. This handles Rust inline `#[cfg(test)]` modules in source files that also contain production code. |
| `none` | Skip the suite; any supplied `--cmd` must still match the pin. Verify that the submitted sha resolves to a commit, then record ok evidence naming the policy. No test command or temporary worktree is needed. |

In `prove` mode, the gate lists every changed file against the merge base (`base...head`), including added, deleted and both sides of renamed files. If the nonempty list contains only paths matching `tests.paths` (or the default test layouts) or the keep set (default manifests and lockfiles plus `tests.keep`), it runs the pinned head command once. No changed test file or scoped proof command is required, so fixture-only fixes covered by `tests.keep` can pass. The receipt records `mode: "run-only (test-only diff)"`, `changed_files` with the complete path list, and `head_mode: "full"`. The summary names the mode and paths. A failing head still fails the gate. An empty code diff still fails; any path outside the test and keep sets retains full prove behavior, with `receipt.mode: "prove"` and `changed_files`. The audited `tests_mode` remains `prove`, preserving policy checks.

`tests.by_kind` overrides the project mode for a task kind (`code`, `docs`, `research`, `design`, `ops`). Missing kinds inherit `tests.mode`, which defaults to `prove`. For example, `{ "tests": { "mode": "prove", "by_kind": { "code": "run-only" } } }` lets a Rust project's code tasks use its inline test suite without a revert proof. Only code tasks require tests evidence for acceptance, so kind overrides affect required tests gating only for code. Docs, research, design and ops already need independent review without a tests gate; their overrides apply only when someone explicitly runs `check tests`. These are owner-controlled project settings, not per-invocation bypass flags.

`tests.expensive: true` keeps an effective `prove` mode and runs the head suite once at the submitted sha, using mapped suites when configured below. When there are files to revert, `check tests` requires pinned `gates.tests_proof_cmd` containing `{tests}`. The gate substitutes the shell-quoted paths of the added or changed test files. The scoped command must pass at head and fail after non-test files are reverted, with the same build-file keep rules. This preserves failing-before proof without running the full suite twice, and a broken scoped command cannot count as proof. This is the documented default for projects: the orchestrator sets it at `init`, for a Node project with `--tests-cmd "npm test" --tests-expensive true --tests-proof-cmd "node --test {tests}"`, then uses `check tests ID`. Once a full run has built a coverage map, the default is crucial mode (below): `--tests-crucial JSON` and the map pinned with `tests map refresh`, so no task runs the full suite. Leave it off only for a suite cheap enough to run twice. The project must have a runner that can select its changed test files; there is no inferred runner across languages. Reviewers check that the scoped command actually runs those tests. `run-only` and `none` keep their respective behavior. False, null or an absent field leaves the normal full-suite proof.


`tests.map` is an optional pinned object from repository source paths or globs to arrays of literal test paths, for example `{ "lib/gates/tests.js": ["test/gates/tests.test.js"], "**/*.md": [] }`. Set or replace it with `project set --tests-map JSON`; `null` clears it. Matching globs use the `tests.paths` syntax and union their suites. Empty arrays explicitly cover paths needing no additional suites. Source and test paths must be relative without parent components, backslashes or NUL bytes; tests cannot be globs. Invalid maps refuse before execution. It is operational at `init` and `project set`, including unchanged values and clearing.

With effective `prove` mode, `tests.expensive: true`, a map, a scoped `{tests}` template and a nonempty `ci.required` naming the full-suite job, the head run uses the changed test files plus mapped suites. A task without a PR retains the full head command because hosted CI is not required. A configured `ci.local` retains the full head command because hosted required jobs no longer run. Helpers and fixtures need source mappings even under broad test globs. The orchestrator pins the job that actually runs the full suite; job contents cannot be inferred from its name. Every changed non-test path needs a map entry, including deleted paths, test support and kept build files. Unmapped paths, missing or non-test mapped paths at head, or an empty selection fall back to `gates.tests_cmd`; missing prerequisites retain that full run too. Deleted tests are excluded. The scoped head and failing-before proof still run only the added or changed tests, with the same reversion and build-file keeps. `run-only` and `none` are unchanged.

`tests.crucial` is an optional pinned array of literal test paths, distinct, relative and without globs, that every head run includes whatever changed. Set it with `project set --tests-crucial JSON`; `null` clears it. It is operational at `init` and `project set`. With effective `prove` mode, `tests.expensive: true`, a pinned `tests.map`, a nonempty `tests.crucial` and a scoped `{tests}` template, the gate runs in crucial mode: the head run is the crucial files, the added or changed tests and the mapped suites of every changed path, expanded into the scoped template, and no full suite runs. Crucial mode needs no PR, `ci.required` job or hosted full run. A crucial path that is not a test file at head fails the gate with `config_failure: {key: "tests_crucial"}` before anything runs. A mapped suite missing at head is left out and listed in `receipt.mapped_missing`. The failing-before proof is unchanged: the scoped command runs the added or changed tests at head and again with non-test files reverted. A test-only diff runs the crucial selection once instead of the full head command, keeping `mode: "run-only (test-only diff)"`. The merge queue's head check runs the same selection, for the files the entry's top task changes against the base tip (`tip...head`), on the merge commit. A task whose effective mode is `run-only` or `none` gets no selection in its tests gate, so its head check runs the full `gates.tests_cmd` as outside crucial mode.

A changed path that no `tests.map` entry covers is a coverage gap in crucial mode, not a reason for a full run. A deleted path needs no entry. An entry covers a path when one of its suites is a test file at head or when it is an explicit empty array. The gate settles each gap by running the task's added or changed tests at head under V8 coverage (`NODE_V8_COVERAGE`, which their child processes inherit), as the scoped proof when there is one: every gap must be a file those processes ran. A gap they do not run, or a gap with no changed test, fails the gate with `worker_failure: true` (`confirmed_failure` for a merged hotfix) and a summary that starts `coverage gap:`, names the files, and says to add a test that runs them. A file no test can run, such as documentation or data, needs a declared map entry instead (an empty array or the suites that read it). The receipt lists the gaps in `coverage_gaps` and the changed tests in `proof_tests`; the summary names the files the coverage run reached. Only JavaScript and TypeScript that Node runs show in V8 coverage; other runtimes rely on map entries.

The map for crucial mode comes from measured coverage. `node scripts/tests-coverage-map.js run --dir DIR -- CMD` runs a node:test command with each test file's coverage kept apart (`lib/tests-coverage-scope.js`, preloaded into every test file process, points its children's `NODE_V8_COVERAGE` at a directory of its own), so code a test reaches only through the CLI it spawns, or loads by name, counts for that test. `test/run.js` does the same when `TC_TEST_COVERAGE_DIR` is set. The result, `tests-coverage-map.json`, is `{sha, tests, map}`: the commit it was built at, the test files that ran and each repository file to the test files that ran any of its code. Test files are not sources. `tower-crane tests map refresh --from-run RUN_ID` downloads a run's `tests-coverage-map` artifact with `gh run download` (or `--file FILE` reads a copy) and pins `tests.map`: measured entries replace the pinned ones, while entries coverage cannot measure, globs and paths that are not JavaScript or TypeScript, stay as declared. It is operational (`tests.map`) and records a `tests map refresh` event with `{run | file, sha, measured, declared, tests}`; a map that is not that shape, or that has glob sources, refuses without a write. The orchestrator runs it after each daily run.

Tests evidence carries `receipt.head_mode` (`mapped`, `crucial` or `full`), `head_reason`, and `head_tests` for mapped and crucial runs. Its summary names the same selection and fallback reason. While a map is pinned outside crucial mode, `gate_policy` also snapshots `tests_map`, `ci_required` and `ci_local`; changing any makes old receipts stale. With `tests.crucial` set it snapshots `crucial`, and in crucial mode it leaves the map and CI settings out: the map is refreshed after every daily run, and binding receipts to it would rerun every open task's tests gate each day. A crucial receipt counts while its head command is the template expanded with `head_tests` and those include every pinned crucial path. Head command receipts must match the pinned template expanded with `head_tests`, and proof receipts still match `proof_tests`. The committed repository seed is `tools/tests-map.json`, generated from imports with `node tools/tests-map.js` (or `node tools/tests-map.js SHA` for a submitted head); shared CLI infrastructure keeps all suites, and uncovered executable paths stay unmapped. The orchestrator pins the seed through the CLI after checking coverage.

Set these fields with `tower-crane project set --tests-mode prove --tests-by-kind '{"code":"run-only"}'` for inline tests, or `project set --tests-expensive true` for a full suite with scoped proof. `--tests-mode null` restores the project default; `--tests-by-kind '{}'` or `--tests-by-kind null` clears kind overrides; `--tests-expensive false` or `--tests-expensive null` restores full-suite reversion. A kind map replaces the whole map and accepts only known kinds with one of the three modes. The expensive flag accepts JSON true, false or null. Malformed mode settings fail the gate before a suite runs.

On both `init` and `project set`, `--tests-mode`, `--tests-by-kind`, `--tests-expensive`, `--tests-paths`, `--tests-keep`, `--tests-host-only`, `--tests-map` and `--tests-crucial` are operational ([Authority](decisions.md#authority)): the orchestrator or the owner, with explicit identity from `--agent` or `TOWER_CRANE_AGENT`. Terminal fallback to owner is insufficient. Setting, clearing and unchanged values all require that identity. Refused calls write no state or events, including other settings supplied in the same call; a refused init creates no state directory. Workers request policy changes from the orchestrator with `tower-crane msg --to orchestrator` or a task note.

The `prove` mode keeps changed declarative manifests and lockfiles at the submitted sha so the reverted tree can still build. Only non-test paths can be kept as build files, and the summary names each one. Test paths and keep globs are used only by `prove`; `run-only` runs the submitted tree intact.

The default keep set matches these basenames in any directory, without case sensitivity:

No general code suffix or arbitrary `*.lock` suffix is kept. Executable build files, including `Makefile`, `setup.py`, Gradle scripts, `*.bzl`, bundler configs, `flake.nix` and MSBuild projects, are reverted by default. A project can explicitly extend the keep set with `tests.keep`, for example `{ "tests": { "paths": ["test/**"], "keep": ["Makefile", "tools/**/*.gradle"] } }`. Set it with `tower-crane project set --tests-keep '["Makefile","tools/**/*.gradle"]'`. The globs use the same repository path rules as `tests.paths` below. A matched non-test path stays unreverted, even if it contains code, so keep these globs narrow and review them as part of the project's gate policy. An empty list or `--tests-keep null` restores only the defaults; it does not disable them. A path classified as a test is always excluded from the build file list.

By default a file is a test when it sits under a `test/`, `tests/`, `spec/`, `specs/` or `__tests__/` directory in any case (`Tests/`, `Test/`), under a directory named like `MyApp.Tests`, `MyApp.UnitTests` or `integration_test`, or a CamelCase one like `AppTests` or `androidTest`, or when its name looks like `foo.test.js`, `foo_test.go`, `foo_spec.rb`, `foo.spec.ts`, `test_foo.py`, `FooTest.java`, `FooTests.swift`, `FooSpec.scala`, `FooIT.java` or `TestFoo.java`. CamelCase forms need their capital, so `latest.js` and `contest.py` stay code. Fixtures and helpers are support code, not tests, even under a test directory: files under `fixtures/`, `__fixtures__/`, `__mocks__/`, `testdata/` or `helpers/` directories, and files named like `helpers.js`, `test_helper.rb`, `stack-fixture.js` or `conftest.py`, are reverted like other code, and editing one is not coverage for a change. `tests.paths`, for example `{ "tests": { "paths": ["src/test/**", "**/*Test.java"] } }`, replaces those defaults with the project's own globs over repository paths: `*` and `?` stay within one directory, `**/` spans any number of directories, `{a,b}` matches either, a trailing `/` takes everything beneath, and matching is case-sensitive. Set it with `tower-crane project set --tests-paths '["src/test/**","**/*Test.java"]'`. It must be a non-empty array of non-blank strings; the CLI trims leading and trailing whitespace before storing them. `--tests-paths null` removes `tests.paths` and restores the default layouts; `[]` is invalid.

`tests.host_only`, for example `{ "tests": { "host_only": ["tests/lab/**"] } }`, lists the test files that cannot run inside a worker sandbox. It takes the same globs as `tests.paths` and is set with `tower-crane project set --tests-host-only '["tests/lab/**"]'`; `[]` lists none and `null` clears it. Every spawned role gets the list as JSON in `TOWER_CRANE_HOST_ONLY`. A sandboxed run (`TOWER_CRANE_SANDBOX=1`) skips the matching files: the runner must honor the variable, and this repository's `test/run.js` does. While the list is set, that runner refuses a directory or a glob selection, since it expands one after the skip and could reach a listed file; a worker names the test files one by one. The worker brief names the same globs under `## Host-only tests`. The tests gate sets `TOWER_CRANE_SANDBOX=0` and drops `TOWER_CRANE_HOST_ONLY` for its commands. It sets `TOWER_CRANE_TEST_EXCLUDE` to the host-only globs for ordinary commands; the runner must honor this JSON exclusion list, and this repository's `test/run.js` does. The gate selects tracked host-only files through `tests.paths` or the default test layouts, excluding fixtures and support files. Default host-only selection also requires a source or test-format suffix (for example `.js`, `.py`, `.sh` or `.feature`); projects with other formats or extensionless tests select them through `tests.paths`. It runs each selected file separately using pinned `gates.tests_proof_cmd` with `{tests}` replaced by that file, including at head and after reversion when the file is selected for proof. Setting `tests.host_only` requires that pinned command. Host-only files run at head even when the ordinary head suite is mapped.

`tests.host_env` is an operational map of environment variable names to string values, set with `project set --tests-host-env '{"TOWER_CRANE_LIVE_CLAUDE":"1","TOWER_CRANE_LIVE_MODEL":"claude-haiku-5-5"}'`. Names use letters, digits and underscores, starting with a letter or underscore; values cannot contain NUL. `{}` sets an empty map and `null` clears it. The gate applies the map only to separate host-only commands, clears their exclusion list, and keeps the gate sandbox markers authoritative. It does not pass this setting to spawned agents or ordinary suite commands.

On Linux, a separate host-only command gets a short `TMPDIR`, `TMP` and `TEMP` of its own when the gate scratch directory is too deep for a live harness's sandbox socket. Claude Code's Linux sandbox listens on `<TMPDIR>/claude-socks-<16 hex>.sock` (or the one byte shorter `claude-http-` name), and socat takes a socket path of at most 108 bytes, so `TMPDIR` must be at most 73 bytes. The short directory is a fresh `tc-XXXXXX` under the user's `~/.cache`, with the home taken from the password database rather than `HOME`, else under `XDG_RUNTIME_DIR`. It is removed when the command ends. When no such directory fits and is writable, the gate refuses before running any command, with a `config_failure` on `tmp_root`. A `TMPDIR` named in `tests.host_env` is used as given. Ordinary suite commands keep the gate scratch.

A tests receipt has `host_only: {run, skipped, unreported, results}` when host-only globs are configured. The first three arrays name files. Each result has `{file, ran, skipped}` with executed and skipped case counts from TAP or Node spec summaries; TODO cases count as skipped. A file with skipped cases also gets `skip_reasons`, up to five distinct reasons, each redacted like the gate output and then cut to 200 characters, from its TAP `# SKIP` or spec `﹣ ... # reason` lines, and the refusal for a changed host-only file lists each file's counts and reasons. A file with both executed and skipped cases appears in both arrays. Missing or inconsistent summaries produce null counts and an `unreported` entry, so exit zero alone is not proof. Prove mode rejects a changed host-only file with no reported executed cases. Run-only and test-only diffs still allow skips and report them in the receipt.

When a head or scoped proof command fails with named tests, the base rerun reads their files from the kept head output: Node spec `test at FILE:LINE:COLUMN` summaries or TAP failure locations. Every failing name must have a safe repository path. Under the spec reporter, an aggregate suite or subtest parent without its own summary location inherits the files of its failing descendants from the streamed indentation. Every failing descendant must have a known location; an incomplete or unsafe report still falls back to the full command. Each distinct reported file runs once at the newest base through pinned `gates.tests_proof_cmd` with `{tests}` replaced by that file. Reported paths run through the selector even when git does not track them at the base, since that command can build generated tests, including a file the head first tracks. A genuinely missing file reports no matching base failure and keeps the head verdict. Host-only failures use their original separate command, keep `tests.host_env` and clear `TOWER_CRANE_TEST_EXCLUDE`; ordinary commands keep the host-only exclusion list and receive no `host_env`. Unknown or incomplete locations or a runner without a pinned file selector fall back to the original full command. The shared-name verdict stays the same.

Completed base results live under `tests-base-cache` in the resolved gate temporary root, separated by the repository's common git directory. Keys include the full base SHA, the original and selected commands, host-only globs, sorted `host_env`, host-command mode, the effective inherited environment, hostname, platform, architecture, Node version and file (or a full-command marker). The environment hash applies the same overrides as the runner and normalizes fresh scratch paths and the POSIX shell working directory. Settings are hashed, and stored output is redacted before writing. A marked lock per key makes simultaneous gates share a run; dead holders are reclaimed, live holders refreshed, and waits are bounded by the command timeout plus the metadata minute. Timeouts, signals, missing commands and runner errors are not cached. Each use prunes completed results to the two most recently used base commits, including the current base, and 64 results per repository (roughly 64 MiB at the one-MiB output limit). Active runs are protected and pruned after release. Cache eviction permits a later rerun.

The selected base commands share the original full base command's timeout budget, measured from the start of the base step. A fresh command receives the time left after worktree setup and cache waiting, and no next command starts after the budget expires. This also bounds generated suites with more files than the lease could count in git. A partially completed comparison records `base_rerun_timed_out` and leaves shared failures unchecked.

The log and summary name the selected base files, uncached attempts and cache hits. Evidence carries `receipt.base_rerun: {base, mode, files, fallback?, results, duration_ms}`; `base` is the full SHA, `mode` is `files` or `full`, and each attempted lookup or run has `{file, command, cached, duration_ms}`. A full-command result uses `file: null`. Durations include cache waiting and worktree setup and cleanup; a hit starts no command or worktree. The head still runs on every gate attempt.

<a id="native-crashes"></a>A child process that a native fault ended (a Node or V8 crash, not a JavaScript error) is not the change's doing. A reverted run is meant to fail, so it reruns only when every failing test shows such a crash: a child ended by `SIGSEGV`, `SIGBUS` or `SIGILL` with empty output. Two error forms count: a `child_process` error or result object as `util.inspect` prints it (`signal: 'SIGSEGV'` with every `stdout`, `stderr` and `output` it shows empty, and its `pid`), and a message that names the signal and ends where the child's output would follow (`exited null (signal SIGSEGV): `). TAP prints only the message. A suite or parent test that failed only through failing tests inside it (spec prints no error under it; TAP gives it `failureType: 'subtestsFailed'`) is judged by those tests; one with an error of its own, such as a failed hook, counts as a failure without a crash. Its rerun follows the rule above, and a passing one records no flaky test, since the reverted run proves nothing either way. At the head, scoped proof or a host-only file, a crash reruns as any failure does, and a test it rescued is flaky with `native_crash: true`. Every crash seen goes into the evidence and its `check tests` event as `native_crash: [{test, signal, pid, core_file?, stack?, core_error?}]`, with `pid` null when the message names none. The summary starts the command's `Rerun: ...` line with `Native crash: ...` when it saw one. `status` prints `native crashes: N in the last 7 days, last TASK at TIME` when there are any, and its JSON always carries `native_crashes: {days, count, last}`.

On Linux, when `kernel.core_pattern` pipes to apport, a CLI tests gate runs each head, scoped proof, reverted, host-only and rerun command with its soft core limit raised to the hard limit; base reruns and the host's core settings stay as they are. apport drops the crash report of nvm's node, since no package owns it, and writes its core to `/var/lib/apport/coredump/core.EXE.UID.BOOT.PID.TIME`; in a pid namespace, such as a sandbox, it drops the core too. After each command the gate takes this user's cores written since the command started. A core whose pid is a crashed child's is copied to `native-cores/` under the task's scratch (directory 0700, file 0600), recorded as `core_file`, and read with `gdb -batch -nx -ex bt [EXE] -c CORE`, passing the gate's own node as `EXE` when the core names it. Up to 40 frames of the crashed thread go into `stack`, and the copy is deleted. When gdb reads no stack, `core_error` gives its first error line and the copy stays private for a person to read until the task's scratch is removed. The core in the shared directory is emptied at once; only root may remove it there. Cores in the window that pair with no crash are emptied too. Another gate whose child crashes while this one's command runs can lose its core that way, and records the crash without it. A core can hold tokens from the process's memory, so it is never uploaded. To record a crash in Node or V8, put the stack in a Node issue draft or here, and pin a Node version that avoids the bug.

The list and tests policy flags also work with `init`. Omitting a flag leaves its field unchanged. Setting a field replaces a non-object `tests` or `ci` section, and clearing removes that malformed section. Object sections keep their other settings; clearing removes the section when it becomes empty. `project set` and `project show` text output print the policy and lists, showing `prove`, `{}` and `false` for absent mode, kind overrides and expensive settings, `default layouts` when `tests.paths` is absent and `[]` when no extra build files or CI apps are configured. Invalid input exits 2 without writing state or events, even when passed alongside valid settings.

## tasks.json

`last_event` is the id of the last event of the commit that last changed tasks.json; a commit that logs no event keeps the previous value. It sits right after `next`. Older files omit it, and null is accepted. `validate` reports drift when `events.jsonl` has no event with that id.

Optional `orphan_retirements` records orphan removals in progress as an array of `{reservation_id, path, branch, since, pid, host, start_ticks, pidns}`. `branch` may be null; `start_ticks` and `pidns` are present where the platform reports them. Under the state lock, `worktree prune --orphans` checks current task ownership and appends its reservation before any destructive Git operation. A task whose `branch` names the worktree's branch owns it even before the task records the worktree. Claim, rework, submit and preparation use the same path/branch guard as task retirement. `worktree orphan retiring` audits reservation acquisition; `worktree orphan cleanup` releases only the matching `reservation_id` and records the outcome. Failed cleanup also releases its reservation. A reservation whose process has exited holds nothing, and the next orphan reservation discards exited entries. The index is omitted when empty.

### Already-merged hotfixes

`hotfix ID --pr N [--sha SHA] [--review URL]` is an orchestrator or owner
command. It verifies that the PR merged into the project base at SHA, which
defaults to the PR's merge commit, and fetches the base once when the merge
or its first parent is not local. A task without a claim, in `todo`,
`rework`, `submitted` or `cancelled`, moves to `submitted` at a new revision.
`hotfix` records `pr`, `merge_sha`, the PR's `head_sha`, the merge's first
parent `base_sha`, `base`, `recorded_at` and `recorded_by`. Repeating the same
record preserves its revision and evidence; a different merge is refused.
The first parent must precede the whole PR, because the gates read only the
merge against it: a two-parent merge must have the PR head as its second
parent, and a single-parent merge must be a squash or a one-commit PR. A
rebase merge of several commits, whose first parent matches the subject and
author time of the PR's second-to-last commit, is refused.

`--review` reads a PR comment posted by a clean-context reviewer outside
Tower Crane, named by its comment URL or id. Workers and reviewers can post as
the same login, so there is no "latest" lookup: the orchestrator names the
exact review. The comment's `author_association` must be `OWNER`, `MEMBER` or
`COLLABORATOR`; anyone else can comment on a public repository. Its first line is `Review (native, clean context)` or
`Review (Tower Crane, clean context)`, its `SHA:` is the merged `head_sha`,
and a `Verdict: pass|fail` line, else a `Blocking findings` section reading
`None`, decides it. The verdict is stored as review evidence at `merge_sha`
with `source: "hotfix review"`, `ref` (the comment URL), `reviewed_sha`,
`author` and `author_association`. It counts as independent review only with a `hotfix` event by the
orchestrator or owner whose `review` names the same URL and verdict at that
revision. A comment on another PR, of another head, by an untrusted
association, or without the title or a verdict is refused. A failing posted review creates the follow-up below.

`accept ID` runs the existing software gates at `merge_sha`. Tests retain
the configured proof mode, reverting the landed changes against `base_sha`;
cleanup scans the same change. CI checks the successful GitHub Actions
`push` workflows on the recorded base at that commit and their required
check runs, even when local CI is configured. A required check run that
the judged base run skipped does not apply only when the skip says nothing
about the change: the same job also skipped at the merge commit, or the
job's own `if:` in the workflow file at the judged commit is false for the
run's event whatever its other terms are (a pull-request-only job such as
`github.event_name == 'pull_request' && ...`). A job skipped by a path filter
or by another job's output stays required, so a docs-only later commit
cannot stand in for code it never tested, and an unreadable workflow file
keeps the job required. A required job that ran must succeed. The summary
lists each required name not applied and why. PR head and mergeability
checks do not apply to a merged PR.

A failed `push` run at the merge commit is a confirmed failure, unless the
base was already red there, and one still running is pending. A failure is
`main_red` only with evidence that the base failed the same way before the
change. CI compares every job that did not pass in every failed full run at
the merge commit (the `push` run, a scheduled or manual run, or a push run
cancelled after a job failed) with earlier runs of the same workflow on the
base at commits the merge commit contains. It reads the merge commit's last
100 ancestors and that workflow's base runs created in the 7 days up to the
failed run, and keeps the last 30 that completed without being cancelled:
the inbox judges the base by the same 30 runs, and a failure older than a
week says little about the base at the merge commit, while the daily
scheduled run still puts seven runs in that week on a quiet base. The newest
is the parent run: the first parent's, or the nearest earlier one when the
concurrency group cancelled it. A failure the parent run shares says the
base was red; one seen only in an older run of the window is a known flaky
test.

A failed job is explained when each failing test its log names failed in an
earlier run in a job of the same kind with the same first error line. The
same kind is the same job name once its shard number is set aside, so the
same runner label and matrix; a test moves between shards as files are
added, but a test that failed only in a proof job that runs the whole suite,
or on another runner, says nothing. The first error line is the one
`ci log --failed-tests` reads under the failure, with the values line added
when it is only a header (an assertion's `strictly equal:`, a diff, a TAP
YAML block), compared without scratch directories (a path keeps its last
segment), times, dates, long numbers and any data dump after the message. An
error of a generic shape (a timeout, a wait for a path, a data dump, or no
word after its last colon but placeholders and operators, such as
`<n> !== <n>`) can be two different failures, so it counts only at the parent
run. A failing suite that only repeats its
failed child counts with its child. A test whose name is in a hunk of the
merge commit's diff counts only when the parent run failed it the same way.
Test names also come from a gate receipt the log prints as JSON (its
`test_failure.names` and `output_tail`), as the gate scratch proof does. A
job whose log names no test is explained only when its name marks a proof,
probe, check or lint job and the parent run failed the job of that name with
the same error line. That line comes from the failing step's own output:
between the step's header group and its `##[error]Process completed` line,
skipping a source line node prints above a caret, the caret and stack frames.
Another step's lines (the checkout's git output, an upload step's echoed
`if-no-files-found: error`) never count, and a failing step with no error
line leaves the job unexplained; a test job that names no failing test (a failed
setup step, a crashed runner) is not. A timed out or cancelled job is never
explained. A job log at the merge commit that cannot be read is an
observation error (`infrastructure_failure`). Any failure left unexplained
keeps the run a confirmed failure, and so does a failed run with no failed
job to compare. CI treats a `main_red` run like a cancelled one, below: a
later green run that contains the merge commit must stand for it, so
`main_red` never passes a hotfix on its own.

The evidence records `hotfix_ci.failure: {classification, runs: [{id,
workflow, event, attempt, conclusion, url, parent_run: {id, sha, event,
conclusion, url} | null, earlier_runs, jobs: [{name, id, conclusion,
explained, error?, failed_before?, tests: [{name, error, file?, touched,
failed_before}], tests_total?}]}]}`, with `classification` `main_red` or
`confirmed`. `failed_before` is `{run, sha, url, job, job_id, error}`: the
earlier run, its job and that job's error line, so the match can be checked
after the logs expire. `error` and `failed_before` on a job are set when its
log names no test; `tests` keeps the first 20. The summary names the parent
run and each failure new at the merge commit. A later check of the same
failed run attempts reuses the recorded classification and reads no logs
again. The alternative of treating failures in jobs or tests unrelated to the
hotfix's changed files as `main_red` is deliberately not implemented: the
suites are integration tests that a change to any library file can break, and
a test file the hotfix edited can still fail for a reason the base already
had.

When every `push` run there was cancelled (a newer
push replaced it in the shared main concurrency group), failed as `main_red`, or none ran, CI lists
the base's workflow runs created since the merge commit's run, or since its
commit date when it has none. It then takes the commits with a successful
`push`, `schedule` or `workflow_dispatch` run of the same workflows (of any workflow when none ran there), oldest
first, the merge commit itself included. A later commit counts only when
GitHub's compare shows it ahead of the merge commit and still on the base.
At that commit, the newest run of each workflow that was not cancelled must
be green, and its check runs, read with `filter=all` so a newer cancelled run
with the same job names cannot hide them, pass the same judgment. The first
commit that passes stands for the merge commit. That green run vouches for
the tree at that later commit, not for the merge commit alone: if a commit in
between fixed or reverted a defect the merge commit brought, CI still passes.
The tests gate, which runs at the merge commit against its first parent,
remains the proof for the merge commit itself. The evidence stays at
`merge_sha` and records `hotfix_ci: {merge_sha, satisfied_by: {sha, runs:
[{id, workflow, event, url}]}}`; the summary names the commit and run.

Each check looks at no more than five candidate commits; each costs two
compares and three paginated listings, so a recheck of a pending hotfix
stays near 25 GitHub calls. A pending result records `hotfix_ci: {merge_sha,
rejected: [{sha, runs, reason}]}`, the commits it turned down and the ids of
their green runs, and the summary says how many commits wait for the next
check. The next check of the same merge commit skips a commit rejected as
`does not contain the merge commit` or `not on BASE`, and one rejected as
`not green` unless it has a green run that is not listed. A failed scheduled
or manual run at the merge commit, or a job that failed before its run was
cancelled, is still a confirmed failure unless it is `main_red`. Until a later run is green, CI is
pending, with `not_running` when no full run on the base is queued or
running. The normal reviewer receives the landed
diff against the first parent and records its verdict at the merge commit.
Waivers cannot accept a hotfix, with one exception below: the owner's
`--waive tests` for tests that already fail at the merge's first parent.

A pass stores status `accepted`, displays `accepted (hotfix)`, and emits an
`accept` event with `hotfix: true`, the PR and a reason saying it merged
before its gates. The matching `hotfix` audit event proves the recorded
merge. `accept` then runs the merge gate, which only confirms that the PR
merged at `merge_sha` with the recorded head and base, and records `merge`
evidence at `merge_sha`; nothing merges the PR again. Dependencies treat it as
accepted. Status counts and `bench tokens` include `accepted_hotfix` as a
separate subset of `accepted`; bench task rows include a `hotfix` boolean.

A confirmed software gate failure or eligible failed independent review creates a separate
task with status `rework` and `hotfix_of: ID`. Its brief preserves the
original instructions and names the failure and a follow-up PR against
the project base. It starts without a branch, PR, SHA or evidence. The
historical task becomes `cancelled` and records `hotfix.follow_up`; further
failures reuse that task instead of creating duplicates. Explicit `rework`
on a submitted hotfix uses the same follow-up path; an accepted hotfix
refuses it, since its merge stands. Its merge commit stays
fixed; workers submit the follow-up task.

Repeating `hotfix ID --pr N [--review URL] [--reason R]` on a cancelled task
with `hotfix.follow_up` re-records it, for a failure that was not the
change's. The task moves to `submitted` at a new revision, so the failed
evidence no longer counts. `hotfix.follow_up` is removed and
`hotfix.superseded` gains `{follow_up, gate, at, by, reason}`. The follow-up becomes
`cancelled` with `superseded_by: ID` and a note with the reason, and a
`hotfix supersede` event records it. The `hotfix` event carries
`previous_status: "cancelled"` and `superseded: {follow_up, reason}`. A later
confirmed failure opens a new follow-up. The command is refused while the
follow-up has a claim or is being retired, and when it has a branch, PR, sha
or worktree or is submitted or accepted. A follow-up with `needs_owner` needs
the owner, through `task.cancel_needs_owner`. A follow-up records the gate
that opened it in `hotfix.follow_up_gate` and the `hotfix rework` event's
`gate` (`rework` for an explicit send-back); older ones are read from the
event's reason. When that gate is `review` or unknown, the re-record needs
the owner, through `task.rerecord_review`. `--reason` on a record that is
not a re-record is refused.

Pending CI, observation errors and timeouts keep the hotfix submitted;
retry its gate when the run completes or the infrastructure recovers.
The tests gate reruns failing names of a hotfix at `base_sha`, the merge's
first parent, not at the newest base, which contains the merge. When every
failing name also fails there, the evidence carries `main_failure` and
`infrastructure_failure`, the hotfix stays submitted with no follow-up, and
the inbox offers `check tests ID`. A name that passes at `base_sha` is the
merge's, even when the newest base still fails it. Without `base_sha` the
rerun uses the merge's first parent. A failure that predates the merge fails
on every rerun; the owner can `accept ID --waive tests --reason R` while the
latest tests evidence at the current head and revision has `main_failure` at
`base_sha`. Any other waiver of a hotfix is refused. The waived evidence and
the `accept` event carry `base_failure: {base_sha, names}`.
When every changed host-only test of a hotfix reported only skipped cases,
the tests failure carries `config_failure: {key: "tests_host_env"}`: there
is no worker to fix it, and the host's opt-ins decide. The hotfix stays
submitted, the inbox shows a `gate_config` item for `tests.host_env`, and
`gates retry ID` reruns the gate after the orchestrator sets the opt-ins.
Missing regression coverage and a proof that passes without the hotfix
are confirmed tests failures.

Evidence that no gate decision reads any more is settled: an entry whose `sha` does not match the task's head or whose `revision` is older, every entry of a cancelled task, and every entry but the merge receipt of a task accepted with a passing merge at its head. Each write stores a settled entry's `summary`, `commands`, `receipt`, `gate_policy`, `ci_policy`, `test_failure` and `capped_review` over 1 KiB of compact JSON in `evidence/<task>/<sha256>.json`, and adds `evidence_refs` to the entry, mapping each stored field to `{sha256, bytes}`. The field itself keeps a placeholder of the same type: `[stored in evidence/<task>/<sha256>.json]` for `summary`, an empty array for `commands` and `capped_review`, null for the others. Evidence at the current head stays inline whatever its size, and unknown evidence types are never stored. So `tasks.json` grows by a bounded amount per receipt, not by the size of its output.

Readers load a stored field on first use and check its byte length and SHA-256; a missing or changed file refuses that read with the file's path. `task show` and other views show the entry as recorded, without `evidence_refs`. Writes that do not use a stored field keep its reference without reading the file. A write reads a stored field back into the entry when the entry becomes current again. The first write by this version moves existing settled fields out; the files are written before `tasks.json` names them. Copy `evidence/` with the rest of the state. Files are never deleted.

The format is additive within schema 1. A pinned older tool reads and preserves `evidence_refs` and the placeholders. Every value its gate, merge and readiness decisions read is at the current head and stays inline, so those decisions do not change. It shows placeholders for settled history, and its gate view of a merged task's earlier receipts sees empty commands. When an older tool writes its own value into a stored field, that value wins and the next write drops the reference.

- `kind`: `code`, `docs`, `research`, `design`, `ops`. Changing it is operational, except leaving `code` (owner-required) and any change on a submitted or accepted task (refused until `rework`) ([Authority](decisions.md#authority)).
- `needs`: capability names, currently only `browser`; defaults to `[]` for new and legacy tasks. Set through `task add/update --needs JSON` or plan import. Duplicate names are removed. A change bumps the revision and requires rework for an accepted task. A `design` task requests the kit automatically; only explicit `needs: ["browser"]` requires a capable route before dispatch.
- `ci_local`: optional local CI override with exactly one of `command` or `args`, and optional `timeout` and `receipts`, extending the `ci.local.by_kind` override shape above. Receipt globs use the same validation and error message as `ci.local.receipts`. Without `receipts`, the task inherits the project's globs; an explicit empty list disables copying for that task. Only `task update ID --ci-local JSON` by the orchestrator or the owner sets it; `--ci-local null` removes it. An accepted task needs `rework` before the override can change. Changing it does not bump the revision; receipt validation checks the current resolved variant, command and timeout.
- `broker_verbs`: optional, the names of the [broker verbs](containment.md#broker-verbs) the task may run, set only by `task update ID --broker-verbs NAME,...` (`''` removes it). Granting a verb whose `delegate` is true, and removing grants, is operational; granting any other verb is owner-required. A grant changes neither the revision nor a live claim, and `task show` lists it.
- `size`: `S` (under an hour), `M` (a few hours), `L` (a day). Anything larger is split; `validate` reports it.
- `tier`: `easy`, `medium`, `hard` or `research`, the current ladder rung that does the task. When `task add` or `plan import` gives none: `research` for kind `research`, `easy` for an `S` `docs` task, `hard` for `L`, else `medium`. Only trivial work starts on the easy rung; small code, ops and design tasks start at `medium`. It changes through `--tier` or a ranged quality escalation; a later size or kind change does not move it. A task file without `tier` gets it the same way when it loads.
- `tier_range`: optional `{ "min": "easy", "max": "medium" }`, containing the current tier. `task add`, `task update` and `plan import` accept an ascending `tier` string such as `easy..medium`, store the range and start at its minimum. The order is easy, medium, hard, research. A single `--tier` clears the range; setting a new range resets its current tier to the minimum. Manual range changes use the operational `task.tier` authority, including clearing a range at its current rung from either the CLI or the board's `/api/tiers`; both record the setting audit.
- `priority`: optional; `urgent` when set, absent means normal. `task update --priority urgent|normal` is operational (orchestrator or owner); `urgent` stores the field and `normal` removes it, without changing the revision or interrupting a live claim. Ready tasks sort urgent first, then by descending unblock count, then task id. `ready`, `spawn --ready`, automation refill, status and the board share that order. Setting `normal` restores the default order; urgency does not bypass readiness blockers, locks or worker limits. A non-string value fails state validation; an unfamiliar string from a newer tool loads and sorts as normal. The CLI status lines and open task lines mark urgent work, the board's ready rows mark it, and task details show the priority.
- `escalations`: optional history of `{ at, agent, from, to, trigger, reason, source, spend_by_rung, decision? }`. `to: null` means the range top opened an owner decision. Sources deduplicate repeated recovery. `escalation_pending: true` means the rung already climbed but its fresh worker has not launched; a successful dispatch clears it under the spawn lock.
- `budget`: optional `{ "hours", "tokens" }`, each null or a non-negative number, set by `task update --budget-hours`, `--budget-tokens`. Enforced like the project budget on the task's own spend.
- `needs_owner`: null, or the reason the owner has to act (a credential, a purchase, a product call). `task add` and `plan import` trim this value; blank values become null. Such a task is never ready on its own; `tower-crane owner-done` clears it. Clearing it, there or by replacing an existing reason with `task update --needs-owner`, is operational: the orchestrator or the owner. Any agent may set a reason when none exists, or keep the same reason.
- `needs_owner_by`: present while `needs_owner` is set, `{ "agent", "role" }` for the write that set the current reason: `role` is `owner`, `orchestrator`, `engine` (the respawn cap) or `agent` (any other identity). `task add`, `plan import`, `task update --needs-owner`, `interrupt --needs-owner` and the respawn cap record it, a hotfix follow-up copies its hotfix's, and keeping the same reason keeps it. `owner-done` and clearing the reason remove it. Cancelling the task is `task.cancel_hold` (operational) when `role` is `orchestrator` or `engine`, and `task.cancel_needs_owner` (owner-required) otherwise. A reason set before this field existed is traced to the last event on the task whose `detail.needs_owner` equals it: `respawn cap` is the engine, an `owner` agent the owner, an orchestrator identity the orchestrator; with no such event it stays owner-required.
- `locks`: an array of unique non-empty resource names, such as `["lab/rdma", "gpu/0"]`; defaults to `[]` when absent. `task add --lock NAME` and `task update --lock NAME` accept repeated names, trim and deduplicate them; update replaces the list, and `--lock ''` clears it. `plan import` accepts the array too. Names are case-sensitive and independent of the environment label. Lock changes are refused under the state lock while the task holds a live lease or worker dispatch reservation; keeping the same set is allowed.
- `environment`: null or a non-empty informational label, such as `"lab"`; defaults to null when absent. Set with `--environment LABEL` on task add/update or the plan field. `--environment ''` clears it. It does not set process environment variables, select a harness or acquire a resource lock.
- `status`: `todo`, `in_progress`, `submitted`, `accepted`, `rework`, `cancelled`. `ready` and `blocked` are computed, never stored.
- `claim`: `{ "agent": "w-3", "since": "...", "until": "...", "from": "todo" }` while in progress; `from` is the status before the claim (`todo` or `rework`), which `release` restores. Repeating `claim` as the live holder extends `until` without changing `since` or `from`. An expired lease frees the task: it counts as `from` again and another agent may claim it. Until someone does, the original claimant can still submit it, or renew it if the task passes the same checks as a claim (no unmet dependency, owner blocker or open decision, and no held resource lock) and the workers limit has room: an expired lease no longer counts toward `limits.workers`, so renewing it takes a slot like a new claim. A claim whose `claim` event has `handover: true` is one a rework handed back to the task's waiting owner ([PR owners](#pr-owners)).
- `ci_dispatches`: optional list of `{ "sha", "branch", "workflow", "at", "agent", "run" }`, one per `ci dispatch`, oldest first. The entry is recorded under the state lock before the dispatch call, with `run: null`, and removed when GitHub refuses the dispatch (`ci dispatch failed`). `run` is the Actions run id, from the dispatch answer or the first manual run of that workflow at that head and branch created no earlier than a minute before `at`, allowing for clock skew, that no other entry names; when GitHub has not listed it yet, the next `ci dispatch` that finds it at that head records it (`ci dispatch run`), also when it then refuses because that run has not completed; one the rate limit refuses reads nothing from GitHub. `ci checks` looks it up for the latest entry without recording it. `sha` is the head the run tests. Entries from the last hour count toward `ci.dispatch.per_hour`.
- `scratch`: optional absolute path to the worker cache shared across this task's attempts. Spawn records it; successful worktree retirement archives and removes the directory and clears the field.
- `archive`: optional summary of the task's [scratch archive](storage.md#scratch-archive), written by accept and retirement.
- `archive_grants`: optional task ids whose archives this task's worker may copy into its scratch with `task archive ID --into`; `task archive ID --grant` adds one.
- `worktree`: optional path, branch, base, creation time and last observed head record; retirement adds `state` (`stale` or `removed`), a failure `reason` and any recovery `saved` path.
- `superseded_by`: optional replacement task id; superseding stores status `cancelled`.
- `retiring`: null, or `{ "since": "...", "pid": 4242, "host": "...", "start_ticks": "...", "pidns": "pid:[4026531836]", "path": "...", "branch": "..." }` while the process that wrote it removes the task's worktree after a merge or cancel. `start_ticks` and `pidns` are set where the platform reports them. Claim, rework, submit and worktree preparation refuse the reserved task, path or branch while that process runs; a marker whose process has exited holds nothing, so a crash cannot strand the task. The removal clears the marker when it ends, whether or not it removed the worktree.
- `submitted_by`: the agent that submitted the current `sha`. Submission clears `claim`; while the task is `submitted`, only this agent can replace the submitted head. A spawned worker whose submit took ownership goes on waiting on the task ([PR owners](#pr-owners)).
- `sha`: null before submission and after a release moves the task to another PR, then the full lowercase commit SHA: 40 characters for SHA-1, 64 for SHA-256. Full IDs are accepted as given without a local lookup, since the commit may exist only in another checkout. Abbreviations are resolved by `submit` with `git rev-parse --verify <sha>^{commit}` in the task repository, first locally and then after fetching the supplied or recorded task branch from origin. A prefix that remains unknown or ambiguous, or resolves to a non-commit object, is refused. Sandboxed workers resolve before forwarding to the host broker, which accepts only the full SHA and runs no Git. Legacy abbreviated submitted SHAs remain stored as written and match evidence and active reviewer dispatches by prefix on read.
- `evidence`: entries `{ "type", "ok", "sha", "agent", "at", "summary", "ref", "revision" }`, plus `"waived": true` on an owner waiver and `"via": "broker"` on evidence the state broker recorded for the agent it names (provenance, not proof: an unsandboxed process can write the same). Types: `tests`, `clean`, `sources`, `review`, `ci`, `merge`, `note`, `final-review`, `verb`, and `archive` for files `task archive --into` copied in, which no gate reads. Only `tower-crane verb` records `verb` evidence, one entry per run, with `verb: { name, params, exit_code, signal, timed_out, resource_reason?, duration_ms, outputs, source }` ([Broker verbs](containment.md#broker-verbs)); it counts toward no gate. Failed review evidence also carries `areas`, the sorted normalized locations from structured `findings[].path` when present, otherwise parsed from blocking findings. Rework preserves those structured locations, including PR-body claims. `rework --from-review` replaces these areas with those from the complete fetched review. Full reviews supply areas only from finding entries in their blocking section. Earlier-blocker status, reproduction references, follow-ups and fenced examples do not supply areas. Standalone evidence summaries use `file:line - finding` entries, optionally prefixed by a blocking count. Legacy evidence without `areas` uses its summary. Review evidence requires `--sha` for the commit reviewed. A spawned reviewer's verdict carries its dispatch revision, even when the brief, acceptance or rework changes the task before the verdict arrives. Review evidence from a reviewer spawn did not start carries the `--revision` it names, which is required and may not exceed the current revision. Other manual evidence records `--revision` when given and the current revision otherwise; `note` can default to the submitted sha. Software gates record the sha and revision they checked.
- `evidence.confirmed_failure`: optional boolean, emitted as true by tests, clean and CI runners when the check confirms a failed attempt. Unavailable test commands do not set it: shell exits 126/127, Windows exit 9009, or exit 1 with only cmd.exe's missing-command diagnostic. Failed-test output accompanied by that diagnostic still confirms a failure. CI sets it for completed uncapped failing runs, including a failing sibling of a capped review, except a hotfix's `main_red` failure at its merge commit ([Already-merged hotfixes](#already-merged-hotfixes)). Missing or pending required checks do not hide a completed uncapped failure in another run. Capped reviews alone, queued or pending runs, missing runs and observation errors do not set it. The same optional field appears in the gate event's `detail` and must match for audited software evidence to count. Legacy evidence without the field remains valid but supplies no confirmed-failure escalation signal.

- `revision`: incremented when acceptance, dependencies or capabilities (`needs`) change, on every `rework` including automatic quality escalation, and when `brief set` changes the brief after the first submission. Identical brief writes and brief edits before the first submission do not increment it. Evidence recorded against an older revision stays in the audit trail and does not count, even when the submitted sha is unchanged. An accepted task's brief, acceptance, dependencies, capabilities and kind cannot change; send it back with `rework` first. A refused brief change leaves the brief, task and audit log unchanged.
- `spend`: `{ "minutes", "tokens", "input"?, "cached"?, "output"?, "entries"? }`. Existing `{ "minutes", "tokens" }` files keep loading. Totals increase under the state lock. Token counts are non-negative safe integers. `input` includes cache reads and writes, `cached` is the cache-read subset of input, and `output` includes reasoning when reported. Do not add `cached` to `tokens` again. A total-only report increases `tokens` without inventing a breakdown; aggregate breakdown fields sum only the reports that supply them.
- `spend.entries`: one record per spend call or exited spawn route: `{ "at", "agent", "minutes", "tokens", "input", "cached", "output", "rung", "harness", "model", "profile", "source", "billing" }`, with optional `cache_write` from manual `--cache-write`, `models` and `provider` (`anthropic` or `bedrock`) for explicitly selected Claude routes. `billing` is inferred from the launch route. A Claude rung pinned to `bedrock` is `api`; a pinned provider decides alone, because the agent's settings turn every other provider switch off. A Claude rung that names no provider is `api` when the launch environment or user settings turn on any Claude Code provider switch: `CLAUDE_CODE_USE_BEDROCK`, `_VERTEX`, `_FOUNDRY`, `_ANTHROPIC_AWS`, `_ANTHROPIC_GOOGLE_CLOUD`, `_MANTLE` or `_GATEWAY`, set to `1`, `true`, `yes` or `on` in any case. On the first-party route, billing follows Claude Code's credential order: a non-empty `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY`, then an `apiKeyHelper` in the user settings, is `api`; then `CLAUDE_CODE_OAUTH_TOKEN` is `subscription`; then `ANTHROPIC_PROFILE`, or both `ANTHROPIC_FEDERATION_RULE_ID` and `ANTHROPIC_ORGANIZATION_ID`, is `api` (a Console credential); anything else is a login (`subscription`). Codex resolves `model_provider` from supported `-c` overrides, the standalone `<profile>.config.toml`, a legacy `[profiles.<profile>]` table and the base `config.toml`, in that order. The local providers `ollama`, `lmstudio` and `oss` have no metered price and are `null`. Any other non-OpenAI provider, such as `amazon-bedrock`, is `api`, even when AWS credentials come from `CODEX_HOME/.env` rather than the launch environment. The OpenAI route is `api` with a non-empty launch `OPENAI_API_KEY`, otherwise `subscription`. Without a named profile or config, Codex uses its OpenAI default. A missing named profile or an unresolved provider configuration yields `billing: null` (unknown), including unreadable or malformed configuration and non-string or empty provider settings. Unknown billing contributes only to list-price USD. Credential variables are checked for presence only; their values are not stored or printed. Billing does not inspect `.env` or login credential files: a key stored only there may be missed, and a launch key alongside an OpenAI login may classify that run as API billing. Manual records and records from before this field have no `billing`. `models` appears when a run used several models (Claude's result names each in `modelUsage`): `model` is then the primary model, the one with the most tokens, and each row `{ model, tokens, input, cached, output }` keeps that model's own counts, so `model` never joins two IDs. Unknown counts and metadata are `null`. `source` is `manual` or `spawn:<agent>`, with `:attempt:<n>` for resumed dispatches and `:route:<index>` for fallback routes. A spawn's rung, harness, configured model and profile come from its dispatch or fallback event; a model named in captured telemetry takes precedence. Model IDs are stored with whitespace trimmed and case folded, and the provider prefix stays in the stored ID; explicit Claude provider entries use plain Anthropic or global Bedrock ids and retain the provider that ran, including each fresh retry. Pricing matches by identity (see Cost samples above), so historical entries price the same way. Only explicit Claude provider entries expand `BUILTIN.claude_aliases`. A profile-only dispatch without a reported model keeps `model: null` and the profile. Manual `--rung` resolves the current ladder; pass `--model` and `--harness` when a native subagent used different values.
- Live usage: while an agent runs, its supervisor reads the harness's own usage every `usage_ms` (default 30 s, minimum 1 s; the first periodic reading after one interval): claude's session file `<CLAUDE_CONFIG_DIR>/projects/<dir>/<session id>.jsonl` and captured usage, the codex rollout for the printed session id, and the captured log for opencode, pi and agy when they expose usage. Claude uses the larger total observed in its session or log during the run. Only session files named for the spawn's own session id are opened, and events never carry their paths. The reading is stored as the route segment's entry, with the `source` the exit collection uses, plus `"live": { "state", "interval_ms", "error"? }`: `state` is `live` with the tokens so far, or `unavailable` with `tokens: null` while the harness has exposed no usage; never a zero. An initial read exception records `unavailable` with the filesystem error class (for example `EACCES` or `EISDIR`, otherwise `Error`), without the error message or path. Later exceptions preserve and age a measured reading. If telemetry returns no usage or a smaller cumulative total after a measured reading, its counters, cost and `at` stay unchanged and its state becomes `stale`. Only an authoritative invocation result may lower the measured total. Recovery from missing telemetry restores `live`. A resumed session counts only what it adds after the dispatch. Only changed readings produce `spend live` events, quiet bookkeeping for the default waiter; `budget stop` still wakes the orchestrator; unchanged files do not refresh the timestamp, and views show a reading older than 10 effective intervals as `stale`. `status.spend.live` omits accepted and cancelled tasks and agents whose newest reading is older than 24 hours, without changing recorded totals. Runaway monitoring uses the full readings, including those older than 24 hours. It includes `at`, `stale_at` and any `error` class; the open board ages each reading every five seconds without requiring a state write or SSE reload: past `stale_at` the page draws the reading stale itself, then asks serve to redraw the queue and status sentence. Live tokens are in the totals. The exit collection replaces the live entry with the exit telemetry, or keeps its last reading without `live` when the exit reports none, so usage is counted once. Live entries are not counted as spawns without usage.
- When claude exits without a result, its supervisor reads the session once more after the process group and output streams close, before recording the exit that permits collection. This includes usage written after the last live sample, even when submission has ended supervision. The resumed-session baseline still applies. Partial assistant-message usage in the log does not skip this read. Collection and recollection keep the reconciled total when the partial log reports less; only a valid invocation result can replace it with a lower total. If this final read is unavailable, collection keeps the last live reading. If an exit collector finalized the entry before the supervisor read its final usage, the final reading replaces that source entry in place and rechecks budgets. It neither adds a second entry nor restores `live` on the collected entry.
- An explicit `interrupt` stops the process group and reconciles its spend on exit. The run keeps its `stopped` phase and the task keeps its revision; recollecting that usage does not count it twice.
- Entry counts include live snapshots and do not establish exit collection. An exit consumer waits for entries without `live` and, when observing a worker exit, the matching `worker-exited` receipt.
- Every completed attempt is sampled before scheduling a retry or selecting a fallback, even if it finishes before the first periodic sample. Claude's result, when present, supplies the invocation total; other harnesses use their own usage sources. A budget breach stops further attempts. The launch also checks the current budget under the state lock before starting a retry or fallback, so another agent's spend or a lowered limit cannot bypass the check.
- A budget stop does not trigger tier-range quality escalation. It leaves the current rung in place and waits for the owner to address the budget.
- Budgets: `project.json budget` and a task's optional `budget` `{ "hours", "tokens" }` (null is no limit) are checked against recorded and live usage at every supervisor sample, including when telemetry cannot be read. Submission ends lease renewal and retries, but accounting and budget enforcement continue until the process group and streams close. A crossing (usage above the limit) stops the agent: the supervisor records `budget stop` with the breaches and `authority: "operational"`, sets the run phase to `blocked: budget: ...`, terminates the process group without a rerun or fallback, cancels a retry still in backoff, and opens one `kind: "spend"` decision per crossed budget with `escalation: { settings: ["budget.raise"], change: { scope, what, limit } }`. Its spend kind retains the independent owner restriction under escalation delegation, unless the owner lifts that kind. An alert opened before kinds were recorded retains the same spend restriction when it has no kind and its escalation contains `budget.raise` with a breach `change` naming a non-empty `scope`, `what: "hours"|"tokens"` and a finite non-negative numeric `limit`. This is a read-time rule: it keeps the old alert on the owner waiting list and refuses orchestrator answer/withdrawal without changing its stored fields. Ordinary budget-tag questions with no breach payload remain eligible for technical delegation. The owner may explicitly lift the alert with `decision delegate --technical true`. The `ask` event records the kind. Reuse requires the same kind and budget breach; legacy or technical questions and approval requests are not reused as spend questions. A task budget's decision blocks the task. `spawn` refuses while a project or the task's budget is crossed. Raising or removing a limit needs the owner directly or a setting approval for the orchestrator; answering the budget alert alone grants no change.
- Manual `spend --cache-write N` adds `cache_write` to the entry. It is included in `input` and separate from `cached`; their sum cannot exceed input. Omitted cache-write counts stay unknown for pricing older telemetry.
- New spend entries, including measured live entries, record `cost_usd` using the exact `review.prices` row first, then the canonical model row as a fallback, at collection time. Claude aliases resolve through `BUILTIN.claude_aliases` for this lookup; the stored model ID remains unchanged, and explicit provider routes keep their provider identity. A run on several models sums each model's cost from its own counts. `review.prices` retains separate provider, context and version rows with their own rates. Only duplicate configured ids after whitespace trimming and case folding are refused, so schema-1 tables with different provider rates keep loading and saving. Missing prices or input, cache and output components produce null. Cost uses the review pricing rules, including conservative cache-write accounting. Missing telemetry preserves the last measured cost, and exit reconciliation prices the final entry once. `task show` exposes `spend_by_rung` with summed tokens and cost; an unknown entry makes that rung's corresponding total null. Escalation records include this breakdown at the climb, while later collection can enrich the task's current breakdown.
- Automatic collection happens for foreground and detached exits, including nonzero exits and killed processes whose logs report usage. Foreground collection, detached monitors and `wait` share one locked exit-observation path. A waiter attempts usage collection when it observes a worker exit. A detached monitor observes the original harness pid (including Linux zombies and pid reuse) and invokes the CLI after exit. Its checks are 500 ms apart; each collection takes the usual state lock with a command deadline of at most 30 s. Failed collection retries for up to 10 min, then logs a recovery command and exits with code 1. If the process cannot be observed for 10 min (another host, a permission error or unavailable Linux process metadata), the monitor exits with code 1 and a recovery command without assuming exit or recording usage. Both deadlines use monotonic time. A known live process is watched until exit; deleting the project stops the monitor. Successful collection stops the monitor. `spend --from-spawn AGENT` can retry collection. A known `source` is counted once even across concurrent retries. Without usage, the entry has `tokens: null`, totals stay unchanged, and status/sketch count spawns without usage. A retry enriches unknown or partial entries if telemetry arrives, applying only counter deltas. Explicitly reported zero is a measured zero.
- `notes`: `{ "at", "agent", "text" }` entries, with optional `kind: "scope-ruling"` for a design change recorded by the orchestrator or owner. The orchestrator folds what matters into the brief. A note starting with `split:` on an `L` task records why it stays whole.

`bench tokens` compares spend entries with every recorded spawn, including reviewers, resumed attempts, fallback routes and fresh retries. Its read-only report lists unmatched source IDs as `missing_spawns`; it does not add placeholder state entries. A matching native manual token report can cover its dispatch, while minute-only reports cannot. Tasks with missing sessions, unknown token entries or any entry marked `live` stay out of all token, category and USD medians and means, including rung and path groups; their recorded spend still contributes to the total cost per accepted task. Each live or unknown token entry contributes once to the report row's `unknown` count. Collection must remove the live marker before the task can become complete. See [bench.md](https://github.com/agent-sh/tower-crane/blob/main/docs/bench.md) for the labeling and pricing method.

Missing input, cached or output counts leave the corresponding task category total `null`, and category medians use only measured totals. Known token totals remain eligible for token medians even when their breakdown is incomplete.

Runaway spend flags are computed on reads and never stored. A `spend` flag belongs to the task (`agent: null`); its text separates the task total, distinct worker count and current claimant's own spend. `worker-spend` flags name the current claimant and sum its entries across routes and retries. Both compare total tokens against the accepted-task median for the same tier and size when at least three samples exist, else the tier median with three samples, else the project median, naming any fallback. Both show cache reads as a share of total tokens and uncached tokens (`input - cached + output`), or unknown for incomplete breakdowns. `status --json` exposes tier norms in `runaway_norms.tiers` and size norms in `runaway_norms.sizes.<tier>.<size>`; size norms add `size`, `size_samples` and `from: tier-size|tier|project`, keeping `samples` as the tier count. Worker count includes distinct claimants and worker spawns, plus worker spend entries; review-rung and known non-worker spawn entries do not add workers. Old workers' spend stays in the task total; only the current claim can raise a worker alarm.

The CLI never writes a dependency on a task that does not exist, a dependency cycle, or a task without acceptance. `validate` still checks files edited by hand.

Task ids are never reused. A new task takes the larger of `next` and one past the highest task id any `events.jsonl` record names, so a task that tasks.json lost keeps its id. `validate` reconciles tasks.json with the log and reports drift in both directions: a task id the log names that tasks.json lacks, a `task note` the log records that the task lacks, a `next` at or below a logged id, and a `last_event` that the log lacks, which means the log lost a write tasks.json kept. It reads under the lock, after recovering any interrupted commit, so a commit in flight is never mistaken for drift. Readers without the lock read the snapshot files before `events.jsonl`, and a commit logs its events before it renames its files, so such a reader never sees a task change whose events it lacks.

Resource lock holders are derived from the same pure event-log, lease and clock view as worker slot holders. A task holds all its locks while its lease is live or its unclaimed worker dispatch reservation holds a slot. Claim, worker spawn and expired-lease renewal refuse conflicting locks under the state lock, naming the resource, task and agent holding it; the same task and agent can consume their own reservation. `ready`, blocked views and task descriptions include conflicts with other tasks. Submission, release and lease expiry free leased locks. Unclaimed reservations free their locks on the matching exit, inactive monitor record or reservation horizon, and retain them through supervised retry and fallback backoff. No process probe can free a lock for one observer alone. Reviewer and other non-worker dispatches acquire no resource locks. Lock and environment changes do not bump the task revision.

Changing acceptance, dependencies, capabilities (`needs`), kind or a local CI override while a claim's lease is live requires `task update --interrupt`. Only the explicit owner, `orchestrator`, or a generated agent with a recorded orchestrator role can authorize the stop. Validation, the requirements edit and the interruption event share one lock, so a refused edit stops nothing. Acceptance, dependency and capability edits retain their revision bump. Adding or clearing capabilities changes what the next spawn receives; repeating an unchanged capability set keeps the claim and revision. Unchanged requirements and metadata changes do not interrupt.

`interrupt ID` clears the claim and restores its `from` status without changing revision, branch, PR, head, evidence or worktree files. Its event records `{ holder, claim, status, revision, reason, phase, active }` and the matched supervisor's run identity when present. `--needs-owner REASON` also sets `needs_owner` in the same write, so dispatch holds the task until `owner-done`; the event then carries `needs_owner` and uses REASON as `reason`, and replacing a different ask audits `task.needs_owner` with `task.interrupt`. The board's Stop sends it. A live supervisor starts in `stopping`; a claim without a live supervisor records `stopped`. The supervisor consumes this request through its existing shutdown path, cancels retries, waits for process-group cleanup and output closure, then records `spawn phase` with `phase: "stopped", active: false` and the usual exit and spend receipts. An interrupted task with a live stopping supervisor still reserves one worker slot; claim and redispatch refuse until cleanup finishes. A manual claim has no active supervisor and releases immediately. Interrupted runs do not produce an exited-without-submit recovery wakeup.

Dispatch recognizes the interruption of the latest worker attempt independently of `submitted_by`. The usual matching-route Codex and command-adapter session policy applies; native Claude starts fresh. Resume restores the interrupted claim's original `since` and `from`, checks blockers and worker limits, and supplies the current requirements with an interruption note. A changed route, missing session or fallback starts fresh in the retained worktree. No session is resumed while the interrupted supervisor is still stopping.

Recorded `active: false` takes precedence over a monitor process that remains alive for usage collection. Interrupting such a claim records `stopped` directly. Final exit handling checks for a matching active interruption under the state lock after waiting for hooks, so a stop request committed during that wait also receives its `stopped` phase and exit receipt. A later `submit` or `rework` event for the task ends the preceding interruption's eligibility for both session selection and prompt construction. Rework resumes from the submission's claim and supplies current review feedback.

Software evidence also has `source` (`check tests`, `check clean`, `check sources`, `check ci`, `check final-review` or `merge`) and `commands`, an array of `{ "command", "args", "cwd", "status", "signal" }` receipts. `command` is the executable name or shell command line, `args` holds its arguments, `cwd` is its working directory, and `status` and `signal` report how it ended (null when unavailable). All commands the gate ran are recorded, including failed commands and GitHub queries. A gate refused before running a process records an empty array; an ok entry needs at least one command to count. In tests mode `none`, the receipt is the Git command resolving the submitted sha; it does not claim that a suite ran. Tests evidence and event detail also carry `tests_mode`, the mode resolved from the project and task kind when checking started, or null for invalid policy. Gate evidence and its event carry the same receipts and revision.

When a test command fails, tests evidence and its audit event also carry `test_failure: { "names": [], "output_tail": "" }`. `names` collects node:test spec (`✖`) or TAP (`not ok`) failure lines. `output_tail` contains at most the last 40 lines and 8192 characters. Before storage or printing, terminal escapes are removed from the full output as for [local CI output](ci.md#local-ci-output), then it is redacted and only then cut to the tail, so a token across the cut is never left as a fragment. Names and tail are redacted against environment values that look like secrets: a value with a token shape, or the value of a credential-named variable (token, secret, password, passwd, credential, API key, access key, private key or cookie) that is 20 or more characters of letters and digits with no spaces. This covers the gate process environment and project, resolved rung and environment-file values. Token shapes are GitHub, API, AWS and Slack keys and `Authorization` header values. A token shape's run is redacted whole at any length, also when more word characters follow it directly, as in `ghp_<token>_backup`, and an AWS key ends at its 20th character. Every shape is found in the same text and overlapping matches are redacted as one, so a header or token that one match leaves exposed is still found. Each shape is a linear scan, so a prefix before megabytes of token characters cannot crash the gate. Paths, file names and commit SHAs are never redacted, and neither are numbers, booleans or short words such as `NODE_ENV=test` or `MAX_THINKING_TOKENS=1`. Environment-file contents are read during the gate and never stored. The check summary prints the same redacted names and bounded tail.

The tests, clean and local CI gates, and the proof run of the tests gate, join a command's stdout and stderr by whole lines. Each stream's text is held until its newline, so a chunk of one stream never lands inside a line of the other, and an unfinished last line ends on its own line when the command closes. The timeout snapshot (`timeout.output_tail`) holds only whole lines, since the rest of an unfinished line can arrive during the shutdown grace. Lines of one stream keep their order. Across the streams, lines appear in the order their newlines reached Tower Crane. A command that block-buffers stdout, such as Python or cargo writing to a pipe, flushes a stdout line only with its buffer, so a stderr line can come before stdout lines written earlier. One pipe shared by both streams would keep the order of the writes, but it would join them mid-line wherever the command flushes mid-line, and a stderr line there cuts a secret into halves the redactor misses. The local CI log and tail and the tests gate's `test_failure`, host-only commands included, redact the joined text as it arrived and also read each stream's own text for secrets. A secret only one stream's text shows, such as a token that stream wrapped onto two lines with a line of the other stream read between the halves, is redacted where each of its pieces landed, and the line ending after a piece stays, a CR with an escape before the LF included. So the result redacts everything either view redacts. Lines never move. Read on its own, a stream can join a token prefix to the token characters that start up to 8 of its following lines, 256 characters at most, as the joined text does for adjacent lines. The start of each of those lines is then redacted too, and a `not ok` line among them can lose its `not` and be missing from `test_failure.names`. A kept tail that drops earlier output starts at a line for the same reason, and a line longer than the kept tail is replaced by `[overlong line omitted]` rather than cut at an arbitrary character. The clean gate removes terminal escapes from the tool's output and redacts it before its failure summary quotes the last 20 lines or the first 200 characters.

Hosted CI evidence and its audit event also carry `ci_policy`: `{ "required": [], "ignore_apps": [], "capped_review": [] }`, with the effective values captured when the check starts. Absent or null policy fields resolve to empty arrays. Capped rules record only `{ "app", "pattern" }`. A malformed policy records `ci_policy: null` on a failed check. The policy snapshot in evidence must match its audit event. Before an audited merge succeeds at the current head and revision, acceptance, merge and task gate reports require a successful hosted snapshot to match the current project's effective policy. A changed policy, malformed current policy or earlier evidence without `ci_policy` needs `tower-crane check ci ID` again. Unrelated fields under `ci` do not invalidate it. A local CI check uses its local receipt instead.

`tower-crane evidence` writes only `review` and `note`. Software types are refused for any agent, whether `--ok` or `--fail`; run their gate commands instead. `final-review` is refused the same way; only `accept` records it. State version 1 and older evidence remain readable. Software entries without the matching gate source and audit event do not satisfy acceptance, so their gates must run again.

`task show` marks software evidence with missing or mismatched gate proof, or an older sha, as `(does not count)` in its text output. Successful tests and clean entries also require their command policy to match current pins; tests entries require the current mode and the current `tests.paths`, `tests.keep` and `tests.expensive` settings. The board ledger validates each entry against the same policy, including after a fresh matching pass. An older revision keeps the `(revision N, does not count)` marker. Each command receipt is printed below its evidence entry, including merge receipts. Owner waivers count without command receipts. The JSON view keeps the stored evidence unchanged and reports the gates separately.

A tests or clean command stopped by its gate deadline records `ok: false`, `infrastructure_failure: true` and `timeout: {minutes, running_files, output_tail}` in both evidence and its audit event. The summary says `timed out after N min`. `running_files` contains paths reported by node:test interruption locations or unfinished top-level TAP file subtests; an empty list means the runner did not identify them. The output tail is captured before termination, redacted and bounded to 40 lines and 8192 characters. Cancellation messages printed after SIGTERM do not become `test_failure` names. A timeout at head, scoped proof or reversion fails the gate without `confirmed_failure`, so it never proves a change or triggers a quality climb.

A command killed by a signal records `runner_crash: true` without `confirmed_failure`. A shell reports that signal as exit 128 plus its number, so such an exit counts the same. A CI check whose failing runs all timed out, were cancelled or never started records `infrastructure_failure: true`; a failing run with conclusion `failure` records `confirmed_failure`, and any other failing conclusion, such as `action_required`, or a required run that completed without success, records `worker_failure: true`. A CI check with runs still in progress records `pending: true`. GitHub observation errors record `infrastructure_failure: true`: a failed `gh pr view`, unreadable GitHub output, or a failed check-runs, check-suites or Actions API read. Unknown mergeability is pending, not an observation error. At a submitted head these errors retry once; a recovered read uses the new CI verdict, and a repeated observation error reworks with its diagnostic. A local CI command (`ci.local`) that times out records the same, and one killed by a signal records `runner_crash: true`. A failing tests or local CI command reruns once first ([gate reruns](gates.md#gate-reruns), [local CI reruns](ci.md#local-ci-reruns)). Automation retries any of these once at the same head, as it does a timeout. A change the worker must fix records `worker_failure: true` without a command verdict: no test covers the change, or it has no changes against the base; automation reworks it at once. A failed `tests`, `clean` or `ci` gate that no flag names records no classification and reworks at once. A gate interrupted by wait shutdown records `voided: true` in the evidence and its audit event: a void checked nothing, so automation runs the gate again instead of settling it, never reworks it, and does not count it toward the one retry. A pending CI run records `pending: true`, and automation keeps it submitted. Pending CI that has nothing queued or running for 30 minutes, or whose PR closed without merging, records `stalled: true`; it also stays submitted. A pinned command that is missing or not installed records `config_failure: {key}`, where `key` names the setting (`tests_cmd`, `tests_proof_cmd` or `clean_cmd`; `tests_crucial` for a crucial path missing at head, whose inbox item names `tests.crucial` and `project set --tests-crucial <JSON>`). The configuration receipt waits for `gates retry` once the command is pinned, and the inbox shows a `gate_config` item addressed to the orchestrator that names `gates.KEY`. Automation still inspects later software gates; an independent failed verdict retries or reworks normally, while successful or pending later gates leave the task submitted. A test that also fails on the base branch records `main_failure: {base, names}` with the names that fail there too, when every failing name does; automation retries it once like an infrastructure failure. When the failing run is a host-only test (`tests.host_only`) and the base fails each shared name with the same first error line, normalized as `main_red` compares CI failures, the failure is the host's and not the change's. A host-only file the task changed counts only when that line is specific, not generic such as a timeout. The evidence then also records `infrastructure_failure: true` and the summary says the task stays submitted. Automation retries it once, then keeps the task submitted without a rework; later software gates still run, the inbox `gate_failed` item names the main failure and offers `check tests ID`, and automation reruns the tests gate when the base tip moves past `main_failure.base`. `gates retry ID` reruns it after a host fix. A different error under a shared name retries once and then reworks. The base is the newer of the local and `origin` branch. Such a run records no `confirmed_failure`, so it never climbs a rung. A run with a name that does not fail on the base keeps its verdict and names the shared ones in its summary. A base rerun killed by a signal checked nothing: the run records `base_rerun_killed: {base, signal, status}` and no `confirmed_failure`, its summary says `Base rerun at BASE was killed (SIGNAL); shared failures were not checked.`, and automation retries it once like a timeout. A base rerun stopped by the gate deadline checked nothing either: the run records `base_rerun_timed_out: {base, minutes}` and no `confirmed_failure`, its summary says `Base rerun at BASE timed out after N min; shared failures were not checked.`, and automation retries it once. Both flags appear in the evidence and its audit event. A tests command failure whose every failing test shows a [native crash](#native-crashes) of a child reruns its files once; each crash seen records `native_crash: [{test, signal, pid, core_file?, stack?, core_error?}]` beside the verdict. A cleanup scan with checks that did not run records `infrastructure_failure: true`.

Tests and clean evidence and their audit events carry `gate_policy`: `{tests_cmd, tests_proof_cmd, paths, keep, expensive}` for tests or `{clean_cmd}` for clean, captured when the check starts. The tests settings are the effective values: `paths` is `tests.paths` (null for the default layouts), `keep` is `tests.keep` (null when unset, which keeps the default manifests and lockfiles) and `expensive` is `tests.expensive === true`. While a map is pinned outside crucial mode, the tests policy also snapshots `tests_map`, `ci_required` and `ci_local`; with `tests.crucial` set it records `crucial`. When configured, it also records `host_only` and a `host_env_sha256` digest of the sorted host environment map, so changes invalidate old proof without duplicating environment values in receipts. Command values are trimmed strings or null. Missing, malformed or changed policy makes previous evidence stale, even if the owner changes commands during a run. Successful receipts must also include the pinned test command or mapped head expansion (except none mode) or the pinned cleanup invocation with its appended arguments. Scoped proof records `receipt.proof_tests`, the changed test paths used to expand the pinned template; mapped head runs also record `receipt.head_tests`; every test shell receipt must match the full command, the mapped head expansion, the proof expansion, a host-only expansion of the pinned proof template for one file in `receipt.host_only.results`, or its expansion for the `files` of an entry in `receipt.reruns`. A head command that failed counts as passed when `receipt.reruns` has an entry with `step: "head"`, `ok: true` and files whose expansion exited 0; a whole-command rerun repeats the head command itself. Host-only expansions count even when all cases in the recorded file skipped. The proof command from the run without the change still counts; any other extra shell command is rejected. Map, expensive-policy and required-job changes invalidate mapped-policy receipts. Acceptance, merge and task reports use the same check. Old receipts without this snapshot require a new check; owner waivers retain their existing behavior.

The CLI refuses manual software verdicts, and software receipts require matching records in tasks.json and events.jsonl. Plain files cannot stop a writer running as the same user from forging those records or an owner waiver. Command receipts show what ran; acceptance checks them and their recorded policy against the pinned commands. The reviewer checks that the configured runners verify the change.

Research Claude fallback routes in the user file inherit the primary `web_mcp` unless they specify their own. The same `{name, command, args}` validation applies to an explicit fallback server. Other harnesses do not inherit it. A route combining an inherited or explicit web MCP with `mcp` is reported and skipped so only the web server loads.

### Research sources

`project.research` is optional and accepts only `min_sources`, a positive integer; it defaults to 10. The explicit owner sets it with `project set --research-min-sources N` (also accepted by `init`). Changing the minimum invalidates sources evidence recorded under a different minimum.

Tasks of kind `research` require sources evidence on every tier. Kind `research` selects the research tier by default. Changing only the kind preserves the existing tier and its role; verification follows the new kind. Tier changes do not remove the sources requirement or citation-review instructions. Code tasks may use the research tier for model selection and retain their code gates.

A research deliverable is committed at `research/<task id>.json`:

```json
{
  "sources": [{"id": "s1", "url": "https://example.org/page"}],
  "claims": [{"claim": "The supported conclusion", "quote": "Exact text from the page", "source": "s1"}]
}
```

The example shows one citation; the default requires at least ten. Every source has a unique non-blank id and an HTTP(S) URL without credentials. Every claim has non-blank `claim`, `quote` and `source` strings; the source names an entry, and every source must be cited. Multiple claims may cite one source. `check sources ID` reads this file through Git at the submitted sha, fetches each page at check time, and finds every quote in its page text. It normalizes Unicode and whitespace, removes inline tags without adding spaces, separates block boundaries, strips comments and script/style/template content, and decodes common and numeric HTML entities. A single-pass scanner tracks quoted tag attributes, nested comments and templates, and raw script/style blocks. Unfinished blocks stay hidden; an unfinished tag or an unquoted `<` inside a tag excludes the rest of the page from matching. Punctuation adjacent to inline markup stays adjacent. It accepts HTML and plain text; PDF, JavaScript-rendered, authenticated and other non-text pages need a publicly fetchable text alternative. Quote matching proves presence; independent review checks source credibility and whether each quote supports its claim, including uncited factual claims elsewhere in the deliverable.

Before each connection, the gate resolves the hostname and refuses any non-public IPv4 or IPv6 answer, including loopback, private, link-local, mapped and special-use addresses. It pins the full validated address list for the socket while retaining the hostname for HTTP Host, TLS SNI and certificate validation. Node can fall back between IPv6 and IPv4 without resolving again; every attempt shares the page timeout. Redirects are followed manually, with the same URL and DNS checks at every hop, up to five redirects. DNS resolution and all redirect hops share the page timeout. The CLI has no setting that permits private addresses; local tests inject a resolver and transport into the gate context.

The gate rejects duplicate URLs (fragments do not distinguish pages), duplicate final redirect URLs, pages with the same extracted text, dead links, missing quotes and uncited sources. Each fetch is limited to ten seconds and 5 MiB; the gate has a two minute deadline to bound stalled responses. Sources evidence carries a `receipt` with `min_sources`, `deliverable` and the fetched `sources`: id, requested and final URL, HTTP status, text SHA-256, fetch timestamp and cited claims. The audit event carries the same receipt; it also records the Git commands resolving and reading the submitted commit. The reviewer context includes this receipt and the instruction to map each claim to its source. A new check always fetches again; acceptance reuses evidence at the same sha, revision and minimum.

### Ready and blocked

A task is ready when its status is `todo` or `rework`, every dependency is `accepted`, `needs_owner` is null, and no open decision lists it in `blocks`. Otherwise `tower-crane ready --all` says what blocks it.

Ready tasks come in priority order: urgent first, then most outstanding dependents (direct or transitive, not yet accepted or cancelled), then by id.

### Release for a decision

`release ID --reason R --pr N` gives back a claim whose work waits on a decision and links PR `N` to the task. `N` must be open and is checked as `submit` checks it. Its head branch must equal the task's `branch`, except when the task has none or moves from a closed or merged PR to `N`: then it becomes the task's `branch`, and the task's `sha` clears, since that submission belongs to the PR it replaces. A task linked to another open PR keeps that PR and refuses the release; once that PR is closed or merged, `N` replaces it. The `pr` and `branch` values stay when the claim is released. The link is written after the owner check, so a release that opens an owner decision and refuses writes no link. The release note records `linked PR #N on branch B`.

The release event's `detail.decisions` lists the ids of the open decisions that blocked the task when it was released. A todo task whose latest release has them can be sent back with `rework`, answered or not: its status becomes `rework` and `revision` advances as for any rework. A todo task released without decisions still refuses `rework`.

Answering the decision removes its block, so the task is ready as `todo` with its PR linked. Its next dispatch continues that PR: when the task's branch is not local, the worktree starts from the branch head on origin, even before any submission, and the worker prompt names the PR. A branch that origin no longer has starts from the base a new task would use.

### PR owners

A worker that `spawn` started owns its PR once it submits: it stays in its session, waits on its own task with `wait --own --task ID --timeout SEC`, fixes what comes back and submits again, until the task is done. A fresh worker would rebuild the context from the brief and notes; the owner keeps it.

- Taking ownership. A `submit` by an agent whose worker spawn on the task has not exited takes ownership while fewer than `limits.owners` other owners wait (default twice `limits.workers`); its event records `own: true`. Past the limit it records `own: false` with `own_refused` (`owner limit reached (N of N waiting: T1, T2)`), the output tells the worker to exit, and the task goes the way it did before owners. A native worker, a PR-body fixer or a worker whose spawn exited takes none. The latest submit decides, so every resubmit asks again. A generated-file repair's submit of the merged head names the waiting owner as `owner`, so the owner keeps waiting on the repaired head.
- Waiting. A waiting owner holds no claim and no worker slot: `limits.workers` counts only leases and reservations. Its supervisor keeps no lease and checks no stall while it waits, and marks its host governor unit `waiting`, which the budget sizes by what it measures ([The budget](containment.md#the-budget)). Review dispatch, the PR-body fixer and the generated-file repair, which otherwise wait for a tracked worker's exit, go ahead while the worker waits as owner: it edits nothing until a handback.
- Handback. A `rework` while the owner waits (a failed tests, clean or ci gate, a failed review, a merge conflict, a person's `rework`) is recorded as any rework: the revision advances, the reason goes into the note and the brief's rework notes, and the gate settles as before. In the same write the task goes back to `in_progress` under a new lease for the owner, whatever the worker limit says, since the owner holds the context: a `claim` event in the owner's name with `{ until, from: "rework", since, handover: true }`, and a `msg` to the owner with `{ to, handover: true, revision, text }` whose text is the rework's full reason (failing tests and the output tail, the review's findings, failing CI jobs and their first log lines). There is no handback when the rework climbs a quality tier, which runs on another rung, or while anything holds a claim: an owner ask, an open decision, a pause, the repeated-review gate, a held lock. An automatic gate rework that `gates retry ID --from-rework` can still undo is not handed back in that write while `gates.rework_hold_min` is above zero: its `rework` event records `owner_held` (the owner), the task stays `rework` with no claim, so the restore stays possible, and the owner keeps waiting. A restore in that time leaves the owner waiting on the restored head. Once the hold ends, the wait host's refill pass hands the task back to the owner as above, before it counts worker slots, unless something holds a claim then. The owner's supervisor keeps the handed-back lease and checks stalls from the handback on, and the shared process detector traces the claim back to the owner's run, so an owner that crashes after a handback is an exited claim (`status`, `release --dead`).
- `wait --own` reads the state in the agent's sandbox and runs no reactions. It prints one JSON line, `{ "type": "own", "outcome", "task", ... }`: `fix` with `revision` and `message` once the task is handed back to the caller, `exit` with `reason` once the ownership ended, and `{ "type": "timeout", "outcome": "wait" }` with exit 2 at `--timeout` while the owner still waits. It rereads the state on each event and at least once a minute.
- Ending. The ownership ends when the task merges (or is accepted without a PR), is cancelled, is claimed by another agent or released, when an `interrupt` stops the owner, a rework is not handed back, the owner's spawn exits, or the task had no event for `limits.owner_idle_minutes` while the owner waited (default 180; the quiet bookkeeping a default `wait` skips, such as `spend live`, `renew` and `hook progress`, is no event). A merge retires the worktree, and the supervisor stops an owner still running then. After that, and when the owner crashes, the next rework goes the respawn path unchanged: refill dispatches a new worker once the old one exited.
- `interrupt ID` on a submitted task, or a held gate rework, whose owner waits records an `interrupt` event with the owner's run, `claim: null` and `owner: true`; the supervisor stops the owner on it as on a claimed run's, and the task keeps its status and revision.
- A failed review whose findings are all PR-body claims keeps its light path: a body fixer edits the PR body without a new revision while the owner waits. It starts as a fresh agent beside the owner, since it cannot resume a session that is still running.
- The reviewer stays a separate clean-context agent: review evidence counts only from the owner or a reviewer spawn, never from the submitter.

### Spawned process exits

On Windows, an npm `.cmd` harness runs as a direct Node process with the shim's script and the original arguments. Spawn events retain the configured harness and route; the recorded pid belongs to the Node process. The supervisor uses the same resolution for retries and fallback routes.

`status` and `ready`, including `ready --all`, report a current claim when its matching spawned process has exited without submitting. This is a computed diagnostic, not a stored status. Their JSON includes `exited_claims: [{ id, agent, pid, log, code, size, tail }]`. `code` is the recorded foreground exit code or null when unknown; `size` is the log's size in bytes or null when unavailable. Text names the process and log, includes a tail of at most 20 lines from the final 8192 bytes, and directs any agent to recover the verified exit with `release --reason`. It never prints a command that supplies owner identity. Missing logs leave the exit visible with a `log unavailable` diagnostic. Foreground spawns retain logs; legacy events with `log: null` have an empty tail.

A `spawn phase` event with `active: false` for that spawn's agent, attempt and pid proves the exit from the event log, so every observer gets the same answer; the supervisor records it only after the harness exited, its process group is gone (on Windows, where the monitor does not track the harness's descendants after it exits, only the harness pid) and no retry or fallback route remains. Without such a record or a `spawn exit` receipt, the views probe the pid. Only the current claimant's most recent spawn counts. A worker can claim after its spawn; earlier claims, release, submit and rework events fence off older spawn records. Reclaiming an expired lease under the same agent identity does not inherit the previous claim's spawn. A submitted task or a manual claim with no matching spawn is not an exited claim. Reading either view writes no state, changes no lease and starts no replacement.

The host recorded by `spawn` bounds local pid checks to that host; older events without it are assumed local. Permission errors and processes on another host do not establish an exit. Linux checks recognize zombie processes and compare the recorded process start time to catch a reused pid. Other platforms use missing pids and recorded foreground exits.

A worker spawn event records the task's `revision`. The supervisor's write of a worker's `spawn exit` also applies the respawn cap: when the task has 3 worker exits at its current revision without a submit, counted since its last `submit`, `owner-done` or `task update` that cleared `needs_owner`, and the task has no owner ask yet, it sets `needs_owner` and appends `respawn cap` with `{ cap, exits, revision, agents, log, needs_owner }`. A run whose monitor died has no `spawn exit`; its `worker-exited` counts instead, and the observer's write that records it applies the cap. Exits with `availability_failure: true`, runs ended by an `interrupt` or a `budget stop`, and runs whose own worker's `release` (its `holder`) records open `decisions` do not count. A `worker-exited` does not count while that run's monitor is still running; its `spawn exit` decides. `task show` adds `respawn_cap: { exits, cap, agents, log, tail }` while that ask holds, with the tail read from the log at show time; state never stores it.

Any agent recovers a verified exited task with `release ID --reason R`. The detector rechecks under the lock; a live or unverified process requires the claimant or the owner; the orchestrator's attempt opens a decision. The usual prior `todo` or `rework` status is restored. The supplied reason stays in the release note; only the observed pid, log path, exit code and log size are preserved in an additional note and the release event's `detail.exited_spawn`. Release does not read or persist log text; the views read the tail live from the log file. Releasing clears the diagnostic; a new claim does not inherit the old process.

## Dispatch events

A `spawn` detail includes `role`, `rung`, `agent`, `harness`, `model`, `profile`, `billing`, `pid`, `host`, `start_ticks`, `pidns`, `cwd` and `log`. `billing` is the route's `api` or `subscription` (see `spend.entries`), or null for a harness without billing, a local Codex provider or a Codex route that cannot be resolved. `model` and `profile` may be null; `start_ticks` and `pidns` are the Linux process identity when available. `pidns` is the recorder's pid namespace (`/proc/self/ns/pid`), where the recorded pid names the process; every record that names a process this way carries it, and a reader in another pid namespace, or one that cannot read its own, never takes such a pid for exited, since a sandbox's namespace hides live processes outside it. The supervisor records `monitor_pid` in the same namespace, so every reader that rebuilds the supervisor or harness record from a spawn detail, such as a reservation or an exit probe, keeps `pidns`. Codex adds `codex_home` to find its exact session under a custom `CODEX_HOME`; legacy events fall back to the current `CODEX_HOME` or `~/.codex`. Both foreground and detached output has a log. A `spend` detail is the entry above; automatic entries name the spawned agent; the audit event names the collector or waiter that recorded them. `spawn exit` records the foreground exit code and rung, and `output_held` when its output stayed open after the harness exited (see the process group shutdown below). A release of an exited spawned claim records `{ reason, holder, status, exited_spawn }`, where `exited_spawn` contains only `{ pid, log, code, size }` observed at release. Unknown exit codes and unavailable log sizes are null. No log text is copied into task notes, release events or worker-exited events. The shared observer records exit wakeups and spend without releasing the claim.

## Hooks and notifications

`type` identifies the event and `to` names the recipient. Every state change goes to `orchestrator` unless a message supplies an explicit `--to`. Commands map to notifications: submit to `submitted`, accept to `accepted`, rework to `rework`, successful merge evidence to `merged`, msg to `worker-message`, owner task or decision notes to `owner-comment`, ask to `decision-opened`, answer to `decision-answer`, decision withdraw to `decision-withdrawn`, release to `released`, and owner-done to `owner-done`. Review and other gate evidence wakes as `evidence`; other changes keep their command name as the type. There is no notification allowlist to hide a new state change: a default `wait` skips only the bookkeeping that arrives with every tool call or lease tick (`hook progress`, `hook report`, `hook inbox`, `renew`, `spend`, `spend live`, `spawn session`, `inbox snapshot`, `inbox ack`, `gate run`), and every event recorded as `owner` reaches the orchestrator whatever its `to`. A `msg` detail is `{ to, text }`, plus `steer: true` when it was sent with `--steer`.

Harness adapters use the CLI `hook` command under the identity fixed in `homes/<agent>/hook.json`. The binding contains `{agent, task, state, harness, attempt}` and cannot name owner. An orchestrator-rung home adds `role: "orchestrator"`, `after`, the byte length of `events.jsonl` when the home was built, and `cuts`, the length of `events.cuts.jsonl` then, which together resolve as the cursor `after:cuts` does for `wait`. A tool through 0.1.2 reading a newer home ignores `cuts` and treats `after` as a plain offset: its `inbox` and `stop` deliver the events a default `wait` would return after that offset, as a list of ids, kinds and authors without detail, and acknowledge them with `hook inbox` receipts. Its `stop` with nothing pending returns `{block:false, hold:true, offset, cursor}` while any task is still open or an accepted PR remains unmerged, and the bridge blocks in `wait --inbox --after cursor` before asking again. The bridge resolves its own binding from the dispatch environment, accepts no binding path, and refuses a binding identity that differs from the caller. Claude and Codex sandboxes protect the generated home and hide every other agent home; Codex session storage is scoped to the agent. Opencode confinement is permission-level only: native file-tool paths cannot stop interpreters or absolute executables approved through Bash. Worker, research, reviewer and small profiles allow explicit task CLI, shim, test-runner and read-only commands and deny unlisted Bash commands. Headless run has no `ask` rules; approved interpreters and test scripts can reach paths outside the worktree and permitted writable directories, or invoke absolute Git/gh executables to bypass publishing denials. Named Git/gh denials apply only to matching Bash requests and shim calls. Both `sandbox` and `osSandbox` remain false, so moving a confined role to opencode is owner-required. Opencode loads its generated message plugin. The plugin invokes the hook bridge with the Node executable that rendered the home; the launch environment replaces caller `PWD` with the task worktree. Agy has a generated startup configuration, but native enforcement is unsupported. Its emitted permission entries are requests, not a guarantee that other homes are hidden or that commands are confined. Its capabilities remain false, so it receives no broker token. Pi isolates configuration and tools without a command sandbox. Command adapters have bindings and command shims without permission renderers. Payload fields never override the binding.

Tool progress appends one `hook progress` row to `progress/<agent>.jsonl`. It takes no lock and reads no state, and a failed append drops the row. No state decision reads it; the supervisor counts a change to the file as activity, as it does for the agent's log and progress paths. Progress rows written to `events.jsonl` before this file existed stay in place, so byte cursors hold, but state snapshots skip them.

An inbox poll, the `UserPromptSubmit` hook and the poll after each tool hook, reads the event log without the lock and returns empty context at once when nothing is pending. With messages pending it tries the lock once, without waiting. A busy lock returns empty context and leaves the messages unread for the next hook. The bridge also turns a failed progress append or poll into empty context with a note on stderr, so neither fails the harness turn. Other hook calls, explicit acknowledgements with message ids, and supervisor writes keep the 65 s per-call limit, which covers the 60 s lock bound plus 5 s; generated registrations allow 135 s for the two calls after a tool. An orchestrator's `Stop` keeps its one-day event-wait allowance.

## Lifecycle events

Hook state lives in the event log, except tool activity, which goes to the agent's progress file:

| Command and type | Detail |
| --- | --- |
| `hook inbox` | `{messages: [event id, ...]}` acknowledging messages delivered to this event's agent |
| `hook progress` | `{harness, tool}`, in `progress/<agent>.jsonl` only; activity for supervision |
| `hook background` | `{harness, attempt}`; a Bash call with `run_in_background` started in this dispatch attempt |
| `hook wait` | `{harness, attempt, source, reasons}`; the one hold a headless worker's stop took before submit, with source `hook-wait:<agent>:<dispatch attempt>` |
| `hook report` | `{report}` captured assistant text |
| `hook git-push`, `hook pr-created` | `{harness, unverified: true}`, meant for a successful shim command; an agent's own binding records it with no push or PR, so it is a hint: check GitHub or the repository before acting on it. A sandboxed codex agent's shims record neither, since its sandbox hides its binding |
| `hook stop` | `{harness, submitted, report, source}`; source is `hook-stop:<agent>:<dispatch attempt>` |

Unread messages are `msg` events with `detail.to` equal to the bound agent and ids absent from its `hook inbox` receipts. Receipts use the state lock; a poll with nothing pending reads the log without it. Payload `ack:false` returns context and message ids without a receipt; a later inbox call with those `ids` writes the receipt. OpenCode delivers only to the session captured by the dispatch's first chat callback and writes its idle delivery receipt after `promptAsync` succeeds. Failed requests leave messages unread. A stop held for unread messages acknowledges them without emitting a final report. Once stopping is allowed, `hook stop` also emits a `msg` to `orchestrator` describing submission state and the last report. Identical reports for a dispatch are deduplicated; a changed report or submission state emits a follow-up. A supervisor stop after process exit leaves unread messages queued. Rework and transient resume prompts include pending messages and acknowledge the included ids after launch. A dry run does not acknowledge. See [CLI: event wakeups](../cli.md#event-wakeups) for each harness's injection and stop limits, including Codex notify and agy's missing resume adapter.

`tower-crane wait` watches this log from an exclusive id or byte cursor and returns the first matching notification as one JSON line (`--follow` prints an id-only line per notification instead and keeps running). Its `offset` is computed when reading and counts UTF-8 bytes through the newline; it is not stored in the log. Default `now` skips complete historical lines. Save the returned `cursor` (or id or offset) and pass it to the next wait so events during handling are not missed. Filters combine recipient, task (including a decision's `detail.blocks`) and event types. Writes by the waiter's agent are skipped, except events recorded as `owner`, `via: automation`, and `worker-exited` and `stall` observations. Owner input remains visible when the waiter also runs as `owner`; observations reach the waiter that appends them. Timeout is a separate `{"type":"timeout","offset":N,"cursor":"N:CUTS"}` result, not an event. Each result's `cursor` is its offset with the length of `events.cuts.jsonl` the reader had applied; passing it back resolves exactly across a lock recovery's cut. Its cursor includes complete lines skipped by filters. See docs/cli.md for options.

Startup and resume without a saved cursor use `wait --timeout 0` to take the current complete-line offset before reading state once. This snapshot emits no observations. The next blocking wait starts from that offset and observes current exits and stalls, keeping events that arrived during reconciliation without replaying history. Owner POST routes preserve serve's identity and require it to be explicitly `owner`; non-owner serve renders no owner forms and refuses those writes.

`spawn` records the job in `role`, the ladder `rung`, generated agent, pid, host, Linux process start ticks when available, and log in its event. The wait engine uses the shared `lib/processes.js` detector for a worker's exit without submission, including failure before claiming, and appends `worker-exited` with agent, pid, attempt, log path, exit code and log size. Log tails remain in the log file; views read them live. It also appends `stall` when both the lease and claimant progress are stale (no progress within the most recently granted claim or renew lease interval). Other claimant writes advance progress; claim and renew do not. Submitted tasks do not produce these events.

Only `owner`, `orchestrator`, spawned agents whose recorded role is `orchestrator`, and verified spawn-monitor collectors run automatic exit and stall observations. The collector CLI must have the recorded monitor as its parent, with a locally visible process matching the recorded host and Linux start ticks when available. Sharing a worker's agent name grants no observer role. Worker, reviewer and other observer identities consume events through `wait` without probing peers or appending lifecycle observations; their explicit usage collection does not scan other tasks. Orchestrators and monitors must run with visibility of worker pids, since `ESRCH` in an agent sandbox can describe a live but hidden worker. Foreground collection keeps the dispatch caller's audit identity; spend entries still name the spawned agent.

New spawns run through the existing `spawn-monitor.js` exit observer, which is the harness parent in foreground and detached modes. It renews the same claimant's most recent lease duration when half the lease remains, while the child runs or a rerun is pending. This margin leaves half a lease for delayed state writes. A worker's submission, release, cancellation, replacement of its claim or a newer spawn stops lease keeping and retries. Reviewers launched on a submitted task keep their retry budget while its submitted sha and revision remain unchanged. Reruns preserve the generated agent, claim `since`, worktree, resolved route and log. A `spawn retry` event replaces the current harness pid without counting as another dispatch. Resumed retries share a spend source; fresh retries record `fresh: true`, `resumed: false` and a new log byte `log_start` for their separate usage receipt. A state-lock timeout keeps the scheduled attempt pending; it does not consume another retry.

Exit 75, SIGTERM, SIGINT, and nonzero exits with a harness-level provider 5xx or outage are transient. Evidence comes from Claude error records (`is_error` or `api_error_status`), Codex `error` or `turn.failed` events, or harness stderr. HTTP 429, rate-limit, temporarily-unavailable and overloaded messages also qualify when reported inside those harness error records. Plain text cannot substitute for an error envelope for these capacity signals. Assistant messages, tool results and other agent output do not classify an outage. The supervisor retries the same route with exponential backoff, capped by `max_backoff_ms`. A provider outage after the route's retry budget advances to its next configured fallback. Exit 75 or a signal alone does not switch routes. A permanent exit, exhausted fallback list, or missing supported session without fallback-enabled outage recovery records `blocked` with a reason and leaves the claim for recovery. A successful exit without submission records `waiting`. A live single-tier stalled process records `blocked: no progress paths or CPU activity`, emits `stall`, and keeps its lease; path, claimant or CPU progress restores `running`.

A resumed Codex or command-adapter session that fails with context overflow gets one fresh retry on the same route, independently of the transient retry budget. Evidence is Codex's `ran out of room in the model's context window` error or Claude's `Prompt is too long` error, including Claude API-error assistant records; quoted work output does not count. The supervisor rebuilds the full task prompt, brief and rework notes in the same worktree with the same agent and claim. It records `spawn fallback` with `reason: "session context overflow"`, `fresh: true`, and `previous.overflowed: true` naming the failed session. An overflow that ends supervision records `overflowed: true` on `spawn exit`. Session eligibility excludes ids marked by either event from later resumes. A fresh attempt that also overflows blocks without another retry. A successful turn completion clears a recovered overflow error. Native Claude dispatch already starts fresh. There is no prelaunch size cutoff: the supported harness interfaces do not provide a reliable current-session size and limit probe, and cumulative usage is not context size.

A structured harness policy refusal advances to the next fallback without outage retries, including when the harness exits zero. Codex and command adapters accept `refusal`, `response.refusal.done`, an `item.completed` refusal item, or an agent-message item with a non-empty `refusal` field. Claude and command adapters also accept `assistant` or `result` records with `stop_reason: "refusal"`, `subtype: "refusal"`, a message stop reason, or a refusal content block. Quoted policy text and tool output do not qualify. A refusal without a remaining fallback blocks and returns a nonzero dispatch result.

A harness login failure is a harness outage, not a task attempt. Evidence comes from the same error envelopes and stderr as outages, plus three records that outage parsing does not read: an agy result with `status: "ERROR"`, an OpenCode `error` event, and a pi `message_end` assistant message with `stopReason: "error"`. The phrases are `Failed to authenticate`, `authentication failed`, an expired OAuth session, `Not logged in`, a sign-in-again message, and an expired refresh token. Claude, Codex, command, agy, OpenCode and pi records match them, and so does stderr text: Codex's expired login prints `Please log out and sign in again.` on stderr. Assistant messages and tool output do not classify it: a JSON record on stderr counts only as one of those error envelopes, so a quoted assistant or tool record never does. A login failure is never retried on its route, and it counts whatever the exit code: pi exits zero after its failed turn. A login failure on the route that ends the dispatch makes `spawn --wait` exit 1, and a healthy fallback after it keeps the success. The exit records `availability_failure: true`, so a ranged task does not climb a tier. The supervisor appends `harness health` with `{harness, status: "unavailable", reason, agent, source: "exit"}`. The first failure of a pause also appends a `msg` to `owner` naming the harness, its reason and its re-login command (`claude auth login`, `codex login`). Later failures of the same pause record health without another notice. A login failure falls back only to a route on a different harness, without outage retries. Dispatch takes no route on a paused harness: the rung runs on its first healthy route, with the healthy routes after it as fallbacks, or refuses with the reason.

Host login checks in `lib/harness-health.js` keep the dispatcher's `NODE_OPTIONS` by design: they are host commands. The agent environment's Node-option filtering does not apply to them.

The pause is the latest `harness health` event per harness, so it survives restarts. Before dispatch reads state, a spawn that is not a dry run runs the due login check of each paused harness, at most every five minutes. The check's interval is claimed under the state lock first: the claim appends `unavailable` with `source: "probe"` and a `probe` token, and the check runs after it, so concurrent spawns run one check. Each check is one tiny request, because stored credentials are not enough: `claude auth status` reports an expired login as logged in. Claude's check is `claude -p "Reply OK." --model haiku --max-turns 1 --tools "" --no-session-persistence --output-format json`, which passes on `is_error: false` with `subtype: "success"`; Codex's is `codex exec --json --ephemeral --skip-git-repo-check -s read-only "Reply OK."`, which passes on a `turn.completed` event. A check that exits nonzero, or runs past 60 seconds, fails. A passing check appends `available` with `source: "probe"`, and a failing one appends `unavailable` with `source: "probe"` and its reason; the next check waits five minutes. Either result is recorded only while the claim is still the latest `harness health` event. Any such event since the claim, such as a login failure, makes the check stale: it appends nothing, and the pause stands. A harness without a login check has no probe: one spawn per interval is let through to test it. The spawn that takes it, as the rung's route or as a fallback the supervisor selects, appends `unavailable` with `source: "probe"` and a `probe` token under the lock, which starts the interval. A dispatch records it with its spawn event, so a launch that fails, even after a lease-first handshake committed the worker's claim, starts no interval. Only that spawn's clean exit (code 0 without a login failure) appends `available` with `source: "spawn"`, and only while its probe is still the latest health event: a worker that started before the pause, or any failure since the probe, clears nothing. Clearing a pause raises no notice.

Every route switch starts fresh with the original brief and task, the same generated agent and worktree, and a rebuilt isolated harness home. It never passes the previous route's session id to resume, even if both routes use Codex. The claim remains unchanged, the retry counter resets to zero, and the new route has its own bounded retry budget. `spawn fallback` emits type `spawn-fallback` to the orchestrator, recording the new `route`, zero-based `route_index`, model, profile, harness, session, pid, log byte `log_start`, reason, and previous process/route detail. Retry, phase and exit records carry the current route metadata. A dispatch that switched routes is not eligible for rework resume; its next dispatch starts fresh after the previous worker has exited. Rework refuses another dispatch while that worker is live or its exit is unverified, even when a fresh session is required.

Ranged workers use a separate quality path. A failed independent review or confirmed tests, clean or CI gate failure at the current submission, an exit without submit (including exit zero and exits before claiming), or a confirmed supervisor stall climbs one tier within `tier_range`. CPU-based stall confirmation requires Linux process metadata. A stall terminates the old worker group and waits for pipe closure and group cleanup before recovery. Review failure waits for the submitted worker to exit. A brokered review records evidence but leaves full-findings rework, the climb and launching to the trusted host monitor or orchestrator wait; the broker executes no repository commands. Recovery collects its usage, clears the claim, sets rework, records `escalate` and dispatches a new agent with the original brief and rework reason. A climb never resumes a session, even when both rungs have identical models or routes. `recover ID` and concurrent observers deduplicate the same failure under the lock. If dispatch is unavailable or capacity is full, the recorded climb stays pending for `recover` or a subsequent orchestrator `wait`.

Quality recovery uses the latest eligible verdict per review or software gate at the current head and revision. `confirmed_failure: true` is recorded by the software gate runner and matched to its audit receipt. It denotes a failed test command, a completed cleanup scan with HIGH findings and no scan gaps, or a completed failing CI run. Configuration errors, incomplete observations, pending CI and missing workflow results remain unconfirmed. A later passing verdict for the same gate removes its failed-attempt trigger. A later passing verdict supersedes an earlier failure; self-reviews and stale verdicts do not replace it. While a worker monitor is running or its exit cannot be verified, recovery needs its matching terminal `spawn exit` receipt with `active: false`, even after submission. A parent's exited PID or an exit notification does not prove its descendants stopped. When the monitor is verified exited, authorized host observers must also verify that its worker process group is gone before recovery. POSIX harnesses start detached, so the recorded launch PID is their process group id. On Linux the host checks that group and ignores zombie members that cannot execute. A parent exit or `worker-exited` notification alone cannot authorize replacement. Live or unverifiable groups keep the failure eligible for retry and record a deduplicated `recover waiting` event and task note with the reason. `recover --json` returns that reason in `waiting`; unsupported platforms or inaccessible process metadata require a terminal cleanup receipt.

`rework` captures and records a known failed attempt before its submitted status is lost. The tier climbs immediately, or the range ceiling opens its owner decision, even if the worker still has pending cleanup. Its fresh dispatch remains pending until the cleanup guard passes. Usage collection can enrich current rung totals after cleanup; the recorded climb retains its snapshot.

Orchestrator `wait` treats recorded but unhandled failures as recovery candidates independently of exit-notification deduplication. Recording `worker-exited` through spend collection or an earlier wait does not consume a climb. A recovery lock timeout leaves the failure eligible for the next watcher or timer check; its notification remains recorded once. A task-specific recovery refusal, such as an unavailable or mismatched linked review comment, is reported without ending the wait host or stopping other tasks' gate reactions and worker refill. The submission remains unchanged until its findings can be resolved. `wait --observe` retains this ranged quality recovery, including full-findings rework, but skips submission automation and capacity refill.

At the maximum tier, recovery records `to: null` and opens one free-text decision blocking the task. The owner can change the plan, extend its range, retry or cancel; answering alone does not dispatch a worker. Availability failures exhausted on the same rung record `availability_failure: true` on the exit receipt and do not quality-escalate. Single-tier tasks do not quality-escalate, but trusted `wait` reworks their current failed reviews and releases verified dead claims before refilling worker slots. A stopped or failed supervisor does not initiate a climb itself; `wait` can recover a verified worker exit after a lost supervisor. Unknown process identity or a live worker never authorizes replacement. Native workers without a spawn receipt keep manual exit and stall recovery.

Both rework and transient retries use the resumable-harness policy in `lib/spawn-session.js`. Codex resumes the exact thread id from its log. Command harnesses receive stable `TOWER_CRANE_SESSION` and the zero-based `TOWER_CRANE_RETRY` attempt counter within each route. Resumed attempts receive only a short interruption note, including the previous exit code or signal, through the prompt argument or `{prompt}` substitution. Claude reruns fresh with a new reserved session id, the original brief and the interruption note; measured native Claude resumes rewrote the fixture's cache. With a configured fallback list, provider outages without a supported session rerun fresh on the same route until its budget is exhausted. Other transient exits without a session adapter block. `--fork-session` is not used for transient reruns.

Child exit and pipe-close events wake the existing monitor immediately. Progress-path walks and CPU sampling run once per second, independent of state events. The monitor checks lease renewal on that interval or when events change, and caches loaded state until `events.jsonl` size or mtime changes. A one-second interval bounds normal lease and stall observation delay without walking a multi-hour agent's worktree ten times per second.

On POSIX, natural agent exit cleans up its non-retained background processes. For contained launches, containment sends SIGTERM to the identified non-retained processes, allows up to five seconds for cleanup, then sends SIGKILL to survivors. Independently retained work stays within its existing bounds under a keeper. Containment failures stop the whole owned attempt immediately. Fixture or uncontained launches and stopping the monitor use the process-group shutdown path: SIGTERM, five seconds of grace, then SIGKILL. Reruns wait for the previous owned cleanup and output-pipe closure, including descendants with redirected output. Windows stops identified non-kept processes individually when retaining work and uses `taskkill /T /F` for full containment cleanup; it never tree-kills a released harness pid on natural exit. A supervisor, broker or gate stop whose `taskkill` fails or outlasts its 10-second timeout while the process still runs then stops that process through its own handle.

Once the harness has exited and its group has stopped, the output pipes get the same five seconds more. Waiting for the group first lets SIGKILL end a member that ignores SIGTERM before anything counts as a holder. A process that still holds them then left the group (a dev server or watcher started in a session of its own) or runs on Windows, which has no group. The monitor stops the processes it can still trace to the harness, gives the pipes two seconds to drain (the software-gate runner's drain), then closes them. Output already read stays in the log and the foreground stream. On Linux it stops, with SIGKILL, the processes that carry the launch's own environment marker `TOWERCRANE_SPAWN_RUN_<monitor pid>_<random>` and their descendants, selected by the marker alone, since the exited harness's pid may now lead another group. A process that cleared its environment and left the group is not found. Every supervisor, harness and gate command starts without an inherited `TOWERCRANE_SPAWN_RUN_*` marker, so a task an agent dispatches, or a gate its wait runs, is not that agent's to stop. A gate's own `TOWERCRANE_GATE_RUN_*` marker stays inherited, so whatever a gate command starts stays inside that gate's cleanup. Cleanup spares recorded dispatch supervisors and registered orchestrator `tower-crane wait|check|accept|merge` processes, together with their descendants. It validates pid/start identity rather than trusting command names or `TOWERCRANE_SUPERVISOR`: a dispatch the agent left running, such as a detached `spawn --wait`, is stopped, but the supervisor it started and that task's agent keep working. A supervisor whose foreground dispatch is gone stops forwarding output and keeps its log. On Windows it takes one process snapshot, skipping each recorded supervisor (`lib/spawn-monitor.js`) or registered controller identity, everything below it, and its parent (libuv keeps a child that is not detached, such as a foreground `spawn --wait`'s supervisor, in a job that kills it when that parent dies), of each process that names the harness pid as its parent and started while the harness ran, then each live process that started after a parent found this way; a process whose own parent already exited cannot be traced. Asynchronous PowerShell calls of at most 350 processes each, to stay under the Windows command-line limit, then open every process, read their creation times from CIM as the snapshot did while holding the handles, and stop each through its handle, parents first, only if its creation time equals the snapshot's, so a pid reused since is left alone. A process that exited before its turn is skipped; one that could not be stopped is named on stderr. Other systems close the pipes without stopping a process outside the group. The attempt then finishes as if its pipes had closed: lease renewal stops, a retry or fallback can start, and `spawn --wait` returns the harness's exit code. stderr names the stopped pids, and the final `spawn exit` records `output_held: { pids, error? }`, where `error` says why no process list could be read.

Signal retries use the signal reported by Node's child-process observer. Windows self-termination reports an exit code instead; a Windows adapter can use exit 75 to identify a transient stop.

Command harness `{brief}` context is an exclusive mode-`0600` temporary file, with no per-copy directory. A single unlink removes the complete resource. The monitor removes the current route's copy after stream closure and process-group shutdown, and on startup or supervision failure. A failed dispatch stops its supervisor and waits for closure before removing any remaining copy and returning. `spawn --wait` removes its copy before returning on normal, nonzero and signal exits.

The CLI transfers a spawn job through a private file in its startup cache directory, then removes it after the monitor reads it and reports the harness pid. The monitor starts with the dispatcher's environment and its user file path resolved. What the agent adds to it (home, shim `PATH`, caches, identity, `TOWER_CRANE_SANDBOX` and credentials) travels with the job's other env values and applies only to the harness process. State commands the monitor and its broker run carry the agent's `TOWER_CRANE_STATE`, `TOWER_CRANE_TASK`, `TOWER_CRANE_AGENT` and `TOWER_CRANE_HOOK` over the dispatcher's environment, nothing else of the agent's. Prompt size stays bounded by the harness argument, without a duplicated supervisor argument. Foreground output is captured by the monitor through the inherited log descriptor before it is forwarded to the CLI. Exit classification waits for both harness pipes to close, including when the dispatch CLI is busy rendering.

`spawn` and `spawn phase` events record `{ agent, pid, monitor_pid, host, phase, retry, active, reason }`, plus process identity when available. Off Windows they also record `run_mark`, the name of the launch's `TOWERCRANE_SPAWN_RUN_*` environment marker; a spawn keeps an exited agent's home and broker directory while a process carrying any of that agent's recorded markers runs on Linux. One `/proc` pass reads every agent's markers when an exited agent with a recorded marker needs the check; an agent with no recorded marker needs no pass. `status` names each home kept only by such processes, `home kept: AGENT by a stray process PID` for one PID or `home kept: AGENT by stray processes P1, P2` for several, and its JSON lists them as `kept_homes: [{ agent, pids }]`. A missing homes directory or one denied with `EACCES` or `EPERM` reports no kept homes. A `spawn` event also records `startup_ms`, how long each supervisor startup phase took, in whole milliseconds: `ready`, from launching the supervisor to its handshake's ready file, and `lease`, recording the lease and opening go (both only for a worker started through the handshake, as on Windows); `receipt`, from go, or from the launch when no go was opened, to the supervisor's receipt; `total`, from the launch to the receipt; and `supervisor`, the supervisor's own phases measured from its process start: `boot` (Node start, module load and job read), `setup` (to the handshake's ready file or the launch), `go_wait` (handshake only) and `launch` (starting the harness, to the receipt). Each dispatch window has the fixed 10 s deadline. `supervisor` is null when the supervisor finished no phase. `phase` is `running`, `retrying`, `waiting` or `blocked`; text views render `retrying N` and `blocked: text`. `status` JSON includes `runs: [{ id, run }]`; `task show` includes `run`, or null after a lifecycle boundary. The board and serve display the same recorded phase. Phase-only writes rerender saved sketches even when task data does not change. A live supervisor with an active run suppresses interim `worker-exited`, early spend collection and non-claimant recovery during backoff. Terminal exits use the shared locked observer to emit one exit notification and collect usage once per route and fresh retry invocation for the dispatch, using log byte boundaries to keep sessions, models, profiles and harnesses separate. The primary source remains `spawn:<agent>` (or its resumed attempt source); fallback sources append `:route:<index>` and fresh retry sources append `:retry:<retry>`. Each invocation contributes to task spend; cumulative usage within a resumed session is counted once. Repeating collection enriches or keeps those entries without double counting.

Exit and stall observations are rechecked and deduplicated under the lock, using a `detail.source` key for the current claim and pid or lease/progress deadline. Concurrent waits see the same event. Detection itself does not clear a single-tier task's claim or change its status. A trusted automation reaction to a verified worker exit runs `release --dead` before refilling slots through `spawn --ready`; `wait --observe` only reports the exit. Stall observations alone do not release claims. Ranged tasks use the quality recovery above. Directory watching plus an internal one-second stat and process check keeps callers blocked until an event or their deadline. The engine closes all watchers and timers when a wait ends.

The trusted `wait` host releases verified dead claims and fills available worker slots through `spawn --ready`, including todo and rework tasks, on a path of its own beside the event reactions: a gate reaction that runs the full suite does not delay it. This also recovers capacity freed before its cursor. Startup, notifications, the fallback tick and the end of each reaction pass trigger the capacity check, as does a timer set to the earliest `gates.rework_hold_min` hold end, so an ending hold dispatches with no other event; a default zero-timeout cursor snapshot does not. One refill runs at a time in a host, and it skips a task whose own gate reaction is still live. A wait ends, by event, timeout or signal, only once neither its reaction pass nor its refill is running; the refill after a pass's reactions runs even when the deadline or a wake came during the pass, so a slot its rework or merge freed fills before the wait returns. `status` names why automatic refill leaves each ready task undispatched (`not dispatched`; JSON `not_dispatched`): no brief, its gate reaction running, a rework hold until a time, the worker limit with its holders, higher-ranked tasks taking the free slots, the dispatch lock's holder, read without clearing a stale lock, or the host governor's latest worker deferral. Spawn retains its worker limit, urgent-first order followed by unblock count and task id, routing, fallback and locked reservation checks. A failed independent review at the submitted head and revision calls `rework --from-review` before inspecting mergeability or running software gates; a failure whose findings are all in the PR body instead dispatches a body-only worker repair while keeping the task submitted. Findings and their comment link are copied into the reason and brief after the existing locked recheck. Rework increments the revision, so a replayed or stale review cannot send that submission back twice. Slot refill runs only in the trusted `wait` host; `wait --observe` and worker waiters skip it.

Each wait remembers ordinary refusals per task in memory for one minute. It retries sooner when that task's dispatch inputs, its kind's ready ordering, brief or task-update receipts, project settings, personal ladder-set receipts or worker holders change. Automatic light-review context is also a dispatch input. Task notes and fallback ticks during that minute do not repeat expensive preparation or its stderr diagnostic. The next timer tick after the minute retries unchanged inputs, including external branch or harness repairs with no event. A successful dispatch clears that task's refusal. Governor deferrals and dispatch locks are never ordinary refusal-cache entries: deferred tasks remain eligible each pass while other tasks keep their own minute cache, even within one kind. This adds no persisted retry fields.

The capacity check clears verified dead worker reservations through the same locked path as `spawn --ready` before counting holders. Cancelling the originating task does not hide its dead reservation from this cleanup.

Ranged review recovery fetches the full matching findings through `rework --from-review` before its revision changes or its climb is recorded. Reviewer and broker callbacks leave that step to the trusted host. `accept` returns a current independent FAIL and its inbox action with exit 1, leaving the submission unchanged; operational `--retry-review` explicitly permits another review at that head and revision. Real review dispatch still reworks a submitted task with a current code FAIL. PR-body false claims and title findings take only the light path. Missing or mismatched findings refuse without changing the task; dry-run review previews do not rework it.

Automatic dead release requires the existing cleanup proof: a terminal monitor receipt or verified monitor exit and an empty process group. A surviving or unobservable descendant keeps the claim and worker slot. Cleanup is checked again under the release lock. Ranged tasks awaiting exit classification or a quality climb keep their claims for quality recovery. A recorded availability failure can release after cleanup when no climb is pending.

## Dispatch receipts and inbox

Each `spawn` also records `route`, `attempt`, `session_id` and `resumed`. A fresh spawn after an isolated session file is missing records `resume_fallback_reason` with the reason it did not resume. A claude spawn whose agent cannot reach something it may expect to records `notices`, the lines spawn also prints: remote hosts claude's sandbox host list leaves out, or a cache root too deep for claude's proxy sockets ([ladder.md](../ladder.md)). `route` holds the resolved rung fields. `attempt` counts spawns for this job and task, including resumed attempts that keep their agent name. Resumed attempts use a distinct log named `<task>-<agent>-attempt-<n>.log`. A resumed Codex dispatch includes `usage_before`, its session's cumulative counters before the new turn. Usage collection subtracts this snapshot; if it is unavailable, the resumed attempt's usage stays unknown. Its spend source is `spawn:<agent>:attempt:<n>`; fresh spawns keep `spawn:<agent>`. Dispatch collects the previous attempt before starting a resume, and repeated collectors update the same attempt receipt.

Harness-specific credential inputs come from the final route resolved under the state lock after worktree preparation. Shared GitHub auth is prepared outside the lock. OpenCode initializes its private mode-600 active auth store with only the rung model's provider entry, if it is API/OAuth, on the primary launch and on fallback launches; wellknown entries and unrelated provider logins are excluded. The private credential copy is inside the role home and removed with it. The source credential file is read without linking the raw store into the agent's home. The launch clears `OPENCODE_AUTH_CONTENT`, so native lookups observe OAuth refresh writes to that store instead of a stale environment snapshot. Refreshes do not change the user's source file. Credential values remain outside argv, generated config, previews and event receipts.

A `startup` event precedes each started agent's `spawn` event, and each route fallback's `spawn fallback` event: the receipt of what the agent was given, `{ agent, role, harness, goal, target: { id, title, acceptance }, rules: [{ path, scope, loaded, bytes }], rules_bytes, rules_tokens, instructions_file, prompt_bytes, prompt_tokens, resumed, receives_prompt, attempt }`. `target.acceptance` is the number of acceptance items, not their text. `scope` is `global`, `project` or `import`; `loaded` is `harness` (importable by the harness at start), `read` (the prompt tells it to read the file, without claiming it was read), or `system` (a Claude/Codex review snapshot). For agents using path imports, Claude quotes paths containing tabs with literal tabs, and marks paths containing line breaks `read`. Claude imports include the generated home's hop in its five-hop limit; files beyond that limit are marked `read`. Codex prefers `AGENTS.override.md` over `AGENTS.md` per directory. Opencode records every house-rule file as `read`, because project instruction discovery is disabled, and `instructions_file` names its generated `agents/gishra-<job>.md`. Its rule paths use the original user config, including a custom config directory and the Claude global fallback. Other harnesses receive their global files as `read`. A command dispatch requires `{prompt}` or `{brief}` in its command argv; without either, spawn refuses before writing a startup receipt. Isolated reviewers also record `system_bytes` and `system_tokens`, separately from the task's user prompt. Claude's reviewer `instructions_file` names an empty `CLAUDE.md`, since its static text is passed by flag; Codex's names the populated `AGENTS.md`. Token estimates are bytes divided by four, rounded up, not measured API cache usage. A resumed session got these with its first prompt.

`session_id` is null on a fresh dispatch and names the reused session on resume. Once stdout exposes the id, an append-only `spawn session` event repeats the attempt's spawn detail with its `session_id`. Match by task, agent, pid and attempt; do not rewrite an earlier event. Codex reports it in `thread.started.thread_id` and Claude in its JSON result. A command harness can emit either record. Session ids stay out of prompts and briefs. On rework, resume selects the most recent worker attempt only when it belongs to `submitted_by`, its session is known, its route and worktree match, and the previous process has exited. Before an isolated Codex resume, spawn checks for the matching rollout under `homes/.codex/<agent>/sessions`. Native Codex resumes; native Claude starts fresh with the review note because measured resumes rewrote its cache. A command adapter can resume through its `{session}` protocol. A missing session or changed rung, route, harness or worktree permits a fresh spawn with the full brief and review note. Review spawns do not resume.

Foreground and detached `spawn exit` events and `worker-exited` observations record the attempt as well as the agent, pid and exit code. A receipt with an attempt matches that attempt's launch by task, agent and pid. A receipt without an attempt matches the latest preceding `spawn`, `spawn retry` or `spawn fallback` with the same task, agent and pid. Both formats release an unclaimed reservation and prove exit for resume, usage collection and recovery. An earlier receipt cannot prove that a later launch exited, even when its pid is reused. The shared resolver is `lib/processes.js`'s `exitSpawn`; `lib/spawn-session.js` exports the shared `exitedAttempt` and `eligible` checks for dispatch and usage collection. When observing an older spawn without an attempt field, the writer derives its attempt from its position in that task and job's spawn history.

<a id="submission-history"></a>

Workers merge the configured base only at first publish, when GitHub reports a conflict, or on an orchestrator or rework request. Other revisions do not fetch or merge the base. The pre-submit checklist runs on the local diff; fixes stay local until the worker pushes and creates or updates the PR once, immediately before submit. Rework follows the same order. CI and revuto findings arrive through the ci gate and rework notes; workers do not wait for them before submitting.

`submit` stores `pushes_since_last_submit` on the task and in the submit event. It counts distinct PR head SHAs observed in paginated Actions `push` and `pull_request` runs for the PR's branch whose creation time is at or after its last submit event, plus the current PR head when it differs from the previous submitted head. The GitHub query starts at the boundary's whole second; in-process filtering retains the exact timestamp. Workflow reruns and multiple workflows at one head count once. The previous submitted head and runs created before the boundary do not count. The first submission counts all observed heads for that branch; changing PR or branch starts a new history. Counts above one print a warning, append a task note and appear in `status` text and JSON (`pushes_since_last_submit: [{id, pushes_since_last_submit}]`). Status reads this receipt offline and only lists counts above one for tasks other than accepted or cancelled. A subsequent submission replaces the task's count; prior counts stay in the event log.

This observed count can undercount or overcount pushes: heads that start no Actions run can be missed, and a late run for a head replaced before the previous submit can be counted in the next interval. Run creation time is not push time. The branch history includes engine and orchestrator pushes, without attributing them to the worker. A count above one calls for inspecting the history; it does not prove that the worker pushed more than once in that interval. The current head counts even before a run starts. A failed or invalid history read records null and `push_history_error` in the event, prints a warning and adds a task note without refusing submission. A gh policy refusal records null and an informational `push_history_note` in the event and submit output, without a warning or task note. A task without a PR, a project without a repository or local CI also records null, without a history error. This diagnostic does not gate submission.

A `submit` event's `detail` records `previous_sha` (null on the first submission), `sha`, `branch`, `pr`, `host_probes`, `pushes_since_last_submit`, `summary` and `scope`, the scope gate's `{ basis, named, outside }` or `{ error }` ([CLI](../cli.md)). A probe-list change at the same commit also records `previous_revision` and `revision`. It adds `precheck` (`pass`, `fail` or `skipped`) only when the submitter passed `--precheck`; no gate reads it. A submitter with a live worker spawn adds `own: true` when the submit took ownership of the PR, or `own: false` with `own_refused` past `limits.owners` ([PR owners](#pr-owners)). A generated-file repair's submit carries the waiting owner as `owner` instead (see `generated merge` below). A named path of `./` represents the whole repository when the brief names a checkout or registered worktree root. A spawned worker's first submission also records its `claim` for restoring the same worker on rework. Resubmission with no lease leaves that receipt intact in the audit trail. Both the replaced head and the new head are recorded, including a submission after rework and a new claim: rework preserves the old sha.

Agy homes place native settings and the rendered `agents/gishra-<job>.md` below `homes/<agent>/home/.gemini/`. Startup receipts name that generated file and mark project house rules as `read`. Original user memory and modular rules are excluded from the prompt, receipt and generated read grants, including imports that resolve to them. Agy permits `tools` and `mcp` opt-ins; its only safe `args` flag is `--print-timeout`, and output remains JSON. Agy has no live message or session-resume adapter. Command shims remain available; real agy is unbrokered and owner-required because its sandbox capabilities remain false. The generated settings do not provide a native enforcement guarantee; failed probe attempts are recorded in ladder.md. See [ladder.md](../ladder.md#agent-files-and-homes) for the documented native configuration.

## Orchestrator inbox

`inbox` derives a snapshot from one state read and cached GitHub observations. It does not change tasks or consume messages. JSON has `items`, the live CPU executor leases as `executors` and `gate_queue`, the same queue `status` shows; text ends with the executor count and a `gate queue` line. Each item has a stable `id`, `kind`, nullable `task`, finding data, and `action: {command, argv}`. Text output includes the same findings and command. A ready or rework task without a brief gets `brief_missing` instead of `ready` or `rework_ready`; `brief set` clears it. A `rework_ready` item for a task automation sent back for a failed gate, unchanged and untaken since, also has `gate` and `restore`, the `gates retry ID --from-rework` command that undoes the rework once the cause is fixed, and `hold_until` while automatic refill holds it (`gates.rework_hold_min`). A task held for its waiting PR owner also has `owner`, and its action is the restore, since the owner takes the task when the hold ends. When the PR is not open, or its head or the local branch moved, `restore` is left out and `restore_blocked` says why. Kinds include `gate_failed`, `ci_stalled`, `review_failed`, `review_body_stuck`, `review_held`, `review_exit_missing`, `review_churn`, `rework_ready`, `ready`, `dead_claim`, `decision`, `accepted_unmerged`, `archive_refused`, `revuto_failed`, `codeql_alert`, `head_changed`, `main_ci_failed`, `main_ci_flaky`, `message`, `stall`, `decision_answer`, `owner_comment`, `governor_deferred`, `governor_stopped`, `github_pending` and `github_error`. `governor_deferred` (id `governor_deferred:TASK:UNIT`) and `governor_stopped` carry the unit kind, its reason and its times, with `status` as their action; they clear on their own ([Host resource governor](containment.md#host-resource-governor)). Open decisions carry their question and options. A technical decision is answered by the orchestrator under the existing answer authority; an owner-only decision (see the decision rules above: an approval request, an escalated question with delegation disabled, an `owner_required` reason, a spend, credential, setting or crisis kind the owner has not lifted, or a technical decision the owner unmarked) needs the owner's supplied choice. A decision's action argv ends in `<answer>` when the orchestrator answers it and `<owner answer>` when only the owner does. Answered decisions retain their choice, note, author and blocked tasks until acknowledged or expired from the view under the closed-task rule below. Owner task and decision comments retain their text and target until acknowledged; a later comment creates a new item.

`gate_failed` items report the latest audited failure for each software gate (`tests`, `clean`, `sources`, `ci`) at the current head and revision of an unmerged submitted or accepted task. They include the gate name, summary, ref, audited `confirmed_failure` flag and any `test_failure` names and output tail. Confirmed code failures resolve through rework carrying the failure summary and its test names. A change the worker must fix (`worker_failure`) offers rework with the gate summary. Pending checks, observation failures and infrastructure failures offer `check GATE ID`; infrastructure findings also retain their timeout metadata, and a failure the base shares carries its `main_failure: {base, names}`. Stalled CI is not a `gate_failed` item: it is a `ci_stalled` item addressed to the orchestrator with the gate summary and `since`, offering `check ci ID`. A missing or uninstalled pinned command is not a `gate_failed` item: it is a `gate_config` item addressed to the orchestrator, naming `gates.KEY` and offering `project set` with the pinned command, and `gates retry` follows once it is set. A hotfix whose changed host-only tests only skipped gets the same item naming `tests.host_env` and offering `project set --tests-host-env <JSON>`. A later pass, rework, a new head or revision, or a confirmed merge clears the finding. Failed gates cannot be acknowledged away. On an open mergeable accepted PR, a stale or unconfirmed failed required software gate offers its check command instead of `merge --accepted`; confirmed code failures offer rework instead; after that rerun passes, the inbox advances to the next blocker or merge. Review blockers still require rework.

## Inbox observation and acknowledgements

Foreground inbox snapshots never launch GitHub subprocesses. The host follower's `wait --inbox` observation refreshes PR observations, CodeQL, linked review comments, rework head checks and base CI concurrently across tasks, with the normal 60 s timeout per GitHub subprocess. Responses, including actual failures, use a 60000 ms refresh interval and are stored in `inbox-github-cache.json` as `{scope, started_at, read_at, main_error, entries: {HASH: {at, tasks, result}}}`. `scope` hashes the repository, base and GitHub host; each entry hashes the command, arguments and relevant task ids, statuses, PRs, SHAs and revisions. Invalid or future timestamps are not reused. Valid observations for unchanged task versions remain visible until replacement, even after one minute, so a slow refresh cannot hide findings. Overdue observations add `github_pending` with `stale: true` and a reminder to refresh; cold reads still return only the unread-data summary. The follower interval uses `started_at`, so late responses do not defer the next minute's refresh. Each refresh prunes responses for closed tasks and obsolete task versions before writing. Missing observations produce one `github_pending:project` item with `tasks`, `count`, `last_refresh` and a summary, rather than a GitHub error for each unread endpoint. Failed cached responses still produce explicit `github_error` findings, and failed linked review reads retain the evidence summary and incomplete marker. The pending item offers an `inbox` re-read while the last completed refresh is less than one minute old, including stale entries between healthy follower passes. A missing, overdue, invalid or future last-refresh timestamp offers `wait --inbox --observe --timeout 1` for one bounded observation. Neither action starts a persistent host, runs software reactions or dispatches workers. A missing rework head observation leaves its restoration blocked until refresh. Foreground base CI findings use recorded events and the last background read error. The pending summary checks the base cache or failed-read receipt independently of PR data, including when no PR is active. This cache is only for inbox observations; gates, restoration and merges outside an inbox snapshot still query GitHub directly.

Owner comment ids are `owner_comment:TASK:EVENT`, with `project` for a decision comment. Each historical owner comment without an event id uses `legacy-HASH-OCCURRENCE` as its event identity, hashing the complete event record and counting identical records in log order. Repeated identical comments remain distinct, ids survive appending events, and history is not rewritten. The item's `event` and acknowledgement action use the same identity. Old task-only acknowledgements do not suppress individual comments; acknowledge their current ids.

`inbox --ack ITEM` emits `inbox ack` with `{item}` for a handled message, stall, decision answer, owner comment or missing review exit. Repeat `--ack ITEM` to acknowledge several current items in one locked write and one event with `{items, count}`. Duplicate ids count once; any unknown, already acknowledged or nonacknowledgeable id refuses the entire batch without a write. A single `--ack` retains its `{item}` receipt and JSON `{acknowledged: ITEM}`; a batch returns `{acknowledged: [ITEM, ...], count}`. Both receipt forms suppress the listed items.

`inbox --ack-before TIME [--kind KIND]` acknowledges all current acknowledgeable items at or before the timestamp in one locked write and one `inbox ack` event with `{items, count, cutoff, kind?}`. `cutoff` is normalized to UTC. The JSON response is `{acknowledged: [ITEM, ...], count, cutoff}`. A batch with no matches still records one event with count zero. `--kind` accepts `message`, `stall`, `decision_answer`, `owner_comment` or `review_exit_missing` and requires `--ack-before`; `--ack` and `--ack-before` cannot be combined. These items expose `at`: the event timestamp for messages, comments, missing review exits and recorded stalls, the lease expiry for a derived stall, and `answered_at` for decision answers. Items newer than the cutoff remain visible. Acknowledgement cannot dismiss task or GitHub findings.

Messages older than 24 h disappear from the unacknowledged view when their task is cancelled or accepted with a recorded merge. Decision answers older than 24 h disappear only when they block at least one task and every blocked task meets that condition. Accepted tasks without a merge receipt, active or unknown tasks, project messages and answers without blocked tasks stay visible until acknowledged. Owner comments do not expire. Expiration changes only the view: it emits no acknowledgement and leaves the history intact.

`wait --inbox` refreshes at startup and once per minute, bounding GitHub requests independently of local hook traffic. It emits `inbox item` for new or changed findings and `inbox snapshot` with item fingerprints to deduplicate concurrent followers. A finding that clears and later returns wakes again. Snapshot and acknowledgement receipts are quiet bookkeeping. T98's plugin watch and orchestrator Stop hooks enable this refresh and direct the session to `inbox`.

Inbox reads, acknowledgements, observation and batch actions require a verified orchestrator or owner role; a verified worker identity alone grants no access. Batch actions preserve the authority table and existing checks. `spawn --ready` selects ready todo and rework tasks without live workers and dispatches serially within the worker limit, rechecking under the spawn lock. `release --dead` rechecks each claim under the release lock and never releases an unknown process. The worker broker rejects this unscoped batch before executing it; a worker can still release its own named task with `release ID --reason R`. `rework --from-review ID` refuses failed reviews whose findings are all PR-body false claims or title findings, with correction instructions; for other failures it retrieves the full matching review body outside the state lock and copies it, including every finding and the comment link, into the rework reason and brief. A linked comment that is unavailable or does not match the submitted SHA refuses without a state change. The command rechecks the head, revision, repository, PR and exact failed review under the rework lock after fetching; a newer verdict or changed task refuses. `merge --accepted` holds the existing queue executor and runs current-base checks and pinned stack merges; refused and pending entries remain for the next invocation while independent mergeable entries proceed. Automatic queue reactions still wait for unknown GitHub mergeability. Already merged PRs at the accepted head are confirmed without current gate evidence. Linked members still require every lower head to pass.

`mcp` serves newline-delimited JSON-RPC on stdio with `inbox`, `spawn_ready`, `merge_accepted`, `rework_from_review` and `release_dead` tools. Initialization, ping and tool discovery do not read or require project state, including outside a Git repository. Each tool call resolves the bound project location and verifies the caller role; missing-project and authorization errors return MCP tool errors without closing the connection. It validates tool arguments and offers no shell, identity or state overrides. Spawned Claude and Codex orchestrators receive this server in their generated homes; workers do not. The plugin ships the server registration and five matching command documents. No new authority class or owner grant is introduced.
