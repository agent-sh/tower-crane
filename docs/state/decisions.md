# Decisions and authority

## Agent identity

The identity recorded in state and events comes from `--agent NAME`, then `TOWER_CRANE_AGENT`. With neither, the CLI uses `owner` only when stdin and stdout are both TTYs and `TOWER_CRANE_TASK` is unset. In every other case it exits 2 with `no agent: pass --agent NAME or set TOWER_CRANE_AGENT`, before reading or writing state. An empty or whitespace-only identity exits 2 with the same message. Help needs no identity.

Resolving either identity source to `owner` (the terminal fallback included) is refused unless the owner runs the process, and the refusal starts with `owner identity needs a process the owner runs (docs/state.md#agent-identity)` and names the rule that failed:

- `TOWER_CRANE_TASK` is set: a task process never acts as owner.
- `TOWER_CRANE_AGENT` names any identity other than `owner`: a process started as another identity, such as `orchestrator` or a spawned `worker-T1-1`, never acts as owner, whatever `--agent` it passes.
- stdin or stdout is not a terminal, and `TOWER_CRANE_OWNER_KEY` does not hold the owner key. The key is the owner's own credential for scripts and other non-interactive owner commands: `tower-crane owner-key --agent owner`, run at a terminal, creates it (mode 600, in a mode 700 directory) as `owner/key` under the canonical `owner_config_dir` recorded in `project.json` (`~/.config/tower-crane/owner/key` by default) and prints its path, never the key. Every spawn creates that directory and hides it from claude's and codex's sandboxes, and from claude's Read, Grep and Glob tools, so no sandboxed agent reads the key. The CLI captures `TOWER_CRANE_OWNER_KEY` privately and removes it from its environment at command entry, before state discovery or authentication can start a child. Nothing it starts, including Git used to discover the state directory, agents or gates, inherits the key. Terminal checks leave piped stdin unchanged for hooks and command input. An unsandboxed process running as the same user can read the user's files, the key included; the key keeps owner identity out of reach of `--agent owner` alone, not of a process that deliberately reads the owner's secrets.

`spawn` passes the name `<job>-<task>-<n>` (`worker-T1-1`, `reviewer-T1-1`) in `TOWER_CRANE_AGENT`. A sandboxed claude or codex agent cannot write the state files (a codex agent's commands write only its own `HOME`, sessions and broker directory there); its state changes go through its spawn's [state broker](../ladder.md#state-broker), which records them under the spawned name whatever the agent passes, allows only its role's commands on its own task, and refuses another identity. Its credential is the token in its private broker directory, made for that spawn and invalid once the agent exits. Its prompt says `you are not the owner; never pass --agent owner` and closes with `run tower-crane with --agent <name> if TOWER_CRANE_AGENT is missing`, so a shell that loses the environment can still record the correct identity.

A spawned harness can run a command before its dispatch records the spawn, and a spawned identity's role comes from that record. The supervisor passes each launch `TOWER_CRANE_STARTUP_DEADLINE`, its launch time plus the startup window (10 s) in epoch milliseconds. A command that carries it, runs as `TOWER_CRANE_AGENT` against the `TOWER_CRANE_STATE` it names, and finds no spawn record for that identity waits at entry until the record appears or the deadline passes, then resolves its role. `owner` and the plain `orchestrator` name, which engine work uses, never wait. An orchestrator's first `wait` therefore registers as a controller even when it starts before its dispatch commits.

The credential location for an initialized project comes only from `project.json`, never from the command's `TOWER_CRANE_CONFIG`, `HOME` or `USERPROFILE`. Changing those variables does not redirect authentication or a pinned sandbox denial. An absent, invalid or missing recorded credential refuses headless owner access. For a project without `owner_config_dir`, only an explicit owner at a terminal can record it with `owner-key`; an existing binding is never replaced. Until it is recorded, spawning still works and hides `owner/` under the spawning environment's resolved Tower Crane config directory, where a terminal `owner-key` would create the key. This denial does not establish a binding or allow owner authentication.

## Authority

The owner hands the run to an orchestrator and is asked only when the owner is required. `lib/authority.js` holds the one table that classifies every guarded setting and command, and one check that every command uses:

- **operational**: the orchestrator or the owner. The orchestrator acts under its own identity; the event records that agent, and `project set`, `ladder set`, `ladder harness` and `ladder save-user` events add `"authority": "orchestrator"`.
- **owner-required**: the owner only. When the orchestrator tries one, the command writes nothing it asked for, opens a decision for the owner and refuses with its id. The decision and its `ask` event carry `escalation: { settings, change }` naming the settings and the requested owner-required values, with options `approve` and `decline`. The same open request reuses that decision. Only the owner answers an escalation, from the CLI or the board. After `approve`, the orchestrator runs the same command again: a request whose owner-required settings and values equal an approved, unapplied escalation is allowed once, and the decision records `applied: { at, by }`. Operational parts of the same command are the orchestrator's either way. `decline`, or the owner making the change, leaves the orchestrator's next attempt to open a new decision. A waiver the orchestrator records under an approval carries `approved_by` with the decision id, and counts only while the log holds that escalation's `ask` and the owner's `approve` answer.
- **refused**: no identity makes the change while the task stands as it is. The command writes nothing and names the step that comes first (`rework`); no decision opens.

Gate command pins and `gates.clean_paths` are operational settings for trusted host gate code. The orchestrator can select that code and the read-only paths its worker invocation needs, including tool installations under the spawning user's home. Declared directories authorize reads of their contents, including data files. The checks for Tower Crane's protected stores still apply. This authority applies to gate tool paths. General `sandbox` grants and ladder reach changes retain owner authority, and workers and reviewers can change neither class.

Harness capabilities are declared once in `lib/agents.js` as `CAPABILITIES`. `lib/authority.js` reads each harness's `sandbox` flag to classify primary, inherited fallback and default-harness moves; it does not infer confinement from private homes or the separate `osSandbox` flag. Opencode has both sandbox capabilities false, so moving a confined role to it requires the owner. `osSandbox` controls verified OS isolation for the state broker and nested Chrome setup; it does not classify ladder reach. New harness renderers change their capability flag; the authority rule and its tests follow it.

The owner can run a project by telling the orchestrator, and every row below has a CLI path: the orchestrator makes operational changes itself and asks only for owner-required ones; the owner approves with `tower-crane answer D<n> --choice approve --agent owner`. A row no command changes, `publish`, is requested with `ask --setting publish`; `ask` without `--question` refuses a row a command changes, since that command applies the approval. From the board (`serve --agent owner`) the owner answers decisions, which approves or declines escalations, and changes the ladder (`/api/ladder`) and tier rungs (`/api/tiers`); those writes go through the same check and audit event with `mode: board`. Board controls for the remaining rows are not built yet (T89 part 2).

Every allowed change of a guarded setting appends one `setting` event in the same write as the command's own event, just before it: `detail: { command, actor, mode, settings, approved_by?, policy? }`; `policy` replaces `approved_by` on a publish the publish policy allowed ([below](#publish-policy)). `actor` is `owner` or `orchestrator`, `mode` is `board` for a write through `serve` and `cli` otherwise, and `settings` maps each guarded setting the command changed to its class. A refused or escalated request records none, and neither does a command that fails after its check: `accept --waive` and `spawn --role orchestrator` apply the owner's approval and audit it only in the write that records the acceptance or the started spawn; unguarded fields such as `name` and `goal` record none.

When the owner's successful write satisfies a request's fields, matching open or approved requests record `applied: { at, by: "owner" }` in that same write. The owner may write additional settings or fields at once; every satisfied request is retired. An open request also becomes answered `approve`, with an owner `answer` event. Failed commands leave these requests untouched, including acceptance that fails a gate and a spawn that never starts. The owner's setting audit uses their own authority, without `approved_by`. A later orchestrator retry needs a new decision, even if the owner has since changed the value again.

Matching preserves the request's target, such as a rung, user file or decision. Ladder/rung objects group fields, so an owner can satisfy an environment request while also writing scope or another rung. Replacement values must match whole: adding keys inside an environment map or routes inside a fallback list does not satisfy a request for a different value. JSON formatting and object key order do not change the value. Orchestrator approval consumption still requires the exact request; only owner-write retirement accepts additional fields.

Budget requests match the owner's written amounts independently of whether those amounts currently raise, lower or repeat the budget. For example, after approving a request to raise hours from 5 to 10, owner writes of 20, 10 and 5 retire that approval at the write of 10. The subsequent orchestrator retry needs another decision. The audit still classifies the owner's decrease or unchanged amount as operational `budget.lower`; operational orchestrator writes do not retire an unused raise approval.

`project set --budget-hours null` and `--budget-tokens null` remove their limits; `task update` accepts the same flags for a task's limits. Removing a finite limit is `budget.raise`, so the owner may do it directly and the orchestrator needs a one-use approval. Task-budget approvals name the task, and a task-budget write cannot retire a project-budget request. Live-budget alerts are owner questions, not setting approvals. `init` accepts the same nullable flags. Other numeric flags retain their numeric-only parsing.

The same rule applies to primary ladder reach grants and task kinds: an owner writing the requested tools, harness, arguments or kind retires the matching request even when the current edit is operational or unchanged. Primary reach requests describe grants, so additional tool or unconfined-route grants in the same owner write are allowed. Only written fields and routes affected by a written harness count; an unrelated model edit does not settle a reach request. Task cancellation and review waivers also retire matching owner requests after their owner-only condition has cleared. Authorization and audits still use the current classes.

Waiver requests include `{ accept, sha, revision, waive, reason }`. Their approval and the recorded waiver must name the same task, SHA and positive revision. Changing acceptance, dependencies or capabilities requires a new approval even when the commit is unchanged. A waiver approval without a revision cannot authorize a new accept or back an orchestrator's waiver evidence; request fresh approval for the current revision.

Release requests include `{ release, holder, claim_since }`, binding the task, holder and claim start time. Renewing that claim keeps the approval usable, but a replacement claim needs a new decision even when the holder has the same name. Browser-kit requests include `{ user_file, servers }`, using the same resolved absolute path the command writes. Changing `TOWER_CRANE_CONFIG` to another target needs another approval, and owner writes retire requests only for their own target file. Legacy approvals without these bindings cannot authorize the corresponding command; request fresh approval.

An interruption audits `task.interrupt` in the write that releases the claim. `task update --interrupt` combines that row with its other guarded changes in one setting event. A mixed waiver request attaches `approved_by` only to owner-required waivers; an operational review waiver retains its own eligibility.

The Controls page (`/controls`) uses this same check and event for every authority row, with `mode: board`. An owner-required change submitted there opens an escalation even for the owner; approving it on the page runs its recorded `request: {command, flags, pos}` through the same command handler as the owner, once. Approving an orchestrator's escalation on the page only answers it: the orchestrator's repeat of the same command uses the approval, as from the CLI. That includes an owner's request the orchestrator then asked for too (`repeat_by`). A publish request is answered the same way. A later save on the page uses only an approval the owner asked for there that no orchestrator repeats; with an orchestrator's approval pending, it opens the owner's own confirmation instead, and saving publish again reports the existing approval without using it. No browser-supplied actor, state path or alternate authority class is accepted. A failed application leaves the approved decision unapplied.

Workers, reviewers and every other identity are refused both. For an operational change they ask the orchestrator (`tower-crane msg --to orchestrator` or a task note), not the owner. An owner-required change they request with `tower-crane ask --question Q --kind setting --setting KEY`, which keeps the decision with the owner. A worker's or reviewer's `ask --kind technical` that names no owner-required setting opens a technical decision the orchestrator can answer; a `spend`, `credential` or `setting` kind stays with the owner (see `decisions.json`).

Tools and MCP servers are operational because choosing what a rung works with is running the project, and the owner's autonomy rule hands that to the orchestrator; the two conditions keep it from widening what an agent reaches. An MCP server runs outside the rung's sandbox, so the orchestrator may opt in only a server already defined in the owner's own harness config (claude `mcp.json` or `.claude.json`, codex `config.toml`, agy `~/.gemini/config/mcp_config.json`, opencode JSON/JSONC config and inline `OPENCODE_CONFIG_CONTENT`); naming another is refused, and the owner adds it. A tool the agent files name (claude tool names, codex features, agy native tool names, pi built-ins) or codex `web_search` re-enables a harness built-in inside the same sandbox; any other tool opens a `ladder.reach` decision. Only opt-ins new to a rung and harness are checked, including rungs a `ladder harness` change moves to another harness. The owner can overrule either condition by making the change. The conditions hold because the rung keeps its sandbox: moving a confined role off a sandboxed harness (including personal fallback routes that follow its harness), or adding args on an unsandboxed harness, opens a `ladder.reach` decision. A route the owner already put there is the orchestrator's to tune with the same args; the orchestrator rung runs unsandboxed, so only args on an unsandboxed harness open a decision there. The sandbox, env, env_file and scope grants, `merge.admin`, `decision_delegation`, budget raises, delegation, the publish policy and publishing outside it stay owner-required.

<a id="owner-rows"></a>The owner sets policy once and the engine applies it. Every owner-required row is a one-time grant, of one of two shapes:

- **Configuration, set once.** The owner sets it for the project, a rung or the user file, and it holds until the owner changes it: `sandbox`, `sandbox.session_bus`, `env`, `env_file`, `scope`, `ladder.command`, `ladder.web_mcp`, `ladder.reach`, `browser_kit` and `delegation` grant power; `budget.raise` grants money; `merge.admin`, `decision_delegation`, `research.min_sources` and `publish.policy` set how the run goes. None is a step of an ordinary day.
- **One use, for one named case.** The approval binds one task, head, revision, claim or decision and is used up by the change it allowed: `waive.tests`, `waive.clean`, `waive.ci`, `waive.sources`, `waive.review_live`, `task.downgrade`, `task.rerecord_review`, `claim.release`, `decision.delegate` and `task.cancel_needs_owner`. Each loosens a check on work the gates judged, or overrides an owner's or a worker's own hold, so it stays with the owner; an ordinary day reaches none of them. A host-only failure main shares keeps the task submitted and reruns when main moves (`automation.js`), with no waiver; a capped or down reviewer is the operational `waive.review`; a claim whose process exited is released by any agent; the orchestrator's own hold is `task.cancel_hold`.

Two former flow gates are policy-driven: an orchestrator's or the engine's hold is cancelled as `task.cancel_hold`, and `publish` follows the publish policy. Decisions whose tasks closed close themselves ([decisions.json](#decisionsjson)), and a worker's question about a failure main shares goes to the orchestrator.

<a id="publish-policy"></a>`project set --publish-policy '{"conditions": [...]}'` records `publish_policy` in `project.json`; it is `publish.policy`, owner-required, and `null` removes it. The conditions are any of `review_clean` (the release task's latest review gate evidence at its head passed and is not a waiver, which only a reviewer spawned for that task, a clean context, or the owner records), `full_suite` (its latest tests gate evidence at its head passed under current pinned commands and test settings, is not waived, ran tests rather than none mode, did not run mapped suites, and reports passing cases with no skips or unreported cases for every configured host-only file tracked at that head) and `main_ci_green` (a fresh read of the base's runs, the one `inbox` makes and reuses for a minute, finds no red workflow). With a policy set, the orchestrator's `ask --setting publish --change '{"task": "T<n>", ...}'` names the release task; when that task is accepted and every condition holds, it exits 0 with no decision and records a `setting` event on that task with `settings: { publish: "owner-required" }`, `policy: { conditions: [{ name, ok }], sha }` and the `change`, in place of `approved_by`. An owner's approval of the same request is still used first. Otherwise it opens or reuses the owner's decision as without a policy; the decision's `why` and the refusal name each failed condition. An empty `conditions` list publishes any accepted task only after the mandatory main push CI check below passes.

<a id="fallback-route-grants"></a>A personal fallback route can carry authority: a grant (`sandbox`, `env`, `env_file`, `scope`), a harness without an OS sandbox (agy, opencode, pi), the `command` harness, args on an unsandboxed harness, `web_mcp`, `mcp`, or a tool that is not a harness built-in. The user file is a plain file: anything running as the user can edit it, the unsandboxed orchestrator included, and `TOWER_CRANE_CONFIG` can name any file. So such a route counts only when `ladder set RUNG --fallbacks` wrote it under the check above, as the owner or with the owner's approval. That write pins a SHA-256 of each route in `owner/route-grants.json` under the project's recorded `owner_config_dir`, beside the owner key that every agent sandbox hides: `{ "version": 1, "files": { "<user file>": { "<rung>": ["<sha256>" or null, by route position] } } }`. The user file key is its canonical path: the real path, in the case the filesystem stores. So a symlink, another case on a case-insensitive filesystem or a relative `TOWER_CRANE_CONFIG` that reaches the same file finds the same pins, and a link moved to another file after the approval finds that file's pins, not the old ones. A key written by an earlier version under the path as spelled still counts for that spelling while the file has no canonical entry; the next pin write for the file moves every such entry under the canonical key and leaves that key in place, as `{}` when no rung is pinned, so old spellings are never read for that file again. The store records no write times: when two old spellings hold the same rung, the spelling the write came through wins, and a route approved only through the other may ask the owner again. The hash covers the route's `harness`, `command`, `args`, `tools`, `mcp`, `web_mcp` and grants, with keys sorted, plus the content of its `env_file`. So approved grants moved to another route, position or harness, or an `env_file` edited after the approval, are not approved. The harness hashed is the one the route resolves to, so a route that inherits the primary's harness is approved only on that harness: moving the primary, which the orchestrator may do among sandboxed harnesses, asks the owner again. Pins are per position: inserting a route before a pinned one, or reordering the list, asks the owner again for each pinned route that moved. Spawn hands each kept route's approved `env_file` hash to the supervisor, which reads the file again at launch, on each retry and at each switch, and refuses the route with a notice (`skipping fallback N`) when the content no longer matches. The pin holds hashes, never values, which are often secrets. The write takes a lock in that `owner/` directory, since every project bound to it shares the file.

Spawn drops a fallback route that carries authority without a matching pin, and says so in the spawn's `notices`; `ladder show` lists it as a problem with the command that approves it. A route that sets only `model`, `profile`, `provider`, `effort` or `supervision` on a sandboxed harness carries none and needs no pin, so personal fallbacks such as `{"harness":"codex","profile":"astra"}` work as before. A route that inherits its harness carries what it sets; the primary's own move off a sandbox is `ladder.reach`. `ladder set --fallbacks` compares a new list with the pinned routes of the old one, not with the file: a route edited into the file by hand counts as new, so its grants, `command` or `web_mcp` are owner-required and an unconfined harness or non-built-in tool opens `ladder.reach`, even when the write leaves the route as the file holds it.

The pin follows the user file: an approval in one project counts in every project bound to the same `owner_config_dir`. A relative path in a pinned route resolves in each repository that runs it: a `sandbox.write` or `sandbox.read` entry grants a different directory per repository, and a relative `env_file` names a different file, whose content then does not match the pin, so the route is skipped there. Give personal routes absolute or `~/` paths. A project without `owner_config_dir` cannot pin, and `ladder set --fallbacks` refuses such routes there until the owner runs `owner-key`.

The research agent ships with network and web tools enabled in code; initializing or tuning its model does not ask for a new grant. Changing its explicit `web_mcp` command or tools is owner-required, including clearing it to return to native web tools. The orchestrator's attempt opens a decision without changing the rung. A setting that widens network access is owner-required under `ladder.reach`; operational built-in opt-ins must keep the existing sandbox network confinement.

`init` checks the same table; with no state to hold a decision, an orchestrator's owner-required `init` setting is refused and it inits without it. The same holds for what `init` copies from the user file, which anything running as the user can edit and `TOWER_CRANE_CONFIG` can name anywhere. Only the explicit owner's `init` copies the primary rungs whole. Any other `init` copies what `ladder set` lets the orchestrator write and prints a `notice:` line for the rest. It leaves out `sandbox`, `env`, `env_file`, `scope`, `command` and `web_mcp`, tools that are not built-ins keeping the rung's sandbox, and MCP servers the owner's harness config does not define. A rung that would run as a command, or outside its role's sandbox on its own harness or the default one, gets its built-in rung on that rung's built-in harness. A rung that keeps its built-in harness and args is not withheld for them: the built-in rung would run the same way. The `init` event lists what was left out under `withheld`, and so does `--json` output. The owner adds any of it with `ladder set --agent owner`, or approves the decision the orchestrator's `ladder set` opens.

The owner is the resolved name `owner`, supplied explicitly by `--agent owner` or `TOWER_CRANE_AGENT=owner`, from a process that passes the [owner identity rule](#agent-identity): no task variable, no other `TOWER_CRANE_AGENT`, and a terminal or the owner key from the project's recorded `owner_config_dir`; the terminal fallback grants no authority. The orchestrator is an explicit identity that some spawn recorded with role `orchestrator`, or, never spawned, the name `orchestrator` (the owner's interactive session). A name any spawn started as a worker, reviewer or small agent is never the orchestrator, nor is a command the state broker runs, nor a `--agent` that differs from a `TOWER_CRANE_AGENT` naming such an agent. A waived gate counts when the owner recorded it, or the orchestrator for an operational waiver. Any agent may recover a spawned claim when the shared process detector verifies its exit under the state lock. Set `TOWER_CRANE_AGENT=owner` per command, never in a shell profile, where it could override a spawned agent's identity.

## decisions.json

```json
{
  "version": 1,
  "next": 2,
  "decisions": [
    {
      "id": "D1",
      "question": "Store idempotency keys in Redis or Postgres?",
      "options": ["redis", "postgres"],
      "recommendation": "postgres",
      "why": "keys must survive a Redis flush; volume is 30/s",
      "blocks": ["T3"],
      "answerers": [],
      "kind": "technical",
      "technical": true,
      "status": "open",
      "answer": null,
      "note": null,
      "asked_by": "worker-T3-1",
      "asked_at": "...",
      "answered_by": null,
      "answered_at": null,
      "answer_rule": null,
      "withdrawn_by": null,
      "withdrawn_at": null,
      "withdraw_reason": null
    }
  ]
}
```

A decision the engine opened for an orchestrator's owner-required change also has `approval_request: true`, `escalation: { "settings": [...], "change": {...} }`, options `["approve", "decline"]`, and, once the orchestrator used an approval or the owner made the matching change, `applied: { "at", "by" }` ([Authority](#authority)). One opened by a command also has `request: { "command", "flags", "pos" }`, the command as it was run; the Controls page applies an approved one the owner asked for there. When the orchestrator asks for the same change while the owner's Controls request is open, it waits on that decision, which records `repeat_by: "<agent>"`; the page then leaves the approval for that agent's repeat. The generated request and its `ask` event carry `approval_request: true`; only marked requests can be reused or applied. Older unmarked decisions cannot authorize a command. A tagged question (`ask --question Q --kind K --setting KEY`) records `escalation` with `change: null` for owner-required tags and is not technical. It is never a one-use approval.

A decision blocks only the tasks it lists. Everything else keeps running. `status` is `open`, `answered` or `withdrawn`. When options are listed, the answer must be one of them. An explicit owner identity can answer every decision. `answerers` lists agents the owner named with `decision delegate DID --answerers JSON`; the owner can replace the list or clear it with `[]`. `decision delegate` is owner-required: an orchestrator request opens an approval for the target decision and supplied fields, then its identical rerun applies it once. The shared audit names `decision.delegate`; closed decisions refuse before opening or consuming an approval. `kind` is what the asker says the question is, and every `ask --question` gives one: `technical`, `spend`, `credential`, `setting` or `crisis` (other values are refused, and a missing kind is a usage error). The question text is never read, so routing depends on the kind and the state alone. `credential` is only for a request that grants a credential or loosens a sandbox: the ask must also name one of `env`, `env_file`, `sandbox`, `sandbox.session_bus`, `scope`, `ladder.reach` or `ladder.web_mcp` with `--setting`, or it exits 2; a host or harness that fails is technical. An approval request is owner-only. An escalated technical question is answerable by the orchestrator under project delegation when no other owner restriction remains; tagging does not lift a kind or `owner_required` reason. Other decisions are owner-only when their `ask` carries `--owner-required REASON` (another call only the owner makes; stored as `owner_required`), or when their kind is `spend`, `credential`, `setting` or `crisis`.

A worker's or reviewer's question (an identity that is neither the owner nor the orchestrator) that blocks a task whose latest tests evidence, at any revision, failed with `main_failure` (every failing name also fails on the base) goes to the orchestrator: it is stored with `kind: "technical"`, `technical: true`, no escalation and no `owner_required`, plus `routed: { to: "orchestrator", task, base, names, asked_kind, dropped?, owner_required? }` keeping what the asker gave. No owner grant fixes such a failure: the gate keeps the task submitted and reruns when main moves. A `spend` or `crisis` question, or one that names an owner-required setting other than a `waive.*` gate waiver, keeps its route. The `ask` event carries `routed`, and the command prints the id with the route.

`crisis` is the one class that reaches the owner unasked: host stability (OOM, fork storm, disk full), data loss or state corruption, a security incident (a leaked secret, a sandbox escape), or a published artifact that is broken. `ask --kind crisis --crisis host|data|security|artifact` stores `crisis` with the class (only a crisis decision has it), is owner-only, and appends a `msg` event to `owner` in the same write. Everything else resolves through policy, the orchestrator or automation. `status` and `inbox` end with one owner line: `owner: crisis D<n> (<class>): <question>` while a crisis is open; otherwise `owner: no crisis; waiting when convenient: <ids>` naming open decisions the orchestrator cannot answer and open tasks whose hold is owner-required; otherwise `owner: nothing needed`. Their JSON carries it as `owner: { line, crisis, waiting }`. A decision the engine opens for an owner-required change or an exhausted quality range has no `kind`; an owner-required change is an owner-only approval request. Budget-stop questions have `kind: "spend"`. An exhausted quality range opens an owner-only question with an `owner_required` reason and no setting escalation. `technical` is stored at ask time: true only for a `technical` kind with no escalation and no reason. Open decisions keep their stored value, so an open technical decision is answerable under the default without re-asking. A decision with no `kind` (opened before kinds were stored) is technical on upgrade with no owner step, unless an approval request or an `owner_required` reason keeps it with the owner; escalated questions follow their own rule; its stored flag is not read. The owner sets `technical` through `decision delegate` (`--technical false` keeps a decision without an escalation with the owner; on a decision with no kind or an escalation it stores `owner_required` as `the owner keeps it with the owner`, which `--technical true` clears). Apart from escalated questions, the orchestrator can answer only a decision that has no owner-only reason and is technical: it has no `kind`, or its `technical` is true (the owner's lift sets it, whatever the kind). This also needs `decision_delegation.orchestrator_technical` not to be false. Approval requests refuse every non-owner answer. Escalated questions refuse non-owner answers except the orchestrator under the two project delegation booleans when no other owner restriction remains; named answerers do not bypass this rule. The owner's `decision delegate DID --technical true` lifts a spend, credential or setting kind and an `--owner-required` reason (its stored `owner_required` becomes `null`), but never an escalated setting; a decision that keeps an owner-only kind or reason refuses `--answerers`. An answer stores `answered_by` and `answer_rule`; older decisions default to no named answerers, not technical, and no answer rule.

A withdrawal sets `status` to `withdrawn` while no answer exists. Its `withdrawn_by` is the verified identity that opened the decision (`asked_by`), `owner`, an orchestrator allowed by the question's answer delegation rule, or `engine` for a moot decision (below). The orchestrator may withdraw another agent's open question, escalated or not, only while that delegation applies; independent owner restrictions remain. Approval requests keep the asker/owner rule. `withdrawn_at` and a non-empty `withdraw_reason` are required with it. The `decision withdraw` event records `detail.decision`, `detail.reason`, `detail.blocks` and `detail.withdrawn_by`, and maps to `decision-withdrawn`. A withdrawn decision no longer blocks its tasks, is off the open list, and cannot be answered, delegated or withdrawn again; it stays in `decisions.json` and in event history. Each blocked task gets a note with the reason.

An open decision closes itself as moot in the write that closes the last task it waits on: every task it `blocks`, and for an approval request the task its `change` names as `task`, `accept` or `release`, is `accepted` or `cancelled` (a superseded task is cancelled). A re-record request (`task.rerecord_review`) acts on cancelled tasks and a `publish` request waits for its task to be accepted, so neither names one. Any write does it, whoever runs it. The decision records `status: "withdrawn"`, `withdrawn_by: "engine"`, `moot: true` and a `withdraw_reason` naming each task and why, such as `moot: T3 accepted, T4 superseded by T5`; its `decision withdraw` event, under the agent whose write closed it, carries the same reason with `withdrawn_by: "engine"` and `moot: true`. No task note is added: every task it named is closed. Only a write that closes one of those tasks makes the decision moot: a decision asked about tasks that were all closed already, such as a publish request for an accepted release task, stays open until it is answered or withdrawn. A crisis decision (`kind: "crisis"`) never becomes moot; the host or data trouble it reports outlives its tasks. A decision that blocks nothing and requests no task change never becomes moot this way.

Answer rules are `owner`, `owner-named-agent`, `owner-technical-delegation` and `orchestrator-escalated-question`. `decisions` text includes the recorded rule. `status` text lists escalated questions the orchestrator answered in the last 24 hours, or whose `blocks` still names a task other than accepted/cancelled, with their author, choice and rule. Its JSON includes the filtered `decisions_orchestrator_escalated: [{ id, answer, answered_by, answer_rule }]` and `decisions_orchestrator_escalated_count`, the total number of those answers recorded. Missing or future answer times qualify only through an open task link. `decisions` retains the full history. The board renders escalated questions as questions; only `approval_request: true` records render as approvals. The `answer` event records the caller in `agent` and `detail.answered_by`, and the rule in `detail.answer_rule`. Refused answers write no event. Answering adds a note with the answer to every task the decision blocked. Optional `notes` contains `{ "at", "agent", "text" }` comments added with `decision note`, including serve's owner form.

The orchestrator's technical rule takes precedence over `answerers`, including for a generated identity with a recorded orchestrator role. Listing that identity cannot authorize a nontechnical answer or one without project delegation. A sandboxed agent may answer through its broker only when the owner named its bound identity for that decision; successful brokered answer events retain the bound identity and carry `via: broker`.
