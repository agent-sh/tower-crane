# CI

### Local CI output

Mapped escape readings merge shared raw spans around recovered values and tokens. Every character and boundary space in a shared span maps to its union, preserving redaction coverage while keeping both endpoints non-decreasing. Synthetic boundary spaces still carry no raw characters for union redaction. A normalized CRLF maps its newline to the LF, so a value recovered through a hidden escape before that LF leaves the following line apart from the header value. For secret values without controls, searches scan contiguous text linearly before exploring escape readings: plain text that merely shares a secret's first two characters does not pay for a search stack. Exact values and matching prefixes interrupted by a control still start searches.

Text cleanup and redaction fail closed when an input exceeds 32 Mi UTF-16 code units, 262144 bookkeeping, allocation and search work units plus one per input character, or a cooperative deadline of 5 seconds plus one per MiB. Cleanup, both escape readings and all stream readings share the budget the outer input sets for one joined log. The size limit is checked before allocating views; work and time are checked during scanning and before returning. Each compact control run costs one quarter of a bookkeeping unit and occupies three Int32 entries in a block. Each four-byte Int32 capacity entry costs one sixteenth of a unit before allocation, including the full new capacity when a map grows; this charge covers Int32 maps, not Float64 interval indexes. Each lazy escape segment costs two units before its two source indices are added. Stretch and sorted-index containers credit their prepaid capacity against later per-entry bookkeeping in the same budget; new allocations always pay their capacity first. View parts are joined in bounded groups instead of retaining every slice until a view is complete. A cleaned view keeps only its text and index tables, not the readings it was made from, so a joined log's view does not hold them while each stream is read. The three cleanup views reuse one Int32 index buffer after consuming each view's spans. Over budget, the whole log or text artifact is replaced by `[unscannable text: <reason>; content omitted]`, including its evidence tail. No input fragment is retained. This also applies to hosted CI log cleanup and gate diagnostics. Ordinary plain, colored and CRLF logs stay scannable within the size limit; dense carriage returns, escape-split values or glued headers can exceed the budget once their work past one unit per character outgrows the 262144-unit floor.

A local CI gate worktree and its scratch directory are removed when the gate ends, so the run keeps what diagnoses it first. Its stdout and stderr go to `logs/ci-<task>-<sha>-<unique>/output.log` in the state directory, joined by whole lines: a chunk of one stream never lands inside a line of the other, and lines appear in the order their newlines arrived, as for the tests gate's output below, with each stream's own text also read for secrets. Terminal escapes (CSI, OSC, DCS and other ESC sequences, in 7-bit and 8-bit forms) and stray control characters are removed first, as `ci log` removes them (a carriage return becomes a newline unless it lies inside a token shape or an environment value, and a run at a token's edge becomes a space), since one inside a token hides it from the patterns. Then the text is redacted like the tests gate's output tail. An OSC, DCS, SOS, PM or APC string ends at BEL (OSC only), `ESC \` or the 8-bit ST, and without one at the next newline or ESC, so it cannot remove later lines. Agents read this log and the evidence's tail.

On a failed run, files named by `artifact_pattern` and then by `artifacts` are copied when they lie inside the worktree or the scratch directory. They go to `ci-artifacts/<the log's directory name>/`, worktree files under `worktree/` and scratch files under `TMPDIR/`, each at its path there. `ci-artifacts/` holds files as the command wrote them, and a receipt can hold the step output the log redacts, so every agent sandbox hides it as it hides `brokers/` (claude `denyRead`, codex `none`, opencode and agy deny rules); only the orchestrator and the owner read it. Text files get the log's escape removal and redaction. A file with a NUL byte or invalid UTF-8 is binary, and its entry says `binary: true`. Decoding it would turn its invalid bytes into U+FFFD, so it is redacted at the byte level and only at exact matches: read one character per byte (latin1), the environment values' UTF-8 bytes and the token shapes become the same ASCII `[redacted:NAME]` markers as in text, and every other byte is kept as written. Before copying, the gate reads the raw bytes again as latin1, UTF-16LE and UTF-16BE at both byte alignments, each with 7-bit escapes and controls removed, with escapes removed and control runs made a space, and with controls alone removed, and, when an escape keeps a final byte or leaves a string unterminated, two more ways with escapes removed gently, as for the log: a stray ESC or an unterminated string loses only its introducer, with a two-character escape made a space and with it joined. It looks for every environment value and token shape in each, for environment values split by any escapes, controls and line breaks in the raw bytes, and for token shapes split across lines in the gently cleaned bytes, as for the log, and, when an escape is lossy, also in those bytes with the escape's space inside a token removed and in the bytes with every escape removed whole, so a token that a real `ESC (B`, or a lone ESC that takes one of its characters, and a line break both split is found. Any ASCII character in UTF-16 has a NUL byte, so the UTF-16 views run only when the file has one or an environment value is not ASCII. Positions found in a view are mapped back to bytes by a second pass over it, not kept in a map per byte. If any of those views shows a secret the exact matches did not remove whole, such as a token in UTF-16 text, a token split by a carriage return, an escape or a line break, a split token whose first character a stray ESC would take, or a token running on past a NUL byte, the file is not copied and its skipped entry names the view. Each file is read from one descriptor opened without following a final symbolic link, after its real path is checked to lie inside the gate directory, and at most the remaining byte budget is read, so a file swapped or grown after the check cannot exceed it. Containment is checked by path, so a hard link inside the worktree is copied; the gate's command could copy that file anyway. Files elsewhere outlive the gate and are listed as skipped. A run copies at most 100 files and 64 MiB; ginza's check receipts measured up to 5.8 MB, and one run writes one or two, so the caps hold ten of the largest while stopping a broad glob from copying a build tree. A passing run keeps no artifacts, since its receipt says what they would.

On pass or fail, files selected by `receipts` are copied to `ci-artifacts/ci-<task>-<sha>-<unique>/receipts/<worktree-relative-path>`. Overlapping globs copy a resolved file once. Resolved paths must stay inside the worktree; an external symbolic link is skipped. Every agent sandbox hides the entire `ci-artifacts/` tree. Only the owner and orchestrator read these payloads; directories have mode 0700 and files 0600. Each stored file is capped at 8 MiB, enough for ginza's largest measured 5.8 MB receipt. Input is processed before truncation. Truncated files end with `[receipt truncated at 8 MiB]`; truncated JSON may no longer parse. Collection has its own 100-file and 64 MiB input budget, and files exceeding that budget are skipped. The check.py adapter names JSON `steps` entries whose string `outcome` is not `"passed"`, using `name` or joined `argv`. Each step's integer `check` indexes `checks` for `exit_code` and `timed_out` details. It also reads string `failure_reasons` and reports false `head_unchanged`, `source_unchanged` and `working_tree_clean_after` fields. It reads before truncation. Command failures list these safe diagnostics and copied references; copy failures never replace the command's exit verdict.

For valid JSON, individual receipt strings and object keys are decoded, cleaned and redacted, then serialized as UTF-8 in the private copy. This includes nested output, arrays and JSON string primitives. Per-field processing can leave credential pieces across array entries or key/value pairs, so the payload stays hidden from agents. UTF-8 with a BOM and valid UTF-16LE or UTF-16BE JSON use the same path; other binary files retain the artifact byte redactor. Numeric literals retain their original precision. Keys that become identical after redaction get numeric suffixes, such as ` (2)`, so each value remains. The entire JSON operation shares the text redaction budget above. Excessive nesting or a budget failure omits the content with a notice. Text that is not JSON-like keeps the ordinary log cleanup and redaction.

When JSON decoding fails, content beginning with `{`, `[` or `"` after whitespace, or containing both quotes and backslashes, is treated as JSON-like. Its copy contains only `[unscannable JSON receipt: invalid or multiple JSON values; content omitted]`. This covers truncated documents, JSONL and prefixed serialized fragments, including BOM and UTF-16 inputs. JSON-like input with an invalid Unicode encoding also keeps only an omission notice. Copies and their paths are retained; recoverable encoded credentials are omitted. Other text keeps the ordinary log redactor.

Only selected adapter diagnostics enter agent-readable evidence. Captured output, arbitrary keys and other receipt fields stay in the hidden copy. Diagnostic strings are redacted individually, then scanned as joined readings of step labels, argv, outcomes and failure reasons, within each receipt and across the collected receipts. If a joined reading reveals a credential the individual passes left whole, the diagnostic summary becomes `[receipt summary omitted: a credential spans fields]`. Redaction or processing limits also replace diagnostics with an omission notice. File references and safe diagnostics remain available; payload contents remain private.

After each run, the newest 5 runs of the task, by the log directory's modification time, stay in `logs/` and `ci-artifacts/`, and older ones are removed. ginza's T1 checked one head three times, so five keep the current head's runs and the last of the head before it.

The evidence and the audit event carry `local_ci`: `log` (the state-relative path of `output.log`, or null when the gate had no state directory, with `log_error` when writing failed), `artifacts` (`{from, path, bytes}` per copied file, with `path` relative to the state directory, `bytes` as stored, and `redacted: true` or `binary: true` when that applies), `artifacts_error` when the copy itself failed, and, when files were not copied, `artifacts_skipped` (the first 20 as `{from, reason}`) and `artifacts_skipped_more` (the rest as a count). `receipts` uses the same entry shape, with optional `truncated: true`; `receipt_failures` lists deduplicated redacted names and reasons, and `receipts_error`, `receipts_skipped` and `receipts_skipped_more` report collection failures in the same way. A failed command adds `output_tail`: the last 200 lines, at most 16384 characters. A local CI script prints each step's output when the step ends, so the failing step is rarely last; over 889 step outputs of ginza's `tools/check.py` the 90th percentile was 114 lines and 6950 characters, so the tail holds the last whole step in nine runs of ten, and the log holds the rest. The summary, which rework reasons carry into worker prompts, keeps the last 20 output lines, names the full log, counts protected artifacts, and lists receipt failures, copied paths, truncation notices and skipped-file reasons.

## Completion hints

`ci completed` records a `ci-completed` hint with `sha` and `revision`.
The host delivers completion hints directly or through `ci webhook`
with GitHub check-run, check-suite or workflow-run JSON. The repository
must match, and only completed checks at active submitted heads count.
The hint triggers a new CI gate query; payload conclusions do not produce
evidence. No webhook listener is installed; pending CI without a hint is
rechecked once a minute by the trusted `wait` watcher, as described below.

## Hosted CI reconciliation

At a submitted head, an ordinary failed `tests`, `clean` or `ci` verdict reworks immediately and stops later gates from running.
Infrastructure failures retry once before rework. A configuration failure waits
for its command to be pinned, while later software gates still collect missing
evidence and settle any independent failure. Pending CI waits for completion.
A worker's `submit` records a head whose checks are still running, so this wait
happens here on the host and not in the worker. A hosted CI failure summary
names the failing jobs and prints the first failing lines of the first three
job logs (the command that reads each other one), redacted as the tests gate
redacts its output, and the rework reason carries that summary to the worker. Hosted CI records `pending: true` while current runs or suites are incomplete,
required runs have not appeared, or GitHub is computing mergeability. It
prints `PENDING` and does not consume an infrastructure retry. The checks are
read even while mergeability is UNKNOWN, so completed failures take precedence
over pending runs and over unknown mergeability. Pending CI with no run queued
or in progress also records `not_running: true`. The trusted `wait` host
schedules reconciliation of pending CI once per minute without a completion
notification, reusing current tests and cleanup passes. It skips a task whose
executor is running or whose earlier reconcile is still queued. A recheck whose
pending result has the same summary, flags, ref and CI policy at the same head
and revision records no evidence and no `check ci` event; the earlier entry
stays the receipt. Pending CI with nothing queued or running for 30 minutes at
the same head and revision, counted from the first such entry, records
`stalled: true` and prints `STALLED`. Checks that are queued or running wait
much longer. A check queued without starting stalls past GitHub's 24-hour
queue limit plus 30 minutes, counted for an Actions job from the later of its
workflow run's `created_at` and `run_started_at` (a re-run keeps `created_at`
and starts a new attempt), and otherwise from the entry that recorded the same pending
summary: a job no runner will pick up. Jobs queued behind other PRs on busy or
self-hosted runners are healthy. A check in progress stalls past GitHub's
6-hour job limit plus 30 minutes from its `started_at` (from the unchanged
summary when GitHub gives no start), such as an app run that crashed after it
opened; jobs that run 20 to 45 minutes with no status change are healthy.
Workflow `timeout-minutes` is not read, so a self-hosted job allowed to run
longer than 6 hours shows as stalled in the inbox. A stall only flags the
inbox: it fails no gate and sends nothing to rework. GitHub creates check runs within a minute
or two of a push and computes mergeability in seconds, so the window is about
15 times the normal delay. A PR closed without merging stalls at once. A stall
is not a verdict on the change: the task stays submitted, no retry is used, and
scheduled rechecks stop for that head. A `ci completed` notification, a manual
`check ci` or a new head restarts them; a manual check of a stalled head starts
a new 30-minute window. Status, the sketch and the board distinguish failed,
stalled, pending and missing gates, including the gate name.

## Main CI and releases

The host follower's `wait --inbox` refresh reads the newest 30 workflow runs and the current head of the project base, alongside its per-PR reads. Foreground inbox reads use cached GitHub data and recorded base CI observations. An unfiltered orchestrator `wait --follow` also refreshes main CI without `--inbox`. These reads reuse `main-ci-cache.json` for a minute; the active-workflow list is reread hourly while CI is red. For each workflow, the newest completed `schedule` or `workflow_dispatch` run decides the recorded red status of its full runs, and apart from them the newest completed `push` run decides its push runs: main pushes run a thin check, so a green push does not clear a red daily run. A cancelled push stays red while a newer push is pending. Superseded cancelled schedule or manual runs are skipped. Reruns keep the previous verdict until they conclude, and workflows outside the listing keep their recorded verdict. Inactive workflows are ignored. Conclusions other than `success`, `neutral` or `skipped` are red for this status view.

A `main ci` event records `{ base, head, read_at, red, push }`. `red` holds the deciding red runs; `push` holds the newest completed push run of each observed active workflow, including green runs. Run records contain `{ workflow, workflow_id, path, id, attempt, number, event, sha, conclusion, url, jobs? }`. Red push runs and other red runs include failing jobs and parsed test names: `{ id, name, conclusion, url, tests: [{ name, error }], log_error? }`. Unchanged observations write nothing; observations older than the last recorded one write nothing. Events belong to their base, so changing the base starts clean.

Red push runs at each head share one `main_ci_failed` item, id `main_ci_failed:project:HEAD_SHA`, with `runs`, combined `jobs`, test names and the first run under `run`. An observer raises its `inbox item` notification once per head, including across reruns. A later green push clears the failed workflow; older-head push failures keep their head item while a newer push is pending or does not trigger the failed workflow. Red schedule and manual runs also keep one item per workflow, id `main_ci_failed:project:WORKFLOW_ID`. The action opens `Fix BASE CI: WORKFLOW (workflow WORKFLOW_ID), red since run ID`, or shows the existing open fix task. A test failing again after a green run creates a `main_ci_flaky` item with `test`, `run` and `earlier_runs`, pointing to an existing or new flaky-test task. These CI items cannot be acknowledged. `status` prints recorded red workflows and their jobs and tests without reading GitHub. A failed inbox CI read is `github_error:project:main-ci`.

For a project with a GitHub repository, `ask --setting publish` always reads the base's runs, active workflows and current head afresh, independently of the inbox cache and optional publish policy. A workflow with completed `schedule` or `workflow_dispatch` runs on the base, its full runs, is judged by the newest of them that was not cancelled: it must be green (`success`, `neutral` or `skipped`) and at or after the base head this read finds, by GitHub's compare of the two (`identical` or `ahead`). The release ships that head, so a full run that predates it refuses with the run, its commit and the command that starts one (`gh workflow run FILE --ref BASE -R REPO`); a newer red or failed full run refuses too, and push runs of that workflow do not count. The read lists the newest 100 completed runs of each full event on the base and, for an active workflow with no deciding run there, that workflow's own 20 newest of each. Any other active workflow keeps the push rule: failed, cancelled, timed-out or unknown push runs refuse publication and name the run; a pending newer push cannot replace that completed push verdict. Disabled workflows do not block releases. For each active workflow absent from the newest 100 completed base-push runs, the check queries that workflow's latest completed push on the base directly. This covers managed workflows and older runs beyond the shared listing. Main push CI means observed push runs on the configured base: tag-only, other-branch and PR-only histories do not count. A workflow with no completed full or base-push history has no verdict to gate; the publication approval flow remains available. A recorded completed push attempt still decides while its run is being rerun and temporarily absent from GitHub's completed listing; a newer completed run or attempt replaces it. Unreadable GitHub responses refuse with the reason. An existing owner approval is left unconsumed on refusal, and an empty publish policy does not bypass a red verdict. Projects without a recorded repository retain the approval flow. The publish policy's `full_suite` condition does not count a crucial or mapped head run as the full suite.

The merge gate applies the same check before merging release PRs, including stack members and asynchronous merges: the full run must be at or after the base head the release PR merges onto. A release therefore takes two full runs on the base: one at the head before the release PR merges, for the merge gate, and one at the release merge commit, for `ask --setting publish`. Dispatch the second (`gh workflow run` on the base, or wait for the daily run) once the release PR has merged. Release detection uses a task or PR title beginning with `Release` and containing a version, or changed `version` values in `package.json`, `.claude-plugin/plugin.json` or `.claude-plugin/marketplace.json`. Unreadable changed manifest patches refuse the merge. Already merged PRs can still be confirmed; repair PRs can merge while main CI is red.
