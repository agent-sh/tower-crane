# The model ladder

Every task has a tier, and the ladder in `project.json` says which harness, model and effort runs each tier and each other job. `tower-crane ladder show` prints it and where each rung comes from; `docs/state.md` has the full shape and the precedence (project, then the user file `~/.config/tower-crane/config.json`, then built-in).

## Swap a model

Change the `model` value on one rung in `~/.config/tower-crane/config.json`. For example, this line chooses the easy model for new projects:

```json
"easy": { "harness": "claude", "model": "global.anthropic.claude-haiku-5-5", "effort": "high" }
```

Put it inside the file's `"ladder": { ... }` object. Replacing the model ID needs no code changes. Keep the harness and effort valid for the CLI you use. Claude models on Bedrock need the `global.anthropic.` inference profile ID, rather than a regional `us.` ID. A rung with an explicit Claude `provider` adds that prefix itself and expands the short names in `BUILTIN.claude_aliases` (`opus`, `fable`, `sonnet`) to the release each names; any full ID passes through unchanged, so a new release needs only the ID. On Codex, use `model` for an explicit ID or change `profile` to the name of your configured profile.

Existing projects keep the ladder copied at initialization. Swap a project rung through the CLI in one command:

```sh
tower-crane ladder set easy --model YOUR_MODEL_ID --clear profile
```

This keeps that rung's harness and effort. `ladder show` confirms the resolved model and its source. [builtin-ladder.json](builtin-ladder.json) records the shipped defaults. Tests pin their own rungs through `fixtureLadder()` and `pinRung()` in `test/helpers.js`; only the defaults test checks that snapshot. `node scripts/probe-model-swap.js` changes every built-in rung to a fictional model on another harness in a temporary copy and checks that only the defaults test fails. It uses the software-gate runner at three workers with a 45-minute deadline, private fixture caches and a short Chrome socket path. Live probes require `TOWER_CRANE_LIVE_MODEL` or `TOWER_CRANE_LIVE_PROFILE` explicitly.

`node scripts/check-model-config.js` scans the raw text of `lib/`, `bin/` and JSON outside documentation for model ID and profile patterns. Comments and strings are checked alike. Every hit outside the BUILTIN table needs an entry in [tools/model-literals.json](../tools/model-literals.json) with an exact file path, matched text and reason. Matching uses the text written in the file.

CI runs the complete model swap probe once on Linux with Node 26. Its temporary repositories live in the runner's cache outside the checkout, so parent project rules, state and agent cache identity cannot affect the fixtures.

| Rung | Does | Good fit |
|---|---|---|
| `orchestrator` | plans, writes briefs, dispatches, runs gates, merges | the strongest model you have, in the harness you talk to |
| `easy` | `S` tasks by default: mechanical, local changes | a fast, cheap coding model |
| `medium` | `M` tasks by default | a strong coding model |
| `hard` | `L` tasks by default: cross-cutting or risky changes | the strongest coding model |
| `research` | tasks of kind `research` by default: open questions, measurements | the strongest model at high effort |
| `review` | fallback for clean-context review | used when no tier rung at the needed level can run |
| `small` | mechanical checks, such as confirming lines the cleanup tool flagged | a small fast model |

`task add` and `plan import` pick a tier from kind and size (`research` for kind `research`, else `S` easy, `M` medium, `L` hard); `--tier` overrides it, and only `--tier` changes it later.

```bash
tower-crane ladder harness codex                                  # every rung without its own harness
tower-crane ladder set easy     --profile luna --effort medium
tower-crane ladder set hard     --harness claude --model opus --effort high
tower-crane ladder set review   --profile sol --effort high
tower-crane ladder save-user                                      # make this ladder the default for new projects
tower-crane task update T3 --tier hard
```

A primary rung is `{ "harness", "model", "profile", "provider", "effort", "args", "command", "supervision" }`, every field optional; a rung without `harness` runs on the default harness. `ladder set` changes only the fields it names and `--clear FIELD` removes one. A write that would leave a rung unable to run (a codex profile on pi, a missing model) is refused. The Settings view of `tower-crane serve` edits the same ladder and each task's tier. [CLI: agents and worktrees](cli.md#agents-and-worktrees) lists the command and effort values each harness takes.

`tower-crane ladder set hard --supervision '{"retries":5,"backoff_ms":30000,"max_backoff_ms":600000,"stall_ms":300000,"progress_paths":["lib","test"]}'` sets retry and progress checks for that rung. `--clear supervision` restores the defaults. Reruns keep the resolved route. Codex and command adapters resume their session; Claude starts fresh with the brief and an interruption note. [State: supervision](state.md#projectjson) records the default values and their reasons.

Fallbacks are personal settings. In `~/.config/tower-crane/config.json` (or `TOWER_CRANE_CONFIG`), set `ladder.easy.fallbacks` to `[{"profile":"sol","effort":"high"},{"harness":"claude","model":"opus","effort":"medium"}]`. They apply to the easy rung in every project, even when the project defines its own primary. A user rung may contain only fallbacks. `ladder set RUNG --fallbacks JSON` edits this personal list through the authority and audit check; it does not write project fallbacks. Edit it separately from primary fields. Operational route fields need no owner answer; command, environment, sandbox and other owner-required changes open an approval, as do new routes that widen reach. The approval binds the user file, rung and full requested list. `ladder show` prints their user-file source and marks routes with unavailable harnesses, profiles or model settings; the supervisor skips these routes. The next route runs after an outage exhausts the current route's retries, or immediately after a structured harness policy refusal. Each fallback inherits the resolved harness and supervision unless it overrides them. Research Claude fallbacks also inherit the primary `web_mcp` unless they specify their own web server; other harnesses do not inherit it. An inherited or explicit web MCP cannot combine with `mcp`. Other fields are independent. Every switch starts a fresh session with the original brief, keeps the claim and worktree, resets the retry budget, emits `spawn-fallback` for the orchestrator, and attributes spend to the route that ran. Use `ladder set RUNG --clear fallbacks` to remove the override, or `--fallbacks '[]'` to empty it. No fallback is enabled by default.

Claude rungs and routes also take `provider: "anthropic"` or `"bedrock"`. An Anthropic Opus primary can put `{"provider":"bedrock","model":"opus"}` first in its personal fallbacks; a Bedrock primary can put Anthropic first. Bedrock uses `global.anthropic.claude-opus-5-5` and Anthropic uses `claude-opus-5-5`, with corresponding global/plain ids for Fable and Sonnet. Routing overrides inherited provider selectors and preserves the original user's authentication through environment, login links and helper commands. Bedrock keeps paths to the user's AWS files across isolated homes. `ladder show` marks missing local credentials or region configuration as unable to run; fallback providers with these problems are skipped. Checks use configuration presence only, without executing helpers or calling a provider. Spend records include the provider that ran. Without an explicit provider, the user's Claude provider settings remain in effect.

Presence checks include inherited, project and rung environment names. A configured `env_file` defers readiness until real launch; previews never read it. File and literal AWS routing overrides take effect in the launch environment. Reviewer candidates use the same provider model identity as spend when comparing median costs.

## How each harness dispatches

A rung on claude, codex, agy or pi always runs through `tower-crane spawn`, including when the orchestrator runs on that harness: only a spawned agent gets its own environment ([Agent files and homes](#agent-files-and-homes)). A native subagent runs inside the orchestrator's session and shares its memory files, settings, hooks and MCP servers; no harness lets it have its own. A rung on opencode, which spawn does not isolate yet, may run as a native subagent when its harness is the orchestrator's.

- **Native** (opencode rungs only). Choose a unique name per attempt, claim workers with that name and a lease sized to the task, and pass the name, task, absolute worktree and state paths, skill path and brief. Every tower-crane call passes `--agent <name>` and, without `TOWER_CRANE_STATE`, `--state <dir>`. Workers use absolute paths under their worktree.
- **Spawned.** `tower-crane spawn --task <id>` runs the rung of the task's tier; `tower-crane spawn --role review --task <id>` selects a reviewer rung by task tier, diff risk and measured median review cost, with the review rung as fallback. Review dispatch requires passing software gates. Do not pre-claim. It starts the selected CLI in the task's worktree with `TOWER_CRANE_STATE`, `TOWER_CRANE_TASK` and `TOWER_CRANE_AGENT` set; a worker claims with that generated identity (`worker-T1-1`, `reviewer-T1-1`). pi loads the matching skill with `--skill`, codex finds it linked in its home, and claude workers get its path in the home's instructions. Workers receive the brief. Claude/Codex reviewers receive static role instructions in the system context and the submitted diff, acceptance, audited gate results and only the brief's `## Reviewer` section in the user message. They use the gate results and run only affected tests after changing a scratch checkout for a probe.
- **Custom command.** A rung with `"harness": "command"` and a `command` array runs any CLI; `{prompt}`, `{brief}`, `{task}` and `{cwd}` are substituted.

`tower-crane spawn --dry-run` prints the command without running it.

## Agent files and homes

Every agent runs under the agent file of its job in `agents/`: `tower-crane-worker.md` (`easy`, `medium`, `hard`), `tower-crane-researcher.md` (`research`), `tower-crane-reviewer.md` (`review`), `tower-crane-small.md` (`small`) and `tower-crane-orchestrator.md` (`orchestrator`). Each one lists, in its frontmatter:

| Key | Says |
|---|---|
| `tools`, `disallowedTools` | claude tools allowed and denied; mapped to pi built-in tool names; denied commands as `Bash(<prefix>:*)` on claude |
| `mcpServers` | always empty in the agent file: spawn adds explicit rung opt-ins and the user kit for browser tasks |
| `skills` | the tower-crane skill the job follows |
| `web` | whether it may browse or search |
| `gitPush` | `branch` (no force push) or `none` |
| `ghWrite` | the `gh` writes it may run; every other `gh` write is denied |
| `worktree` | `write` or `read`: whether its commands may change the worktree |
| `sandbox` | whether its commands request a sandbox; verified confinement is available on claude and codex, while agy enforcement is unsupported |
| `writeOutside` | what its commands may write outside the worktree: `state` (the tower-crane state directory, for the unsandboxed orchestrator only; a sandboxed role changes state through the [state broker](#state-broker)), `git` (the repository's git directory and the worktree's admin directory inside it, named on its own because codex keeps a workspace's git directory read-only unless a rule names it, so a worker can fetch, add, commit and push; the parts that make git run commands stay read-only, see [shared git directory](#shared-git-directory)), `cache` (a cache of the agent's own, `tower-crane/agents/<state hash>/<agent>` under `XDG_CACHE_HOME` or `~/.cache` (`%LOCALAPPDATA%` on Windows; an `XDG_CACHE_HOME` that is itself an agent's cache, inherited from a supervisor started in that agent's env, is ignored, so the cache never nests), for scratch, test temp files and tool caches; `XDG_CACHE_HOME`, `GOCACHE`, `GOMODCACHE` and `npm_config_cache` point into it, and it is removed with the agent's home. The cache root stays read-only: installed tools, gate commands and spawn receipts live there), and for the orchestrator `homes` and `worktrees` |
| `codexDisable` | codex features it does not get |

| Role | Tools | Web | git push | gh writes | Worktree | Writes outside it |
|---|---|---|---|---|---|---|
| worker | Bash, Read, Edit, Write, Grep, Glob, Skill | no | its branch, no force | `pr create`, `pr edit` | write | git, cache |
| reviewer | Bash, Read, Grep, Glob, Skill | no | no | `pr comment` | read | cache |
| small | Bash, Read, Grep, Glob | no | no | none | read | none |
| orchestrator | all but NotebookEdit | yes | branches, no force | reads plus `pr`, `issue`, `release`, `repo` (not `repo delete`), `api`, `workflow`, `label`, `gist` | write | unsandboxed: it starts the other agents, whose sandboxes do not nest in its own |

**Native agents cannot have an environment of their own.** A native subagent runs inside the session that starts it, so that session's memory files, settings, hooks and MCP servers reach it, whatever its agent file says. Claude Code still reads these files as plugin agent frontmatter (`tools` is the allowlist, `disallowedTools` the denials, `skills` is preloaded), but tower-crane never dispatches a claude, codex, agy or pi rung natively: those rungs always go through `tower-crane spawn` ([How each harness dispatches](#how-each-harness-dispatches)).

**Spawned claude, codex, agy and pi agents** get the file rendered to flags and a home of their own at `homes/<agent>/` in the state directory, built fresh, private (mode 700, files 600) and under the lock for every spawn: Claude, Codex and pi use it as their config directory (`CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `PI_CODING_AGENT_DIR`), with `home/` inside it as `HOME`. Agy uses `homes/<agent>/home/` as `HOME` and keeps its config under that HOME's `.gemini/`. Nothing one agent writes there reaches the next, and a spawn removes the homes of agents whose process has exited. The user's memories, skills, plugins, hooks, MCP servers and approved-command rules never load, including what a harness finds under `HOME` (codex reads skills from `~/.agents/skills`). The agent's `HOME` links `.gitconfig`, `.config/git`, `.config/gh`, `.aws` and `.ssh` from the user's. Agy also links ADC credentials and, for explicit MCP opt-ins, MCP OAuth tokens.

**House rules** reach spawns by path, except for the Claude/Codex reviewer snapshots described below, so an edit applies to the next agent ([`lib/rules.js`](../lib/rules.js)). The chain starts with the user's global rules for the harness:

- Claude: `CLAUDE.md` and `rules/*.md` in the user's Claude config directory.
- Codex: `AGENTS.override.md` or `AGENTS.md` in the user's Codex home.
- OpenCode: `AGENTS.md` in `$XDG_CONFIG_HOME/opencode` (default `~/.config/opencode`), falling back to the user's Claude `CLAUDE.md`.
- Pi: `AGENTS.md`, falling back to `CLAUDE.md`, in the original user's `$PI_CODING_AGENT_DIR` (default `~/.pi/agent`), recovered from the home marker for nested isolated dispatches.
- Agy: no user global rules. User `GEMINI.md`, `AGENTS.md` and modular rules in the original `.gemini` directory are excluded from the prompt, startup receipt and generated read grants. Project rule imports that resolve to these files are excluded too.
- Command: the existing global files from all these locations. A custom command has no instruction discovery contract, so both its prompt and `{brief}` name the files to read. Spawn requires `{prompt}` or `{brief}` in the command argv and refuses before startup when neither is present.

The chain then includes `AGENTS.md`, `CLAUDE.md` and `CLAUDE.local.md` in every directory from the filesystem root down to the worktree (`.claude/CLAUDE.md` too, inside the repository), followed by their Claude `@path` imports. Codex prefers `AGENTS.override.md` over `AGENTS.md` in each directory. A Claude worker's home `CLAUDE.md` uses absolute import lines, quoting paths containing spaces or tabs and preserving literal whitespace; nested quoted or escaped imports are discovered too. `@~/` imports get another absolute import because Claude resolves `~` from the agent's isolated `HOME`. For agents using path imports, only files reachable within Claude's five-hop limit, including the generated home's hop, are marked loaded; the prompt tells the agent to read the rest. Codex loads its selected worktree instruction file and reads the rest. OpenCode keeps the user's `HOME` and receives global and project files marked `read`. Pi uses its isolated `HOME`, disables context discovery and receives every global and project rule marked `read`. Agy runs in a fresh HOME and receives project rule paths marked `read`; the original user memory and modular rules are excluded. The receipt makes no unverified loading claim. For agents using rules by path, the prompt's `## House rules` lists each file as loaded or to read, and its `## Goal` states the project goal and the task's target and asks the agent to restate both in its first message. `spawn --dry-run` shows the chain with its size; a `startup` event records it for each started agent.

Claude/Codex reviewers snapshot the same chain's contents into their shared system context instead of repeating worktree paths in the user message; edits apply on the next dispatch. Their startup rules are marked `system`, including imported files that a path-based Claude dispatch would need to read separately. Every prompt's `## Goal` states the project goal and task target and asks the agent to restate both.

Measured on 2026-10-07 for this repository's T88 (bytes; tokens are about a quarter): before this chain, a claude worker loaded only its home `CLAUDE.md` (1.3 KB of role text): no repository `AGENTS.md`, no ancestor `~/projects/AGENTS.md`, and neither `~/.claude/CLAUDE.md` nor the `~/.config/agents/SHARED.md` it imports. A codex worker loaded its home `AGENTS.md` and the worktree's `AGENTS.md` (1,733), but not `~/.codex/AGENTS.md` (11,779) or `~/projects/AGENTS.md` (1,444). With the chain, the claude worker loads 14,273 bytes of rules (about 3,570 tokens) and the codex worker reads 13,223 more (about 3,300 tokens); the prompt grows by about 1,350 bytes (8,521 to 9,875 for claude, 9,830 for codex, with T88's rework brief).

`TOWER_CRANE_LIVE_CLAUDE=1` or `TOWER_CRANE_LIVE_CODEX=1 node --test test/live-rules.test.js` runs the real harness against rule files that each give a random house token: a user global file and its `@import` in a config directory of the test's own (linking the user's login, never writing the user's), an `AGENTS.md` above the repository and the repository's. The worker must name every token and restate the goal and target in its first message, and the `startup` event must list every file; it prints the startup size and the measured input tokens.

- **claude**: the config directory holds `CLAUDE.md` (the agent file's body, its skill's path and the house rules' `@path` imports; empty for reviewers, whose text is in the home's `system.md`, passed with `--append-system-prompt-file`), `settings.json` and `mcp.json`. `settings.json` carries only the provider settings from the user's `settings.json` (`CLAUDE_CODE_USE_*`, `AWS_REGION`, `AWS_PROFILE`, model and base URL names) the sandbox and Tower Crane message hooks. A credential helper the user sets (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`) is not copied, since the command may hold the credential: the home names `lib/auth-helper.js`, which reads and runs the user's command each time claude asks. `.credentials.json` is a link to the user's. Flags: `--setting-sources user` (so a repository's `.claude/settings.json` and `settings.local.json`, with their hooks and plugins, do not load), `--permission-mode acceptEdits`, `--tools` and `--allowedTools` from `tools`, `--disallowedTools`, `--strict-mcp-config --mcp-config <home>/mcp.json` and `--disable-slash-commands`. Reviewers also use `--exclude-dynamic-system-prompt-sections`. Every Claude spawn sets `FORCE_PROMPT_CACHING_5M=1`. A credential kept only in the user's settings env reaches the agent only when spawn runs with it in its environment, as it does from a Claude Code session.
- **claude's sandbox**: every sandboxed role runs Bash in claude's own sandbox with `failIfUnavailable`, so a sandbox that cannot start stops the agent instead of running it unconfined, and `allowUnsandboxedCommands: false`. Writes: the worktree for a worker (and the repository's git directory, as claude allows for a linked worktree), never for reviewer and small, whose worktree is in `denyWrite`; plus the `writeOutside` directories: the agent's own cache for worker, reviewer and researcher test runs. The state directory, agent homes included, is in `denyWrite`, and so are the protected parts of the [shared git directory](#shared-git-directory): the [state broker](#state-broker) writes it. The agent homes, `brokers/` in the state directory and the [owner key](state.md#agent-identity) directory are in `denyRead`; `allowRead` reopens only the dispatch's own home and its own `brokers/<agent>/`, so no agent reads another's broker token. claude checks its own Read, Grep and Glob tools against permission rules rather than the sandbox, so each `denyRead` entry is also a `Read`, `Grep` and `Glob` deny rule in `permissions.deny`, for the path and everything under it. A deny rule takes no exception: those tools cannot read the dispatch's own home or broker directory either (Bash can), and a home or broker directory spawned later stays hidden. `network.allowAllUnixSockets` is on, because the socket filter's seccomp helper needs a nested user namespace that hosts like this one refuse ("nested userns is capability-restricted"); in its place `denyRead` hides `/var/run/docker.sock`, `/run/docker.sock`, `/run/user/<uid>` (SSH agent, D-Bus, GPG) and the user's `~/.ssh` and `~/.aws`. Hiding a directory hides the sockets in it, so a sandboxed `connect()` there fails with `ENOENT` (`test/live-sandbox.test.js`, run with `TOWER_CRANE_LIVE_CLAUDE=1`); a socket in a directory not on that list stays reachable. The sandbox keeps a `.claude/.cc-writes/` directory in the worktree, which spawn adds to the repository's `info/exclude`. Network: all domains.
- **codex**: `config.toml`, and each `<profile>.config.toml`, are parsed and rebuilt from the user's files with only the model, provider and auth-store keys by name (never `model_instructions_file` or other instruction sources), providers in any TOML layout without any token, key, header, auth or env value, and the MCP servers the rung opted in to. It installs Tower Crane native message hooks and notify, grants trust to the generated hook commands with `-c bypass_hook_trust=true`, and adds the permission profile `tower-crane`: read anywhere, write the worktree only when `worktree` is `write`, write the `writeOutside` directories, temp and the agent's own `HOME`, read-only on the state directory and on the protected parts of the [shared git directory](#shared-git-directory) (other worktrees' admin directories included), no access to the [owner key](state.md#agent-identity) directory, other agent homes or `brokers/` in the state directory except write on the agent's own `brokers/<agent>/` (codex mounts readable paths before it hides a directory and writable ones after, so a readable path under a hidden one is hidden too), network on. `AGENTS.md` holds the agent file's body for workers, or the complete static system context for reviewers; `rules/tower-crane.rules` forbids the denied command prefixes; `auth.json` and `.env` (where codex reads an AWS profile or Bedrock token) are links; the job's skill is linked under `skills/`; `sessions` links to `homes/.codex/<agent>/sessions`, which outlives the home so usage can be read after the agent exits. Flags: `-c default_permissions="tower-crane"` (`":danger-full-access"` for the orchestrator), `-c approval_policy="never"`, `-c web_search="live"` for research (or explicit `web_search` opt-in), `-c web_search="disabled"` otherwise, and `--disable` for each of `codexDisable`.
- **git and gh**: all spawned harnesses get `bin/` in the home first on `PATH`, holding `git` and `gh` shims (`lib/shim.js`) that allow a list and refuse the rest, aliases included, whatever the option order. git: git's own commands, wherever the sandbox lets them write (a reviewer's worktree is read-only, while the temp and cache dirs where test fixtures run `git init`, `git config` and `git commit` are not); a push to a repository on this machine, as test fixtures do, only in the plainest form `git push <dest> [refspec...]` with no option anywhere after `push` (git accepts abbreviated options, so any option voids the exception and the role and force rules apply), and only when every URL git would push to is a path or `file://` after git's own URL rewriting (`remote get-url --push --all` for a named remote, `ls-remote --get-url` for a URL or path) and no `pushInsteadOf` rule is set; and a push to another machine only on `gitPush: branch`, with no option but `-u`, `--set-upstream`, `-q`, `--quiet`, `-v`, `--verbose` and `--porcelain` spelled exactly (git accepts abbreviations, so any other could force, delete or mirror), no refspec that starts with `+` or `:`, and no `remote.*.mirror` key (whatever its value) or forcing `remote.*.push` in the configuration; a plain local push may force or delete, as fixtures do. Before the subcommand: `-C`, `-c` (only `user.name`, `user.email`, `init.defaultBranch`, `commit.gpgsign`, `tag.gpgsign`, `core.autocrlf`, `core.quotepath`, `advice.*` and `color.*`, since any other setting could rewrite a URL, add a push URL or define an alias), `--git-dir`, `--work-tree`, `--namespace`, `--no-pager`, `-P`, `--literal-pathspecs`, `--no-optional-locks`, `--bare`, `--no-replace-objects`. gh: read commands (`pr view`, `pr diff`, `pr checks`, `pr list`, `issue view` and the like) plus the role's `ghWrite`.
- **agy startup**: the fresh `HOME` holds `.gemini/antigravity-cli/settings.json`, `.gemini/config/mcp_config.json` and `.gemini/config/agents/gishra-<job>.md`. The selected agent describes native tools, `mainAgent: true`, `subagent: false`, no plugins, its role's linked skills and the rung's named MCP definitions plus any configured browser kit. Spawn selects it with `--agent gishra-<job> --disable-slash-commands`. Only `modelProvider: "gemini"` is retained from user settings. Original user memory and modular rules are excluded from the prompt and generated read grants. Workspace MCP configs and role overrides refuse startup. Rung args allow only `--print-timeout`; output stays JSON for result and usage capture. The generated home and linked credentials isolate startup configuration.

Agy native enforcement is unsupported. Its capabilities are `sandbox: false` and `osSandbox: false`: moving a worker, reviewer or small rung to agy or adding agy args requires an owner decision. Agy receives no broker token and sets `TOWER_CRANE_SANDBOX=0`. Spawn still emits requested native permission settings and `--sandbox` for roles that request it, and refreshes sibling-path rule entries when homes are created. These settings and flags do not establish filesystem confinement, hiding of other homes, shell escape prevention, or push, gh-write and web restrictions. Git and gh wrappers are placed on PATH; their checks also do not establish native agy enforcement.

The failed probes are the reason for the false capabilities. On 2026-10-08, real agy 1.3.1 worker and reviewer attempts returned model refusals before the requested tool actions. The small attempt returned `denied_actions: [{action: "read_file", display_name: "ListDir"}]` with no response. None created its disposable write target, but no shell, sibling-broker, escape or web tool results proved the requested restrictions. Push and gh-write checks used wrappers, not native agy enforcement. A generated orchestrator returned `HEADLESS_PROBE` for a harmless command; that result does not establish confinement. No native enforcement guarantee is offered for agy, including Windows.

Agy's [CLI reference](https://antigravity.google/docs/cli/reference), [custom subagents](https://antigravity.google/docs/subagents), [MCP configuration](https://antigravity.google/docs/mcp), [rules](https://antigravity.google/docs/rules), [permissions](https://antigravity.google/docs/permissions) and [sandbox](https://antigravity.google/docs/sandbox) document the emitted configuration (read 2026-10-08). [Installation and auth](https://antigravity.google/docs/cli/install) documents OS keyring sign-in and `GEMINI_API_KEY`. The generated home links MCP OAuth tokens for opted-in servers and ADC credentials when present; it never copies credentials or links the user's `.gemini` directory. File links use the existing Windows hard-link fallback and directory links use junctions.

Live startup on 2026-10-08 with agy 1.3.1: three fresh first turns per setup, the same disposable Git worktree and prompt (`Reply with READY. Do not use tools.`), `--model "Gemini 3.8 Flash (High)"` in both setups and no session resume. **gh auth**: a gh login kept in the system keyring is out of a sandboxed agent's reach, since the sandbox hides the user's D-Bus socket. It is not written to files, argv, dry-run output or events. Agent commands can read `GH_TOKEN`, so a command that talks to GitHub without gh is not held to the gh allowlist. Harness output is persisted unredacted (the spawn log, and transcripts in the agent's home), so a token an agent prints is kept there.

A worker asks the orchestrator. An opted-in claude tool joins `--tools` and leaves `--disallowedTools`; an opted-in codex feature is enabled, and `web_search` turns search back on. An opted-in MCP server is taken by name from the user's harness config with its command, args and URL but without its `env` or headers, so a secret it needs comes from the environment; claude pre-approves its tools (`mcp__<name>`). `spawn --dry-run` names both. Anything else is refused.

Limits. The orchestrator runs unsandboxed on both harnesses: it starts the other agents, which build sandboxes of their own that do not nest inside one. The shims see `git` and `gh` as found on `PATH`: a program called by its absolute path, or run from a script, is not checked. On macOS, claude keeps an OAuth login in the keychain under a name tied to the config directory, so a subscription login does not carry over to a home; API key, Bedrock and Vertex setups do.

### Shared git directory

Linked worktrees share the repository's git directory, and git outside any sandbox (the harness process, Tower Crane, the owner) runs commands that its config and hooks name: `core.fsmonitor`, hooks, filter, diff and merge drivers. A sandboxed role with `writeOutside: git` writes the common directory, since every ref update takes `packed-refs.lock` there, and its own `worktrees/<name>/`, but not these, which claude's sandbox lists in `denyWrite` and codex's profile marks `read`: `config`, `config.worktree`, `hooks/` and `info/` in the common directory, `config` and `hooks/` of each submodule under `modules/`, and `config.worktree`, `commondir` and `gitdir` in the worktree's admin directory, plus the worktree's `.git` file (those last three decide which config git reads there). Spawn creates any of them that is missing, so no sandbox masks a missing path with a file the agent could replace. Tracing git 2.53 with strace in a linked worktree shows commit, rebase, fetch and push write only `objects/`, `refs/`, `logs/`, `packed-refs` and its lock in the common directory and files in `worktrees/<name>/`; `push -u` writes `config` (the upstream), so `tower-crane worktree` sets `branch.<name>.remote` and `branch.<name>.merge` on the host and a worker publishes with a plain `git push` (or `git push origin HEAD`); `gc` writes `info/refs`, so background gc is off for agents (below).

The harness process of a sandboxed claude or codex role runs its own git outside the sandbox, in the worktree the agent writes. Spawn starts it with `GIT_CONFIG_NOSYSTEM=1`, `GIT_PROXY_COMMAND` empty unless set, and command-scope entries (`GIT_CONFIG_COUNT`, which win over every config file) appended to any it inherits (`lib/harness-git.js`): `core.hooksPath` the null device (or a trusted absolute one), `core.fsmonitor=false`, `diff.external`, `core.askPass`, `core.alternateRefsCommand`, `core.sshCommand`, `protocol.ext.allow=never`, no submodule recursion, `gc.auto=0` and `maintenance.auto=false`, the credential helper lists cleared and refilled from the trusted ones, and, for each filter, diff, merge, gpg, trailer, tool or remote command the repository's config names at launch, the trusted value or one that runs nothing. Trusted means the global or command scope, which no agent writes. The agent's own commands inherit that environment, but they run inside the sandbox, where the repository's hooks and drivers may run as they do for the owner: the git shim drops those entries, all but `gc.auto` and `maintenance.auto`, when claude's sandbox (`SANDBOX_RUNTIME=1`) or codex's (`CODEX_SANDBOX`) marks the command. `TOWER_CRANE_GIT_ENV` names the range of entries spawn added. A config file the owner includes from a path the agent writes can still name a new driver after launch; the sandbox keeps the rest of the shared config out of reach. `test/live-git-sandbox.test.js` probes the real sandboxes from a worktree: writing `core.fsmonitor` to the shared config and a `hooks/post-checkout` both fail, commit, rebase onto main, fetch and push still work, and the harness's `git status` runs nothing planted. The codex probe needs no model call and runs wherever codex and user namespaces are available (`tests.host_only`); the claude one makes a model call and runs with `TOWER_CRANE_LIVE_CLAUDE=1`.

### State broker

A sandboxed agent reads the state directory but cannot write its state: `project.json`, `tasks.json`, `decisions.json`, `events.jsonl`, the lock, the logs and other agents' homes are read-only or hidden in its sandbox. What its commands can still write there is its own: for codex its `HOME` (`homes/<agent>/home/`), its sessions (`homes/.codex/<agent>/`, which `spend --from-spawn` reads, so the usage collected from them is the agent's own report) and its `brokers/<agent>/`, which the broker never reads back; for claude nothing, though the harness process itself writes its config directory, `homes/<agent>/`. For a claude or codex agent whose file says `sandbox: true`, the spawn monitor, which runs outside the sandbox, listens for that agent alone for as long as it supervises it (`lib/broker.js`). It writes `broker.json` into the agent's private broker directory, `brokers/<agent>/` in the state directory (mode 700, the file mode 600), with the address and a random token made for that spawn, and starts the agent with `TOWER_CRANE_BROKER` naming that file. For a claude agent the address is a Unix socket, `broker.sock` in that directory, or, when that path is too long for a socket address, in a fresh private directory under the temp dir; claude's sandbox has no host loopback. Codex's sandbox refuses connecting to a Unix socket, so for a codex agent it is TCP on `127.0.0.1` at an ephemeral port (`host` and `port`), which any local process can reach; the token, readable only by that agent, is what admits a request. On Windows it is a named pipe. The broker serves the whole spawn, its personal fallback routes from the user file included: it starts when any route runs a sandboxed harness, listens on what each of those harnesses needs (both, for a rung that falls back from claude to codex or back, the agent trying the socket first), and every sandboxed route gets `TOWER_CRANE_BROKER`. `test/live-sandbox.test.js` checks both against the real harnesses, a forged write refused and a note recorded through the broker; run it from an unsandboxed user session with `TOWER_CRANE_LIVE_CLAUDE=1` or `TOWER_CRANE_LIVE_CODEX=1`. In the agent, a tower-crane command that only reads (`task show`, `task list`, `brief get`, `project show`, `ladder show`, `validate`, `ready`, `decisions`, `status`) runs as usual; any other command aimed at the broker's state directory goes to the broker, and one aimed at another state directory, such as a test fixture's, runs in the agent. The broker checks the token, refuses an `--agent` that is not the spawned agent's name, allows only the role's commands on the agent's own task (positional ID, `--task` and `--blocks`), and runs the command as a CLI process outside the sandbox in the task's worktree, as the spawned agent on the spawn's state directory, naming `--agent` and `--state` before the agent's own arguments so a `--` among them stays the agent's. Records it writes carry `"via": "broker"`; that is provenance, not proof, since any unsandboxed process can write the same. Roles and their commands: worker `claim`, `renew`, `release`, `submit`, `spend` (its own spawn only), `task note`, `msg` (to `orchestrator` or `owner` only), `ask` and `decision withdraw` (only a decision it asked, as the CLI checks); reviewer `evidence --type review`, `task note`, `msg` (to `orchestrator` or `owner` only), `ask` and `decision withdraw` (the same asker-only check); small `task note`; and every role `answer` (under its bound identity, subject to owner-set decision delegation) and `hook`, for the [message hooks](#agent-files-and-homes), with its own `homes/<agent>/hook.json` binding only. `worktree` runs in the agent, as a read: it prints the worktree spawn made. The broker runs outside the sandbox, so it never executes anything the agent controls: no `check` (the project's tests and cleanup are the agent's code, and `--cmd` is its shell) and no git, whose repository config and commits the worker writes and which can run commands they name (merge drivers, `core.fsmonitor`). A command it runs finds no repository, and does not render the sketch, whose gate report reads the repository; the next write outside the broker renders it. A resubmit that checks the task's PR runs `gh pr view -R` with the project's `repo` and no repository for git to read, and is refused when `repo` is unset. A worker runs its tests in its own sandbox; the gates that run code (`check`, `merge`) are the orchestrator's. A command that reads stdin (`-` as a value) sends it with the request. The orchestrator is unsandboxed and writes the state itself. The broker closes when the agent exits: it removes the broker directory, drops open connections and kills any command it is still running together with every process under it, so nothing it runs writes after the spawn ends; the token is no longer accepted anywhere. A refused `msg` appends a `msg refused` event naming the agent, the task and the intended recipient, never the text. The rule covers brokered agents only. Agents on other harnesses (pi, opencode, agy and command) are not sandboxed and write the state directly, with no broker to refuse a message; that is why a worker, reviewer or small rung on one of them is owner-required (`ladder.reach`, [Authority](state.md#authority)).

### Reviewer cache

Claude/Codex reviewers split their context at dispatch. The system context contains the reviewer role and skill, the house rule chain's current contents (including imports), the configured standards, and the repository's `docs/state.md` acceptance-gates and `docs/cli.md` gates sections when present. It contains no task id, agent identity, brief, submitted sha, diff or gate results. Repository labels are relative to the checkout; external rule paths stay absolute, so changing checkout depth does not change the prefix. A changed rule, standard or contract changes the prefix on the next dispatch. Task context and audited gate receipts stay in the user message, even when a large diff is referenced by file.

Claude writes this text to `system.md` in its home and passes it with `--append-system-prompt-file` and `--exclude-dynamic-system-prompt-sections`; a file keeps it off the command line, which Windows caps at 32,767 characters, and the text is byte-identical across reviewers. `spawn --dry-run --json` shows it as `system`. Each reviewer has an isolated filesystem cache at `$XDG_CACHE_HOME`; `GOCACHE`, `GOMODCACHE` and `npm_config_cache` stay inside it. Provider prompt-cache reuse does not share those filesystem caches. ## Research network tools

The research rung renders `tower-crane-researcher.md`, with the same file permissions, git/gh shims, writable paths and sandbox as a worker. It permits web tools and requires actual network research with at least `research.min_sources` distinct cited pages (default 10). Its generated identity remains `worker-<id>-<n>` and it follows the work skill. Claude permits native `WebSearch` and `WebFetch`; its sandbox allows outbound domains `*` while preserving worker file confinement. Codex explicitly uses `-c web_search="live"`; `codex --help` on 2026-10-07 describes `--search` as enabling the native live Responses `web_search` tool. HTTP fetching through Bash retains the same command sandbox.

Claude providers such as Bedrock may lack native web tools. Configure just the web server in the project or user ladder:

```sh
tower-crane ladder set research --web-mcp '{"name":"harness-web","command":"node","args":["/absolute/path/to/harness-web/server.mjs"]}' --agent owner
```

The user defaults use the same `ladder.research.web_mcp` object. Its allowed fields are only `name`, `command` and `args`; secrets belong in the inherited process environment or the owner-configured environment file. Do not copy `env` from `~/.claude.json`. Use absolute script paths for portability across isolated homes; a bare executable command resolves on PATH. Claude loads only this server through `--strict-mcp-config --mcp-config <home>/mcp.json` and approves only `mcp__<name>__websearch` and `mcp__<name>__webfetch`. Native web tools are omitted in this mode. `web_mcp` applies only to research on Claude and cannot combine with `mcp`. Other roles retain their existing tool defaults and explicit owner opt-ins.

Agy research rungs render the researcher role with native `search_web` and `read_url_content` tools and the same generated configuration and git/gh wrappers as other agy workers; native enforcement is unsupported. OpenCode, pi and command receive researcher instructions, but have no Tower Crane sandbox or web-tool renderer. Configure their search/fetch tools and equivalent file/git confinement in their harness or command wrapper before dispatch; Tower Crane does not enforce those harness permissions. Tasks of kind research on every tier still require the same sources gate and claim-to-citation review. Commit the structured deliverable described in [state.md](state.md#research-sources).

## Review selection

`tower-crane accept` refuses review evidence recorded by the agent that submitted the task. Review dispatch gives the reviewer a clean context, so its model may match the builder. Selection starts at the task tier, raises for a broad or risky diff, and promotes to a stronger tier when T31 review spend shows its median cost is no higher. Unknown usage leaves the complexity choice intact. The `review` rung is used when no tier rung at the needed level can run. `tower-crane validate` warns only when no reviewer rung can run.

Only an explicitly identified owner can set `project set --review-policy JSON`. Its prices use the configured model IDs shared by rungs and spend entries, with whitespace trimmed and case folded. Provider prefixes remain distinct. Codex profiles resolve their actual model from the user's origin configuration, matching dispatch even when the caller's home is isolated: `<profile>.config.toml` or `[profiles.<profile>]` in `config.toml`; a readable standalone profile or a named profile table can inherit the base config's top-level model. An unknown profile keeps its configured identity. Every Claude rung expands `BUILTIN.claude_aliases` to its release ID; explicit provider routes also add their provider prefix. Native Claude review-spend aliases resolve through the same table before matching samples to prices; recorded IDs stay unchanged.

Run `TOWER_CRANE_LIVE_REVIEW_CACHE=1 TOWER_CRANE_LIVE_MODEL=YOUR_MODEL node --test --test-name-pattern="real Claude reviewers" test/reviewer.test.js` to measure first-turn reviewer cache reads and writes. Choose a Claude model that supports prompt caching; the probe requires an explicit model and a logged-in Claude CLI.
