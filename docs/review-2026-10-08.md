# Review of main, 2026-10-08

Owner, 2026-10-08: "look what can break, do deep reviews." This is a clean-context review of `main` at `f9d0061`, not of a PR; every probe was rerun with the same verdicts after merging `main` at `5d39794`. It covers the state broker and identity, secrets handoff and redaction, sandboxes and shims per harness, gates and their evidence binding, stacks and merge, the board's write paths, and the supervisor's reactions.

## Method

Every probe ran the real CLI or library against a scratch repository built by `test/helpers.js` under `TOWER_CRANE_TEST_TMP=~/.cache/t101-review/tmp`, with stub harnesses (`test/fixtures/harness-stub.js`, and shell stubs for opencode, agy and pi) and a fake `gh` (`test/gates/helpers.js` `fakeExec`). No probe touched this project's state directory. Code-execution probes only appended a line to a marker file in the scratch directory.

The scripts are in `research/T101-probes/`. Each file records `{ id, surface, command, expected, observed, verdict }` into `research/T101-probes/results/<file>.json`; the appendix lists every probe. To rerun:

```sh
env -u TOWER_CRANE_STATE -u TOWER_CRANE_TASK -u TOWER_CRANE_AGENT -u TOWER_CRANE_BROKER \
  TOWER_CRANE_TEST_TMP=~/.cache/t101-review/tmp node research/T101-probes/<file>.js
```

Two live probes (L1, L2) ran inside this worker's own claude sandbox. They used `test -w` and `test -r` only: no file outside the worktree was opened for reading or changed.

Verdicts: `CONFIRMED` means the expected protection did not hold, `held` means it did, `by design` means the behavior matches the documented contract, and `inconclusive` means the probe did not reach the state it needed.

66 probes: 22 confirmed, 38 held, 5 by design, 1 inconclusive. The confirmed probes group into 13 findings.

### F1. Critical: sandboxes can write the whole user cache

`agents/tower-crane-worker.md` and `agents/tower-crane-reviewer.md` list `writeOutside: cache`, which `lib/agents.js` `outsideDirs` resolves to `XDG_CACHE_HOME` or `~/.cache` as a whole (`cacheDir`). Programs that run outside the sandbox keep files there.

- S1: a claude worker spawn's `sandbox.filesystem.allowWrite` holds `<home>/.cache` itself.
- L1, inside this worker's sandbox: `test -w` succeeds on `~/.cache/claude-scratch-2026-10-06/tower-crane-tool/bin/tower-crane.js` and `lib/broker.js`, the CLI `~/.local/bin/tower-crane` runs for the owner and the orchestrator, and that the broker (`lib/broker.js` `CLI`) runs for every brokered command; on `~/.cache/claude-scratch-2026-10-06/clean-cmd.sh`, this project's `gates.clean_cmd`; on `~/.cache/tower-crane`, where spawn writes `job.json` for the monitor; and on `~/.cache/go-build`.

Impact: one edit in the cache gives a sandboxed worker code execution in its own broker, the orchestrator and the owner's shell. That bypasses every other control in this review. The scratch-under-`~/.cache` convention in the owner's rules makes this likely on any machine.

Fix direction: give each agent a cache directory of its own (for example `~/.cache/tower-crane/agents/<agent>`, pointed to by `XDG_CACHE_HOME` and the tool cache variables), never the cache root. Refuse `sandbox.write` entries that contain the tower-crane install, the CLI on PATH or a gate command's program.

### F2. Critical: worker-written git config runs in unsandboxed git

`writeOutside: git` lets a worker write the repository's common git directory, which holds `.git/config`. That access is needed for commits. The shim allows `git config` (X6). `lib/state.js` notes that the broker runs no git for this reason, but the orchestrator's git does: `S.git`, `lib/worktree.js` and the gates (`lib/gates/common.js` `git`) call plain `git` with the repository's config.

- X8: with `core.fsmonitor` set in the shared `.git/config` to a script, `tower-crane worktree T3 --agent orchestrator` ran the script twice, from the new worktree's directory.

Impact: a sandboxed worker runs commands as the orchestrator: outside the sandbox, with its environment and the gh token. The same works through `core.hooksPath`, `diff.external`, filter and merge drivers, `core.sshCommand` and `credential.helper`. Every git command the owner runs in the main checkout is affected as well.

Fix direction: run Tower Crane's own git with config that a worker cannot steer, for example `-c core.fsmonitor=false -c core.hooksPath=/dev/null` plus `--no-ext-diff` and `--no-textconv`, or `GIT_CONFIG_NOSYSTEM` with a `GIT_CONFIG_COUNT` override set. Better still, keep `.git/config` and `config.worktree` read-only in the sandbox and grant only `objects`, `refs`, `logs`, the worktree's admin directory and `index`. Gates already run in a detached worktree; give them a clean `GIT_CONFIG_GLOBAL` and `safe.directory` policy too.

Related, not filed separately: the tests and clean gates run code the worker wrote, outside any sandbox and with the orchestrator's environment. That is the gates' design, but `docs/state.md` should say so and the gates should drop secrets from that environment.

### F3. High: `--agent owner` grants owner without a task variable

`lib/authority.js` `actor()` returns `owner` for `--agent owner` before it checks `TOWER_CRANE_AGENT`. `bin/tower-crane.js` refuses owner only while `TOWER_CRANE_TASK` is set.

- I1: `TOWER_CRANE_AGENT=orchestrator tower-crane project set --merge-admin true --agent owner`, with no TTY and no `TOWER_CRANE_TASK`, exits 0 and sets `merge.admin: true`. The control I1b, the same call with `--agent orchestrator`, opens a decision as designed.
- I3: `env -u TOWER_CRANE_TASK TOWER_CRANE_AGENT=worker-T1-1 tower-crane project set --workers 4 --agent owner` exits 0.

Impact: every owner-required setting and waiver is enforced only against an orchestrator that complies. The same holds for workers on opencode, agy, pi or command rungs (H-opencode, H-agy, H-pi run unconfined). `docs/state.md#authority` says that a `--agent` differing from a `TOWER_CRANE_AGENT` that names a spawned agent is never the orchestrator. The code does not apply that rule to owner, and nothing guards the native orchestrator.

Fix direction: refuse `--agent owner` whenever `TOWER_CRANE_AGENT` names anything other than `owner`. Require owner commands to come from an interactive terminal (stdin and stdout TTY), or from a credential the owner holds that agents cannot read (an owner key outside every sandbox, checked by the CLI). Record the terminal check in the event.

### F4. High: any local process can take the board's owner token

`tower-crane serve --agent owner` embeds its per-run token in `/settings` and `/` as `<meta name="tower-crane-token">`. The Host and Origin checks stop browsers, and they hold (W3, W4). A local client that sends no Origin header is let through.

- W6: a plain HTTP client GETs `/settings`, reads the token and POSTs `/api/decisions/D1/answer`: 200, and D1 is answered by `owner`.
- W7: the same client POSTs `/api/ladder` setting the medium rung to `harness: command, command: ["/bin/true"]`, an owner-required `ladder.command` change: 200.

Impact: while the owner's board runs, any process on the machine can answer the owner's decisions and choose the program the next spawn runs. `docs/state.md` says both rendered sandboxes allow TCP loopback, so this includes sandboxed agents.

Fix direction: deliver the token only to the owner's browser: print a one-time URL with the token in the fragment, then exchange it for an HttpOnly, SameSite=Strict cookie. Or bind to a Unix socket with 0600 mode, or require the token on GETs of pages that embed it. Deny the sandboxes loopback access to the serve port.

### F5. High: sandboxes can read the user's credential stores

`lib/agents.js` `claudeSandbox` denies reads only of other homes, broker directories, docker sockets, `/run/user/<uid>`, `~/.ssh` and `~/.aws`. Network is `allowedDomains: ['*']`.

- S2: the rendered `denyRead` leaves `~/.config/gh`, `~/.claude`, `~/.codex`, `~/.docker`, `~/.npmrc`, `~/.netrc` and `~/.git-credentials` readable.
- L2, inside this worker's sandbox, `test -r` only: the owner's `~/.config/gh/hosts.yml`, `~/.claude/.credentials.json`, `~/.codex/auth.json`, `~/.docker/config.json`, `~/.npmrc` and `~/.config/tower-crane/config.json` are readable; `~/.ssh` shows as empty.

Impact: the agent homes isolate what the harness loads, which `test/isolation.test.js` proves, but not what the agent's shell can read. The gh token that spawn passes on purpose has narrow use through the gh shim; the gh credentials on disk can be used directly. The model and provider credentials can also be sent anywhere.

Fix direction: deny reads of the user's credential stores by default: gh, claude, codex, docker, npm, pypi, cargo, netrc, git-credentials, kube, gcloud and azure. Codex should get the same list. Keep an owner-set exception for a rung that needs one.

### F6. High: review evidence from any name passes the review gate

`lib/tasks.js` `eligibleGateEvidence` accepts any review whose agent is not `task.submitted_by`. Recording review evidence needs no role: only the broker limits it, and only for sandboxed workers.

- I6: `tower-crane evidence T1 --type review --ok --sha <head> --agent made-up-reviewer`, a name no spawn started, makes `task show` print `gates: review ok`.
- I7: `tower-crane accept T1 --agent orchestrator` then accepts the docs task on that review alone.

Impact: the independent review, the one gate that stands for judgment, can be met by the orchestrator or an unsandboxed worker under a new name. T34's automation (PR #78, not on main) reacts to `evidence` events of type review and merges without an agent turn, so this becomes a path to merge.

Fix direction: count a review only when the recording agent is a reviewer spawn for this task at this sha and revision (the `spawn` event with `role: reviewer`), or the owner. Give an orchestrator's own review a separate, owner-waivable gate.

### F7. Medium: the merge gate does not check the PR's base branch

`lib/gates/merge.js` `run` compares the base only when `task.stack_disabled` is set. The gh shim lets a worker run `gh pr edit --base` (X7).

- M1: an accepted task whose PR base is `release`, with `project.base: main`, is merged: `ok=true`, with the summary "merged PR #42 into main".

Impact: code gated and reviewed as a diff against `main` lands on another branch, which may deploy, and the record says it went to `main`. M2 shows a fork PR passing the plain path as well; the head match still binds it to the accepted commit, so that case is informational.

Fix direction: refuse when `baseRefName` differs from the task's target base (`stack.targetBase`), and on the plain path refuse `isCrossRepository` as the stack path does. Report the real base in the summary.

### F8. Medium: rework and brief changes do not invalidate a review

`rework` sets status and claim but not `revision`. `brief set` changes nothing that evidence binds to.

- G3: review ok at sha X; `rework T1 --reason "the reviewer missed a broken link"`; the worker claims and resubmits the same X; `accept T1` passes on the review that rework rejected.
- G4: after a review, `brief set T2` adding a requirement leaves `review ok`. The control G5 shows that an acceptance change does bump the revision.

Fix direction: bump `revision` on rework, or record the rework time and count only evidence made after it. Bump it on a brief change once the task is submitted, or fold a brief hash into the evidence.

### F9. Medium: stack merge lands a head pushed after its last check

`lib/gates/merge.js` `stackMerge` re-reads every head, then runs `gh stack merge --squash`, which has no head-match option, as the code notes.

- M4: with a fake gh whose head moves between the last `pr view` and `stack merge`, the moved head lands. The gate reports "stack merge not confirmed" afterwards; the code is already merged.

Fix direction: before the stack merge, lock the heads the merge will take. For example, have each branch's head protected by a ruleset or push protection that the worker's token cannot bypass. Or merge each PR with `gh pr merge --match-head-commit` bottom up when the stack API cannot pin heads. Until then, document the window and alert loudly when the after-check differs.

### F10. Medium: codex config redaction misses common credential keys

`lib/agents.js` `SECRET` matches `token|secret|password|...|api_key|...` with an underscore. `[model_providers.p]` keys named `apikey`, `key` and `bearer` pass the scrub.

- S6: a codex worker spawn copies all three values into `homes/worker-T2-1/config.toml` in the state directory. `api_key`, the control, is dropped.

Fix direction: keep only the fields `L.CODEX_KEYS` names for providers (an allowlist), rather than removing the keys the regex catches. Add `key`, `apikey` and `bearer` to the regex at least. Cover each with the isolation test's planted-secret walk.

### F11. Medium: the git shim pushes to any ref

`lib/shim.js` `gitDenied` with `gitPush: branch` checks options and refuses refspecs that force or delete. It does not check the destination ref.

- X1: `git push origin HEAD:main` is allowed.
- X2: `git push origin HEAD:refs/tags/v9.9.9` is allowed.

Impact: without branch protection on the remote, a worker publishes straight to the base branch or creates release tags. With protection, the push fails remotely, but the shim's comment ("push ... on gitPush branch") promises more than it checks.

Fix direction: allow only `refs/heads/<task branch>` as the destination, the branch `tower-crane task show` names. Resolve `HEAD`, bare names and `src:dst` forms against it, and refuse `refs/tags/*`.

### F12. Low: a worker can message another task's agent

`lib/broker.js` lets a worker run `msg` with no `--task` to any `--to`.

- B12: `msg --to worker-T1-1 "note from T2"` from worker-T2-1 is authorized.
- B13: `harness-hooks.unread` delivers it into worker-T1-1's context as "Message from worker-T2-1 for T2".

Impact: one worker's text enters another worker's prompt, crossing the per-task boundary the broker keeps everywhere else. `docs/cli.md` documents `msg --to NAME`, but not that a worker may reach other workers.

Fix direction: for a brokered worker, allow `--to orchestrator` (and the owner) only. Or let the orchestrator relay messages.

### F13. Low: a worker can record `hook git-push` with no push

`hook git-push` and `hook pr-created` are meant to come from the shim after a successful command, but a worker may call them directly with its own binding.

- R1: `tower-crane hook git-push --binding homes/worker-T1-1/hook.json` with no push records a `hook git-push` event.

Impact: nothing on main reacts to these events yet. Any reaction built on them, such as T34's automation, should check GitHub or the repository instead of trusting the event.

Fix direction: drop the two actions from the broker's `hook` allowance and record them from the shim through a path the agent cannot call. Or document them as hints and verify on use.

## What held

The broker refuses other tasks, other identities (`--agent` inline or spaced), other roles' commands, `--from-spawn` and bindings of other agents, and wrong tokens. It replaces `--state` and `--agent` (B1 to B4, B6 to B11, B14). Owner identity is refused while `TOWER_CRANE_TASK` is set (I2). A worker's `--agent orchestrator` is refused (I4). Software gate evidence cannot be recorded by hand (I8), and a hand-written `tasks.json` entry without its audit event does not count (G6). Review evidence binds to sha and revision across resubmits (G1, G2), and an acceptance change bumps the revision (G5). The plain merge refuses a moved head (M3). The shim refuses force, `+` and `:` refspecs and `-c core.fsmonitor` (X3 to X5). Serve refuses POSTs without the token, from a non-owner serve, from other origins, with a rebound Host or a non-JSON type (W1 to W5). The env_file value and the gh token reach no state file, receipt or dry-run output (S3 to S5). Hook stop messages stay attributed to the sender's own task (R2), and a worker's hook cannot name another task (R3). Moving a worker rung off claude and codex is owner-required (H-reach).

## Limits

- T34's reactions are not on main: its PR #78 is submitted, not merged. This review probed the reactions main has (hook events, stop messages, stall sources). F6 and F13 are the inputs T34's automation trusts; carry them to T34's review. R4, which tests whether claimant activity defers a stall, did not reach a stall state in the scratch setup and is marked inconclusive.
- The stubs do not enforce a sandbox. The sandbox findings rest on the rendered sandbox settings (S1, S2) and on the live checks in this worker's own claude sandbox (L1, L2). Codex's rendered permissions were not walked path by path.
- M4 uses a fake gh. It shows the gate's ordering; how wide the window is on GitHub was not measured.
- The task is kind `research`, but its evidence is local probes, not web sources: this worker may not browse the web. No `research/T101.json` source list exists, so the sources gate will need the owner's waiver or a kind change.
