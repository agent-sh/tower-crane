## Method

The scripts live in `research/review-2026-10-09/`. Every probe creates an
isolated Git repository with `test/helpers.js` under
`$XDG_CACHE_HOME/T144-probes`, inside this worker's directory under
`~/.cache`. Gate worktrees and temporary files also stay under that cache.
Each repository is removed in `finally`; helper seeds are removed on exit.
The harness drops inherited `TOWER_CRANE_*` variables before loading fixtures.
It never uses the project's state directory for a probe.

The run used Linux, Node 26.10.0, and `nice -n 19`. Probes run serially,
except L01's three competing CLI claims. No full test suite ran. The real
tests gates run only a fixture's `node test/value.test.js`. Scratch state
is created and changed through CLI commands using explicit identities;
no scratch command uses owner identity.

There are three evidence levels:

- CLI integration: A16, L01 to L08, G01 to G07, G11 and G12 run real
  commands and inspect their resulting state and audit receipts. Expiry
  probes preload a clock advanced by two minutes instead of editing leases.
- Library execution: merge probes inject GitHub responses at the existing
  execution boundary. G08 runs a real process timeout through the tests
  gate with a three-second library argument. G09 observes the default
  shell budget. G10 injects a normalized timeout at the merged-head shell
  boundary after real Git merges. A21 uses real conflicting Git branches
  and a simulated GitHub mergeability response.
- Event replay: scheduler, reservation and snapshot probes run the current
  library functions on clones of CLI-created scratch state. Synthetic
  receipts stay in memory. `harness.load` exposes private functions and
  substitutes state access in memory without editing `lib/` or `bin/`.
  These probes test the decision logic, not cross-host transport.

To rerun all probes from the checkout root:

```sh
nice -n 19 node research/review-2026-10-09/run.js
```

The runner also accepts a group (`automation`, `merge`, `lifecycle`, `gates`, `processes`)
or one probe ID. It writes `{ id, surface, command, expected, observed,
verdict }` records under `research/review-2026-10-09/results/`.
[The main run](../research/review-2026-10-09/results/all.json) contains 56
probes; [A21's additional run](../research/review-2026-10-09/results/A21.json)
checks conflicts before gates. Each receipt identifies the checkout SHA,
Node version, platform and scratch root.
[The gate rerun](../research/review-2026-10-09/results/gates.json) and
[A16 rerun](../research/review-2026-10-09/results/A16.json) retain the
observations after the base update.

Verdicts follow the previous review: `CONFIRMED` means the expected
protection did not hold; `held` means it did; `by design` means the
behavior matches the contract; `inconclusive` means the probe did not
reach the state it needed. A runner error produces `inconclusive` and a
nonzero exit. Reproducing a defect is a successful probe run, so
`CONFIRMED` alone does not make the runner exit nonzero.

The original review has 57 distinct probes, 70 recorded results. Initially:
14 confirmed, 37 held, 6 by design, 0 inconclusive. With the affected

0 inconclusive. The confirmed probes group into four follow-up findings

### F1. High: test selection and proof settings do not bind evidence

`lib/tasks.js` `gatePolicyMismatch` checks the command policy and the
resolved tests mode. `lib/gate-commands.js` `resolve` snapshots
`tests_cmd` and `tests_proof_cmd`. Neither binds `tests.paths`,
`tests.keep` or the effective `tests.expensive` setting.

G03 first runs a passing, audited regression proof through the CLI. After
`project set --tests-paths '["elsewhere/**"]'`, the task still reports
`tests ok`. An explicit rerun at that same head fails with
`no test covers this change`. G05 enables expensive proof without a
proof command: the old evidence remains green, but a rerun refuses the
missing scoped-proof command. G04 records a pass with `value.js` kept,
then removes that keep; the old pass still counts despite never proving
the newly required revert.

Impact: acceptance and merge can count proof that the current project
policy would reject. This is separate from command and mode invalidation,
which hold in G01 and G02.

Repro: `nice -n 19 node research/review-2026-10-09/run.js G03`

Proposed acceptance: "Tests receipts and audit events bind the effective
test-path matcher, keep policy and expensive-proof setting in addition
to command and mode; changing an effective proof input makes prior
evidence stale in task reports, acceptance and merge, including changes
made during a running gate; unrelated executor settings keep it valid."

### F2. High: renewing an expired claim bypasses readiness

`lib/tasks.js` `claim` calls `blockReasons`. `renew` checks worker
capacity and resource locks after expiry, but does not recheck
dependencies, `needs_owner` or open blocking decisions.

L05 claims T1 for one minute, advances the CLI clock by two minutes, and
adds an unmet dependency on T2. A fresh claim refuses with
`T1 is blocked: depends on T2 (todo)`. `renew` by the former claimant
succeeds. L06 repeats the sequence with a new owner blocker: claim
refuses, renewal succeeds. L03 and L07 show that capacity and lock
checks still hold on this path.

Impact: a formerly expired worker can make its lease live again after
the task's requirements or prerequisites changed. It can continue work
that a new claimant is explicitly forbidden to start. T136 addresses
unclaimed reservations and startup, not this expired-renewal path.

Repro: `nice -n 19 node research/review-2026-10-09/run.js L05`

Proposed acceptance: "Renewing an expired lease must pass the same
dependency, owner-blocker and decision readiness checks as claiming it,
as well as worker-slot and resource-lock checks; a refused renewal
leaves the expired claim unchanged; ordinary renewal of a live,
unchanged claim still succeeds."

### F3. Medium: automation never reruns policy-stale evidence

`lib/automation.js` `software` defines `attempted` from type, head and
revision alone. If any matching attempt exists, it skips `runGate`,
then reads the current gate report and stops when that evidence is stale.

A16 uses a real CLI tests pass, verifies it counts, changes the pinned
tests command, and verifies the pass is now stale. A real watcher then
consumes the submission. The `check tests` event count remains one;
the task still reports that its command policy no longer matches.
This is not the deliberate suppression of retries after a test failure:
the prior result was successful, and the command contract changed.

Impact: startup reconciliation and later lifecycle reactions cannot
advance the task until someone explicitly runs the gate. The same
head and revision can require a new software check after a settings change.

Repro: `nice -n 19 node research/review-2026-10-09/run.js A16`

Proposed acceptance: "Automation reruns software gates when their
successful evidence no longer matches current gate inputs, including
command and effective tests policy changes; it still avoids retrying
a failed gate at unchanged inputs without an explicit retry."

### F4. Medium: merged stack members miss the confirmation-only path

`lib/check.js` `runGate` calls `gate.confirm` without current evidence
only when `!isStacked`. A lower task is considered stacked when a
linked upper task includes it in its chain, even if that lower PR
already merged remotely.

M10 supplies an accepted ordinary PR with no current review or CI
evidence and a matching remote merged head. It makes one read and
records a successful confirmation. M11 adds a linked upper task and
repeats the lower-task merge. The command refuses on missing gates
before any GitHub call, so the matching merged head cannot be confirmed.
The GitHub response is a fixture; no live PR was merged.

Impact: recovery after a remote merge and lost local receipt works for
ordinary PRs, but can leave stack members without merge evidence.
T125 is accepted and its ordinary-PR recovery works. Its broader
receipt-recovery intent needs this follow-up. The queue now skips
unadvanceable entries, so this probe does not establish that unrelated
PRs are blocked behind the member.

Repro: `nice -n 19 node research/review-2026-10-09/run.js M11`

Proposed acceptance: "An accepted stack member already merged remotely
at its accepted head can record confirmation-only merge evidence
without current software or review evidence; confirmation performs no
merge or retarget operation, still rejects a different landed head,
and preserves partial-chain receipts."

## The 104 queued-without-done reactions

The count in the brief is an incident symptom, not a queue-depth metric.
`automation queued` is historical and carries a source event ID.
`waiting` requires a current eligible source, excludes tasks with live
executors, and excludes sources whose latest receipt is terminal.
It does not append a `done` receipt just because a task was cancelled
or a source became stale.

- A11 leaves 104 queued receipts for a cancelled task: zero are runnable.
- A12 leaves 104 current sources behind a dead holder: all become runnable.
- A13 puts the same number behind a live holder: none enter another
  executor, while a different task can use the second slot.
- A20 runs `consume` after the holder dies: all 104 get `done` and none
  remain pending.
- A08 confirms that an error receipt can be explicitly replayed, but
  `waiting` does not automatically drain it. A10 confirms fresh startup
  reconciliation for an accepted PR. A09 records the documented limit:
  no-PR tasks are outside startup's active-PR reconciliation.

The review did not read or replay the production incident log. Its
specific 104 sources therefore remain unclassified. An orchestrator
diagnostic should join each queued source to its current task, head,
revision, latest reaction receipt and executor identity. It should
separate runnable, busy, terminal, stale and cancelled sources. This
is a useful addition to T141's queue display, not evidence that all
104 need gate runs.

## What held

The local executor cap, PID-start identity check, foreign-host task
reservation, FIFO ordering, stale-head filtering and cancellation
filtering held. A successful merge event remains eligible for its
post-merge sweep while obsolete submission reactions do not.
Stack acceptance order is determined by its lowest unmerged member.

The ordinary merge path pins the head, confirms a merge despite a
branch-deletion error, refuses to count an OPEN PR after a zero exit,
and refuses a different remotely merged head. Remote stack membership
rejects an untracked lower PR before merging.

Only one concurrent claimant wins. Takeover excludes the previous
claimant. Expired renewals respect capacity and locks. Cancelled tasks
reject renewal and submission. Matching exit receipts release
reservations; an old attempt's receipt cannot release a newer attempt.

Changed tests commands, tests modes, cleanup commands and hosted CI
requirements invalidate their evidence. Unchanged commands and changed
executor capacity keep evidence valid.

### F5. High: SIGTERM closes the watcher but automation keeps draining

In P01, two submitted tasks wait behind an executor cap of one. T1's
gate starts, a second watcher queues T2, and the probe signals only the
executor PID. The signal acknowledgment arrives, but T1's gate remains
alive. After the probe releases that gate, the same executor PID starts
T2's gate and remains alive.

P02 sends SIGTERM to the executor and then explicitly sends SIGTERM to
T1's separate gate process group. The first gate's command receipt records
`signal: SIGTERM`. The same executor still starts T2.

`lib/events.js` `interrupt` closes the watcher and resolves `wait` with
code 130. The awaited `automation.consume` call is still running.
`lib/automation.js` has no cancellation check before its next reserve
or queue drain. Gate processes keep Node's event loop alive after the
wait promise resolves.

Impact: an operational stop request does not prevent further gates,
review dispatch or merge reactions in that consume path. Only gate
execution was exercised here; no PR was merged.

The claim that signaling only the executor kills its gate did **not**
reproduce. P01's gate survived. P02 distinguishes the separate child
termination from the executor signal instead of attributing both to one
signal. SIGKILL was used for fixture cleanup; the probe does not claim
that every other possible shutdown method fails.

Repro: `nice -n 19 node research/review-2026-10-09/at-revision.js b3111056bcc5e0d3b898abb355bd5e8fb7721b8e P02`

Proposed acceptance: "SIGTERM or SIGINT cancels the waiter's in-flight
automation, stops and reaps its active gate process group, releases its
reservation, and exits without starting any queued reaction; pending
work remains available to another executor. A CLI test queues two tasks,
signals during the first gate, and verifies no second reaction starts
under the signaled PID."

### F6. Medium: another task's gate inherits the exited worker's environment

P03 verifies that T1's worker process exits with code zero before the
first gate. Its supervisor then drains queued T2 using the same monitor
PID. `spawn --wait` remains pending until the held gates finish, then
exits zero. This matches the documented supervisor reaction and shared
queue design. It demonstrates why supervisor lifetime need not end at
worker exit; it does not measure a 3.5-hour run.

P04 inspects only four fixture environment fields. T2's gate has exactly
T1's departed worker values for `TOWER_CRANE_TASK`, `TOWER_CRANE_AGENT`,
`HOME` and `XDG_CACHE_HOME`, including `TOWER_CRANE_TASK=T1` and
`TOWER_CRANE_AGENT=worker-T1-1`. Its cache differs from the dispatcher's
cache. No credentials or other environment values are recorded.

`lib/spawn-monitor.js` restores the dispatcher's PATH around its
post-exit `automation.consume`, but leaves the rest of the monitor's
worker environment in `process.env`. `reactionContext` constructs an
orchestrator context for state writes; shell gate children still inherit
the process environment.

Impact: commands for another task run with a stale task identity and
isolated worker home/cache. Child CLI calls can select the wrong task or
be refused as the old worker. This is broader than T133's cache-root fix.
No nested reviewer cache was reproduced: the fixtures deliberately stop
at tests gates and never dispatch a reviewer.

Repro: `nice -n 19 node research/review-2026-10-09/at-revision.js b3111056bcc5e0d3b898abb355bd5e8fb7721b8e P04`

Proposed acceptance: "Post-worker automation uses an explicit dispatcher
environment for every gate child, clearing the departed worker's task,
agent and broker identity and restoring dispatcher home/cache settings;
project-configured gate inputs remain available. A two-task supervisor
test proves that T2's gate does not inherit T1's isolated environment."

and the recorded T120 failure. No live merge, stack API request, real model
invocation, remote-host execution or external web research ran. The addendum
uses a stub harness through the real spawn supervisor. The report
does not establish whether the submitted T120, T135 or T136 fixes

claimant may submit after expiry until a takeover; it is not counted
as a lease-renewal bypass.
